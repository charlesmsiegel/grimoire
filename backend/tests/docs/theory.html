Judge 1

Theory: This suite models grimoire's failure surface as silent drift around a plain-file store that outlives the code that wrote it: it believes bugs arrive as a new writer/reader/mutator added beside a store-wide rule nobody re-reads, as a crash or a second writer landing between two disk writes, and as today's code failing to read what an older version wrote. So its budget goes to executable declarations of those rules (AST guards over the production package, each with a stated blind spot), crash-and-contention injection at every side-effect boundary, and one checked-in store that today's code did not write. Per-module behavioural tests are the floor underneath that, not the point.

Instead of: The other coherent reading is that this is an ordinary per-module regression suite (test_<module>_store.py plus one giant test_routes.py) that happens to carry some lint-ish extras. I rejected it because the extras are where the reasoning lives and the per-module files defer to them: each guard, the frozen store and the cassette exist because a real bug shipped past green per-module tests (#233 temp+replace drift, #254/#255 the lock domain living in a docstring, #205 reading an older store, #204 seven inline LLM fakes), and each states what it deliberately cannot see. A suite whose theory were 'cover each module' would not have written test_the_sweep_covers_the_whole_store_not_a_corner_of_it or test_the_guard_actually_detects_a_raw_write.

Judge 2

Theory: This suite models grimoire's real failure modes rather than its feature list: a plain-file store on a possibly-synced folder that concurrent requests and mid-flight crashes can corrupt, scene transcripts that cannot be regenerated, one nondeterministic provider behind a single DI seam, and an Android build that must install the very same source. It therefore spends most of its budget on things a per-feature test cannot buy — static guards that walk the production package's own AST to catch silent drift in cross-cutting rules (atomic writes, overlay reads, lock domain and order, import form, pydantic dialect, path resolvers, usage metering), one checked-in store tree that today's code did not write, threads and injected exceptions at every side-effect boundary, and a shared LLM fake that refuses an unmatched request instead of defaulting. The unifying belief is that this system does not break loudly — it drifts — so the suite's job is to make drift fail a test run.

Instead of: The other coherent reading is 'a large per-module regression suite that happens to have some clever meta-tests bolted on': one file per store module, tests as behavioural documentation, and the guards as decoration. I rejected it because the design pressure visibly went into the meta-machinery — every guard states its own reach and where it stops, caps its own exemptions so a rubber stamp fails, and carries tests proving the detector can still fail (test_atomic_guard.py:177); the frozen fixture forbids its own regeneration and backs the snapshot with hand-written semantic assertions so a regenerated snapshot cannot make it vacuous (test_frozen_campaign.py:14); and the cassette proves its matchers still occur in prompts rendered from the real templates (test_llm_fakes.py:1). A documentation-shaped suite builds none of that.

Judge 3

Theory: This suite models grimoire's real failure surface as silent drift in a filesystem-backed store that outlives the code reading it, rather than as ordinary defect density.
