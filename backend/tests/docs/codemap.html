The largest package in the repository is the test suite

backend/tests is 166 files and 62,576 lines — more code than the backend it tests (43,000) and more than the frontend (49,000). At 4,708 test functions it accounts for the bulk of the repository's 54.7% test-line share.

It is not just a large suite; it is a suite with three distinct kinds of test in it, and the unusual ones are what make the backend's design claims believable: architecture guards that parse the package's own AST, a frozen store fixture that no current code wrote, and a cassette-based LLM fake that answers by request shape rather than call order.

Three kinds of test

1. Architecture guards

Nine tests that read backend/src/grimoire as an AST and fail the build on a rule violation: backend/tests/test_atomic_guard.py, backend/tests/test_overlay_guard.py, backend/tests/test_paths_guard.py, backend/tests/test_pydantic_guard.py, backend/tests/test_import_guard.py, backend/tests/test_lock_order_guard.py, backend/tests/test_lock_domain_guard.py, backend/tests/test_path_guard_store.py, backend/tests/test_usage_guard.py. Each accepts a reasoned escape marker, checked by backend/tests/guard_markers.py.

2. The frozen campaign

backend/tests/fixtures/frozen_campaign is a whole store tree checked in as a fixture — the only store in the repository today's code did not write. Its home/ directory is never regenerated, because its value is being old: it is what catches a change that breaks reading what an earlier version wrote. The expected output of the read-only sweep is regenerated deliberately by backend/tests/fixtures/frozen_campaign/sweep.py.

3. Scripted and cassette LLM fakes

backend/tests/llm_fakes.py is the single injected fake, bound at app.dependency_overrides. Scripted fakes answer by call order; a cassette answers by what the request looks like, and a request matching no entry raises rather than defaulting — so a reworded prompt fails here loudly instead of everywhere else quietly.

A suite that tests the architecture, but cannot say what it misses

This package does something most test suites do not: it holds the production package to structural rules mechanically, so several of the backend's design claims are facts rather than intentions. What it does not do is measure itself. There is no coverage tooling configured for pytest anywhere in this repository, so 4,708 test functions have never been asked which lines they never execute.

Risk ranking

1. Nothing measures this suite. No pytest-cov, no coverage configuration, no coverage artifact anywhere in the repository for Python. The frontend measures itself at 85.8% of lines and its config explains at length why the istanbul provider and all: true are load-bearing for that number to be honest — so the reasoning exists in this repository; it has simply never been applied to the larger and more safety-critical half. Every claim about backend coverage today is an inference from 4,708 test names.
2. One 9,892-line file holds the entire HTTP surface. backend/tests/test_routes.py is the single largest file in the repository, with 737 branches. It is where a test for a new endpoint naturally lands, so it grows monotonically, and a failure in it points at "the API" rather than at a subsystem.
3. The guards are coupled to the source layout they police. backend/tests/test_lock_domain_guard.py names modules explicitly, so moving or renaming a store module means editing a declaration in backend/src/grimoire/store/locks.py and a test. That is the price of the mechanism and it is worth paying — but it means the guards impose a refactoring tax proportional to how often the package is reorganized.
4. 355 tests contain control flow. A for or if inside a test body means the test can pass by iterating zero times. Concentrated in backend/tests/test_lock_domain_guard.py (40) and backend/tests/test_routes.py (31) — and in the guards the loop is intrinsic, since the test's job is "for every module, assert". Worth an explicit non-empty assertion on the collection being iterated; I did not verify whether the guards have one.
5. 33 tests contain no assertion. Spot-checking these, backend/tests/test_casefile_route.py:70 asserts through a helper that takes an expect=404 argument, and backend/tests/test_assets_store.py:673 is an explicit "does not raise" test with a comment saying so. Both are legitimate patterns the detector cannot see through, so this count should not be read as 33 tests that cannot fail.

What the Health grade over-counts here

This package draws 3,513 of the repository's findings, and the two largest categories are artifacts of what test code legitimately looks like:

  • 1,725 magic_number — literal expected values are the point of an assertion. 632 of them are in backend/tests/test_routes.py alone.
  • 707 local_import — imports inside test functions. The module-scope import rule the repository enforces applies to backend/src/grimoire, not to tests, so these are outside the rule rather than violations of it.

Together they are 69% of this package's findings. The grade on the Health page is computed before that judgment is applied, which is why the two documents should be read together.
