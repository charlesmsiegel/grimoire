A run outlives its request

The API is a layered monolith's HTTP/runtime edge. It validates user intent, delegates durable changes to the store, and turns model work into discoverable runs independent of sockets. Subjects identify affected records; classes decide exclusion and delivery behavior (backend/src/grimoire/routes/runs.py:3, backend/src/grimoire/routes/runs.py:8).

Replay precedes provider preflight so a removed key cannot invalidate an already landed turn. Setup's mutations share the same identity fence and campaign hold; terminal fencing alone would leave a replacement scene holding somebody else's post (backend/src/grimoire/routes/scenes.py:839, backend/src/grimoire/routes/scenes.py:980, backend/src/grimoire/routes/character_turns.py:91). A restart or expiry still loses attempt adoption (backend/src/grimoire/routes/runs.py:73).

Never abandon a deletion thread while recording its run as over: otherwise another pass or library move can start beneath continuing writes. Shutdown requests stop before cancelling the task group (backend/src/grimoire/runner.py:261, backend/src/grimoire/runner.py:293, backend/src/grimoire/main.py:375).

Prompt rendering, model retries and call metering are outside this unit's ownership; those steps belong to the store-context and inference/gateway paths (backend/src/grimoire/inference.py:4).

A run's frames and cancellation flags are runtime data; they are not a persisted attempt ledger (backend/src/grimoire/routes/runs.py:73, backend/src/grimoire/routes/runs.py:282).

Validation and journal ownership cross the route/store cut. The registry class owns run state and indexes; the surrounding runs.py module also exposes HTTP endpoints and orchestration helpers. Its detached-start helper hands work to the runner, and maintenance setup reserves a run, pins the root and claims resources before starting the worker (backend/src/grimoire/routes/runs.py:1683, backend/src/grimoire/routes/runs.py:1721, backend/src/grimoire/routes/runs.py:2405, backend/src/grimoire/routes/runs.py:2451). Failure propagation

Each run gets its own failure boundary so one exception cannot cancel siblings and the backup ticker (backend/src/grimoire/runner.py:19). HTTP routes use one upstream failure map; streams carry in-band error events once headers are sent (backend/src/grimoire/routes/common.py:90). Startup contention logs and skips individually retryable migrations rather than refusing to boot (backend/src/grimoire/main.py:325).

Concurrency

The portal owns event-loop-affine async events; synchronous handlers must not mutate them from arbitrary threads (backend/src/grimoire/runner.py:75). Turn ownership tokens are explicitly process-local, unlike campaign record locks (backend/src/grimoire/routes/streaming.py:98). Maintenance uses a shielded thread and retains exclusion until its actual return (backend/src/grimoire/runner.py:293).

Maintainer risk order

  1. Retrying after run loss. Reaping or process restart loses attempt mapping and can duplicate a post/reply on resend (backend/src/grimoire/routes/runs.py:73).
  2. Hotspot orchestration changes. Any setup mutation added before reservation or outside the identity hold can corrupt replacement-scene ownership (backend/src/grimoire/routes/scenes.py:863, backend/src/grimoire/routes/scenes.py:980).
  3. Revision races on ordinary records. Conflict checks close the human edit window but not simultaneous compare/write races outside the group path (backend/src/grimoire/routes/common.py:63, backend/src/grimoire/routes/entities.py:231).
  4. Cross-file roll handoffs. The accepted crash windows can omit narration beats or follow-up checks despite non-corrupt records (backend/src/grimoire/routes/streaming.py:4).
