300 endpoints, thirteen routers, one load-bearing ordering

backend/src/grimoire/routes is the HTTP surface: 16 modules and 7,737 lines exposing 300 endpoints under /api. It is a thin layer by intent — route bodies validate, call into store, and shape a response — with two exceptions that carry real logic: the SSE streaming machinery and the scene routes.

The package's defining property is that router include order is part of its correctness. FastAPI matches in registration order and never backtracks, so the generic entity routes must come last, and seven pairs of patterns genuinely cross — a concrete URL exists that both match, with the winner decided purely by include order. backend/tests/test_route_order.py pins every one of those decisions.

The interesting invariants here are about routing and about turns

Two rules in this package cannot be expressed in types and would fail silently if broken: which route wins when two patterns match the same URL, and which in-flight turn owns a scene. Both are handled deliberately; one is tested, the other is argued in comments.

Failure handling

  • StoreBusy becomes a 409 in one app-level handler rather than at ~35 call sites (backend/src/grimoire/main.py:241).
  • The abort path persists partial output inside a shielded cancel scope (backend/src/grimoire/routes/streaming.py:83), because the disconnect is not an LLMError and the ordinary error handler never runs for it.
  • A failed alternates sidecar write is swallowed on purpose (backend/src/grimoire/routes/streaming.py:113) so a landed generation is not reported as a failure the user retries into a duplicate.
  • 288 raise_without_from findings. Route bodies convert store exceptions into HTTPException without from exc, so the original traceback is dropped from the chain. Individually harmless for the client, collectively a real cost when debugging a 500 in a local app with no error tracking.

Risk ranking

1. backend/src/grimoire/routes/scenes.py concentrates the package's complexity and its churn. 2,394 lines and 321 branches — more branches than the next three modules combined — with 86 commits in 24 months and a hotspot score of 27,692 against 4,704 for the runner-up. Three functions in it trip high-severity cognitive- or cyclomatic-complexity detectors (backend/src/grimoire/routes/scenes.py:437, backend/src/grimoire/routes/scenes.py:650, backend/src/grimoire/routes/scenes.py:1114).
2. Route ordering is correct but fragile by construction. The rule is enforced by a test, which is the right answer — but the failure mode without that test is a route that silently never runs, and the package is one include_router line away from it at all times.
3. Validation has nowhere good to live. Because Android pins pydantic 1.x, the models carry no validators, so field-level rules are written by hand inside route bodies. That is a stated constraint rather than an oversight, but it means validation is the one concern in this repository with no single owner.
4. 310 missing return annotations. In a package whose entire job is shaping responses, the response shapes are largely untyped on the Python side. FastAPI still documents them from the return value at runtime, so this is a readability and refactoring cost rather than a correctness one.

What the Health grade over-counts here

All 24 mutable_class_attribute findings are false positives — every one is a pydantic model field with a list default, such as backend/src/grimoire/routes/models.py:62 and backend/src/grimoire/routes/models.py:89. Pydantic deep-copies mutable defaults per instance, so the shared-state bug the detector describes cannot occur. They are 24 of the 38 high-severity findings in this package that are not unused_import, so excluding them changes the picture substantially.
