Judge 1

Theory: A world is a library of hand-editable Markdown/JSON records; a campaign is a play-through of one world that reads through to it live and materializes a record only where it diverges, recording the divergence as a content-hash 'base' so later world edits arrive as reviewable sync rather than silent overwrite. Around that sit the guarantees a plain user-owned folder does not give: whole-file atomic publication by rename, a per-campaign reentrant lock that is also an OS file lock, four explicit states a record id can be in (inherited / materialized-with-base / tombstoned / detached-because-the-world-original-died), and fail-soft JSON reads that log exactly when failing soft would ADD content instead of removing it. Everything else here — scenes, sheets, absorb, prompt context — is campaign-local state layered on that same substrate.

Instead of: The other coherent reading is that a campaign is a full copy of its world taken at fork time — which this code literally used to be — or, more generally, that store/ is a persistence/DAO layer under a domain model living somewhere else. Both are rejected on the code's own evidence: campaigns/lifecycle.ensure_campaign_slim is a one-time migration that demotes the surviving full copies to the overlay layout and stamps world_copy: overlay, and the domain rules themselves (world-info activation and secrecy, sync arbitration, dice grammar, absorb routing) live in this package while routes/ only marshals HTTP. store/ is the model; the filesystem is its representation, not its subject.

Judge 2

Theory: A worldbuilding library is a directory tree the user owns, edits by hand, syncs and can corrupt; worlds hold authored records and a campaign is a copy-on-write fork that materializes a record only where play made it diverge, with tombstones for deletion and detachment for a world original that vanished. The code's job is to make that tree behave like a database without one: publish every record by rename so a reader never sees a half-write, serialize all campaign-scoped read-modify-writes on a single per-campaign lock that spans threads and processes, and answer a corrupt file with an empty value while naming, per reader, which direction that failure moves the content. Where the guarantee stops - power loss, two devices on one synced folder, an ACL-managed store - is written down rather than implied.

Instead of: The other coherent reading is 'the persistence tier of a three-tier app': routes on top, store beneath, templates beside. I rejected it because roughly a third of the package touches no storage at all and says so in its own first line - dice.py is a pure roll engine, epub.py assembles a book that is never written into the store, suggest.py/absorb/context are prompt builders, and context/semantic.py makes an outbound HTTP call. The boundary the code actually holds is 'everything except HTTP request/response shape and the generative LLM call', i.e. this is the domain layer, named after its persistence half.

Judge 3

Theory: This models a user-owned folder of Markdown/JSON as the database of record for a worldbuilding app: worlds hold canonical records, and a campaign inherits them copy-on-write, materializing a record only when it diverges (edit, version lock, delete-as-tombstone, or detachment when the world original is deleted out from under it). Because there is no DBMS, every guarantee a DBMS would supply is hand-built and its exact reach is written down: crash-safety is temp-write-fsync-rename with power-loss durability explicitly disclaimed, mutual exclusion is one declared per-campaign lock domain with its non-members named, and every reader assumes the files were hand-edited, synced or half-written. The invariant the whole thing is shaped around is that a scene transcript cannot be regenerated, so a lost update there is unrecoverable in a way a lost display panel is not.

Instead of: The other coherent reading is that `store` is a persistence adapter -- a file-backed repository layer sitting under a domain that lives elsewhere. I rejected it because the domain lives here too: fact ledgers with supersession semantics (store/facts.py:1), reversal semantics for edits (store/undo.py:1), prompt-context assembly (store/context/__init__.py:1), EPUB export, a chub.ai client and a dice engine that says outright it touches no filesystem (store/dice.py:12). The three genuinely persistence-shaped modules (atomic, locks, overlay) are 3 of 172. The unifying idea is not 'how bytes reach disk' but 'the user's folder IS the database', which is what forces the hand-built atomicity, the hand-declared lock domain, and the fail-soft reads whose direction of failure is argued one at a time.
