Judge 1

Theory: This models a solo roleplay campaign as two different worlds and gives each its own shape: a library of authored records — worlds, campaigns, and the kinds of entity inside them — every one of which is read first and edited only on request through the same two-pane page; and a scene being played, where the transcript on screen is not necessarily the transcript the next write will land in. The play screen is organised entirely around that second fact — `loaded {cid, sid, token}`, `transcriptIsActive`, `sceneLocked` and a window token exist because a player can switch campaigns mid-stream, rename a scene while it generates, or page history while a reroll settles, and those races are the app's dominant failure mode. Over both sits one shell rule: a page's 274px context column answers 'what am I navigating' and main answers 'what am I reading', with the ⌘K palette as the only global navigation surface.

Instead of: The other coherent reading is 'a REST admin UI over a markdown store' — routes mirror endpoints, api/client.ts mirrors the backend's surface one-for-one, and the editors are forms. I rejected it because it cannot account for where the code's mass actually is. Under a CRUD theory the API client would be a thin fetch wrapper, yet it carries in-flight GET coalescing, a `fresh` opt-out with retirement semantics, and mutation event channels hung off the mutators so no view can forget (frontend/src/api/client.ts:48, frontend/src/appEvents.ts:16); and CampaignView's bulk would be form state, yet it is ownership guards whose comments name the specific bug each one closes. A CRUD reading would classify all of that as noise, which is the test it fails.

Theory: This SPA models a single-user, local-first roleplay campaign manager as a set of rooms over a filesystem store: every page is the same shape — a 274px context column answering "what am I navigating" beside main answering "what am I reading" — and every record is a read-first list/detail with an explicit edit step and an on-disk revision that a save can be refused against. The play screen is the one room with a different subject: a live turn, where the hard problem is proving at every instant which campaign, which scene and which fetch the transcript on screen belongs to, because streams, reroll windows and shared in-flight GETs can all land against a scene the reader has since left. Everything else in the unit — the shared request map, the shell-wide stale-signal channels, the store-move retirement — exists to keep a server answer from being adopted by a screen it is no longer about.

Instead of: The other coherent reading is 'a thin CRUD renderer over a REST API', with correctness living on the server and the client merely painting responses. I rejected it because the densest, most-argued machinery here is entirely client-side identity reasoning that a dumb renderer would never need: `transcriptIsActive` as a named invariant (routes/CampaignView.tsx:323), alternates scoped by a cid/sid/window triple (routes/CampaignView.tsx:75), and a GET-sharing map with a deliberate `fresh` opt-out and a whole-map retirement on store move (frontend/src/api/client.ts:81). The client holds its own model of which answers are still about what is on screen; that is the theory, not painting.

Judge 3

Theory: This models solo tabletop play as two different kinds of thing: records you author (worlds, characters, lore, greetings, modules, presets — each a two-pane list/detail with an explicit edit step and a content hash so a concurrent write from a sync client or another editor becomes a question rather than a loss), and one scene you play (a live transcript the server streams into). The hard part the play route is built around is identity under motion: a response must be discarded unless the (campaign, scene, transcript-window) it was issued for is still the one on screen.

Instead of: The other coherent reading is that this is a thin presentation layer over the FastAPI routes — 240 typed RPC wrappers plus React screens, whose only theory is 'mirror the backend'. I rejected it because the frontend carries domain concepts the wire does not hand it: `SceneDraft` is a closed union over where a scene came from (greeting/generated/custom/saved) that the server has no equivalent of and that encodes a rule the server cannot state (a greeting draft has no premise and no cast by construction); `EntityScope` is the frontend's own name for the copy-on-write campaign fork; and secrecy normalization, sheet pool floors and connection-readiness are re-decided here because the UI must answer before a round trip. A pure mirror would also not bother to distinguish 'unknown' from 'zero' in the library counts.
