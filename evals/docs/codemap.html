Data ownership

The case builder writes only the active throwaway library, production metering writes that library's ledger, and harvest copies the rows into the result with eval scope. The CLI may then write an explicitly named run report; report comparison reads that file without consulting private settings or current rates. evals/cases.py:6 evals/runner.py:24 evals/runner.py:549 evals/runfile.py:10

Checked-in reply artifacts have two owners with intentionally different privileges: hand-authored counterexamples remain fixed; opt-in live recording replaces only the compliant baseline. A recording is evidence about how code handles that text, not a statement about what a provider currently emits. evals/cases.py:100 evals/runner.py:747 backend/tests/llm_fakes.py:80

The core report shape still thinks in prompt-response cases: the history experiment constructs a Case with dummy builders and empty graders/recordings. The production dependency is deliberate: cases call real builders and graders reuse real consuming parsers, with documented exceptions when tolerant parsing would normalize away the violation. Failure and concurrency boundaries

A provider failure and a grader crash become case results with distinct errors; baseline-write failures retain the paid observations. Follow-up timeout is stronger: it propagates so the isolate can keep its root, preventing a straggler from writing after environment restoration. evals/runner.py:798 evals/runner.py:802 evals/runner.py:809 evals/run.py:68

The library selector is process-global environment state. Overlapping isolate contexts in one process can point a worker at another case; these context managers should not be mistaken for task-local roots. evals/runner.py:101 evals/run.py:75
