Judge 1

Theory: Every prompt-shaping feature in grimoire (length budget, roll protocol, absorb contract, lore containment) is a hypothesis about what the model will do, and this unit turns four of them into pass/fail questions that need no human judgement. Each case builds a real fixture campaign in a throwaway GRIMOIRE_HOME, assembles its prompt with the production builder, and scores output with graders that re-use the production parsers, so the suite fails exactly when the app's own understanding of its output changes. The load-bearing split is between the half that is checkable offline and deterministically (is the instruction still IN the assembled prompt; do the graders still fire on their counterexamples) and the half only a paid live call can answer (does the model still obey it) — and the code says which side of that line every check sits on.

Instead of: The other coherent reading is 'a small eval framework': a pluggable harness with cases, scorers, a runner and a report, which is the shape almost any repo would produce from this brief. I rejected it because the code refuses that generality at every point and says so — README.md:15 states outright that it is not a framework but four questions; there is no rubric, no judge model, no metric aggregation, no per-case config; graders are hand-written functions bound to named production parsers (graders.py:22) and their checks are named after app internals (length.reply_words, fence.check_known); and Case carries exactly the four fields those four questions need (cases.py:78). Reading it as a framework would make its deliberate narrowness look like missing features, when the narrowness is the theory.

Theory: This treats grimoire's prompt templates as hypotheses about model behaviour and makes four of them falsifiable: each case builds a real fixture campaign in a throwaway GRIMOIRE_HOME, assembles its prompt with the production builder the app itself calls, and scores the result with graders that re-use the app's own output parsers. Because the offline half can only score a fixed recording, each case also grades the freshly assembled prompt, so an instruction leaving a template fails immediately, and each grader is proved live by a counterexample recording naming the exact set of checks it must trip. Judge 3

Theory: This unit models the claim that grimoire's prompt templates are hypotheses about model behaviour, and that a hypothesis is testable as a case: build a throwaway fixture campaign, assemble the prompt through the app's own builder, and score the resulting text with the app's own parsers. Because a checked-in recording cannot react to a template edit, each case also grades the freshly assembled prompt (rendering the section template itself and requiring it verbatim), so an instruction that leaves the prompt fails offline in pytest, while the question of whether the model still obeys a reworded instruction is deferred to an opt-in, non-gating live run. Each grader is proved by a hand-authored counterexample that names the exact set of checks it must trip.

Instead of: The other coherent reading is 'a small LLM eval framework' — datasets, metrics, judges, scores tracked across samples. I rejected it because none of that vocabulary is in the code: a Check is a boolean (evals/graders.py:37), a variant has exactly one recording, a counterexample is judged by set equality on failure names (evals/runner.py:61), and the README says outright it is not a framework but four pass/fail questions (evals/README.md:12). Read as a framework the code looks impoverished; read as a prompt-contract regression test with a live probe bolted on the side, every choice — deriving the absorb contract from parse_output, rendering sections instead of pinning prose, scoring the raw JSON rather than the tolerant parser's output — falls into place.
