# Device sync: revisions and conflicts

**Status:** first slice of [Sync Revisions And Conflict Core](roadmap/sprints/sync-revisions-and-conflict-core.md) (Wave 3, #019), implemented as `grimoire.sync` over the [native store](STORAGE.md). It synchronizes **two libraries that are both open locally**: a desktop folder and a phone folder, or any two copies of one library. Pairing and an authenticated peer transfer over this core are [028's first slice](DEVICE_SYNC.md); there is no UI yet. A green test suite proves this contract, not a working phone sync.

## What it guarantees

- **Timestamps never decide.** Sync compares bytes (etags). Nothing in `grimoire.sync` reads a clock, a modification time or randomness; a test pins this.
- **Non-overlapping edits merge deterministically.** `sync(a, b)` and `sync(b, a)` produce byte-identical libraries, the sync bookkeeping included.
- **Nothing is silently overwritten, resurrected or dropped.** Overlapping edits, deletions, records the other library cannot accept, and anything without a provable common ancestor become **named conflicts**. Each device keeps its own file and also receives the other device's version under its `.conflicts/`.
- **Crash-safe.** Every write is a 010 transaction. After a crash, reopening both libraries and syncing again reaches exactly the state an uninterrupted sync reaches.
- **One bad record never blocks the rest.** A path or source the other library cannot apply, a write the policy denies, or an unusable file becomes a conflict, and everything else still syncs.
- **Converged means no conflicts.** Two libraries are converged when a sync reports no conflicts. A `held` conflict (a family whose merge rules do not exist yet, see below) is therefore never converged, even though nothing is wrong on either device.

## What is synchronized

`grimoire.sync.syncable(path)` is the single definition of the synced set, and the extension point for later families (021 accepted events and wrap-ups, 023 holdings, 035 scenes, ledgers). In this slice it covers the canonical records of 010 and of [107](CHATS.md): source manifests, definition revisions, campaign instances, 107's play-scope (`campaigns/<id>/scope.json`) and chat (`campaigns/<id>/chats/<chat_id>.json`) records, [017](GRAPH.md)'s relation records (`campaigns/<id>/relations/<relation_id>.json`), [020](EVIDENCE.md)'s create-only knowledge records (events, evidence and knowledge-log batches under `campaigns/<id>/events/` and `campaigns/<id>/evidence/`), and [018](IMAGES.md)'s art: image objects and placements (`images/` and `placements/` under a source's `_source/` or a campaign) and their blobs under `assets/blobs/`. Instances, scopes, chats, relations and knowledge records are campaign-local: each is its own admission unit, never grouped with a source. Each art file is its own unit too, never grouped with its source (see "Art" below). S3 is proven both on a synthetic instance-shaped chat and on real 107 chats made by `grimoire.chatstore`:
- a lorebook attached on one device and a world attached on the other touch different files, so both merge;
- concurrent edits of one chat record are a keep-both conflict, and the new participant's actor still travels;
- after either, each device's navigation index still finds exactly one chat.

Never transferred:
- device-local state: `.txn/`, `.conflicts/` and `.sync/`;
- **derived indexes**, such as 107's navigation index. It is rebuilt from canonical records on each device, never synchronized as a second owner.

Reported as `skipped` and never touched:
- ledgers under `authority/`;
- the library marker;
- unknown root entries such as `worlds/`, and anything under `assets/` that is not a blob name;
- **held back until their merge rules exist** ([App-Managed Device Sync (028)](roadmap/sprints/app-managed-device-sync.md) owns them): 021's accepted events and scene wrap-ups (`accepted/`, `wrapups/`) and 023's holdings (`holdings/`). Their own stores commit several files as one unit (an event with the relations it changes; one operation across several holders), and two devices accepting events offline would collide on ordinals, so copying them file by file would deliver half an operation or freeze a campaign's event stack;
- for the same reason, **every 017 relation of a campaign that holds an accepted event on either device** (or whose `accepted/` folder, in any spelling, or the campaign folder, `campaigns/` or the library root, cannot be listed: the check fails closed, and `resolve` makes it on the very scans it writes from): a relation 021 changed must never arrive without the event that changed it. A held relation is still tracked: it gets no decision, but an agreement both devices already hold (identical bytes) is recorded like any other, and an uncertain base stays in the pending marker, so lifting the hold later can never undo a deletion. A campaign with no accepted event syncs its relations as usual;
- the reserved campaign family `scenes/`, and any file under `events/` or `evidence/` that is not a knowledge record of a known family;
- non-record files.

Held paths are not silent. Every held path whose two devices are not byte-identical (one side absent, different bytes, or blocked) is also a **`held` conflict**, as is a held folder that cannot be listed on either device. A `held` conflict copies nothing, keeps nothing and archives nothing; the path stays in `skipped` too. It ends only when both devices hold identical bytes (or neither holds the path), and `resolve` refuses every held path.

Sync compares whole files. It never interprets payloads, never merges inside a file, and never treats source inheritance (`derived_from`, `base`, portrayals) as device ancestry. These structural readings are the only exceptions:
- a manifest's `heads`, for the head-dependency rule;
- for art: an image object's `blob`, a placement's `mode` and `image`, and an instance's derivation (its `derived_from` entity, which inherited source art needs); a blob's name is its content address (sha256 and extension);
- on a true first sync only, a record's `previous` field, for one-hop lineage;
- when `resolve` replaces a definition revision, the store's reference check reads every manifest's heads and links, every instance's `derived_from`, `base` and pinned payload references, other revisions' pinned payload references, and every string in scope, chat, relation and knowledge payloads (a pinned reference, or an unpinned one beside a `resolved_revision`).

## Device identity

`identify(store, device_id)` writes `.sync/device.json`. Device IDs are supplied by the caller and never generated. An ID is one lowercase identity segment that is also a portable path segment.

Refusals:
- a library with no identity, or a damaged one: `NoDeviceIdentity`;
- two libraries with the same ID (the same library twice, or a folder copied together with its `.sync`): `SameDevice`;
- changing a valid ID without `replace=True`: `IdentityExists`.

A damaged identity file is replaced by `identify`. When a device's valid ID changes, the same commit **retires** each of its peer archives and markers, with every shard its root lists (the retired root names them; no other shard is read), and its kept-version record (a retired one reads as missing, with no notice): the file stays present but is rewritten as `grimoire.sync.retired/1`, which records only the paths it named and is never valid again. The next sync of the new ID is therefore conservative rather than a first sync, the retired paths stay uncertain (a tombstone is not forgotten), and renaming the devices back can never revive an outdated base. If **both** devices take new IDs, neither has any file for the new pair, so the next sync is a true first sync (see Limits).

## Bookkeeping (`.sync/peers/<peer>/`)

- **`archive.json`** holds the last agreed state per path. `{"agreed": E}` means both devices verifiably held exactly E. `{"deleted": E}` is a **tombstone**: both devices were absent after last agreeing on E. Tombstones are kept, except a blob's (below, "Sharding and tombstones").
- **`pending.json`** records what an unfinished sync published on this device: `{"from": E0, "to": E1, "base": A}` per path (A: the agreed etag both archives held when it was written, or `null`), or `{"uncertain": true}`. It is written in the **same transaction** as the data, and that data commit happens even when nothing is copied if the marker changes (for example, to record uncertainty), so a crash before the pending step can never leave rewritten archives without it. An entry is removed only after both archives are written and its path is resolved. A path whose base was `uncertain` and that did not end agreed, or that ended absent on both devices with no known tombstone (or with disagreeing ones, after a crash between the two archive commits), keeps (or gains) `{"uncertain": true}`, so the uncertainty survives the sync that saw it: otherwise the next sync would see a `none` base, and a one-sided deletion would be undone by a create-only copy.

- **`keeps.json`** (028, `grimoire.sync.keeps/1`) records, per path, the etags of the peer's versions a sync wrote on this device as the first copy of those bytes there (`delivered`, recorded in the data commit that writes the keep), which of those this device dismissed (`dismissed`) with the archive base of the conflict they were dismissed in (`base`: `none`, `agreed:E` or `deleted:E`; `null` when nothing is dismissed), and this device's own versions that `resolve` held here (`held`, never also delivered). See "Keep-both". Only `dismiss` adds a dismissal, and a completed sync drops it with its conflict; a delivered version stays while a slot holds it or it is dismissed; `resolve` adds a held version in the same commit as the hold (and takes those bytes out of every other pair's delivered versions), `identify` carries held versions to the new ID's record, and a sync drops one only once no slot holds those bytes.

Each file carries a `check` digest of its own content. A file that is not strictly valid is **ignored and reported** (`SyncReport.notices`), never partially trusted. This covers bad JSON, a wrong format, an archive for another pair of devices, and a failed `check`. An ignored `keeps.json` honours no dismissal (every kept version is delivered as before 028), and the next completed sync (or a data commit that keeps a version first) replaces it. The holds it listed are then unknown, which is safe: only a keep that writes the first copy of its bytes is ever recorded as delivered, so no slot already standing, a hold included, ever becomes dismissable.

### Sharding and tombstones (028)

An archive or marker that fits 010's 8 MiB file cap (about 23,000 paths at typical lengths) is still one `/1` file, byte for byte as 019 wrote it, and a `/1` file is always read as-is, so an existing library needs no migration. One that would not fit is written as format **`grimoire.sync.archive/2`** (or `pending/2`): the root `archive.json` lists 16 or 256 shards, `archive.<prefix>.json`, keyed by the first one or two hex digits of the SHA-256 of each path, each with the etag that shard must have. Each shard holds exactly the entries whose path hashes to its prefix, with its own `check`. The width is the smallest whose every file fits by an upper-bound size estimate, a pure function of the entries, so `sync(a, b)` and `sync(b, a)` still write identical bytes. Two hex digits hold about six million paths; past that the plan is refused before any write (`ArchiveTooLarge`), as before.

- **Crash safety.** Every file of one document is written in the same 010 transaction (and its step, as before), so a crash leaves the old root with its old shards or the new root with its new ones.
- **Damage.** The root's etag list binds the set. A listed shard that is missing, torn, edited or of another commit, a root that is gone while shards remain, or a path in the wrong shard makes the **whole document ignored and reported**, exactly like a damaged single-file archive: every path it names is uncertain (a keep-both conflict, never a copy or a deletion), and a tombstone in it is not forgotten.
- **Stale shards.** When a document shrinks back to one file or changes width, the shards it no longer lists stay on disk: 010 commits never delete. They are never trusted and **never read or sent**: only the shards a root lists are read (and travel in 028's snapshot), so a stale or planted file costs nothing. A later write of that name reads it then, only for its compare-and-swap. Where the root itself is missing, the folder is listed (names only): shards without their root make the document ignored, never a first sync.
- **Tombstones.** A tombstone is dropped only where it provably decides nothing: a blob's. A blob's bytes are its name, so its tombstone could only ever have flagged the same bytes coming back, and row 12's exception already copies those like a new file. Every other tombstone is kept, because it is what turns a one-sided re-creation of the deleted bytes into a `resurrected` conflict instead of a silent copy. Tombstones of records therefore still grow with every deletion; sharding is what keeps them from stopping the sync.

## Base derivation

A `.sync` file that exists but cannot be read (an I/O error, a file held by another program), or that exists only under a look-alike spelling (`Pending.json`), stops the sync with `SyncInterrupted` before anything is written. An unreadable marker must never look like a missing one.

A path's base is trusted only where **both devices' own records agree**:
1. **Archive candidate:**
   - `first`: neither device has any file at its archive location for this pair (a true first sync);
   - the shared entry, when both archives are valid and hold the identical entry;
   - `none`: both archives are valid and neither has an entry (a path new since the last sync);
   - otherwise `uncertain`: one archive is missing or ignored, or the entries disagree.
2. **Pending override.** If either device has a pending entry for the path, the base is `agreed to` only when every entry names the same `to` and each device holding one still has those bytes: the copy verifiably landed, and the peer held `to`. If both archives already agree on that `to` and did not already when the marker was written (its `base`), the marker is stale (a crash after the archives were written but before the marker was cleared) and the archive base stands: archives are only written after verification. Anything else is `uncertain`: a revert to the old bytes, an edit racing the copy, disagreeing entries, or a marker that parses but is invalid (ignored).

`uncertain` never copies anything. This is what defeats:
- a **clone** of a library that synced with the phone: its archive cannot make one device's version look like an ancestor;
- **ABA** after a crash: the user restores the exact old bytes before the sync finished.

## Decision table

Each device's file is `absent`, `present(etag)`, or `blocked`. A file is blocked when it is:
- a link;
- a look-alike spelling;
- unreadable, oversized or not a regular file (a directory where a record belongs counts too);
- not strict JSON;
- in a newer format;
- an envelope whose address does not match its path;
- a blob whose bytes do not hash to its name or sniff to its extension (`corrupt`), or that cannot be read, is empty or over 32 MiB (`unreadable`);
- either member of a **cross-kind instance pair** (`instance_id_conflict`): one instance id held under two kinds in one campaign, exactly the files `load()` excludes. `resolve` cannot end it; the user deletes or renames one member, and the next sync decides both paths again. A copy that would form such a pair on the receiver is refused there (`unapplicable`), so a pair made across devices (each creates `x` offline as another kind) never stalls a sync.

The rows are evaluated top to bottom, and swapping the devices mirrors every decision.

| # | Base | Devices | Decision |
|---|---|---|---|
| 1 | any | either blocked | conflict `blocked` |
| 2 | any | equal etags, or both absent | agreed |
| 3 | `uncertain` | differ | conflict `missing_ancestor` |
| 4 | `first` | one absent | copy (create-only) |
| 5 | `first` | both present | copy if exactly one side's `previous` is the other's etag (not for immutable records: revisions, knowledge records, image objects and blobs), else `missing_ancestor` |
| 6 | `none` | one absent | copy (create-only) |
| 7 | `none` | both present | conflict `missing_ancestor` |
| 8 | `agreed E` | one is E, the other present | copy the other over E; an immutable record (revision, knowledge record, image object or blob) is `revision_modified` |
| 9 | `agreed E` | one is E, the other absent | conflict `deleted` (deletion is not propagated) |
| 10 | `agreed E` | one absent, the other not E | conflict `edit_delete` |
| 11 | `agreed E` | both present, neither E | conflict `concurrent` |
| 12 | `deleted E` | one absent, the other is E | conflict `resurrected`; a blob is copied instead (create-only, as row 13): its name is its content hash, so the same blob again is never an outdated version |
| 13 | `deleted E` | one absent, the other not E | copy (a new record at a deleted path) |
| 14 | `deleted E` | both present, different | conflict `concurrent` |

A copy publishes the other device's **exact bytes** (`Transaction.put_exact`), so both devices converge on one etag. Those bytes still exist on the other device, so an aborted commit drops the copy rather than parking it under `.conflicts/` (journal kind `replica`). Before it is admitted, three overrides apply:
- **Head dependency.** A copy lands only if, once the commit is applied, the destination means what the origin means. Every revision the record pins must hold the origin's bytes on the destination, already or copied in the same commit: a manifest's heads (which must exist on the origin) and link endpoints, an instance's `base` and `derived_from`, and any pin in a payload or unknown field. That is the set the store's reference check counts (`replica.pinned_by`), less the implicit head (an entity's only revision, when its manifest declares none): a manifest copied without a head becomes byte-identical on both devices, so resolve's identical-manifest exemption still lets that revision be resolved. A 107 chat never lands without the play scope (`scope.json`) the origin homes it in, so the receiver never shows an `orphan_chat` it would then answer with a fresh scope of its own. Every campaign instance or chat a scope or knowledge record names (a 107 chat's roster actors, a 017 relation's endpoints, a 020 record's holders and participants, and the chat a 020 batch came from) that the origin holds must be present on the destination too, and a 020 knowledge record's campaign must exist there (a scope or an instance, 020's own test) whenever it exists on the origin: sync never creates the state 020's append refuses (`unknown_campaign`, `unknown_chat`, `unknown_actor`). A path that is blocked on either device (unreadable, a link) is unknown, never "absent on both": it is unmet. Text that parses as a reference to a path no library can store (a reserved device name) names nothing and is no dependency. Holding one copy can unmeet another's dependency, and can make what is left unacceptable to the store (a manifest held back leaves its new head revision alone in the source), so admission and this check repeat together until neither drops anything: after planning, after a unit is refused, and after a denial (a dependent of a denied write becomes `denied`). So a copied record never silently means other bytes on the destination, and never pins a revision that is still in conflict, which would make that conflict unresolvable. Otherwise the conflict is `head_dependency`. Art has its own requirements (see "Art").
- **Name collision.** A destination path that collides with a differently spelled entry gives `name_collision`. A canonical path that exists on a device only as a look-alike (`R9.json`) is blocked there (the scan's `shadowed` reason: unknown, never absent, so a case-only rename is never read as a deletion), and is reported as `name_collision` too.
- **Destination preflight.** The destination's writes are checked once with 010's read-only `Transaction.check()`. Only if that check fails are they admitted unit by unit, and a unit the store refuses becomes `unapplicable`. A unit is one instance, one manifest with its head revisions, the other revisions of one entity, or one art file. Campaign-local records other than instances are checked alone, and so is each source; the instances of one campaign are admitted cumulatively in sorted path order, so two copies that would form a cross-kind pair never both pass. Each art file is checked once, over the accepted copies its owner needs (a blob alone; a source's image or placement over that source's accepted copies; a campaign's over its accepted scope and instances); only when a source fails as a whole are its units admitted one by one, cumulatively (manifest units first), so two units that are each acceptable but not together (one entity id under two kinds, from another tool) are never both admitted. Manifests that link to other sources are then admitted cumulatively in sorted order, so a cross-source link cycle is caught. In that fallback, one final combined check of everything admitted runs before the commit, defensively: by construction it accepts what admission accepted, and if it does not the sync stops with `SyncInterrupted` before writing. Library-wide problems propagate and are never blamed on one path.

**Denied writes.** Authorization cannot be dry-run without consuming approvals, so a data commit uses 010's partial mode (`commit(..., on_denied=...)`). Each write is authorized exactly once. A write denied for its path (not granted, approval required, reserved) is dropped together with every copy of the same source (an art file only for itself), becomes conflict `denied`, and its pending entry is removed. What remains is checked again. If it is no longer acceptable on its own (for example, another source's manifest needed the denied one), it is re-admitted unit by unit, and each refused unit is also `denied`; that and the dependency check repeat together until neither drops anything, so a denial never stalls the rest. A denial that is not about a path propagates: an unissued handle, or an unavailable authority. Approvals consumed by dropped dependents are reported in `SyncReport.consumed_approvals`.

## Art

018's art is three kinds of file, and sync never creates a state the 018 batch would refuse:
- **Blobs** (`assets/blobs/…/<sha256>.<ext>`) are content-addressed and create-only: a blob is copied only onto an absent path, never over other bytes, and never deleted. A blob's tombstone never blocks it: when a blob deleted on both devices (by hand, ending a `deleted` conflict, or because it was oversize) is imported again, the same bytes under the same name are copied like a new file (row 12's exception), and the new image and placement that need it arrive with it. A scan lists blobs by name and size without reading them. A blob is hashed (and sniffed) when it is about to be copied, and on first sight: while the pair's archive does not record it as agreed. Once both archives agree on it and both sizes still match, it is **trusted by agreement** and not read again. A blob only one device holds is read only if it is to be copied: not while it is a conflict that copies nothing (`deleted`, `missing_ancestor`, `blocked`, `name_collision`), and not when the receiver's durable authority grants its handle no write there (below). A copy is staged lazily (`Transaction.put_blob_exact`): the origin's bytes are loaded at authorization and again at staging, one blob at a time, and every load must be exactly the planned size, extension and hash, or the sync stops as a stale write. A blob that fails its hash or sniff is `blocked` (`corrupt`) on that device and is never copied from it.
- **Image objects** are create-only like definition revisions (the immutable rows of the table). An image needs its blob identical on the receiver, and its owner there: a source image needs the source's manifest; a campaign image needs a scope or an instance of that campaign. An image object 018 cannot show (W6: not under the image schema, a payload its codec refuses, or a blob the origin's scan lists at another size than the object's `payload.blob.size`, which the resolver reads as `blob_size_mismatch`) is never copied, and neither is any placement that shows it: copied, a create-only object could never be repaired from the origin. The check reads the scan's listed size, never the blob.
- **Placements** are ordinary three-way records. A placement needs its subject present on the receiver (the source's manifest and the entity's head revision, identical; or the campaign instance), and for `set` or `adjust` the image it shows and that image's blob, identical. Inherited source art shown on a campaign instance also needs the instance identical (so its derivation is the same), the deriving entity's manifest and head revision identical, and, for `adjust`, that entity's placement in the same slot with its image and blob. A placement whose payload cannot be read (018's own codec decides, under 018's placement schema only), or that the origin's own batch would refuse (W8's `validate_placement`, so a source placement edited by hand to `hide` or `adjust` is `mode_not_allowed`; an image outside its scope, an `adjust` of nothing or of an inherited placement 018 cannot read, an `adjust` naming another picture than the one the entity's placement shows, a derivation naming an entity no library can store), is never copied.
- **Excluded sources (W5).** Art belongs to a source (a source image or placement) or shows that source's picture (a campaign placement that inherits it through the instance's derivation, or adjusts it). The 018 batch accepts such art only while the source is admitted (W5 `excluded_source`), and the resolver shows none of an excluded source's art. A present manifest is not enough: `load()` also excludes a source whose manifest reads, for a record in it that claims another source (`ownership`) or for a cross-source `identity_conflict`. So such art is never copied while **either** device's `load()` excludes that source; campaign art that reads no source (a campaign image, a `hide`) is unaffected, and blobs still land. Each device's verdict is the store's shared, cached [`excluded_sources()`](STORAGE.md#read-only-helpers-107): `load()`'s own algorithm, cross-source conflicts included, read once per plan and only when an image or placement is to be copied (an unchanged library costs one `stat` per manifest and revision entry and reads no file; no blob is read). `resolve` reads both devices' verdicts the same way and refuses what a sync holds.
  - **The origin's exclusion** holds the art as a state the batch refuses (like W6): on the origin it resolves to nothing, so a receiver that admits the source would show pictures the origin does not; the exclusion contests the source's own identity, so the head revision and scope sync would compare come from data `load()` rejected; and an image object is create-only and deletions never propagate, so a copy could never be withdrawn if the origin's repair removes the art instead of the damage.
  - **The receiver's exclusion** is an unmet requirement on the receiver: the copy would create a state the receiver's own batch refuses. Sync holds all three receiver cases as `head_dependency`: source art into a source the receiver's own files exclude (which the store would also refuse, as `unapplicable`, before this check), a cross-source exclusion, and a campaign placement that inherits a picture from an excluded source. The store sees neither of the last two (it checks one source's scan, and a campaign asset against its campaign only), so its own check is only the backstop. It reads the receiver's verdict as it stands before the commit, which errs only toward waiting: art whose source this very sync repairs on the receiver waits one more sync, and art whose source this sync newly excludes there lands byte-identical to the origin's, unseen until that source is repaired.
  - Either hold lifts by itself once that device admits the source again; the next sync copies the art.

An unmet requirement (or such a refused placement, or art of an excluded source) is a `head_dependency` conflict, never `held` (which is only for the families above), whose detail names the missing paths or the refusal. A blocked subject, such as either member of a cross-kind instance pair, is unknown and therefore unmet. Blob writes need an `assets` grant. A device whose handle lacks one receives no blob: each blob copy is `denied`, and so is every image and placement that needs one of those blobs. It still receives art that needs no new blob (a `hide` placement, an image whose blob it already holds, and placements showing such images), and everything else. When the receiver's library is bound to a durable authority that issued its handle, `plan_sync(left, right, handles)` (which `sync` calls) sees that no active grant covers the blob and plans it as `denied` without reading it; otherwise the commit denies it, after its plan hashed it and its authorization loaded it. An authority that is not usable (closed, or poisoned by a failed ledger flush: `DurableAuthority.usable` is false) plans nothing as `denied`: the commit decides, and its denial for an unavailable authority propagates ("Denied writes").

## Keep-both

For every conflict except `denied` and `held`, each device whose peer has a present, usable version receives that version as a **kept version**. Blobs are never kept: other bytes under a blob's name are corruption, not a version. It goes under `.conflicts/<hash16>/<name>~<digest12>[.N]`, through `Transaction.keep_version`. The authorization address is distinct from the record's own: `kept/<hash16>/<digest12>[-N]/<name>`. So "keep these bytes beside p" and "overwrite p" are different approvals, and they appear under different `preview()` keys.

A slot already holding those bytes is reused, so a kept version is not written again (a human who deletes one slot and edits another can leave two identical copies), and a conflict stays reported on every sync until a human ends it. A kept version that cannot be written (for example, because of path limits) is reported as `kept: false`. A device that has moved on from the base is never handed that base as a kept copy: it is not the peer's version. A device whose own file could not even be read receives nothing: there is nothing to keep it beside, and the next readable sync decides the path. A `denied` conflict keeps nothing either: the denial is only known while committing, after kept versions were planned. Both versions stay canonical on their own device, and the conflict is reported on every sync until the grant changes. Kept versions are not indexed: `load()` still shows one record per path.

**Dismissing a kept version** (028). Deleting a kept file by hand does not stick: the next sync delivers it again into the empty slot. `dismiss(store, peer, path, kept=<etag>, handle, approvals=None)` records the decision instead, in this device's `keeps.json` for the pair, keyed by the path and the etag of the dismissed bytes. No timestamp decides anything:
- Only a version a **sync wrote here from the peer** can be dismissed: `keeps.json` lists those etags. A file under `.conflicts/` may also be this device's own version that `resolve` held, perhaps its only copy anywhere, and the slot cannot tell; `resolve` therefore records each hold as `held` in the receiver's `keeps.json`, in the same commit as the hold, and a held version is never recorded as delivered, never honoured as dismissed, and never dismissable. A device paired with several peers keeps every pair's versions in one `.conflicts`, so `dismiss` also refuses bytes any pair's record holds (or might: an ignored record's holds are unknown). A keep is recorded in the same data commit that writes it, so a crash, a race or a dropped connection after that commit never leaves it unrecorded, and only when it writes the first copy of its bytes at its path: a slot found already holding those bytes, or a second copy beside one, may be a hold, so it is never taken for a delivery. A dismissal records the base this device's archive holds for the path (refused while that archive is not valid).
- A sync never keeps those bytes for that device again while the conflict stands on the same archive base, and reports the device in `Conflict.dismissed`. A **different** version from the peer (other bytes) is kept as usual; the peer going back to the dismissed bytes while the conflict is open is not delivered again.
- It never touches the other device: the peer's file stays its canonical record (`resolve` can still choose it), the conflict is still reported until a human ends it, and the peer still keeps this device's version unless it dismisses it too.
- A dismissal lasts as long as its conflict. The pending step of a completed sync drops the dismissals of every path no longer in conflict (and a delivered version once no slot holds it and it is not dismissed), `resolve` drops those of the conflicts it ends in its own archive commit, and a dismissal is honoured only on the archive base it was recorded with, and only while no pending marker has moved the path's base (a `resolve` interrupted after its copy landed leaves the marker, so the next conflict keeps the version again). The record stays small, and the same bytes in a later conflict are kept again.
- It is written in one 010 transaction, authorized like a keep: `APPLY` on the kept version's own address, so a handle that may not write kept versions may not dismiss one. The record is journaled as `.sync` state, so a crash leaves it written or not.
- It refuses (`DismissRefused`, nothing written) a peer that is not a device ID or is this device, a blob or a path sync does not carry, an etag that is not one, this device's own current version, a version no sync delivered here from the peer, a pair whose archive here is not valid, or a version `resolve` held. Dismissing twice writes once. The kept files are not deleted (010 never deletes); `Dismissal.slots` names the ones holding those bytes. They are bytes the peer's sync delivered and no `resolve` here held, so the app may delete them, and no sync rewrites them.

While a conflict stays open and one device keeps editing the record, every new version it sends lands in a new slot, so kept versions still accumulate (one per sync, up to the record's size each) unless each is dismissed.

`resolve` marks its copy in the receiver's pending marker in the same transaction, as a sync does, so an interrupted resolve followed by a revert is a conflict, never an overwrite. It refuses while either device's marker for the pair is ignored.

Kept copies of the **other device's** version are regenerable (journal kind `keep`): an aborted commit drops them, because the other device still holds the bytes. The version `resolve` replaces is the receiver's own and may exist nowhere else (`hold`): an aborted commit preserves it like any other version.

## Ending a conflict

- `resolve(left, right, path, keep=<etag>, expected={device: etag | None}, handles, approvals=None)` makes the device that does not hold `keep` receive it. Its replaced version is kept under `.conflicts/` in the same transaction, and both archives then record `agreed keep`.
  - **Manifest:** absent head revisions are copied with it. A head revision that differs must be resolved first. When a differing head revision has the same ID on both devices and the manifests differ too, neither can be resolved first: each device's manifest pins its own revision. Add a new revision on one device and move its head there, then resolve the old revision and the manifest.
  - **Definition revision:** allowed only if nothing on the receiving device can pin it: a manifest head, a link endpoint, an instance's `derived_from`, `base` or a pinned reference in its payload, a pinned reference in another revision's payload, or any text in a scope, chat, relation or knowledge record that names it (a chat's source bindings). Every parsable record is checked, those of excluded sources included. A manifest byte-identical to the receiving device's copy of the winner's manifest is exempt: it is the winner's own manifest, which names the revision being replaced by ID. A blocked path that could be or hold a record means "cannot prove unreferenced" (`RevisionReferenced`), so it blocks revision resolves until it is fixed; a blocked entry that cannot hold records (a root-level link, a non-JSON note under `sources/`) does not.
  - **Knowledge records** are never replaced: they are immutable evidence. When the receiver lacks the chosen record (an uncertain base after a re-identification, say), `resolve` delivers the campaign's whole knowledge log unit create-only: every record of that campaign the winner holds and the receiver lacks, records and batches together. It refuses when the two logs diverged (a path both hold differently): merging two devices' logs belongs to 028.
  - **Art:** a blob is delivered create-only and only after it is verified (hash and sniff) on the winner; a receiver that already holds other bytes under its name is refused (that is corruption: 018's `repair_blob` fixes it). An image object is create-only too: refused when the receiver holds different bytes. An image or placement is refused until every requirement of "Art" holds on the receiver, the receiver's blobs verified.
  - **Refused (`ResolveRefused`, nothing written):** a held path (an accepted event, wrap-up or holding, or a held relation), a member of a cross-kind instance pair, the receiver's grant refuses the write, a deletion choice, a blocked side, `keep` matching neither device, either device differing from `expected`, an archive for the pair that is missing or ignored on either device, or a record it would write (the chosen one, or a head revision a manifest resolve copies with it) whose pinned revisions differ between the devices or are blocked on either (resolve the revision first), whose named actors, chat or (a chat) play scope the receiver lacks, or (a knowledge log) whose campaign the receiver lacks. Rewriting such an archive would forget why every other path is uncertain, so the devices must complete one sync first; that sync records the uncertainty in the pending markers.
- Deleting a record on both devices by hand ends a `deleted` conflict, and a tombstone is archived.

## Apply order and crash safety

`plan_sync(left, right, handles=None)` only reads (directory listings are cached for the whole plan). With `handles`, it reads each receiver's active grants (never asking for an audited decision) to plan a blob its handle cannot write as `denied` (see "Art"). `SyncPlan.preview()` gives, per device, the exact bytes of every authorized write.

`apply_sync(plan, handles, approvals=None)` writes in a fixed order, where `a` is the lower device ID:
1. data(a): copies, kept versions and the merged pending marker, in one transaction;
2. data(b);
3. verify: every published and kept file is re-read and must hold the planned bytes;
4. archive(b), then archive(a);
5. pending(b), then pending(a).

An archive entry `agreed E` is written only after both data commits and verification succeeded, and only for paths both devices verifiably held as E. A first sync with nothing agreed still writes an empty archive.

Errors:
- These stop the sync with `SyncInterrupted`, and no archive is written after the stop:
  - a stale write (a library changed after planning);
  - `WriteConflict` (an external edit raced publication; 010 kept the human's file);
  - a per-path refusal at commit time;
  - a failed verification.
- `CommitIncomplete`, `OSError`, `PendingRecovery`, `RecoveryBlocked` and root or V1 errors propagate; 010 recovery owns them.

`sync_until_quiet` retries `SyncInterrupted` until a sync completes and writes nothing. Its report merges every attempt: all copies, notices and consumed approvals, and the conflicts of the final sync. After `attempts` it raises the last error, or `SyncNotQuiet`, carrying the merged report.

**Lock order.** Within one process each library has one re-entrant lock (`LibraryStore.lock`) that its commits and reads take. A thread that holds two libraries' locks takes them in one global order, by root path and then by lock (two opens of one folder share a root, and still both raise `SameDevice` in either argument order); no thread ever waits for the first library while holding only the second. Planning holds both for the whole plan, in that order, so two syncs of the same pair in opposite argument order cannot deadlock (pinned by a test running both orders concurrently). A blob copy is loaded lazily from the origin inside the destination's commit (`put_blob_exact`'s reader takes the origin's lock), so every sync data commit, and `resolve`'s commit, first takes both libraries' locks in that order and holds them through the commit: a commit on the later library never holds it while waiting for the earlier one that a planner already holds (pinned by a test racing a planner against a blob copy, for both `sync` and `resolve`). The blob bytes are still loaded one at a time, only when the commit needs them.

## Limits

- An archive or pending marker past one file's capacity is sharded (028, "Sharding and tombstones"), up to about six million paths per pair; a plan past that is refused before any write (`ArchiveTooLarge`). Record tombstones are never compacted, because none can be dropped without losing a resurrection check.
- Not in this slice:
  - more than two devices, transport and pairing;
  - causal branches, and history beyond one agreed etag per path;
  - deletion propagation, and resolving toward a deletion;
  - ledger sync;
  - semantic or field-level merge (042);
  - dependency checks beyond references to revisions, named instances and chats, and a knowledge record's campaign (a 017 relation waits for endpoint instances the origin holds; one the origin lacks too is delivered, as 017 tolerates).
- A true first sync, or one after `.sync/` was deleted or both devices were re-identified, re-creates records deleted on one device beforehand. After a tombstone, resurrection is detected only for the exact tombstoned bytes, and never for a blob (its bytes are its name). On a first sync every path the devices already agree on is marked in the data commits (and so is any agreement whose base does not record it: a conflict ended by hand, byte-identical records made offline, an agreement after a tombstone), so a crash after the first data commit never leaves a `first` base behind (a crash before it persisted nothing: that is still a true first sync).
- A crash between the two archive commits of a **first** sync leaves one archive missing and the other valid. Until the next sync completes, only the pending markers carry the agreement: a path both devices still hold as that sync left it stays `agreed` (both data commits marked the same `to`), and the next sync writes both archives. Every other base is `uncertain`: a path created, edited or deleted on either device in between, or one that was in conflict. Such a change is then a keep-both `missing_ancestor` conflict (nothing is lost) instead of a copy or a deletion, until it is resolved. The same holds for a crash before both archive commits, and for a relation held back on that first sync once its hold lifts.
- A manifest `load()` admits with a problem it drops (one malformed link, say) is not a writable envelope, so sync blocks it: a permanent `blocked` conflict, and revision replaces in that library are refused until it is fixed.
- **Independently created actors no longer merge.** 107 named a new actor `<entity>-<n>` by the first free number in its campaign, so two devices that each added the same character to one campaign offline created byte-identical records that sync treated as agreed. A library with a device identity now numbers actors per device, `<entity>-<tag>-<n>` ([DEVICE_SYNC](DEVICE_SYNC.md#per-device-ids)). Actors two such devices created *before* that change still merge. 034's unique items are numbered the same way, `<base>-<tag>-<n>`, except one particular (`individual`) artifact, whose tag comes from its definition so two devices making it collide on one id; items two devices made before either was identified share an id too, and since their records differ they arrive as a keep-both conflict, not a merge.
- **Knowledge logs are not merged yet.** Knowledge records are immutable like definition revisions: a new one is copied create-only, a changed one is `revision_modified`, and `resolve` never replaces one (it only delivers a log the receiver lacks). 020 commits an append as its records plus one batch, so a campaign's knowledge log is **one unit**. It moves only when it can be seen whole on both devices: an `events/` or `evidence/` folder (or one below) that cannot be listed or is spelled differently, or an unlistable campaign folder, `campaigns/` or root, holds it back (fails closed), and `resolve` refuses it then too. Otherwise, if any of its paths is a conflict (two devices appending the same batch number offline, or a blocked or refused record), none of that campaign's knowledge copies land, and they are reported as skipped; if one of its copies is denied, the others are dropped with it and reported as `denied` conflicts. Each device keeps a healthy log of its own appends; the batch is a keep-both `missing_ancestor` conflict. A single device's appends still sync whole. Merging two devices' logs into one belongs to 028.
- **A restore after a finished sync is an edit.** Pending markers protect a restore of the old bytes made before the archives record the copy: the holder of a marker no longer holds its `to`, so the path is a `missing_ancestor` conflict that keeps both versions (even when the copy was already verified). Once the archives are written, a restore is an ordinary later edit and is synchronized as one.
- **Denials are coarse.** A denied write drops every copy of its source to that device (instances and art files are independent), not only the writes that strictly depend on it.
- **Blobs are trusted by agreement.** After one verified agreement a blob is identified by its name, its size and the pair's archive, and is not read again. A blob corrupted in place at the same size after that stays `agreed` and undetected by sync. It is never propagated (a blob is only ever copied onto an absent path, from a hashed origin), and locally `read_image_bytes` raises `BlobCorrupt` and `repair_blob` fixes it. No inode or modification-time cache is kept: timestamps never decide.
- **Art costs reads and archive entries.** Each copied blob is read about five times (the plan's hash, authorization, staging, the commit's temp digest and verification), one blob at a time. `SyncPlan.preview()` loads every blob it copies; an `assets` grant, not per-blob approval, is the normal path. A blob the receiver may not write is read by no sync when the receiver's library is bound to its durable authority (as [production libraries must be](STORAGE.md)); on an unbound library (test fixtures) the plan cannot see the grants, so such a blob is hashed and loaded again on every sync until its grant is added. A blob only one device holds that is in a conflict that copies nothing is not read, so a corrupt one reports that conflict's code rather than `blocked`; `resolve` hashes it before delivering it. A picture is about three archive paths (blob, image, placement), so one archive file holds roughly 7,600 pictures before it is sharded. A plan that copies an image or placement also asks each device for its `excluded_sources()` (W5): on an unchanged library that is one `stat` per manifest and revision entry, but on a store's first call, or for a source changed since, it reads that source's manifest and revisions again, which the plan's own scan has just read too.
- **A damaged campaign art layer is not reproduced.** Sync never moves non-record files, so a receiver can show inherited source art where the damaged origin shows `Unavailable` (018's damaged-layer rule); the origin reports the damage in `load()`.
- **Single-device trust in markers and lineage.** A pending marker is trusted on one device's word, and the `check` digest detects damage, not forgery. `.sync` writes need no handle. Likewise `put_exact` publishes bytes verbatim, `previous` included, and a true first sync trusts one-hop `previous` lineage (row 5): a writer with APPLY that calls it directly can claim any ancestor; and its `allowed_manifests` (the identical-manifest exemption `resolve` uses) is taken on the caller's word. Keeping `.sync` writes and `put_exact` out of workers' reach is the application's job until 007/028 integrate.
- **Link-drop policy.** A copied manifest is admitted exactly as a local commit of it would be. Under 010's accepted link-order policy, it can cause *another* source's cross-source link to be dropped on the destination, and the next `load` reports it.
- 010's R7 window remains: an external edit landing exactly between a target's guard read and its `replace` is lost. 019 narrowed it for a file being created: its directories are now made before that guard read, so only the publish step's own path re-check (a stat, no read of the file) and the `replace` remain in the window.
- **Rollback.** A pre-019 build cannot recover an unfinished journal that contains `replica`, `keep`, `hold` or `state` entries (`RecoveryFailed`, unknown kind). Finish recovery with a 019 build, or use `discard_journal`. A build from before art sync finds a "bad entry" in an archive or marker that records art paths, ignores the whole file, and treats every path as uncertain: conservative, and not supported on this pre-release branch. A build from before 028 finds an unknown format in a sharded (`/2`) root and does the same; it cannot read `keeps.json`, so it delivers dismissed versions again.
