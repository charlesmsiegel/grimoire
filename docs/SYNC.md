# Device sync: revisions and conflicts

**Status:** first slice of [Sync Revisions And Conflict Core](roadmap/sprints/sync-revisions-and-conflict-core.md) (Wave 3, #019), implemented as `grimoire.sync` over the [native store](STORAGE.md). It synchronizes **two libraries that are both open locally**: a desktop folder and a phone folder, or any two copies of one library. Pairing and an authenticated peer transfer over this core are [028's first slice](DEVICE_SYNC.md); there is no UI yet. A green test suite proves this contract, not a working phone sync.

## What it guarantees

- **Timestamps never decide.** Sync compares bytes (etags). Nothing in `grimoire.sync` reads a clock, a modification time or randomness; a test pins this.
- **Non-overlapping edits merge deterministically.** `sync(a, b)` and `sync(b, a)` produce byte-identical libraries, the sync bookkeeping included.
- **Nothing is silently overwritten, resurrected or dropped.** Overlapping edits, an edit against a deletion, records the other library cannot accept, and anything without a provable common ancestor become **named conflicts**. Each device keeps its own file and also receives the other device's version under its `.conflicts/`.
- **A deletion travels, and what it removed stays recoverable** (028). A record one device deleted while the other still holds exactly the version they last agreed on is deleted there too; that device keeps the removed version under its own `.conflicts/`, recorded as `held` so it is never dismissable. A deletion that would leave anything on the receiver needing the deleted record is held back as a conflict (`delete_dependency`), and create-only families never propagate a deletion ("Propagated deletions").
- **Crash-safe.** Every write is a 010 transaction. After a crash, reopening both libraries and syncing again reaches exactly the state an uninterrupted sync reaches.
- **One bad record never blocks the rest.** A path or source the other library cannot apply, a write the policy denies, or an unusable file becomes a conflict, and everything else still syncs.
- **Converged means no conflicts.** Two libraries are converged when a sync reports no conflicts. A `held` conflict (a family whose merge rule does not exist yet, see below) or a `merge_review` (a campaign's ledger merge waiting on its owner) is therefore never converged, even though nothing is wrong on either device.

## What is synchronized

`grimoire.sync.syncable(path)` is the single definition of the synced set, and the extension point for later families (021 accepted events and wrap-ups, 023 holdings, ledgers). In this slice it covers the canonical records of 010 and of [107](CHATS.md): source manifests, definition revisions, campaign instances, 107's play-scope (`campaigns/<id>/scope.json`) and chat (`campaigns/<id>/chats/<chat_id>.json`) records, [017](GRAPH.md)'s relation records (`campaigns/<id>/relations/<relation_id>.json`), [020](EVIDENCE.md)'s create-only knowledge records (events, evidence and knowledge-log batches under `campaigns/<id>/events/` and `campaigns/<id>/evidence/`), [036](TRANSCRIPTS.md)'s create-only chat transcript pages (`campaigns/<id>/transcripts/<chat_id>/<seq>.json`), [035](SCENES.md)'s played turns (`campaigns/<id>/turns/<turn_id>.json`, mutable: changed by compare-and-swap, so ordinary rows; see "Played turns" below), and [018](IMAGES.md)'s art: image objects and placements (`images/` and `placements/` under a source's `_source/` or a campaign) and their blobs under `assets/blobs/`. Instances, scopes, chats, relations, knowledge records, transcript pages and turns are campaign-local: each is its own admission unit, never grouped with a source. Each art file is its own unit too, never grouped with its source (see "Art" below). S3 is proven both on a synthetic instance-shaped chat and on real 107 chats made by `grimoire.chatstore`:
- a lorebook attached on one device and a world attached on the other touch different files, so both merge;
- concurrent edits of one chat record are a keep-both conflict, and the new participant's actor still travels;
- after either, each device's navigation index still finds exactly one chat.

Never transferred:
- device-local state: `.txn/`, `.conflicts/` and `.sync/`;
- **derived indexes**, such as 107's navigation index. It is rebuilt from canonical records on each device, never synchronized as a second owner.

Reported as `skipped` and never touched:
- ledgers under `authority/`;
- the library marker;
- unknown root entries such as `worlds/`, and anything under `assets/` that is not a blob name;
- nothing is **held back** any more (the `held` code is kept for a family whose merge rule comes later): 021's accepted events and scene wrap-ups, 023's holdings and the relations of a campaign with an accepted event merge as ledger units (below, "Ledgers (028)"), and 035's played turns merge as their own family (below, "Played turns");
- the reserved campaign family `scenes/`, and any file under `events/` or `evidence/` that is not a knowledge record of a known family;
- non-record files.

Held paths (none at present) are not silent. Every held path whose two devices are not byte-identical (one side absent, different bytes, or blocked) is also a **`held` conflict**, as is a held folder that cannot be listed on either device. A `held` conflict copies nothing, keeps nothing and archives nothing; the path stays in `skipped` too. It ends only when both devices hold identical bytes (or neither holds the path), and `resolve` refuses every held path.

### Ledgers (028)

A campaign's **ledger** is never decided file by file: 021's accepted events and scene wrap-ups (`accepted/`, `wrapups/`), 023's holder files (`holdings/`) and, when either device holds an accepted event in that campaign (or its `accepted/` folder, in any spelling, or the campaign folder, `campaigns/` or the root cannot be listed: the check fails closed, and `resolve` makes it on the very scans it writes from), the campaign's 017 relations. Their own stores commit several files as one unit (an event with the relations it changes, one operation across several holders), so the campaign's ledger files are **one unit** (`grimoire.sync.units`), merged by [LEDGER_MERGE](LEDGER_MERGE.md):

- Where both devices hold every file of the unit identically, it is agreed, as any path is.
- Otherwise each device's files are its ledger, and the **base** is what the pair last agreed on, chosen for the unit as a whole so that its files never mix generations (an operation agreed in one holder file and new in another would read as half an operation). Per file it is the entry both archives hold. Where the archives disagree, which only a crash between their commits leaves, both entries are agreements the pair held, and the newer is used: the one an unfinished sync's pending marker names as its `to`, else the one whose bytes are still at hand, else the lesser etag. The choice never depends on which device starts the sync, because a merged file's `previous` is its base's etag. A sync stopped before its archives leaves markers whose `to` is newer. A merged file's `to` was held by neither device before it landed, so the markers' `to`s are the unit's base only where the merge landed on **both** devices: for every marked file of the unit, each device's marker names it or the device holds it now. A merge only one device took (a stop between the data commits) is merged again from the generation before: the archived agreement, else the agreement the marker was written over, else none. That gives the same files, because the merge is idempotent over the side that already took it. The base's bytes come from whichever device still holds them, or from the pair's **base cache**. A removal's marker (a relation's propagated deletion, made before its campaign had a unit) is no merged file: it gives its path the base any path's marker gives (`deleted E` once the deletion verifiably landed) and never decides whether the unit's merge landed. The unit's base is every one of its files' base for the pair's bookkeeping too (pending markers and archives), so a file whose own markers alone would read as uncertain (a stop between the data commits, then both devices playing on) never gains an `uncertain` entry that would leave the unit with no base at the next sync.
- A clean merge travels as ordinary copies to each device lacking the merged files. A unit lands all of it or none of it on a device: admission, dependencies and a commit's denial take out the whole unit. A file a merge leaves out would be a deletion, so it is a fault, never written.
- Under the sync's locks, just before each data commit, every unit that commit writes is listed again on both devices: its own kinds only (relations only where they are in the unit), each readable file by etag and each file the scan found blocked by name alone. A ledger file either device added or changed since the plan (an event accepted mid-sync), or a folder of the unit that became a link or cannot be listed (never followed: it hides what it holds), stops the commit (`SyncInterrupted`), and the next sync merges again. A blocked file never stops it: 019 decides that file on its own (`blocked`), or the merge stops for review on it (`unreadable`).
- A merge that stops is a **`merge_review`** conflict on every file of the unit the two devices hold differently. `Conflict.review` holds the review's items (`ledgermerge.ReviewItem`: reason, subject, detail), and `Conflict.token` names the unit's files as they stood. On top of the merge's own reasons, sync adds `unreadable` (a blocked or undecodable file), `unlistable` (a folder of the unit, the campaign, `campaigns/` or the root that cannot be listed, or a look-alike spelling of a folder of the unit, where `relations/` is a folder of the unit only while the campaign's relations are in it: an unlistable `relations/` of a campaign with no accepted event stops no holdings merge, as an unreadable relation file there stops none; where the campaign has no ledger file on either device or in either archive, the conflict is on the folder itself, as is one on `campaigns/` or the root while no campaign has a unit; `resolve_ledger` refuses such a review, which ends once the folder can be listed) and `no_base` (an agreed version neither device nor the base cache holds, an agreed deletion, or an uncertain agreement, for a file the devices hold differently). Nothing of that ledger is copied, kept or archived. The merge runs again on every sync, so the conflict ends by itself once the devices agree, or by `resolve_ledger`.
- **Base cache.** `.sync/peers/<peer>/bases/<key>.json` holds the exact bytes of a ledger file (an event, wrap-up, relation or holder file) as the pair last agreed on it. `<key>` is the first 32 hex digits of the SHA-256 of the file's path, so every entry's name has one length however deep the ledger file is, and its bytes are used only where their etag is the agreed one. It is written in the archive commit, whenever a ledger file's archive entry changes to a new agreement. On a system whose path limit the entry's name would exceed (`LibraryStore.sync_state_fits`), no entry is written: the cache is a copy a merge may need, never a reason for the archive commit to fail. It needs no delete: there is one entry per file, rewritten in place. Files left under `bases/` in any other layout are never read. It roughly doubles the disk a ledger takes. Limit: an agreement with no cache entry (recorded before this version, or on a system that cannot store one) has none. If both devices change such a file before a sync records a new agreement for it, that file is `no_base` and needs `resolve_ledger`.
- `resolve(...)` refuses a ledger file and points to `resolve_ledger`.
- **Deletions (028).** Row 9 never reaches into a ledger unit ("Propagated deletions"). A file of the unit one device removed (by hand, or a damaged library: 021 and 023 have no delete) is a merge the ledger merge never makes, so the unit stops for review (`deleted`): nothing is removed on the other device, no tombstone is archived and nothing is kept. `resolve_ledger` keeping the device that still holds the file puts it back; keeping the device that removed it is refused (`not_on_kept_device`), and `resolve(..., keep=None)` is refused as for any ledger file. A relation deleted while its campaign had no accepted event is an ordinary record, so the deletion propagates; once the campaign has a unit its tombstone stands as it is (both devices lack the file, so the unit is quiet there), and a file written again at that path stops the unit for review (`no_base`: the pair agreed it was deleted). A deletion of a record a ledger file still names (an instance with a holder file, say) is held back as `delete_dependency`, as for any record. The base cache is never consulted for a tombstone: an entry left for a path that is no longer agreed is read only where its bytes' etag is the agreed one, so it can never stand in for other bytes. Proved in `backend/tests/test_sync_ledger_deletion.py`.

`resolve_ledger(left, right, campaign, keep, token, handles, owners=None, approvals=None)` (`grimoire.sync`) ends a campaign's `merge_review`. It writes only that campaign's ledger unit, with `apply_sync`'s own steps, so it is as crash-safe as a sync: no other copy, kept version or propagated deletion (and so no holds step), locally or over the transport; those wait for the next sync.

- `keep=MERGE` (`grimoire.sync.MERGE`, an enum member no string equals) takes the merge the review would make once its policy reasons are accepted (`ledgermerge.POLICY`: one chat on both devices, a revocation the other device built on). Nothing is discarded. A review with any other reason has no such merge, and is refused.
- `keep=<device id>` (a string; a device may be named `merge`, and `"merge"` then names it) takes that device's ledger files, as they stand, for both devices. It **discards** the other device's changes to that ledger, so the losing device's handle must be one of its library's `owners` (its `DurableAuthority.owners`). 021 and 023 have no delete, so a file only the losing device holds (an event it accepted) is refused (`not_on_kept_device`): revoke it on that device first.
- Refused (`ResolveRefused`, nothing written): a `token` other than the unit's as it stands now, meaning either ledger changed since the review was reported. Also refused: a campaign with no ledger files, a `keep` that is neither `MERGE` nor a device id of the pair (the string `"merge"` included, where no device is so named), and a ledger file that names a record (an instance a holder file or an event names, say) the receiver lacks, which only another copy of the sync would bring: sync first, and the review's token still stands.
- `resolve_ledger` (and `plan_resolution`, which 028's transport replays) is the only way to decide a review: `plan_sync` takes no decision.

Sync compares whole files. It never interprets payloads, never merges inside a file, and never treats source inheritance (`derived_from`, `base`, portrayals) as device ancestry. These structural readings are the only exceptions:
- a manifest's `heads`, for the head-dependency rule;
- for art: an image object's `blob`, a placement's `mode` and `image`, and an instance's derivation (its `derived_from` entity, which inherited source art needs); a blob's name is its content address (sha256 and extension);
- on a true first sync only, a record's `previous` field, for one-hop lineage;
- for a campaign whose two knowledge logs diverged (028), every knowledge file of it, assembled by 020's own `assemble` and checked for rulings both devices added (see "Knowledge logs (028)");
- when `resolve` replaces a definition revision, the store's reference check reads every manifest's heads and links, every instance's `derived_from`, `base` and pinned payload references, other revisions' pinned payload references, and every string in scope, chat, relation and knowledge payloads (a pinned reference, or an unpinned one beside a `resolved_revision`).

### Played turns (035, 028's turn merge)

A turn is one mutable file per played turn of one chat, so it takes the ordinary decision rows: a turn one device changed since the agreement is copied over it, two devices' edits of one turn are a keep-both `concurrent` conflict, and `resolve` ends one like any mutable record. Two devices that play one chat offline write two files with two ids (the device tag, [SCENES](SCENES.md#a-turn)); the next sync copies both, and the chat is then **forked** on both devices until its owner chooses which branch goes on ([SCENES](SCENES.md#forked-chats)). The choice is a `set_aside` mark written on each losing branch's first turn, so it travels as those files do: the same choice made on both devices is byte-identical (agreed), and different choices made offline mark different files, are both copied, and leave the same `conflict` state on both devices, never a silent flip. Untagged turns (played before `identify`) that collide by id are ordinary keep-both conflicts.

Beyond the head-dependency rule every campaign record has (the actors a turn names that the origin holds, and the revisions its lines pin), a turn never lands without (`sync.turns.turn_needs`), whether or not the origin still holds them: its chat record and the campaign's play scope, the turn it `follows`, and the turn its mark names as `chosen`. Otherwise the receiver could not place it (a gap) or would read a choice naming nothing. A blocked one is unmet. A turn written before `follows` existed is placed after the turn before it of its own device, else the untagged one, else the only one, so what the origin places it after is needed too (`sync.turns.turn_named`): that turn, or, short of its own device's and the untagged one, every turn of that number the origin has, so the receiver places it as the origin does (after the only one, or nowhere when there are several). A blocked one there counts as present: it never lands alone beside another device's turn of that number and reads as played after it. An unmet need is a `head_dependency` conflict naming it, and the turn lands with the next sync that can carry it.

Two devices' edits of one turn (a mark each, a pause on one and a strike on the other) are a keep-both conflict, and each device keeps its own canonical version until it is resolved, so the two may read different turns of that chat. The scene reads this device's kept-version records (`sync.turns.open_conflicts`: a path where a pair's entry names a version of the peer's that this device has not dismissed, either the one the pair's last sync kept or tried to keep (`open`, whatever the conflict's base and whichever pair first wrote those bytes here) or one delivered in the conflict that stands) and fails closed: while any turn of a chat is in such a conflict, or a record of a peer that may have synced the campaign cannot be honoured, every write to the chat but a pause is refused `turn_conflict`, and a pause in the peer's version kept here holds play too, so both devices show it ([SCENES](SCENES.md#forked-chats)). `resolve` (or a sync that finds the devices agree) lifts it; on this device alone, so does dismissing the peer's version, or ending the pairing with that peer (`unpair`: the records of a peer whose pairing record reads as revoked hold nothing, which is the owner's way out for a lost peer). Sync never propagates a turn's deletion, so a turn one device lost is a `deleted` (or `edit_delete`) conflict that holds the chat on both devices, the one that still holds the turn included, until `resolve` gives it back (a turn's deletion cannot be chosen: turns are not a family sync deletes). A library whose device identity is damaged or missing beside pair records cannot attribute them, so every chat of it waits until it is identified again. A record lost (missing beside a pair that completed a sync), damaged or unreadable holds the campaigns that pair synced, and so does any one beside kept versions of the chat's turns when no record can tell (`<sync records unreadable>`); a pending marker, an archive or a kept file lost or damaged changes nothing the scene reads while the record stands, and a lost or damaged pairing record is never taken for an ended pairing. A turn whose predecessor is in such a conflict lands after the receiver's version of it, and is played on only once it is resolved. And a turn written before `follows` can still be placed differently by a receiver that already holds its own device's or an untagged turn of the number before it that the origin lacks.

## Device identity

`identify(store, device_id)` writes `.sync/device.json`. Device IDs are supplied by the caller and never generated. An ID is one lowercase identity segment that is also a portable path segment.

Refusals:
- a library with no identity, or a damaged one: `NoDeviceIdentity`;
- two libraries with the same ID (the same library twice, or a folder copied together with its `.sync`): `SameDevice`;
- changing a valid ID without `replace=True`: `IdentityExists`.

A damaged identity file is replaced by `identify`. When a device's valid ID changes, the same commit **retires** each of its peer archives and markers, with every shard a sync would read with it (the retired root names them): those its root lists, or every shard of that kind on disk when the root and its listed shards are no valid document (a damaged root lists none), and its kept-version record (a retired one reads as missing, with no notice): the file stays present but is rewritten as `grimoire.sync.retired/1`, which records only the paths it named and is never valid again. The next sync of the new ID is therefore conservative rather than a first sync, the retired paths stay uncertain (a tombstone is not forgotten), and renaming the devices back can never revive an outdated base. If **both** devices take new IDs, neither has any file for the new pair, so the next sync is a true first sync (see Limits).

## Bookkeeping (`.sync/peers/<peer>/`)

- **`archive.json`** holds the last agreed state per path. `{"agreed": E}` means both devices verifiably held exactly E. `{"deleted": E}` is a **tombstone**: both devices were absent after last agreeing on E. Tombstones are kept, except a blob's (below, "Sharding and tombstones").
- **`pending.json`** records what an unfinished sync published on this device: `{"from": E0, "to": E1, "base": A}` per path (A: the agreed etag both archives held when it was written, or `null`), `{"from": E, "to": null, "base": A}` for a deletion of E it made here (028), or `{"uncertain": true}`. It is written in the **same transaction** as the data, and that data commit happens even when nothing is copied if the marker changes (for example, to record uncertainty), so a crash before the pending step can never leave rewritten archives without it. An entry is removed only after both archives are written and its path is resolved. A path whose base was `uncertain` and that did not end agreed, or that ended absent on both devices with no known tombstone (or with disagreeing ones, after a crash between the two archive commits), keeps (or gains) `{"uncertain": true}`, so the uncertainty survives the sync that saw it: otherwise the next sync would see a `none` base, and a one-sided deletion would be undone by a create-only copy.

- **`keeps.json`** (028, `grimoire.sync.keeps/1`) records, per path, the etags of the peer's versions a sync wrote on this device as the first copy of those bytes there (`delivered`, recorded in the data commit that writes the keep), while the path is in conflict (as the last sync that saw it found it) the archive base that conflict stands on (`base`: `none`, `agreed:E` or `deleted:E`; `null` once it is not, or when nothing is delivered), which delivered versions this device dismissed in that conflict (`dismissed`), and this device's own versions that `resolve` held here (`held`, never also delivered), and, while a conflict stands, the peer's version that the pair's last sync kept or tried to keep here (`open`, an etag, or `none` for a conflict of the decision table in which the peer holds no version to keep, because it deleted the path or cannot read it; written only when there is one: each sync's keeps step and pending step set it from that sync's conflicts, whatever their base and whether or not the keep wrote anything; a version this device dismissed keeps its `open`, which the scene then skips; `resolve` retires a conflict's deliveries before its data commit but keeps its `open` until the archive steps after that commit landed, so a refused or failed resolve leaves the conflict standing; `identify` carries it to the new ID's record). `open` says only that the devices still disagree on that path (the scene waits on it): it never makes anything dismissable or deletable, and a peer may write it freely over the transport. See "Keep-both". A completed sync always leaves the record, an empty one included, so one found missing beside a pair that completed a sync was lost. Only `dismiss` adds a dismissal, and a sync drops it with its conflict (in its keeps steps, before either archive records the agreement); a delivered version stays, only while its conflict stands on the same base (a conflict that ends or moves to another base takes its deliveries with it: their slots stay and are never dismissable, since once the devices agree a kept copy may be the last copy of a version neither holds, and a later conflict on the path is another conflict), while a slot holds it (or might: one cannot be read) or it is dismissed; `resolve` adds a held version (and takes those bytes out of every other pair's delivered versions) in a commit of its own just before the commit that writes the hold, locally or over the peer transport, whichever device receives, `identify` carries held versions to the new ID's record (and leaves a record it cannot honour as it is), and a sync drops one only once no slot holds those bytes and every slot named for them reads (an unreadable slot is unknown, never absent: it may be the hold). One record holds every conflict of the pair, within 010's file cap: when more deliveries than fit are recorded at once (thousands of conflicts in one sync), the excess goes unrecorded (dismissed ones and those already recorded are kept first), so those kept copies are simply never dismissable and the sync goes on; a dismissal makes room the same way, but never by dropping an earlier dismissal: what a full record keeps first is the dismissals it holds, then a new one, then deliveries already recorded, then new ones, so `dismiss` refuses one that would evict another. A sync adds no dismissal and never lengthens one, so recorded dismissals outgrow the cap only if `resolve` adds holds to a full record; then the last ones by path go, and those versions are kept again. Holds never give way. They alone fill the cap only past tens of thousands of versions `resolve` held and nobody deleted (a hold goes once its slot does); the write then fails and the sync or resolve stops before anything of it is written.

Each file carries a `check` digest of its own content. A file that is not strictly valid is **ignored and reported** (`SyncReport.notices`), never partially trusted. This covers bad JSON, a wrong format, an archive for another pair of devices, and a failed `check`. An ignored `keeps.json` honours no dismissal (every kept version is delivered as before 028), and the next completed sync (or a data commit that keeps a version first) replaces it. The holds it listed are then unknown, which is safe: only a keep that writes the first copy of its bytes is ever recorded as delivered, so no slot already standing, a hold included, ever becomes dismissable.

### Sharding and tombstones (028)

An archive or marker that fits 010's 8 MiB file cap (about 23,000 paths at typical lengths) is still one `/1` file, byte for byte as 019 wrote it, and a `/1` file is always read as-is, so an existing library needs no migration. One that would not fit is written as format **`grimoire.sync.archive/2`** (or `pending/2`): the root `archive.json` lists 16 or 256 shards, `archive.<prefix>.json`, keyed by the first one or two hex digits of the SHA-256 of each path, each with the etag that shard must have. Each shard holds exactly the entries whose path hashes to its prefix, with its own `check`. The width is the smallest whose every file fits by an upper-bound size estimate, a pure function of the entries, so `sync(a, b)` and `sync(b, a)` still write identical bytes. Two hex digits hold about six million paths; past that the plan is refused before any write (`ArchiveTooLarge`), as before.

- **Crash safety.** Every file of one document is written in the same 010 transaction (and its step, as before), so a crash leaves the old root with its old shards or the new root with its new ones.
- **Damage.** The root's etag list binds the set. A listed shard that is missing, torn, edited or of another commit, a root that is gone, not JSON or cut short while shards remain, or a path in the wrong shard makes the **whole document ignored and reported**, exactly like a damaged single-file archive: every path it names is uncertain (a keep-both conflict, never a copy or a deletion), and a tombstone in it is not forgotten.
- **Stale shards.** When a document shrinks back to one file or changes width, the shards it no longer lists stay on disk: 010 commits never delete. They are never trusted and **never read or sent**: only the shards a valid root lists are read (and travel in 028's snapshot), so a stale or planted file costs nothing. A later write of that name reads it then, only for its compare-and-swap. Whenever the root and the shards it lists give no valid document, for any reason (the root missing, not JSON, cut short or listing a set that does not match), every shard of that kind standing in the pair's folder is read too (and sent in 028's snapshot), only for the paths it names: a root that no longer names its shards never makes their paths drop out of the plan. Shards without a usable root make the document ignored, never a first sync, and every path a readable one names is uncertain, so a sync that rebuilds the archive (even after both devices lost their roots) forgets none of its tombstones, and a later restore of deleted bytes is a conflict, not a copy. A shard that cannot be read stops the sync, as any unreadable `.sync` file does; one that does not parse names nothing.
- **Tombstones.** A tombstone is dropped only where it provably decides nothing: a blob's. A blob's bytes are its name, so its tombstone could only ever have flagged the same bytes coming back, and row 12's exception already copies those like a new file. Every other tombstone is kept, because it is what turns a one-sided re-creation of the deleted bytes into a `resurrected` conflict instead of a silent copy. Tombstones of records therefore still grow with every deletion; sharding is what keeps them from stopping the sync.

## Base derivation

A `.sync` file that exists but cannot be read (an I/O error, a file held by another program), or that exists only under a look-alike spelling (`Pending.json`), stops the sync with `SyncInterrupted` before anything is written. An unreadable marker must never look like a missing one.

A path's base is trusted only where **both devices' own records agree**:
1. **Archive candidate:**
   - `first`: neither device has any file at its archive location for this pair (a true first sync);
   - the shared entry, when both archives are valid and hold the identical entry;
   - `none`: both archives are valid and neither has an entry (a path new since the last sync);
   - otherwise `uncertain`: one archive is missing or ignored, or the entries disagree.
2. **Pending override.** If either device has a pending entry for the path, the base is `agreed to` only when every entry names the same `to` and each device holding one still has those bytes: the copy verifiably landed, and the peer held `to`. If both archives already agree on that `to` and did not already when the marker was written (its `base`), the marker is stale (a crash after the archives were written but before the marker was cleared) and the archive base stands: archives are only written after verification. Anything else is `uncertain`: a revert to the old bytes, an edit racing the copy, disagreeing entries, or a marker that parses but is invalid (ignored). A deletion's entry (`"to": null`) works the same way: when every entry for the path deletes the same E and each device holding one is still absent, the base is `deleted E` (the tombstone the uninterrupted sync records; if both archives already say `deleted E`, the marker is stale and gives the same answer); a restore, a re-creation or disagreeing entries are `uncertain`. A build from before 028 does not read such an entry: it ignores the whole marker, so every path is uncertain there (conservative).

`uncertain` never copies anything. This is what defeats:
- a **clone** of a library that synced with the phone: its archive cannot make one device's version look like an ancestor;
- **ABA** after a crash: the user restores the exact old bytes before the sync finished.

## Decision table

Each device's file is `absent`, `present(etag)`, or `blocked`. A file is blocked when it is:
- a link;
- a look-alike spelling;
- unreadable, oversized or not a regular file (a directory where a record belongs counts too);
- not strict JSON;
- in a newer format;
- an envelope whose address does not match its path;
- a blob whose bytes do not hash to its name or sniff to its extension (`corrupt`), or that cannot be read, is empty or over 32 MiB (`unreadable`);
- either member of a **cross-kind instance pair** (`instance_id_conflict`): one instance id held under two kinds in one campaign, exactly the files `load()` excludes. `resolve` cannot end it; the user deletes or renames one member, and the next sync decides both paths again. A copy that would form such a pair on the receiver is refused there (`unapplicable`), so a pair made across devices (each creates `x` offline as another kind) never stalls a sync.

The rows are evaluated top to bottom, and swapping the devices mirrors every decision.

| # | Base | Devices | Decision |
|---|---|---|---|
| 1 | any | either blocked | conflict `blocked` |
| 2 | any | equal etags, or both absent | agreed |
| 3 | `uncertain` | differ | conflict `missing_ancestor` |
| 4 | `first` | one absent | copy (create-only) |
| 5 | `first` | both present | copy if exactly one side's `previous` is the other's etag (not for immutable records: revisions, knowledge records, transcript pages, image objects and blobs), else `missing_ancestor` |
| 6 | `none` | one absent | copy (create-only) |
| 7 | `none` | both present | conflict `missing_ancestor` |
| 8 | `agreed E` | one is E, the other present | copy the other over E; an immutable record (revision, knowledge record, transcript page, image object or blob) is `revision_modified` |
| 9 | `agreed E` | one is E, the other absent | delete E on the device that holds it (028, "Propagated deletions"): manifests, definition revisions, instances, scopes, chats, relations and placements. Knowledge records, transcript pages, image objects and blobs: conflict `deleted` (create-only; a missing one is damage, never a choice) |
| 10 | `agreed E` | one absent, the other not E | conflict `edit_delete` |
| 11 | `agreed E` | both present, neither E | conflict `concurrent` |
| 12 | `deleted E` | one absent, the other is E | conflict `resurrected`; a blob is copied instead (create-only, as row 13): its name is its content hash, so the same blob again is never an outdated version |
| 13 | `deleted E` | one absent, the other not E | copy (a new record at a deleted path) |
| 14 | `deleted E` | both present, different | conflict `concurrent` |

A copy publishes the other device's **exact bytes** (`Transaction.put_exact`), so both devices converge on one etag. Those bytes still exist on the other device, so an aborted commit drops the copy rather than parking it under `.conflicts/` (journal kind `replica`). Before it is admitted, three overrides apply:
- **Head dependency.** A copy lands only if, once the commit is applied, the destination means what the origin means. Every revision the record pins must hold the origin's bytes on the destination, already or copied in the same commit (a merged ledger file is both devices' work: a pin the origin lacks, from an event it keeps of the destination's own, holds when the destination keeps that revision): a manifest's heads (which must exist on the origin) and link endpoints, an instance's `base` and `derived_from`, and any pin in a payload or unknown field. That is the set the store's reference check counts (`replica.pinned_by`), less the implicit head (an entity's only revision, when its manifest declares none): a manifest copied without a head becomes byte-identical on both devices, so resolve's identical-manifest exemption still lets that revision be resolved. A 107 chat never lands without the play scope (`scope.json`) the origin homes it in, so the receiver never shows an `orphan_chat` it would then answer with a fresh scope of its own. A 035 turn never lands without its chat, the play scope, the turn it follows and the turn its mark names (see "Played turns"). Every campaign instance or chat a scope or knowledge record names (a 107 chat's roster actors, a 017 relation's endpoints, a 020 record's holders and participants, and the chat a 020 batch came from) that the origin holds must be present on the destination too, and a 020 knowledge record's campaign must exist there (a scope or an instance, 020's own test) whenever it exists on the origin: sync never creates the state 020's append refuses (`unknown_campaign`, `unknown_chat`, `unknown_actor`). A path that is blocked on either device (unreadable, a link) is unknown, never "absent on both": it is unmet. Text that parses as a reference to a path no library can store (a reserved device name) names nothing and is no dependency. Holding one copy can unmeet another's dependency, and can make what is left unacceptable to the store (a manifest held back leaves its new head revision alone in the source), so admission and this check repeat together until neither drops anything: after planning, after a unit is refused, and after a denial (a dependent of a denied write becomes `denied`). So a copied record never silently means other bytes on the destination, and never pins a revision that is still in conflict, which would make that conflict unresolvable. Otherwise the conflict is `head_dependency`. Art has its own requirements (see "Art").
- **Name collision.** A destination path that collides with a differently spelled entry gives `name_collision`. A canonical path that exists on a device only as a look-alike (`R9.json`) is blocked there (the scan's `shadowed` reason: unknown, never absent, so a case-only rename is never read as a deletion), and is reported as `name_collision` too.
- **Destination preflight.** The destination's writes are checked once with 010's read-only `Transaction.check()`. Only if that check fails are they admitted unit by unit, and a unit the store refuses becomes `unapplicable`. A unit is one instance, one manifest with its head revisions, the other revisions of one entity, or one art file. Campaign-local records other than instances are checked alone, and so is each source; the instances of one campaign are admitted cumulatively in sorted path order, so two copies that would form a cross-kind pair never both pass. Each art file is checked once, over the accepted copies its owner needs (a blob alone; a source's image or placement over that source's accepted copies; a campaign's over its accepted scope and instances); only when a source fails as a whole are its units admitted one by one, cumulatively (manifest units first), so two units that are each acceptable but not together (one entity id under two kinds, from another tool) are never both admitted. Manifests that link to other sources are then admitted cumulatively in sorted order, so a cross-source link cycle is caught. In that fallback, one final combined check of everything admitted runs before the commit, defensively: by construction it accepts what admission accepted, and if it does not the sync stops with `SyncInterrupted` before writing. Library-wide problems propagate and are never blamed on one path.

**Denied writes.** Authorization cannot be dry-run without consuming approvals, so a data commit uses 010's partial mode (`commit(..., on_denied=...)`). Each write is authorized exactly once. A write denied for its path (not granted, approval required, reserved) is dropped together with every copy of the same source (an art file only for itself), becomes conflict `denied`, and its pending entry is removed. What remains is checked again. If it is no longer acceptable on its own (for example, another source's manifest needed the denied one), it is re-admitted unit by unit, and each refused unit is also `denied`; that and the dependency check repeat together until neither drops anything, so a denial never stalls the rest. A denial that is not about a path propagates: an unissued handle, or an unavailable authority. Approvals consumed by dropped dependents are reported in `SyncReport.consumed_approvals`.

**Propagated deletions (028).** Row 9's `delete` is made on the device that still holds E, through 010's `Transaction.delete_exact` ([STORAGE](STORAGE.md)): in the same transaction E is kept beside the path as a `hold` (it may now exist nowhere else), and the removal is compare-and-swap on E, so a later edit there is never removed. Only the families above, which 010 can delete. A ledger file (an accepted event, wrap-up or holder file, or a relation of a campaign with an accepted event) is never deleted this way, whatever its kind: its campaign's unit decides it ("Ledgers (028)"), and 035's played turns are not a family that propagates deletions. A deletion is **held back** as conflict `delete_dependency` (the record stays, nothing is kept) when anything the receiver would still hold after this sync (its records and this sync's copies to it, held families included) needs it:
- a revision any record left pins (a manifest head, an instance's `derived_from` or `base`, any pinned reference in any text of any record), or the last revision of an entity an unpinned reference names;
- a manifest, while any record of its source or any reference into it is left (so a source is deleted as a whole: its manifest and revisions together);
- an instance, chat or relation any record left names; a chat's play scope while the chat is left; a chat while one of its transcript pages or turns is left;
- a campaign's last scope or instance while anything else of that campaign is left;
- whatever 018 art left still needs (an image's owner, a placement's subject and the image it shows).

It is read generically and conservatively: every string of every record left (keys included) is tried as every kind of reference, so the check errs only toward holding a deletion back, which keeps both versions and loses nothing. Any path under `sources/` or `campaigns/` the receiver cannot read (a link, a look-alike, an unreadable file), or an unreadable library root, holds every deletion there back: nothing can prove it does not need the record (the root's other entries, `assets/` included, never hold records). Holding one deletion back keeps a record whose own needs then count, so the check repeats until it drops nothing, and again after a denial drops copies. The store then checks a device's deletions together with that device's copies, so it judges them over what the commit leaves (a manifest copy that drops a head no longer pins the revision deleted with it, and an entity's last revision being deleted is not its implicit head); at commit it checks again, under the lock, that no record staying pins a deleted revision, and the data commit (or the serving device's replayed step) judges the dependencies again over a fresh scan under its lock, so a record written there since the plan that needs a deletion stops the commit before anything is written (`SyncInterrupted`, or a `stale` refusal over the transport), and the next sync holds it back. Under both devices' locks, the same commit first checks that the device the deletion came from still lacks the record: one put back there since the plan stops the commit the same way, with nothing deleted and no tombstone archived, and the next sync finds both devices agreeing (or judges the new bytes). A deleting commit keeps both libraries locked until its step is observed, so over the transport the deleting device stays as checked until its peer has replayed the step; a serving device the deletion came from is asked itself ([DEVICE_SYNC](DEVICE_SYNC.md), `check`). Only if that check fails are the deletions admitted cumulatively, in sorted path order and in passes, each joining those already admitted when the store takes them together, never alone (a source deleted as a whole would fail piece by piece); one it refuses becomes `unapplicable`, and the record stays. The deletion's own write is authorized like a copy (below): a deletion denied, or one a denial leaves needed, is `denied` with its hold dropped, and the record stays. So that a deletion denied on every sync settles as one stable `denied` conflict, holds(d) first checks the deletions and their holds against the data commit's handle with no approval (`Transaction.check(handle)`, read-only, its decisions audited): one refused for its path, and any one that denial leaves needed, is `denied` before its hold is recorded, so nothing is written for it, and the syncs go quiet. One an approval the data commit carries may allow is left to that commit, which decides with the approval; a refusal not about a path is left to it too. `SyncReport.deleted` lists `(path, device)` for each deletion made.

## Knowledge logs (028)

Knowledge records are immutable like definition revisions: a new one is copied create-only, a changed one is `revision_modified`, and `resolve` never replaces one (it only delivers a log the receiver lacks). 020 commits an append as its records plus one batch, so a campaign's knowledge log is **one unit**:
- It moves only when it can be seen whole on both devices: an `events/` or `evidence/` folder (or one below) that cannot be listed or is spelled differently, or an unlistable campaign folder, `campaigns/` or root, holds it back (fails closed), and `resolve` refuses it then too.
- If any of its paths is a conflict (a blocked or refused record, a record or batch both devices hold with different bytes), none of that campaign's knowledge copies land, and they are reported as skipped.
- If one of its copies to a device is denied, the others to that device are dropped with it and reported as `denied` conflicts. The copies to the other device still land: that device then holds both logs, merged, and the denied device its own.

**Two devices' appends merge.** An identified library names each batch for its device (`batch/<seq>-<tag>.json`), and each append extends every head of the log ([EVIDENCE](EVIDENCE.md#the-knowledge-log)). So two devices that appended to one campaign offline wrote different files, every one of which the other lacks: sync copies them all create-only (rows 4 and 6), exactly as it copies one device's appends, and both devices end with byte-identical knowledge files that 020 reads as one log. Nothing existing is rewritten and sync writes nothing but copies, so `sync(a, b)` and `sync(b, a)` stay byte-identical and a crash at any commit is a crash of an ordinary copy (`test_sync_faults.py`). The next append on either device joins both heads.

**What sync refuses to merge.** When both devices hold knowledge files of a campaign that the other lacks (the logs diverged), sync reads them structurally before copying (`grimoire.sync.knowledge`, with 020's own `assemble`), so it never creates a log 020 would not read whole:
- the union of both devices' logs of the campaign (their batches and the records some batch lists) must assemble with nothing quarantined and no problem. A record no batch lists is in neither log (020 never reads it as knowledge): it is not checked and crosses as an ordinary create-only copy, as before 028. That refuses a belief chain both devices extended (a fork, or two roots), a contribution used on both, and one record both devices wrote identically, which each device's batch lists;
- no proposition may have gained a ruling on both devices. Two devices deciding canon on one proposition offline are conflicting edits; "the later sequence governs" would silently overrule one of them.

A refused merge holds the log as one unit, as diverged logs always were: each batch that would have crossed is an **`unapplicable`** conflict whose detail names the records (never their text), each device keeps the other's batches under `.conflicts`, the rest of the campaign's knowledge copies are skipped, and each device keeps a healthy log of its own appends. `resolve` refuses it too (it would deliver the union). It ends when one device's offline appends are rolled back as 020 documents (remove its newest batches and exactly the records they list): the other's then sync over whole. A one-way copy (one log already holds all of the other) is never checked, as before.

**Deletions never touch a log.** Knowledge records and batches are create-only, so sync never deletes one (a merged batch or record missing on one device is a conflict, never a propagated deletion, and the other device's log still reads whole), and a deletion of anything a log's records name, or of a campaign's last scope or instance while its log is left, is held back (`delete_dependency`, "Propagated deletions"). 035's played turns sync (028's turn merge) but are not a family that propagates deletions, so row 9 on one stays a `deleted` conflict that keeps it (`test_sync_deletion.py`).

**Record ids.** 020 takes record ids from its callers. Two devices that used one id for different bytes made a path conflict (above), never a merge; allocators must device-tag new ids ([EVIDENCE](EVIDENCE.md#deferrals)). Logs that forked under the untagged names (identified libraries that appended before this build) still collide on `batch/<seq>.json`: a keep-both `missing_ancestor` conflict with the log held, as before.

## Art

018's art is three kinds of file, and sync never creates a state the 018 batch would refuse:
- **Blobs** (`assets/blobs/…/<sha256>.<ext>`) are content-addressed and create-only: a blob is copied only onto an absent path, never over other bytes, and never deleted. A blob's tombstone never blocks it: when a blob deleted on both devices (by hand, ending a `deleted` conflict, or because it was oversize) is imported again, the same bytes under the same name are copied like a new file (row 12's exception), and the new image and placement that need it arrive with it. A scan lists blobs by name and size without reading them. A blob is hashed (and sniffed) when it is about to be copied, and on first sight: while the pair's archive does not record it as agreed. Once both archives agree on it and both sizes still match, it is **trusted by agreement** and not read again. A blob only one device holds is read only if it is to be copied: not while it is a conflict that copies nothing (`deleted`, `missing_ancestor`, `blocked`, `name_collision`), and not when the receiver's durable authority grants its handle no write there (below). A copy is staged lazily (`Transaction.put_blob_exact`): the origin's bytes are loaded at authorization and again at staging, one blob at a time, and every load must be exactly the planned size, extension and hash, or the sync stops as a stale write. A blob that fails its hash or sniff is `blocked` (`corrupt`) on that device and is never copied from it.
- **Image objects** are create-only like definition revisions (the immutable rows of the table). An image needs its blob identical on the receiver, and its owner there: a source image needs the source's manifest; a campaign image needs a scope or an instance of that campaign. An image object 018 cannot show (W6: not under the image schema, a payload its codec refuses, or a blob the origin's scan lists at another size than the object's `payload.blob.size`, which the resolver reads as `blob_size_mismatch`) is never copied, and neither is any placement that shows it: copied, a create-only object could never be repaired from the origin. The check reads the scan's listed size, never the blob.
- **Placements** are ordinary three-way records. A placement needs its subject present on the receiver (the source's manifest and the entity's head revision, identical; or the campaign instance), and for `set` or `adjust` the image it shows and that image's blob, identical. Inherited source art shown on a campaign instance also needs the instance identical (so its derivation is the same), the deriving entity's manifest and head revision identical, and, for `adjust`, that entity's placement in the same slot with its image and blob. A placement whose payload cannot be read (018's own codec decides, under 018's placement schema only), or that the origin's own batch would refuse (W8's `validate_placement`, so a standalone source placement edited by hand to `hide` or `adjust` is `mode_not_allowed`, read against the entity's head revision, which must be identical on both sides; an image outside its scope, an `adjust` of nothing or of an inherited placement 018 cannot read, an `adjust` naming another picture than the one the entity's placement shows, a derivation naming an entity no library can store), is never copied.
- **Derived portrayals ([046](INHERITANCE.md#art-down-a-base-chain)).** A placement on an entity whose head revision has a `derivation` may `set` its own source's picture, `hide` or mark `unresolved`, and is copied as above. A `hide` also needs the source's manifest identical, so the receiver selects the same derived head, where a clear is allowed. Its `adjust` and its `inherit` are held, and so is a campaign `inherit`: each shows what the base chain shows, which sync does not compare yet, so a concurrent change up the chain could show another picture on each device. Each ancestor's placements sync on their own. A campaign `set` or `adjust` of a picture an instance inherits from further up the chain than its own derivation entity is held too, and so is any campaign `adjust` on an instance whose file has pinned art (`art_pin`): it re-crops the frozen picture, not the entity's live placement that sync compares.
- **Excluded sources (W5).** Art belongs to a source (a source image or placement) or shows that source's picture (a campaign placement that inherits it through the instance's derivation, or adjusts it). The 018 batch accepts such art only while the source is admitted (W5 `excluded_source`), and the resolver shows none of an excluded source's art. A present manifest is not enough: `load()` also excludes a source whose manifest reads, for a record in it that claims another source (`ownership`) or for a cross-source `identity_conflict`. So such art is never copied while **either** device's `load()` excludes that source; campaign art that reads no source (a campaign image, a `hide` or an `unresolved` slot) is unaffected, and blobs still land. Each device's verdict is the store's shared, cached [`excluded_sources()`](STORAGE.md#read-only-helpers-107): `load()`'s own algorithm, cross-source conflicts included, read once per plan and only when an image or placement is to be copied (an unchanged library costs one `stat` per manifest and revision entry and reads no file; no blob is read). `resolve` reads both devices' verdicts the same way and refuses what a sync holds.
  - **The origin's exclusion** holds the art as a state the batch refuses (like W6): on the origin it resolves to nothing, so a receiver that admits the source would show pictures the origin does not; the exclusion contests the source's own identity, so the head revision and scope sync would compare come from data `load()` rejected; and an image object is create-only and its deletion never propagates, so a copy could never be withdrawn if the origin's repair removes the art instead of the damage.
  - **The receiver's exclusion** is an unmet requirement on the receiver: the copy would create a state the receiver's own batch refuses. Sync holds all three receiver cases as `head_dependency`: source art into a source the receiver's own files exclude (which the store would also refuse, as `unapplicable`, before this check), a cross-source exclusion, and a campaign placement that inherits a picture from an excluded source. The store sees neither of the last two (it checks one source's scan, and a campaign asset against its campaign only), so its own check is only the backstop. It reads the receiver's verdict as it stands before the commit, which errs only toward waiting: art whose source this very sync repairs on the receiver waits one more sync, and art whose source this sync newly excludes there lands byte-identical to the origin's, unseen until that source is repaired.
  - Either hold lifts by itself once that device admits the source again; the next sync copies the art.

An unmet requirement (or such a refused placement, or art of an excluded source) is a `head_dependency` conflict, never `held` (which is only for the families above), whose detail names the missing paths or the refusal. A blocked subject, such as either member of a cross-kind instance pair, is unknown and therefore unmet. Blob writes need an `assets` grant. A device whose handle lacks one receives no blob: each blob copy is `denied`, and so is every image and placement that needs one of those blobs. It still receives art that needs no new blob (a `hide` or `unresolved` placement, an image whose blob it already holds, and placements showing such images), and everything else. When the receiver's library is bound to a durable authority that issued its handle, `plan_sync(left, right, handles)` (which `sync` calls) sees that no active grant covers the blob and plans it as `denied` without reading it; otherwise the commit denies it, after its plan hashed it and its authorization loaded it. An authority that is not usable (closed, or poisoned by a failed ledger flush: `DurableAuthority.usable` is false) plans nothing as `denied`: the commit decides, and its denial for an unavailable authority propagates ("Denied writes").

## Keep-both

For every conflict except `denied`, `held` and a ledger file's (028: a ledger is merged again by every sync, from the versions both devices still hold), each device whose peer has a present, usable version receives that version as a **kept version**. Blobs are never kept: other bytes under a blob's name are corruption, not a version. It goes under `.conflicts/<hash16>/<name>~<digest12>[.N]`, through `Transaction.keep_version`. The authorization address is distinct from the record's own: `kept/<hash16>/<digest12>[-N]/<name>`. So "keep these bytes beside p" and "overwrite p" are different approvals, and they appear under different `preview()` keys.

A slot already holding those bytes is reused, so a kept version is not written again (a human who deletes one slot and edits another can leave two identical copies), and a conflict stays reported on every sync until a human ends it. A kept version that cannot be written (for example, because of path limits) is reported as `kept: false`. A device that has moved on from the base is never handed that base as a kept copy: it is not the peer's version. A device whose own file could not even be read receives nothing: there is nothing to keep it beside, and the next readable sync decides the path. A `denied` conflict keeps nothing either: the denial is only known while committing, after kept versions were planned. Both versions stay canonical on their own device, and the conflict is reported on every sync until the grant changes. Kept versions are not indexed: `load()` still shows one record per path.

**Dismissing a kept version** (028). Deleting a kept file by hand does not stick: the next sync delivers it again into the empty slot. `dismiss(store, peer, path, kept=<etag>, handle, approvals=None)` records the decision instead, in this device's `keeps.json` for the pair, keyed by the path and the etag of the dismissed bytes. No timestamp decides anything:
- Only a version a **sync wrote here from the peer** can be dismissed: `keeps.json` lists those etags. A file under `.conflicts/` may also be this device's own version that `resolve` held, perhaps its only copy anywhere, and the slot cannot tell; `resolve` therefore records each hold as `held` in the receiver's `keeps.json`, and a held version is never recorded as delivered, never honoured as dismissed, and never dismissable. The record is committed on its own **before** the data commit that writes the hold, never staged inside it, by a resolve over the peer transport too, whichever device receives ([DEVICE_SYNC](DEVICE_SYNC.md#resolving-a-conflict-over-the-transport)): 010's recovery may finish a partly published commit without a `.sync` file whose staged copy is gone or damaged, which would leave a slot the hold reused (bytes once delivered) still listed as delivered and so dismissable, though it is the only copy. If the data commit then never lands, the record holds bytes `resolve` did not take: that only fails closed, and a sync drops the entry once no slot holds those bytes. A device paired with several peers keeps every pair's versions in one `.conflicts`, so `dismiss` also refuses bytes any pair's record holds (or might: an ignored record's holds are unknown). A keep is recorded in the same data commit that writes it, so a crash, a race or a dropped connection after that commit never leaves it unrecorded; that commit also guards the record by compare-and-swap against the one the plan read, even when it adds no delivery (a slot the person deleted, refilled with bytes already recorded, rewrites the record's own bytes), because the plan keeps a version only where that record did not dismiss it: a dismissal committed between `plan_sync` and `apply_sync` (or after a transfer's snapshot) stops the commit, and the next plan honours it, instead of the older plan writing the dismissed copy back. A keep is delivered only when it writes the first copy of its bytes at its path: a slot found already holding those bytes, or a second copy beside one, may be a hold, so it is never taken for a delivery. A slot that cannot be read (an I/O error) is unknown, never absent: no keep beside it is a first copy, no sync or peer drops a hold while it is unreadable, and `dismiss` refuses while any slot named for the version is unreadable. Only a path still in conflict can have a version dismissed: once the devices agree again (a sync finds them identical, or `resolve` ends the conflict) the record's `base` is `null`, and `dismiss` refuses, because a kept copy may then be the last copy of a version neither device holds any more.
- A sync never keeps those bytes for that device again while the conflict stands on the same archive base, and reports the device in `Conflict.dismissed`. A **different** version from the peer (other bytes) is kept as usual; the peer going back to the dismissed bytes while the conflict is open is not delivered again.
- It never touches the other device: the peer's file stays its canonical record (`resolve` can still choose it), the conflict is still reported until a human ends it, and the peer still keeps this device's version unless it dismisses it too.
- A dismissal lasts as long as its conflict. A sync takes every path it no longer finds in conflict out of conflict in both devices' records (its keeps steps), its deliveries and dismissals dropped, **before** either archive records the agreement, so a crash or a dropped connection after an archive step never leaves a kept copy dismissable: it may be the last copy of a version neither device holds any more (the peer took this device's version, or both went back to the bytes they last agreed on, which leaves the archive unchanged). The pending step of a completed sync then drops the rest (a delivered version once no slot holds it and it is not dismissed, and the base of a conflict a pending marker moved), `resolve` drops those of the conflicts it ends (with their deliveries) on both devices, each in a commit of its own **before** anything of the resolve is written: only the receiver's data commit writes a pending marker, so after a crash between that commit and the archive steps the winner's own archive, marker and record would still read as the open conflict, and its kept copy of the receiver's former version (the only copy once the receiver holds the winner's, say after the receiver deleted its own) would be dismissable. A resolve that then stops leaves the conflict open with those deliveries unrecorded, which only fails closed. A dismissal is honoured only on the archive base it was recorded with, and only while no pending marker has moved the path's base (a `resolve` interrupted after its copy landed leaves the marker, so the next conflict keeps the version again). The record stays small, and the same bytes in a later conflict are kept again.
- It is written in one 010 transaction, authorized like a keep: `APPLY` on the address of the slot that holds the version (`kept/<hash16>/<digest12>[-N]/<name>`, one-to-one with the slot, as a keep's is; slot 0's when no slot holds it), so a handle that may not write kept versions may not dismiss one, and a grant on one slot never names another slot's file safe to delete. Every other slot it names (a person who copied a kept file can leave two) is authorized on its own address first, by a commit that keeps the bytes the slot already holds and so rewrites nothing; a denial for any slot refuses the dismissal, even of a version already dismissed, before the record is written. The record is journaled as `.sync` state, so a crash leaves it written or not.
- It refuses (`DismissRefused`, nothing written) a peer that is not a device ID or is this device, a blob or a path sync does not carry, an etag that is not one, this device's own current version, a version no sync delivered here from the peer, a path no longer in conflict with the peer, a record whose base is not the one this device's own archive and pending marker now give the path (the archive must be valid and the marker must neither be ignored nor hold the path: so a record an earlier build left past an agreement, or any record the archive has moved past, is never trusted alone), a version `resolve` held, or a version one of whose kept-version slots cannot be read (it might hold anything, a hold even, so no slot beside it is named safe to delete). Dismissing twice writes once. The kept files are not deleted (010 never deletes); `Dismissal.slots` names the ones holding those bytes. They are bytes the peer's sync delivered and no `resolve` here held, so the app may delete them, and no sync rewrites them.

While a conflict stays open and one device keeps editing the record, every new version it sends lands in a new slot, so kept versions still accumulate (one per sync, up to the record's size each) unless each is dismissed.

`resolve` marks its copy in the receiver's pending marker in the same transaction, as a sync does, so an interrupted resolve followed by a revert is a conflict, never an overwrite. It refuses while either device's marker for the pair is ignored.

Kept copies of the **other device's** version are regenerable (journal kind `keep`): an aborted commit drops them, because the other device still holds the bytes. The version `resolve` replaces is the receiver's own and may exist nowhere else (`hold`): an aborted commit preserves it like any other version.

## Ending a conflict

- `resolve(left, right, path, keep=<etag>, expected={device: etag | None}, handles, approvals=None)` makes the device that does not hold `keep` receive it. Its replaced version is kept under `.conflicts/` in the same transaction, recorded as `held` in the receiver's `keeps.json` for the pair and taken out of every other pair's `delivered` versions in a commit just before it, and both archives then record `agreed keep`. Over the peer transport ([DEVICE_SYNC](DEVICE_SYNC.md#resolving-a-conflict-over-the-transport)) the same records (both devices' with the conflict ended, then the receiver's hold) are committed the same way, each in a commit of its own before the data, whichever device receives.
  - **Manifest:** absent head revisions are copied with it. A head revision that differs must be resolved first. When a differing head revision has the same ID on both devices and the manifests differ too, neither can be resolved first: each device's manifest pins its own revision. Add a new revision on one device and move its head there, then resolve the old revision and the manifest.
  - **Definition revision:** allowed only if nothing on the receiving device can pin it: a manifest head, a link endpoint, an instance's `derived_from`, `base` or a pinned reference in its payload, a pinned reference in another revision's payload, or any text in a scope, chat, relation or knowledge record that names it (a chat's source bindings). Every parsable record is checked, those of excluded sources included. A manifest byte-identical to the receiving device's copy of the winner's manifest is exempt: it is the winner's own manifest, which names the revision being replaced by ID. A blocked path that could be or hold a record means "cannot prove unreferenced" (`RevisionReferenced`), so it blocks revision resolves until it is fixed; a blocked entry that cannot hold records (a root-level link, a non-JSON note under `sources/`) does not.
  - **Knowledge records** are never replaced: they are immutable evidence. When the receiver lacks the chosen record (an uncertain base after a re-identification, say), `resolve` delivers the campaign's whole knowledge log unit create-only: every record of that campaign the winner holds and the receiver lacks, records and batches together. It refuses when the two logs diverged on a path (both hold it differently), and when the receiver also holds files the winner lacks and their union fails the merge check of "Knowledge logs (028)".
  - **Transcript pages** are never replaced either: a page the receiver lacks is delivered create-only, and one both devices hold differently is refused (neither replaces the other; two writers of one page number is a 035 runner bug or a hand edit). A page names neither its chat nor (for a label-only speaker) any actor in its payload, so its chat (`campaigns/<id>/chats/<chat_id>.json`) is its dependency, in a sync and in `resolve`, even when the sending device no longer holds that chat: a page never lands on a device without the chat it belongs to (a later chat given that id would inherit it).
  - **Art:** a blob is delivered create-only and only after it is verified (hash and sniff) on the winner; a receiver that already holds other bytes under its name is refused (that is corruption: 018's `repair_blob` fixes it). An image object is create-only too: refused when the receiver holds different bytes. An image or placement is refused until every requirement of "Art" holds on the receiver, the receiver's blobs verified.
  - **Refused (`ResolveRefused`, nothing written):** a ledger file (an accepted event, wrap-up, holding, or a relation of a campaign with an accepted event: see `resolve_ledger`), a member of a cross-kind instance pair, the receiver's grant refuses the write, a blocked side, `keep` matching neither device, either device differing from `expected`, an archive for the pair that is missing or ignored on either device, or a record it would write (the chosen one, or a head revision a manifest resolve copies with it) whose pinned revisions differ between the devices or are blocked on either (resolve the revision first), whose named actors, chat or (a chat) play scope the receiver lacks, or (a turn) whose chat, play scope, preceding turn or chosen turn it lacks, or (a knowledge log) whose campaign the receiver lacks. Rewriting such an archive would forget why every other path is uncertain, so the devices must complete one sync first; that sync records the uncertainty in the pending markers.
- `resolve(..., keep=None, ...)` chooses the **deletion** (028). The device that still holds the record receives: as row 9's propagated deletion does, it records its version as `held` (in a commit of its own, before the data), keeps it as a hold and removes the record with `delete_exact` in one transaction, marked `{"from": E, "to": null}`; both archives then record `deleted E`. Resolving a manifest toward its deletion takes along each revision of that source the receiver holds whose base is `agreed` on those bytes and which the other device lacks (a source is deleted as a whole: alone, each would need the other). Refused (`ResolveRefused`, nothing written but the kept-version bookkeeping a resolve commits first) for every refusal above that applies, when both devices hold the record or neither does, for the families sync never deletes (knowledge records, transcript pages, played turns, image objects and blobs: keep a version instead; a ledger file is refused above), and wherever a sync would hold the deletion back (`delete_dependency`: something left on the receiver still needs it; resolve or delete that first). Under both devices' locks, before anything of the deletion is written, the receiver must still hold each version it deletes and the other device must still lack each path; otherwise it is refused as changed since the conflict was reported, with no tombstone archived (a record written again there would be `resurrected` at the next sync). The dependencies are judged again there too.
- Deleting a record on both devices by hand ends a `deleted` conflict, and a tombstone is archived.

## Apply order and crash safety

`plan_sync(left, right, handles=None)` only reads (directory listings are cached for the whole plan). With `handles`, it reads each receiver's active grants (never asking for an audited decision) to plan a blob its handle cannot write as `denied` (see "Art"). `SyncPlan.preview()` gives, per device, the exact bytes of every authorized write.

`apply_sync(plan, handles, approvals=None)` writes in a fixed order, where `a` is the lower device ID:
1. holds(a), only when a receives deletions (028): its `keeps.json` for the pair lists each version it is about to delete as `held` (and no other pair's record lists it as delivered), in a commit of its own, exactly as `resolve` records a hold, so 010's recovery of the data commit can never leave the kept copy dismissable; then data(a): copies, kept versions, deletions (each with its hold) and the merged pending marker, in one transaction;
2. holds(b), then data(b);
3. verify: every published and kept file (each deletion's hold included) is re-read and must hold the planned bytes, and every deleted path must be absent;
4. keeps(b), then keeps(a) (028): each device's `keeps.json` with every conflict this sync ended taken out of conflict (`base: null`, its deliveries and dismissals dropped) and every conflict that stands recorded `open` with the peer's version, only where that changes it (so a sync that finds a new conflict writes these two commits too);
5. archive(b), then archive(a);
6. pending(b), then pending(a).

An archive entry `agreed E` is written only after both data commits and verification succeeded, and only for paths both devices verifiably held as E; a propagated deletion's `deleted E` only once the path is verifiably absent on both. A first sync with nothing agreed still writes an empty archive.

Errors:
- These stop the sync with `SyncInterrupted`, and no archive is written after the stop:
  - a stale write (a library changed after planning);
  - `WriteConflict` (an external edit raced publication; 010 kept the human's file);
  - a per-path refusal at commit time;
  - a failed verification.
- `CommitIncomplete`, `OSError`, `PendingRecovery`, `RecoveryBlocked` and root or V1 errors propagate; 010 recovery owns them.

`sync_until_quiet` retries `SyncInterrupted` until a sync completes and writes nothing. Its report merges every attempt: all copies, notices and consumed approvals, and the conflicts of the final sync. After `attempts` it raises the last error, or `SyncNotQuiet`, carrying the merged report.

**Lock order.** Within one process each library has one re-entrant lock (`LibraryStore.lock`) that its commits and reads take. A thread that holds two libraries' locks takes them in one global order, by root path and then by lock (two opens of one folder share a root, and still both raise `SameDevice` in either argument order); no thread ever waits for the first library while holding only the second. Planning holds both for the whole plan, in that order, so two syncs of the same pair in opposite argument order cannot deadlock (pinned by a test running both orders concurrently). A blob copy is loaded lazily from the origin inside the destination's commit (`put_blob_exact`'s reader takes the origin's lock), so every sync data commit, and `resolve`'s commit, first takes both libraries' locks in that order and holds them through the commit: a commit on the later library never holds it while waiting for the earlier one that a planner already holds (pinned by a test racing a planner against a blob copy, for both `sync` and `resolve`). The blob bytes are still loaded one at a time, only when the commit needs them.

## Limits

- An archive or pending marker past one file's capacity is sharded (028, "Sharding and tombstones"), up to about six million paths per pair; a plan past that is refused before any write (`ArchiveTooLarge`). Record tombstones are never compacted, because none can be dropped without losing a resurrection check.
- Not in this slice:
  - more than two devices, transport and pairing;
  - causal branches, and history beyond one agreed etag per path;
  - ledger sync;
  - semantic or field-level merge (042);
  - dependency checks beyond references to revisions, named instances and chats, and a knowledge record's campaign (a 017 relation waits for endpoint instances the origin holds; one the origin lacks too is delivered, as 017 tolerates).
- A true first sync, or one after `.sync/` was deleted or both devices were re-identified, re-creates records deleted on one device beforehand. After a tombstone, resurrection is detected only for the exact tombstoned bytes, and never for a blob (its bytes are its name). On a first sync every path the devices already agree on is marked in the data commits (and so is any agreement whose base does not record it: a conflict ended by hand, byte-identical records made offline, an agreement after a tombstone), so a crash after the first data commit never leaves a `first` base behind (a crash before it persisted nothing: that is still a true first sync).
- A crash between the two archive commits of a **first** sync leaves one archive missing and the other valid. Until the next sync completes, only the pending markers carry the agreement: a path both devices still hold as that sync left it stays `agreed` (both data commits marked the same `to`), and the next sync writes both archives. Every other base is `uncertain`: a path created, edited or deleted on either device in between, or one that was in conflict. Such a change is then a keep-both `missing_ancestor` conflict (nothing is lost) instead of a copy or a deletion, until it is resolved. The same holds for a crash before both archive commits, and for a relation held back on that first sync once its hold lifts.
- A manifest `load()` admits with a problem it drops (one malformed link, say) is not a writable envelope, so sync blocks it: a permanent `blocked` conflict, and revision replaces in that library are refused until it is fixed.
- **Independently created actors no longer merge.** 107 named a new actor `<entity>-<n>` by the first free number in its campaign, so two devices that each added the same character to one campaign offline created byte-identical records that sync treated as agreed. A library with a device identity now numbers actors per device, `<entity>-<tag>-<n>` ([DEVICE_SYNC](DEVICE_SYNC.md#per-device-ids)). Actors two such devices created *before* that change still merge. 034's unique items are numbered the same way, `<base>-<tag>-<n>`, except one particular (`individual`) artifact, whose tag comes from its definition so two devices making it collide on one id; items two devices made before either was identified share an id too, and since their records differ they arrive as a keep-both conflict, not a merge.
- **Knowledge logs** merge by copying (028, see "Knowledge logs (028)"); a merge that needs a choice stays a conflict, and logs that forked under 020's untagged batch names still collide.
- **A restore after a finished sync is an edit.** Pending markers protect a restore of the old bytes made before the archives record the copy: the holder of a marker no longer holds its `to`, so the path is a `missing_ancestor` conflict that keeps both versions (even when the copy was already verified). Once the archives are written, a restore is an ordinary later edit and is synchronized as one.
- **A copy that only a deletion of the same sync makes possible lands one sync later.** Copies are admitted before deletions (whether a deletion orphans anything depends on what the copies leave), so the store judges each copy over the receiver as it is: a manifest that drops the head of an entity with several revisions, deleted in the same sync, is refused while those revisions are still there, and an instance id moved to another kind is refused while the old kind's file is. The copy is `unapplicable` for that sync, a deletion it would have made possible stays `delete_dependency`, and the next sync (or a peer transfer's next pass) makes both. Nothing is lost or resurrected meanwhile.
- **A hold recorded for a deletion that then does not happen stays held.** holds(d) commits before the data commit, so when that commit then drops the deletion (denied there after all, for one an approval was expected to allow or a grant revoked meanwhile, a record written since the plan needs it, a crash), the record's version stays listed as `held` and out of every other pair's `delivered` versions: a kept copy of those bytes is never dismissable. That fails closed (a copy kept, nothing lost); a later deletion of the record reuses the same entry.
- **A deletion is held back generously.** The dependency reading for deletions treats any string that parses as a reference as one, so text that merely looks like a reference (a note quoting `world:harbor/character/wren`) keeps a deletion back as `delete_dependency`. That only ever keeps both versions; the person deletes the dependent too, or resolves toward a version. A held-back deletion's receiver still holds the record: nothing is kept for it until it is deleted.
- **Denials are coarse.** A denied write drops every copy of its source to that device (instances and art files are independent), not only the writes that strictly depend on it.
- **Blobs are trusted by agreement.** After one verified agreement a blob is identified by its name, its size and the pair's archive, and is not read again. A blob corrupted in place at the same size after that stays `agreed` and undetected by sync. It is never propagated (a blob is only ever copied onto an absent path, from a hashed origin), and locally `read_image_bytes` raises `BlobCorrupt` and `repair_blob` fixes it. No inode or modification-time cache is kept: timestamps never decide.
- **Art costs reads and archive entries.** Each copied blob is read about five times (the plan's hash, authorization, staging, the commit's temp digest and verification), one blob at a time. `SyncPlan.preview()` loads every blob it copies; an `assets` grant, not per-blob approval, is the normal path. A blob the receiver may not write is read by no sync when the receiver's library is bound to its durable authority (as [production libraries must be](STORAGE.md)); on an unbound library (test fixtures) the plan cannot see the grants, so such a blob is hashed and loaded again on every sync until its grant is added. A blob only one device holds that is in a conflict that copies nothing is not read, so a corrupt one reports that conflict's code rather than `blocked`; `resolve` hashes it before delivering it. A picture is about three archive paths (blob, image, placement), so one archive file holds roughly 7,600 pictures before it is sharded. A plan that copies an image or placement also asks each device for its `excluded_sources()` (W5): on an unchanged library that is one `stat` per manifest and revision entry, but on a store's first call, or for a source changed since, it reads that source's manifest and revisions again, which the plan's own scan has just read too.
- **A damaged campaign art layer is not reproduced.** Sync never moves non-record files, so a receiver can show inherited source art where the damaged origin shows `Unavailable` (018's damaged-layer rule); the origin reports the damage in `load()`.
- **Single-device trust in markers and lineage.** A pending marker is trusted on one device's word, and the `check` digest detects damage, not forgery. `.sync` writes need no handle. Likewise `put_exact` publishes bytes verbatim, `previous` included, and a true first sync trusts one-hop `previous` lineage (row 5): a writer with APPLY that calls it directly can claim any ancestor; and its `allowed_manifests` (the identical-manifest exemption `resolve` uses) is taken on the caller's word. Keeping `.sync` writes and `put_exact` out of workers' reach is the application's job until 007/028 integrate.
- **Link-drop policy.** A copied manifest is admitted exactly as a local commit of it would be. Under 010's accepted link-order policy, it can cause *another* source's cross-source link to be dropped on the destination, and the next `load` reports it.
- 010's R7 window remains: an external edit landing exactly between a target's guard read and its `replace` is lost. 019 narrowed it for a file being created: its directories are now made before that guard read, so only the publish step's own path re-check (a stat, no read of the file) and the `replace` remain in the window.
- **Rollback.** A pre-019 build cannot recover an unfinished journal that contains `replica`, `keep`, `hold` or `state` entries (`RecoveryFailed`, unknown kind). Finish recovery with a 019 build, or use `discard_journal`. A build from before art sync finds a "bad entry" in an archive or marker that records art paths, ignores the whole file, and treats every path as uncertain: conservative, and not supported on this pre-release branch. A build from before 028 finds an unknown format in a sharded (`/2`) root and does the same; it cannot read `keeps.json`, so it delivers dismissed versions again. A build from before deletion propagation cannot recover an unfinished journal with a `remove` entry (`RecoveryFailed`, unknown kind: finish recovery with a current build), ignores a pending marker that records a deletion (every path uncertain), and reads row 9 as a `deleted` conflict again: a deleted record whose tombstone is archived is then simply absent on both devices.

The unreduced explorations exist as opt-in tests (`GRIMOIRE_EXHAUSTIVE_SYNC=1`): every mutating operation with crashes, torn writes and errors, about 220 points and two minutes on Linux, ran with no violation; an edit at every operation (two targets) takes about 15 minutes, so run it with `-o faulthandler_timeout=0` or the 120-second fault handler prints a traceback partway through. Read faults (an unreadable marker, record or verification read) are covered by monkeypatched scenarios, because the harness faults only mutating operations. The harness proves convergence and no lost version at every commit boundary for its fixtures; it does not by itself pin the apply order or that a replaced version is a `hold` rather than a `keep` (no explored point restores old bytes, and no explored resolve aborts). Those are pinned by monkeypatched scenarios that crash between named steps and then meddle (`test_sync_guards.py`, `test_sync_scenarios.py`, `test_store_scan_edges.py`).
