# Response targets and speaker attribution

## Purpose

Scene prose should be guided by simple, approximate length targets. A scene
opening needs a substantial narrator setup; each NPC then contributes a
shorter response. Continuing a scene uses the same shorter target for each
speaker. Grimoire knows who it asked to speak, so model output should be prose,
not a script with model-chosen `**Name:**` headers. The application writes the
speaker headers and chooses portraits from known actors. Player characters are
never generated by the model.

The existing Markdown scene transcript remains the stored format. This change
does not rewrite historical scenes, greetings, or user-authored text.

## Response controls

Replace the named response preset UI with two settings groups: **Scene
opening** and **Scene continuation**. Each has an approximate word target and
an approximate paragraph target. Both numbers are positive integers and are
presented to the model as guidance, not as hard caps or post-generation
truncation. The initial defaults are 400 words and 3 paragraphs for Opening,
150 words and 2 paragraphs for Continuation.

Opening applies to the narrator's opening contribution. Continuation applies
to each NPC contribution in that same opening, to each NPC continuation, and
to narrator contributions after the opening. The targets describe one
speaker's prose, not a total for a multi-speaker turn. The existing turn chip
offers one-shot Continuation word and paragraph targets for that turn.

The two groups inherit per field through the existing scene, campaign, and
global scopes, with narrower explicit values winning. The effective value and
its source are visible where the user edits these settings. Prose style is a
separate control and continues to inherit as it does today. The five old
length knobs, named length bundles, custom response presets, and the combined
generation switch leave the active UI. Existing preset files and stored
references are not deleted. A read-only compatibility path uses their old
word and paragraph values for continuations when no new value overrides them,
and continues to honor their style choice until a direct style setting
overrides it. New Opening values do not inherit old preset budgets because
the old opener had its own independent shape rule.

## Generation and transcript flow

Normal scene continuations already generate one actor at a time by default:
the continuation engine selects an actor before each model call. The optional
combined mode is the legacy exception. Make the existing individual path the
only active continuation path. Prompts for an assigned
NPC or narrator request unlabeled prose, spoken dialogue in quotes, and no
actions or dialogue for PCs. Remove instructions that ask the model to divide
a response into `**CharacterName:**` blocks. The application uses the selected
actor's canonical full name when saving a response in the existing transcript
format. Any internal handoff protocol remains separate from reader-visible
prose.

Generated openers are the remaining combined call today. Change that route to
reuse the individual path's actor-scoped prompt composition and speaker
attribution, while retaining the opener's draft-before-adoption lifecycle.
An opener draft is one sequence: a narrator generation using Opening targets,
then one generation for every present NPC using Continuation targets. The
sequence follows the scene's stable cast order. Each call receives the full
opener context and the contributions already drafted in this sequence, so an
NPC can respond to the setup and earlier NPCs without any provisional scene
write. A draft has structured contributions with actor reference, display
name, and prose; the stream identifies the current speaker before its text
deltas. The UI previews each contribution under its known speaker and portrait.
Acceptance is one scene operation: validate that the scene is still empty and
the planned speaker identities, names, and locked versions still match, then
serialize every contribution as the same `**Name:**` transcript blocks used
today. It must not persist a partial opening. Saving a complete draft as a
greeting serializes the same canonical labels into the existing greeting body
format. Existing greetings
and manually authored first posts continue to work.

A failed or interrupted generation leaves completed contributions visible as
a draft, discards any incomplete contribution, reports the failing speaker,
and offers retry for the missing contributions. It writes no transcript posts
before acceptance. Retrying an
already completed request must replay its result rather than charge for a
second set of calls. A cast change or another first post between draft and
acceptance rejects stale adoption with a clear error. Canceling or leaving an
opener never leaves a half-written scene.

## Names and portraits

Full actor names are unique across distinct characters and PCs in a World and
in each Campaign's effective library (its own actors plus inherited World
actors). The comparison ignores case and surrounding whitespace. Different
versions of the same actor may retain the same name. A new actor, version,
rename, import, or campaign localization that would introduce a duplicate
name is rejected before writing; the error identifies the conflicting actor.
Selecting a different version cannot introduce a conflict either. This is a
name rule, not an ID rule: IDs and existing file layouts remain unchanged.

The live opener preview uses its actor references for portraits. In saved
scenes, an exact full-name label resolves to the matching cast member and its
locked version portrait. New continuation responses use the existing
response ledger's actor reference: the scene read API supplies it to the
frontend by joining on the already stored response ID. The transcript file
gains no new identity field or message format. Historical abbreviated labels continue to
use the current unique-prefix fallback. If pre-existing data has duplicate
full names, the reader shows the text and a neutral portrait until the names
are resolved; it does not choose an arbitrary actor.

## Compatibility and failures

Old scene transcripts, manually edited labeled text, imported transcripts,
greetings, and archived response variants remain readable. Existing stored
preset references remain harmless and supply fallback values where described
above. Unreadable or missing legacy presets supply no values. Bad new target
values are rejected by write APIs and ignored on read in favor of the next
valid scope or default. A model that includes its own leading name label
despite the prompt has that label stripped. A label for another speaker, or
multiple script blocks, rejects that contribution for retry. The model cannot
assign a different speaker.

The existing scene lock and run replay rules apply to adoption and detached
generation. Prompt capture and usage accounting record each model call under
the opener attempt, while preserving speaker identity for inspection. A
failure on one call cannot silently mark the whole opener complete.

## Verification

Backend tests cover per-field setting inheritance and legacy fallback, the
opening versus continuation prompt budgets, speaker-specific unlabeled
prompts, sequential opener context, complete and partial draft behavior,
idempotent replay, stale adoption, canonical Markdown serialization, greeting
compatibility, and duplicate-name rejection across actor kinds, versions,
imports, inherited World actors, and Campaign localizations. Existing-name
collisions remain readable without an arbitrary portrait.

Frontend tests cover the two setting groups at each scope, effective values,
the removal of preset and combined-mode controls, per-speaker opener streaming
and retry, use/save actions, and correct portraits in live and reloaded scenes.
Run the repository gate (`make check`) and verify the opener and continuation
flows against an isolated placeholder store.
