Give climate.json an owning store module (#237)

base main @ ecf54768 → 51fe690a · +374/−85 · rebased 2026-07-28

What this change actually does

A campaign's default climate — the file backend/src/grimoire/store/campaign_climate.py owns, campaigns/<cid>/climate.json — is no longer read and written by whoever happens to need it. Four call sites across three layers (create, HTTP update, the weather resolver, the climate-referrer scan) now go through one module, and the HTTP layer stops touching the disk for this file entirely.

One user-visible behavior change rides along, and it is a bug fix rather than a refactor artifact: the referrer scan behind the climate delete/revert warning used to read the file directly, so a campaign with no climate.json — every campaign predating the weather work — was reported as using no climate, when at runtime it resolves to the shipped preset on every turn. It now reports the effective default (backend/src/grimoire/routes.py:2087). A second gap made that fix inert in the UI: the editor asked for referrers only when deleting, never when reverting a customized preset — the widest case of all, since a customized fallback preset silently governs every campaign without a default of its own. Both paths now disclose (frontend/src/components/ClimateEditor.tsx:99-126).

The HTTP surface is unchanged: GET/PUT /api/campaigns/{cid}/climate keep their request and response shapes, and the 400 for an unknown climate now comes from the store's ClimateError rather than a duplicated check in the route.

  • No migration. Campaigns with no climate.json are still not backfilled; they are simply now understood, consistently, as "unset → fallback" by every reader.

Two flows move; one of them changes what the user is told

Reading a campaign's default climate and writing it are pure re-plumbing — same disk, same semantics, one hop added. The flow worth reviewing is delete-or-revert a climate, where both the set of campaigns reported and the set of situations in which the report is fetched at all have changed.

What moved

  • The lookup now runs on both paths. frontend/src/components/ClimateEditor.tsx:99-126 — the if (!reverting) gate is gone. A revert changes the tables under everything using the id, so it has the same audience as a delete.
  • Fail-closed extends to revert. A failed referrer lookup previously blocked only deletes; it now blocks reverts too, with the verb switched in the message (frontend/src/components/ClimateEditor.tsx:112-115).
  • The reported set grew. Campaigns whose climate.json is absent, malformed or dangling are now reported under the fallback id instead of under nothing (backend/src/grimoire/routes.py:2081-2088).
  • Per-campaign error handling left the route. The old scan caught OSError/ JSONDecodeError/AttributeError per campaign; resolve_default cannot raise those, so the try is gone rather than silently dropped. The deliberate non-catch around list_campaigns() — an unreadable campaign list is an unknown, not an empty result — is untouched at backend/src/grimoire/routes.py:2076-2079.
Cost paid for the truthful answer: the scan now calls climates.get() once per campaign, and that function rescans both climate directories per call (backend/src/grimoire/store/climates/__init__.py:71-76). Previously the scan read one small JSON per campaign. For a local library of tens of campaigns and a handful of climate documents this is unmeasurable; it is worth knowing if the referrer scan ever moves somewhere hot.

Verdict: mergeable. Two judgment calls to agree with, no must-fix.

The refactor is the shape the issue asked for and the tests can fail. What a reviewer actually has to decide is whether they accept (1) answering the issue's "overlay bypass" with an argument rather than an overlay, and (2) widening the referrer scan to the effective default, which reports campaigns that no file names. Both are defended in code comments; neither is hidden.
