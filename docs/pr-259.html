Lift the path-escape guard into paths.safe_id and apply it in the campaign/world/character/PC root resolvers (#240)

base origin/main @ 50154fb2 → fix-240-safe-id-guard @ cc11a8c4 · round 5 · generated 2026-07-29

Four path resolvers stop trusting their caller — and one of them changes meaning

Every id-to-path resolver in the store now routes through a single guard, backend/src/grimoire/store/paths.py:114, which rejects ids that don't name a direct child of their parent directory. Four resolvers that previously joined a caller-supplied id onto a path unchecked — campaign_root, world_root, characters._char_dir, pcs._pc_dir — now raise their own NotFound instead.

The most serious finding on this PR was not an escape — it was an alias. Win32 trims trailing dots and spaces off a path component, so realm. opens worlds/realm. delete_world("realm.") therefore reached the live world, then compared the raw realm. against campaigns' stored realm references, concluded nothing used it, and shutil.rmtree'd it out from under the campaign. Reproduced on this machine before fixing. backend/src/grimoire/store/paths.py:144 now rejects any id Windows would normalize, on every platform — a store is synced between them, so an id has to mean the same thing on both.

The guard is also stricter than any of the copies it replaces except one: it rejects :. That was sheets._safe_part's idea and the other nine copies missed it. It is not cosmetic on this project's primary platform — Path("store/worlds") / "C:evil" evaluates to C:evil, because a Windows drive-relative id discards the base path entirely. Neither a / nor a \ check catches that.

The second-order change is the one to actually review: an empty world id used to be load-bearing. Five call sites passed meta.get("world", "") to mean "this campaign has no world" and depended on world_root("") resolving to the worlds parent directory. Rejecting "" would have broken all five, so they move to campaigns.world_root_of (backend/src/grimoire/store/campaigns.py:48), which resolves absence to a path below the campaign's own campaign.md — a regular file, so the filesystem itself guarantees nothing can ever occupy it.

Change classification

Security hardening primary

Guards added to 4 resolvers; : added to the guard's reject set. Defense in depth — the issue states plainly this is not a demonstrated exploit, since FastAPI path params don't match /.

Refactor bundled

Ten near-duplicate helpers collapse into one. Mechanical and large by line count (13 of 19 files), but it is the fix: the copies that were never made were exactly the resolvers that lacked the guard.

Behavior change review this

world_root("") no longer resolves to the worlds dir. Five call sites migrated. This is the only part of the diff that can regress working behavior.

Two flows move; everything else is a rename

Thirteen of the nineteen files change only which function name they call. Two runtime flows genuinely change shape: resolving a record id to a path, and resolving a campaign's world root when the campaign has no world.

Flow 1 — id → path, for a caller that is not an HTTP path parameter

Before

sequenceDiagram
  participant C as CLI script / body field
  participant W as worlds.world_root
  participant FS as filesystem
  C->>W: world_root("../campaigns")
  Note over W: no guard
  W-->>C: Path(store/worlds/../campaigns)
  C->>FS: read through that path
  FS-->>C: contents of a sibling collection

After

sequenceDiagram
  participant C as CLI script / body field
  participant W as worlds.world_root
  participant S as paths.safe_id
  participant FS as filesystem
  C->>W: world_root("../campaigns")
  W->>S: safe_id("../campaigns")
  S-->>W: False
  W-->>C: raise WorldNotFound
  Note over FS: never touched

What moved

  • New failure mode on a previously-succeeding path. Four resolvers can now raise where they previously always returned a Path: backend/src/grimoire/store/worlds.py:32, backend/src/grimoire/store/campaigns.py:23, backend/src/grimoire/store/characters.py:33, backend/src/grimoire/store/pcs.py:33.
  • Error propagation is unchanged for HTTP callers because each resolver raises its own domain NotFound, which routes already map to 404 (the except CampaignNotFound handlers already spread across backend/src/grimoire/routes/). The single exception is _world_root_or_404, which called world_meta_path (and thus world_root) outside any handler — fixed at backend/src/grimoire/routes/common.py:110.
  • Return-None contracts preserved by short-circuit ordering. characters.dir_hash (backend/src/grimoire/store/characters.py:301) and card_hash (backend/src/grimoire/store/characters.py:279) must keep returning None, not raising, for a bad id. They still do, because not safe_id(cid) is evaluated before the _meta_path/_card_path call that would hit the raising resolver. This ordering is now load-bearing and undocumented — see the walkthrough.
  • CLI scripts change from silent misbehavior to a clear exception: backend/scripts/ingest_scene.py:31 and backend/scripts/redownload_chub.py:43 are precisely the non-router callers the issue names.

Before

sequenceDiagram
  participant O as overlay.wroot_of

  participant FS as filesystem
  O->>W: world_root("")
  W-->>O: Path(store/worlds)
  Note over O,FS: the worlds PARENT, which exists
  O->>FS: exists()? -> True

After

sequenceDiagram
  participant O as overlay.wroot_of
  participant C as campaigns.world_root_of
  participant FS as filesystem
  O->>C: world_root_of(cid)
  C->>C: campaign meta has no world

What moved

  • Same outcome, different route. Both versions surface "the world holds no records". The old one got there by scanning a real directory that happened to contain no <kind>/<id>.md files; the new one never touches the filesystem in a meaningful place.
  • One observable behavior does flip: wroot.exists(). It was True, it is now False. campaigns.ensure_campaign_slim (backend/src/grimoire/store/campaigns.py:175) branches on exactly that, so a world-less campaign stamped world_copy: full now skips migration instead of running it against the worlds dir. That is the correct behavior — there is nothing to slim against — and backend/tests/test_path_guard_store.py:154 pins it.

Aliasing, and the enumeration/resolution contract round 5

Two distinct lessons arrived together, and both are more interesting than the traversal the ticket opened with.

An id that aliases another id is not a distinct child. The guard had been built entirely around escaping — separators, .., drive letters. Trailing dots and spaces escape nothing; they simply name a directory that already has another name, and that was enough to walk straight through the WorldInUse check and delete a world a campaign depended on. backend/src/grimoire/store/paths.py:144 closes it; backend/tests/test_path_guard_store.py reproduces the deletion and asserts the world survives.

Enumeration has to agree with resolution. Two findings looked separate — a 500 on the character list, a server that would not boot — and were one bug: listings returned whatever directory names they found, then handed them to resolvers that refuse them. The startup one is the worse of the two, because migrations.migrate_scene_ids() runs inside the FastAPI lifespan, so one stray directory stops the app starting at all. Fixed at the principle rather than the two reported sites: worlds, campaigns, characters, pcs, entities (list/refs/counts), greetings and scenes all filter on the same guard now (backend/src/grimoire/store/worlds.py:66, backend/src/grimoire/store/campaigns.py:101).

Such a directory is only creatable on POSIX — Windows refuses the name at mkdir — so those two tests are skipped on Windows, and the filter wiring was verified separately by making the shared guard reject a name this machine can create and confirming every listing drops it.

Rebased across a structural change on main. #241 split the route modules into a routes/ package while this branch was open, so the rebase dropped every route-side change as a modify/delete conflict.
