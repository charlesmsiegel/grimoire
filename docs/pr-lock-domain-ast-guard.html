PULL REQUEST REVIEW

Lock-domain AST guard

What this change actually does

It adds a fifth static architecture guard and, to give that guard something to check, converts the campaign lock domain from prose into three module-level constants.

It also closes a real race that the guard's own review surfaced. Campaign creation was not serialized: create_campaign published the campaign meta file — which is what makes a directory a campaign to list_campaigns — and only then wrote the manifest, calendar, climate and starting sheets. A second grimoire process could find the campaign inside that window and write to it, and sheets.seed would overwrite the result. Creation now holds the campaign lock from before publication through the last initializing write.

And it closes a stall that widening that lock introduced. The wider span ran calendars.validate_calendar inside it, which imports every user-authored calendar provider and calls that provider's own validate_rule — unbounded plugin code that this repo already forbids under the campaign lock, because one bad calendar would block every writer in the campaign. The calendar config is now resolved and validated from the world root before the lock is taken.

Otherwise the behavioral change is to CI, not to the app: from this commit on, a new module that mutates campaign-scoped state fails the test suite until a human classifies it, and a new mutator inside an already-declared domain module fails until it takes campaign_lock(cid) or is explicitly exempted with a stated reason.

One runtime flow changed: campaign creation

Almost every production line added is a constant, a docstring or a comment, and no signature changed (analyze_blast_radius: "no changed symbols detected"). The exception is campaigns.create_campaign, which now holds the campaign lock across publication and initialization — a race the guard's review surfaced. Both that flow and the contributor's are diagrammed below.

Campaign creation — the race, and the fix

Before — publication opens a window

sequenceDiagram
  autonumber
  participant A as process A (creating)
  participant FS as store
  participant B as process B
  A->>FS: mkdir, write campaign.md
  Note over FS: the campaign now EXISTS to list_campaigns
  B->>FS: list_campaigns -> sees it
  B->>FS: take campaign lock, write a sheet, release
  A->>FS: write manifest, calendar, climate
  A->>FS: seed: copy world sheets
  Note over FS: B's completed write is overwritten

After — creation is atomic to observers

sequenceDiagram
  autonumber
  participant A as process A (creating)
  participant FS as store
  participant B as process B
  A->>FS: resolve + VALIDATE calendar (plugin code, unlocked)
  A->>FS: take campaign lock
  A->>FS: mkdir, write campaign.md, manifest, calendar, climate
  B->>FS: list_campaigns -> sees it
  B--xFS: blocks on the campaign lock
  A->>FS: seed (reentrant, same lock)
  A->>FS: release
  B->>FS: proceeds against a fully initialized campaign

The fix is the lock's span, not its presence. Serializing only seed left the window open: process B could take the lock, write and release entirely before seed ran.

The span has an upper bound as well as a lower one. Its first version reached far enough to cover validate_calendar, which imports every user-authored provider in <home>/calendars/ and then runs that provider's validate_rule. Nothing bounds how long a hand-written plugin takes, and the repo already pins the rule for the two scene mutators that need a calendar (test_calendar_plugin_code_never_runs_under_the_campaign_lock) — it simply did not cover the creation path, so nothing failed. Resolution and validation now read from the world root before the lock, which is equivalent (copy_calendar is write_calendar(croot, read_calendar(wroot))) and leaves only this package's own file writes inside.

The span reaches down as well as up: it covers the mkdir. That is not about serialization — acquisition can raise (StoreBusy on a timeout), and with the directory already created that leaves an empty orphan whose only effect is to make uniquify read the name as taken, so the next attempt silently becomes <name>-2. Like the plugin-code stall, this failure mode arrived with the lock rather than predating it.

What moved

  • The source of truth for the domain moved from prose at backend/src/grimoire/store/locks.py:9-12 to three constants at backend/src/grimoire/store/locks.py:107 (DOMAIN_MODULES), :117 (OUTSIDE_DOMAIN) and :133 (UNREVIEWED). The paragraph that used to name the four unlocked mutators now points at the constants instead (backend/src/grimoire/store/locks.py:71-73).
  • Two functions gained an explicit exemption rather than an implicit one: backend/src/grimoire/store/audit.py:147 and backend/src/grimoire/store/audit.py:158. Each states why the campaign lock is not required, and the limit of the lock it does take.
  • create_campaign and sheets.seed now take the campaign lock — the only runtime change in the diff — and create_campaign's calendar handling moved out of that span so no plugin code runs under it.
  • Nothing moved in the lock ordering. The module_edit -> campaign -> {audit baseline, rolls} order documented at backend/src/grimoire/store/locks.py:37-48 is unchanged.

Does the guard actually fail? (mutation-tested, not assumed)

A guard that cannot fail reads as coverage. Both regression shapes were verified by injecting a real offender into the working tree and confirming a red run, then reverting:

InjectedShapeResult
scenes.set_summary(cid, sid, text) without @_serialized #254 — transcript lost update failed: store.scenes.set_summary
a new campaign-scoped store module doing read → mutate → atomic.write_text #255 — module silently outside the domain failed: store.notes

In total 82 self-tests pin the detector's own semantics in backend/tests/test_lock_domain_guard.py — that a decorator counts only when it wraps its target under the lock on every executed path, that every write in a locking function runs inside the block (not merely that the block exists), that pure delegation to a locked helper is not flagged while a wrapper with a write of its own is, and that cyclic helpers terminate.

The twenty-five detector fixes from rounds nine through seventeen were mutation-tested the same way: each was reverted alone and its test confirmed red. Read that claim with the Review Walkthrough's round-twelve note in mind — the harness making it was itself defective until that round, and every case was re-run once it was fixed.

Verdict: mergeable

A guard mutation-verified to fail on both regression shapes it targets, a declaration honest about how little of the codebase it enforces, and — found by reviewing the guard — one real race fixed in campaign creation. That race is the only runtime change and is the thing to read closely; everything else is constants, comments and tests.

One decision needs a human, not a test. After seventeen review rounds both of the guard's polarities were inverted to a closed whitelist that fails loud: a form it does not recognize reads as unserialized. It is therefore deliberately stricter than the codebase, and its value depends on people answering a complaint with a marker or a whitelist entry rather than by loosening the polarity back. If that trade is wrong for this project, the whitelist is where to argue it.

Two attempts, and the difference is instructive. The fix that works is the lock's span: creation now holds the campaign lock from before publication through the last initializing write (backend/src/grimoire/store/campaigns.py:184-241) — and no further: the calendar resolution and validation ahead of it are deliberately outside, because validate_calendar runs user-authored plugin code. seed keeps its own acquisition — public API, reentrant lock, so nesting is free.

what a reviewer should check that no callee inside the new span acquires another lock. Verified: modules.resolve, calendars.copy_calendar and campaign_climate.write_default acquire nothing, so the documented module_edit → campaign → {baseline, rolls} order is preserved and the full suite passes with no hang.

Two patterns worth more than the individual fixes

Wrong prose, not wrong code. The findings that mattered most were factual claims I had written and not checked: "the cid isn't reachable yet", "locking the writer is enough", "the atomic guard catches that form", "Path.touch takes only keywords". Two were live races. A guard whose escape hatch is a free-text justification inherits the quality of those justifications.

Patching instances, not classes — twice over. Rounds 1–4 each fixed the reported case and left the adjacent seam; three separate findings were variants of "ast.walk descends further than the semantics do". Round 5 restructured that into one traversal — and round 6 then found four instances of a second generator hiding behind it: "accept on finding one qualifying case" where the semantics demand every case, in yields, decorator wrappers, aliases and returned names.

Round 6 removed that generator — one traversal, one polarity. Round 7 then produced three more findings of a third shape, and this is the one that ended the pattern: a syntactic test standing in for the semantic fact "this lock protects this campaign". hold_all(x) where x merely mentions cid; an alias whose parameters bind the caller's cid onto another name; a local variable shadowing campaign_lock. Eight findings across the rounds were new ways to spell "looks locked".

Round 8 is the honest coda: the inversion was partial. I predicted round eight would complain about false positives, since recognition now fails loud. All three of its findings were false negatives — because the inversion covered "is this locked?" and left "is this a mutation?" and "is this the decorated target?" as accept-unless-spotted. The polarity was fixed in one of three places and described as though it had been fixed everywhere. That is the same over-claiming the earlier rounds punished, one level up.

Round 7 inverted the polarity instead of learning a ninth spelling. Recognition is now a closed whitelist of four forms, and anything else fails loud. That is the first change that cannot be defeated by inventing a new spelling, because unrecognized spellings no longer pass — and it is also the first that knowingly buys safety with false alarms. The guard's docstring now states that reach honestly rather than implying it understands Python's binding semantics, which it does not.

The round-eight prediction was right, and was honoured

It was stated so it could be wrong visibly: "if a ninth round finds another primitive, the right response is not to add it. It is to invert that surface too." Round nine found os.open — a create-and- truncate that never calls os.write because it hands the fd on — which is a seventh entry for a list that had already taken six.

It was not added. Inside os and shutil, where a receiver unambiguously names the filesystem, the question is now "is this a known reader?" and everything else publishes. The evidence that this was the right shape rather than a tidier list: shutil.copytree is used twice in this package today, no enumeration across nine rounds had it, and the inversion catches it without anyone noticing it first.

The boundary is honest about where it stops. p.foo() cannot be told from some_dict.foo() without type inference, so a path-valued receiver keeps the enumerated names and keeps their documented blind spot (Path.replace).

Round nine also caught this branch reintroducing the bug it fixed

The race fix widened create_campaign's lock — and the widened span ran calendars.validate_calendar inside it, which imports every user-authored provider and calls that provider's own validate_rule. The repo already has a rule against exactly this (test_calendar_plugin_code_never_runs_under_the_campaign_lock), written because one bad plugin stalls every writer in the campaign. The existing test only covered the two scene mutators, so nothing failed.

This is the sharpest instance of the pattern the whole review has: a fix that is correct about the thing it is looking at and wrong about the thing beside it. The calendar config is now resolved and validated from the world root before the lock, leaving only this package's own file writes inside; a new test probes the lock from every provider entry point and fails against the previous span.

The round-nine prediction named the right class and the wrong remedy

It said the remaining risk had moved to scope and binding resolution, and that the answer was to keep narrowing what counts as resolvable. All four of round ten's findings were that class, so the prediction held — but the framing was wrong in a way worth recording. These were not four separate resolution failures. They were one rule, checked at some boundaries and not others:

An acquisition only counts when this campaign's id reaches the parameter the lock is keyed on. Round seven checked that for aliases. Round nine checked it for delegation. Round ten found the two boundaries left — into a decorated target, and into a callee with no parameter to bind at all. Every round "narrowed what counts as resolvable" at whichever boundary was reported, and the class stayed open because the rule was never stated once and applied everywhere. It is now, in the docstring and in the code.

Two of round ten's four were also the quietest failure mode this guard has: the caller read as serialized and propagation stopped at it, so it was reported by neither check — strictly worse than if the helper had taken no lock at all. That pairing has now appeared twice (round nine's argument swap, round ten's parameterless helper), which suggests any future change to one check should be tested against the other.

Round eleven: the fix introduced the bug, in the same commit

The most useful finding on this PR, and it is about the review rather than the code. Round ten closed a double silence — a caller that read as serialized and was dropped from the mutator report, so nothing named it — by refusing to let a cid-less helper vouch for its caller. The same commit kept a bypass for locks.hold_all(...), reasoning that an all-campaign holder covers whatever the caller's campaign is.

That reasoning read the callee's name, not its argument. hold_all([]) and hold_all([sid]) are equally hold_all. The bypass reopened the exact failure mode the commit was written to close, and did it while the commit message claimed the mode was closed.

Round eleven's other finding is the same shape: the requirement that a lock's receiver be spelled locks was itself the fix for def put(cid, campaign_lock=nullcontext), and def put(cid, locks=fake) defeats it identically. Both are a name standing in for a binding — which is the class this report has claimed to have closed twice now.

The pattern worth carrying out of this PR: a fix that narrows a rule should be tested against the failure it is narrowing, not only against the reported instance. Both of these would have been caught by asking "what else satisfies the new check?" before writing the commit message.

Round twelve: the verification itself was unsound

Every round since the ninth has claimed its fixes were "mutation-tested — each reverted alone, its test confirmed red". That claim rests on a harness, and in this round the harness reported a case as still passing when the test in fact failed.

The cause is that CPython invalidates a .pyc on (mtime, size). Successive mutations written inside the same clock second can match a cached one, so pytest imported the previous mutation rather than the current one. The harness now sweeps __pycache__ and runs with PYTHONDONTWRITEBYTECODE.

What makes this the most serious item on the PR is the direction it could have failed in. A false "still passes" is loud — it stopped the round and got investigated. The identical mechanism produces a false "fails as expected", which is silent, and would have voided the verification claimed in three consecutive rounds while reading as rigor. All twelve cases were re-run under the hardened harness and every one goes red without its fix, so the claims stand — but until this round they were luckier than they were sound, and a reader should weight the earlier "mutation-verified" language accordingly.

Where the next hole most likely is

Two rules have now had to be stated once and applied everywhere, each after being fixed at four or five separate instances:

  1. An acquisition only counts when this campaign's id reaches the parameter the lock is keyed on (rounds 7, 9, 10, 11).
  2. A name is not a binding (rounds 10, 11, 12 — and on the mutation side, 10 and 12).

The pattern across both is that the guard trusts something syntactic as a proxy for something semantic, and the review finds the next spelling of it. So the place to look is not a list of shapes but the remaining proxies: every predicate that still concludes something about runtime from a token. The honest limit is unchanged — this is an AST guard, not a type checker.

Round thirteen sharpened this into something actionable. Four of its five findings were the second rule again, and what they had in common was not the rule but the enumeration underneath it: the shadowing check knew about parameters and = but not import; the alias resolver knew ast.Assign but not ast.AnnAssign; the receiver check knew locks but not the store that store.locks hangs off. Stating the rule once was necessary and was not sufficient, because the rule is applied over a hand-listed set of binding forms, and that list has the same property every other enumeration on this PR had — it grows by one each time somebody looks.

The three assignment walkers now share one _bindings helper, which is the same consolidation that ended the drift on the mutation side. The remaining exposure is the forms still not enumerated: global and nonlocal rebinding, setattr, class-body scope, and conditional imports. A reader deciding how much to trust this guard should read that as the live limit rather than the polarity inversions, which are settled.

Round fourteen confirmed that prediction and sharpened it again. One of its four findings was an unenumerated binding form (target: Callable = fn) sitting inside the very helper introduced to close that class — the consolidation was right and one call site had not been moved onto it. Another was the marker audit still skipping the lock module after _survey had stopped: half a fix, shipped as a whole one.

So the two-line summary of this review, for anyone deciding how much weight to put on the guard: every rule here was stated after being fixed at four or five instances, and the round after each rule was stated found it unapplied at one more site. That is not an argument the guard is unsound — its classification of the tree has never changed across sixty-two findings — but it is the reason the docstring's list of recognized forms, rather than the code, is the thing to read before trusting it.

Round fifteen is the exception worth reading, because it made a stated limit narrower instead of restating it. Until it, entering the campaign lock anywhere made the whole function read as serialized — so a mutator could lock around pass and publish outside the block. Every other finding on this PR was a way to look locked; this one was a function that genuinely locks, and writes somewhere else.

What it says about the review as a whole: the machinery to answer it had existed since round six. _under_lock has asked "does every occurrence run while the lock is held?" for yields and for decorator target invocations that entire time. Nobody asked it about the function's own writes. The recurring failure on this branch is not missing capability — it is a correct rule with an incomplete list of places it is applied, and that has now been true of the binding rule, the shadowing rule, the publication surface, and the traversal.

Round sixteen produced the review's first false positive — open("a"), a filename, read as append mode. Sixty findings in, every one had been the guard accepting something unsafe; this was the guard rejecting something safe, which is the cost side of the trade the docstring has been promising since round seven. It is worth knowing that side of the ledger stayed empty this long, and that when it opened, the cost was a read-only module being pushed into the declaration rather than anything silent.

Chasing round sixteen's async with case then surfaced a second false positive, this one mine and latent: a with reached as a body statement never had its own context evaluated, so a lock nested inside with suppress(...) read as unlocked. Round fifteen's write-position rule is what made it reachable. The traversal now examines every node through one step — the fifth site where "one rule, applied everywhere" was the fix rather than another branch.

Round seventeen is the same story a sixth time, and the cleanest illustration of it. Round fifteen made the position of a function's writes matter — and then returned, so a locked atomic.write_text(...) followed by an unlocked _unsafe(cid) was accepted, with the private delegate skipped by _analyze and therefore named by neither check. A function mutates two ways, by writing and by calling something that writes; the rule was applied to one of them.

Worth recording because it went the other way for once: the first fix attempted here rejected the same helper called inside the block, which would have been a false alarm on legitimate code. The "what else satisfies this new check?" probes caught it before the commit rather than the next round catching it after — which is the first time on this PR that step prevented a defect instead of documenting one.

Invariant impact

This change strengthens one invariant and weakens none. "Every campaign-scoped mutator in a domain module serializes on campaign_lock(cid)" was previously maintained by review attention alone; it is now maintained by a test for the 5 declared domain modules.

It also creates a new obligation the codebase did not have: the three declarations must be kept true. That obligation is itself test-enforced in both directions, so it does not become a second thing to remember — which was the whole failure being fixed.

Honest limit worth repeating from the guard's own docstring

The guard checks that a lock is taken, never that it is taken widely enough. A read-modify-write whose read sits outside the with — precisely the bug scenes._serialized exists to fix — passes. Analysis is also per-module: mutation propagates through a module's own helpers, never across an import.
