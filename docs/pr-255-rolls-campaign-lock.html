grimoire #255 — Review

Move the roll log onto the shared per-campaign lock domain

base main @ 46e6aae1 → fix-255-rolls-campaign-lock @ d8428e58 · +119/−41 across 3 files · generated 2026-07-28

The roll log stops being its own lock domain

Every mutating entry point in backend/src/grimoire/store/rolls.py used to serialize on a registry private to that module. It now takes locks.campaign_lock(cid) — the same object scenes, sheets, proposals, audit and the module-pack swap already share. The private registry is deleted outright; the module no longer imports threading.

Observable behavior change: a roll append now blocks while any other campaign-scoped mutation of the same campaign is in flight, and vice versa. Most visibly, module publication — which holds every campaign's lock across the pack swap (backend/src/grimoire/store/module_edit.py:504-511) — now excludes roll appends. Previously it did not, even though it already excluded the proposals those rolls are tagged with.

Nothing about the on-disk format, the entry schema, the id scheme, or the read paths changes. read, get and replay still take no lock at all.

One lock boundary moved; no call sequence did

No caller was edited, no step was added or removed from any flow, and no new external call appears. What changed is which lock object a roll write acquires — which alters what a concurrent flow can do while it runs. The two flows below are where that is visible.

  • Lock boundary only: backend/src/grimoire/store/rolls.py:67 acquires locks.campaign_lock(cid) where it previously acquired a module-private RLock. Same critical section, same contents, different object.
  • The multi-campaign holder at backend/src/grimoire/store/module_edit.py:504-511 is unchanged but now covers one more writer.

What moved:

  • Before this change these were different locks, so both nestings were trivially safe. After it they are the same object, and safety rests entirely on campaign_lock returning an RLock (backend/src/grimoire/store/locks.py:57-62).
  • The second nesting is new since #254. Scene mutators now hold the campaign lock, and all three scene_refs.repoint call sites live inside @_serialized functions (backend/src/grimoire/store/scenes.py:182, :322, :889) — so a scene rename reaches rolls.repoint_scenes with the lock already held. On the pre-#254 tree this path held nothing.
  • proposals.locked is a thin wrapper over the same registry (backend/src/grimoire/store/proposals.py:26-35), so _project_resolution holds it at depth 1 and each rolls call re-enters at depth 2.
  • Guarded by test_rolls_mutators_are_reentrant_under_a_held_campaign_lock (backend/tests/test_locks_store.py:228-254), which runs the nesting in a worker thread with a bounded join so a regression fails in seconds rather than hanging the suite.
The one ordering rule this could have broken, checked. scene_refs.repoint (backend/src/grimoire/store/scene_refs.py:17-22) walks six stores in sequence: audit.repoint_scenes takes the baseline lock (backend/src/grimoire/store/audit.py:143-152) and rolls.repoint_scenes now takes the campaign lock. Since the scene mutator already holds the campaign lock across the whole walk, the baseline lock is still acquired under it — campaign → baseline, which is the documented direction (backend/src/grimoire/store/locks.py:38). The reverse never occurs. The audit prompt path only calls the lock-free rolls.read (backend/src/grimoire/store/audit.py:232).

Invariant impact

Strengthened, not weakened. The "concurrent campaign mutations serialize" invariant previously had a hole this diff closes. The unification argument in backend/src/grimoire/store/locks.py:3-12 — that a module edit must exclude a proposal derived from the pack it is about to replace — now extends transitively to the rolls those proposals produce.

One invariant now rests on a load-bearing detail worth naming: correctness depends on campaign_lock being an RLock, and this diff adds the third dependent. audit.apply_delta → sheets.set_field was first; #254 added the scene-write nesting; this adds _project_resolution → rolls and scene-rename → rolls.repoint_scenes. Both the docstring (backend/src/grimoire/store/rolls.py:19-27) and a test (backend/tests/test_locks_store.py:228-254) record it.

Pre-existing, out of scope, now filed as #267: two multi-campaign lock holders acquire in different orders. backend/src/grimoire/store/module_edit.py:509 iterates campaigns.list_campaigns(), which sorts by updated descending (backend/src/grimoire/store/campaigns.py:64), while the world-module rebind route at backend/src/grimoire/routes/worlds.py:80-85 iterates a list sorted by id. Run concurrently they can ABBA-deadlock, and the module-edit lock does not save them — every _campaign_locks() call site sits inside with _M: but put_world_module never takes _M at all. Both comments claim to be the sole multi-lock holder (backend/src/grimoire/store/module_edit.py:506-507, backend/src/grimoire/routes/worlds.py:84), so each was written without knowledge of the other. This diff neither introduces nor worsens it — rolls takes exactly one lock.
