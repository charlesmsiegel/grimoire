promote_image stops swapping through a temp: republish both slots, and repair the temps the old swap stranded

base origin/main @ 75076ea3 → fix-253-promote-image-swap @ 144911f6 · +647/−12 · 8 commits · rebased 2026-07-28

Making an image the avatar stops being a three-step file dance

backend/src/grimoire/store/assets.py:387 — promotion no longer moves files. It reads both images into memory and republishes each through put_image: the promoted bytes to avatar.<ext>, the demoted avatar's bytes to the promoted image's slot. The old code renamed src → promote-tmp → and avatar → src's slot, and a crash between renames left the store with a file under promote-tmp.png and no avatar at all.

Two behavioral consequences a reviewer should hold onto. The avatar slot now always resolves — every instant it holds either the old or the new image, because put_image writes before it unlinks the extension it replaces. And reads now repair damage: image_path (backend/src/grimoire/store/assets.py:244) and list_images (backend/src/grimoire/store/assets.py:268) call _heal_stranded_promotion, which renames a leftover promote-tmp.* into the avatar slot, or into a free gallery slot when a working avatar exists.

Two smaller contract changes ride along: promote-tmp (case-folded) is now a rejected image name (backend/src/grimoire/store/assets.py:29), and promoting a file whose extension isn't allowlisted now raises instead of silently renaming it — surfaced as HTTP 400 by all four promote routes.

The one loss the change introduces, and why it is still a net win. Publish #1 replaces avatar.<ext>. When the promoted image shares that extension — the common png → png case — the old avatar's bytes then exist only in memory, so a crash before publish #2 loses the demoted image and leaves its slot holding a duplicate of the new avatar. The old code lost nothing in that window but left no resolvable avatar, so this trades a rare loss of a demoted image for eliminating a rare loss of the avatar itself. Keeping both would need a third slot and therefore the temp-file recovery protocol the change deletes. Disclosed, not hidden — but it is a genuine regression in one narrow window and deserves an explicit reviewer nod.

What did not change

  • Reads still take no locks. image_path/list_images remain unsynchronized, so a reader landing between the two publishes sees the promoted image in both slots. The change makes the swap crash-safe, not atomic to observers — stated in the docstring (backend/src/grimoire/store/assets.py:409-414) rather than fixed.
  • _image_lock's keying. Still an exact string (backend/src/grimoire/store/assets.py:60), so case-variant names remain unserialized on case-insensitive filesystems. Scoped out with a documented reason; recovery works around it by case-folding its own slot choice.

  • No frontend change. The gallery still renders only avatar and gallery_N (frontend/src/components/CharacterEditor.tsx:119) — which is precisely why the backend recovery is needed rather than optional, since a stranded temp is invisible in the UI.
  • No observability. Recovery repairs damage and logs nothing; a store that quietly had files moved gives the user no record. Defensible for a rename-only repair, worth a conscious decision.

What moved

  • Lock boundary is new and wraps the whole swap — backend/src/grimoire/store/assets.py:421. Previously promotion took no lock, so an upload could land between renames.
  • Bytes are copied, not moved — backend/src/grimoire/store/assets.py:432-433. Both files are read before either is written, so publish #1 can't destroy the input to publish #2.
  • Validation moved earlier — backend/src/grimoire/store/assets.py:429-431. An unsupported extension now fails before any write instead of surfacing from put_image mid-swap.
  • New error propagation: a promotion with no avatar to swap back verifies its own delete and raises OSError if the source survived — backend/src/grimoire/store/assets.py:435-448. Previously that failure was swallowed by delete_image, and overlay.promote_image silently mis-decided its tombstone (backend/src/grimoire/store/overlay.py:449).
  • mtimes now change on both files, since they're rewritten rather than renamed. Harmless and slightly better: the ?v= cache token derives from mtime+size (backend/src/grimoire/store/assets.py:286), so browsers refetch.

What moved

  • Reads are no longer side-effect free. backend/src/grimoire/store/assets.py:256 and :277. The happy path costs one extra glob and takes no locks (backend/src/grimoire/store/assets.py:204); only a directory that actually holds wreckage acquires anything.
  • The heal reaches through the overlay. overlay.list_images scans both campaign and world roots (backend/src/grimoire/store/overlay.py:396-402), so a campaign read repairs world-side damage. Deliberate and tested (backend/tests/test_overlay.py:313): the damage is the world's, the repair is a rename, and the campaign layer still shadows it.
  • Nested lock acquisition now exists. promote_image holds {name, avatar} and calls image_path, which can enter the heal and acquire {promote-tmp, avatar, gallery_N}. No cycle: every set contains avatar and each caller sorts its whole set — reasoned out at backend/src/grimoire/store/assets.py:98-110.
  • Bounded retries, unbounded progress. backend/src/grimoire/store/assets.py:163 — the budget is spent only on lost races, so a directory with many temps is fully repaired in one scan while a hostile writer can't spin the loop.
Flow-level risk worth a reviewer's attention. The heal fires on the read path, so it runs under whatever concurrency the read path has — including many simultaneous requests for the same missing avatar. That is safe here (all healers serialize on the promote-tmp and avatar locks, and a loser observes stray.exists() == False and re-decides), but it means a filesystem that permanently refuses the rename gets one failed attempt per read forever. The failure is swallowed by design (backend/src/grimoire/store/assets.py:226-227) and nothing reports it.

Invariant impact

  • Strengthened — "the avatar slot always resolves". Previously held only outside promotion's window; now holds always. This is the issue's core ask.
  • Strengthened — "one file per logical image". Both publishes clean their stale sibling; backend/tests/test_assets_store.py:298 pins that a cross-extension swap leaves no phantom.
  • Weakened — "reads don't mutate the store". Two read entry points now rename files. No caller depended on read purity (verified: no read-only-root callers of image_path/list_images exist), and failure is swallowed rather than propagated, but the invariant is genuinely gone and future code must not assume it.
  • Weakened, narrowly — "a swap loses nothing". A crash between the two publishes loses the demoted image in the same-extension case. Traded knowingly against the avatar hole.
  • Now assumed in one more place — "promote-tmp is not a user image". Previously an implicit consequence of the old rename target; now load-bearing for _heal_stranded_promotion and enforced in _safe_name. Enforcement only applies going forward, which is exactly the residual risk the docstring records.
  • Unchanged and still relied upon — put_image's write-before-clean ordering (from #233). The new swap's crash-safety is entirely borrowed from it: if someone ever reorders put_image, promotion silently loses its guarantee. Worth a comment there pointing back, though the coupling is at least stated in the promotion docstring (backend/src/grimoire/store/assets.py:399-402).

Test quality — where the coverage actually is, and isn't

No coverage artifact in the repo, so this is read from the tests themselves, not measured.

  • strong Crash windows: parametrized over every cut point × same/cross extension (backend/tests/test_assets_store.py:275). The fault injector hooks two different mechanisms, so it doesn't encode the implementation it was written for.
  • strong Concurrency: real threads for promotion-vs-promotion and promotion-vs-upload, asserting the permutation invariant and no deadlock (backend/tests/test_assets_store.py:517, :551).
  • strong Recovery: adopt-as-avatar, gallery fallback, mtime tie-break, slot-taken re-decision, retry budget, case-variant slot, failed rename, healthy-directory no-op.
  • gap No test drives recovery concurrently with an upload using real threads — the slot race is covered by a deterministic monkeypatched simulation (backend/tests/test_assets_store.py:424), which pins the re-decision logic but not the real interleaving.
  • gap The inner windows of atomic.write_bytes (failed replace, leftover temp) are not exercised through promotion; they're covered in backend/tests/test_atomic.py, which the test docstring now cites by name.
  • gap Nothing tests the nested promote_image → image_path → heal path, where a promotion in a damaged directory adopts a stranded temp as the avatar and then immediately swaps it. Reasoned safe (reentrant locks, sorted sets); unverified by test.

Verdict — mergeable; the must-fix list is empty

The change closes the issue's actual failure (a promotion that leaves no avatar and an unreachable file), does it by removing the mechanism rather than adding recovery machinery around it, and repairs stores already damaged. Test quality is above this repo's norm — the fault injector and the "promotion only permutes the images" invariant are the right abstractions. What follows is discretionary.

Should-fix

  1. Point put_image back at its dependant. backend/src/grimoire/store/assets.py:325 — its write-before-clean ordering is now load-bearing for promotion's crash-safety, and nothing at that site says so. One comment prevents a future reorder from silently breaking promote_image.
  2. Decide, explicitly, that a permanently failing heal stays silent. backend/src/grimoire/store/assets.py:226-227 — on a read-only store this retries and fails on every read forever with no record. Swallowing is right for the read path; a one-time log would still be cheap.

Nits

  1. backend/src/grimoire/store/assets.py:448 — the trailing clear_focus is redundant: put_image already clears focus whenever the name is the avatar, and that call always precedes it on the success path. Harmless defence, or dead weight, depending on taste.
  2. _HEAL_RETRIES = 8 (backend/src/grimoire/store/assets.py:163) is unexplained as a number — the comment justifies the semantics (races, not repairs) but not the magnitude.

Explicitly out of scope, with reasons in the code

  • _image_lock's exact-string keying leaves case-variant names unserialized on case-insensitive filesystems — verified pre-existing at the base commit, affects put_image/delete_image equally, and closing it means re-keying #233's design.
  • Reader-visible atomicity of the two-slot swap: would require locking the read path, a different change to a documented stance.
