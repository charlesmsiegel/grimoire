Serialize every scene mutation on the campaign lock (#254)

base origin/main @ 48dc925d → 7c50fc9d · +297/−15 · generated 2026-07-28

Scene transcripts stop losing messages under concurrency

Before this change, every mutator in backend/src/grimoire/store/scenes.py read a scene file, changed it in memory, and wrote the whole thing back — with nothing serializing the sequence. Two writers that overlapped both read v0; the second publish silently erased the first one's message. After it, all 17 public mutators run under locks.campaign_lock(cid) with the read inside the lock, via a new @_serialized decorator at backend/src/grimoire/store/scenes.py:115 (18 applications, counting two private inners).

The user-visible consequence is narrow but severe: a player typing while a model reply is being persisted could lose either message, in the one data store in this app that cannot be regenerated. No API, schema, or on-disk format changes — the transcript file is byte-identical to what the old code would have produced in the uncontended case.

One flow changes: the chat turn

The runtime path this diff alters is a player message racing the persistence of a model reply — the ticket's own scenario. Nothing else about the turn moves: the LLM call, the streaming frames, the proposal handoff and the on-disk format are untouched. What changes is where the lock boundary sits.

Before — the lost update

Both writes are complete and atomic (#233). The loss is invisible precisely because nothing is corrupt.

After — serialized on the campaign

    participant M as Reply thread
    participant L as campaign_lock(cid)
    participant F as scene.md
    M->>L: acquire
    U-->>L: acquire (blocks)
    M->>F: read v0
    M->>F: write v1

    L-->>U: granted

The read moves inside the lock — that is the load-bearing part. Serializing only the write would have both threads publish the same stale body.

What moved

  • New lock boundary around every scene mutation — backend/src/grimoire/store/scenes.py:115-152. Acquired per call, released on every path including exceptions (a with block), so a raised SceneNotFound or a failed os.replace cannot strand it.
  • Nested acquisitions are now routine, and were already routine. proposals.commit_narration persists a reply through a callback while holding this same lock (backend/src/grimoire/store/proposals.py:27-35), and the route's projection sequence wraps a read-then-append idempotency check in it (backend/src/grimoire/routes.py:3817, appending at backend/src/grimoire/routes.py:3834). Reentrancy is what keeps those working, not an accident.
  • Calendar resolution moved out of the critical section — backend/src/grimoire/store/scenes.py:194-214 and backend/src/grimoire/store/scenes.py:837-850. That path imports and executes user-authored plugin files from <GRIMOIRE_HOME>/calendars/, whose duration this codebase does not control.
  • Nothing else entered the critical section. No LLM call is held across the lock: _chat_stream and _continuation_stream take it inside finalize, after the stream completes (backend/src/grimoire/routes.py:2539-2543 and backend/src/grimoire/routes.py:2568-2572).
Contention is bounded by design, not by luck. The lock is campaign-wide, so a scene write now also excludes sheet writes, audit baselines and proposal transitions for that campaign — but every one of those critical sections is a file read plus a file write. The one actor that holds the lock for a long span is module publication, which holds every campaign's lock across a pack swap (backend/src/grimoire/store/module_edit.py:504-511); blocking chat appends during that swap is the intended exclusion, not a regression.

Are the tests falsifiable?

Concurrency tests are the easiest kind to write so they can never fail. These are not:

  • _widen_the_write_window (backend/tests/test_scene_store.py:982-996) patches parse_frontmatter to sleep 50 ms after every scene read, so the pre-fix code loses a message on every run rather than one in a thousand. All three lost-update tests fail on main.
  • _lock_is_free (backend/tests/test_locks_store.py:129-150) probes from a second thread on purpose — the lock is an RLock, so asking from the holding thread would always answer "free" and the test would pass vacuously. It also asserts the probe finished rather than reading an empty result as "held".
  • The calendar guard watches get_provider, normalize and friendly (backend/tests/test_locks_store.py:164-175) — covering only the import would let the other two drift back inside the lock unnoticed — and asserts the watcher fired at all before asserting on its results.
  • scenes joins the parametrized no-second-registry guard at backend/tests/test_locks_store.py:195, so a future refactor that hands scenes a private lock fails a test instead of silently reopening the race.
