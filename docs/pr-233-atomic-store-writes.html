grimoire #233 — Atomic store writes — Review

Route every store record write through one crash-safe helper

base main @ 39743b1a → 39a016b4 · +1057/−224 · 46 files · generated 2026-07-28

What this change does

Every Markdown and JSON record in the store was rewritten with a plain Path.write_text — truncate, then write. This routes all ~100 write sites through one crash-safe helper, store/atomic.py, so a failure between those two steps can no longer leave a truncated record.

The motivating case is scenes.append_message: it read the whole transcript, appended one block, and rewrote the file on every single message. A scene transcript is the one piece of user data in this app that cannot be regenerated — not from the chronicle, not from the model.

The mechanism

backend/src/grimoire/store/atomic.py:88 — tempfile_for is the single primitive; write_text and write_bytes are thin wrappers. The sequence: mkstemp beside the target → close the descriptor → caller writes → reopen O_RDWR and fsync → carry the target's mode → os.replace.

The guarantee is atomicity, not durability. A reader sees the whole old version or the whole new one, never a partial one. It is not power-loss durability: CPython's os.replace uses MoveFileExW without MOVEFILE_WRITE_THROUGH, and the parent directory is not fsynced on POSIX, so the rename itself may not survive a power cut. The first draft of the design claimed more than this; the claim was narrowed after review. Stated at backend/src/grimoire/store/atomic.py:1.

Three fixes that are not just mechanical

Most of the diff is a one-line substitution repeated ~100 times. These three are not, and are where review attention belongs:

  • File mode preservation (backend/src/grimoire/store/atomic.py:67). mkstemp creates 0600. Without an explicit chmod, the first atomic write would silently narrow every group/world-readable record to owner-only on Linux, macOS, and the Android build. This is a bug the retrofit would have introduced, not one it fixes.
  • Narrowed retry (backend/src/grimoire/store/atomic.py:61). Retrying every PermissionError would delay permanent failures (read-only target, a directory ACL denying child-create) and widen the pre-existing unlocked read-modify-write race: writer A fails its replace, sleeps, then lands a stale temp on top of writer B's completed update. Restricted to winerror 32/33 with ~50 ms total backoff.
  • An ordering bug in assets.put_image (backend/src/grimoire/store/assets.py:124). It unlinked prior-extension files before writing the new one, so any failure between lost the image outright — atomicity cannot fix a delete-first ordering. Reordered to write first.

A read path changed too

Reordering put_image alone was insufficient. image_path returned sorted(d.glob(f"{name}.*"))[0] — the first alphabetically. Writing avatar.webp over an existing avatar.png leaves both present for a moment, and the sort hands back the stale .png. So backend/src/grimoire/store/assets.py:54 now breaks the tie by newest st_mtime_ns, which also makes a failed sibling-unlink self-healing rather than permanently wrong.

This is the one intentional change to existing read semantics, and it is slightly outside the issue's literal scope. It was an explicit decision, not drift.

Found while building the report

The blast-radius pass surfaced routes.py:2018 writing a campaign's stored climate default with a plain write_text — a store record written from outside the store package, which the original store/-only guard did not scan. Fixed, and the guard was widened to the whole grimoire package. The same sweep caught backend/scripts/ingest_scene.py:41.

What did not change

  • No locking was added. scenes.append_message still has no per-scene lock, so two concurrent appenders can still lose a message. Pre-existing, deliberately out of scope, and the retry was constrained specifically so this change does not widen it.
  • Multi-file atomicity. characters.write_card still writes a card and a meta file separately; a crash between them still leaves the pair inconsistent. Each file is individually valid, which is what this buys.
  • assets.promote_image (backend/src/grimoire/store/assets.py:144) — the avatar swap is a three-rename sequence that can strand a temp and leave the avatar missing. A recovery-protocol problem, not a torn write. Explicitly scoped out.
  • module_edit's zip extraction stays a bare write_bytes, marked # atomic-ok: — it writes into an unpublished staging tree published by a single rename, and per-member fsync would only slow large imports.

What moved in the write path

Before: truncate, then write

The window between truncation and the final byte is the bug. Any failure inside it — crash, full disk, sync-client conflict — leaves the record truncated, and a concurrent reader can observe the half-written file directly. 

sequenceDiagram
    participant C as Caller (append_message)
    participant FS as Filesystem
    participant R as Concurrent reader

    C->>FS: read_text(scene.md)
    C->>C: append one block
    C->>FS: write_text(...) — truncates scene.md
    Note over FS: scene.md is now EMPTY
    R->>FS: read_text(scene.md)
    FS-->>R: truncated / partial transcript
    C->>FS: ...bytes land
    Note over FS: a crash anywhere here loses the transcript

After: publish by rename

The live pathname is never truncated. It changes from the old inode to the new one in a single os.replace, so a reader sees one whole version or the other. 

sequenceDiagram
    participant C as Caller (append_message)
    participant A as store.atomic
    participant FS as Filesystem
    participant R as Concurrent reader

    C->>FS: read_text(scene.md)
    C->>C: append one block
    C->>A: write_text(scene.md, body)
    A->>FS: mkstemp(dir=scene.md's own dir)
    A->>FS: close fd
    A->>FS: write bytes to .scene.md..tmp
    R->>FS: read_text(scene.md)
    FS-->>R: previous transcript, complete
    A->>FS: reopen O_RDWR, fsync
    A->>FS: chmod to target's mode
    A->>FS: os.replace(tmp, scene.md)
    Note over FS: pathname flips atomically
    R->>FS: read_text(scene.md)
    FS-->>R: new transcript, complete
Why the descriptor is closed before yielding. mkstemp returns an open fd, but thumbs.py hands the path to PIL's im.save() and never holds the bytes. So tempfile_for closes the fd immediately and yields only a path (backend/src/grimoire/store/atomic.py:102): nothing of ours is holding a handle that could block the replace on Windows, and there is no sharing-mode negotiation with PIL. The fsync then needs its own reopen — O_RDWR, because Windows FlushFileBuffers requires write access.

The failure path

On any exception the temp is unlinked and the exception re-raised, leaving the previous record byte-for-byte intact. The unlink is best-effort: the same scanner or sync client that can block a replace can briefly block a delete, and failing to clean up litter must not mask the real error. 

flowchart TD
    A[mkstemp beside target] --> B[caller writes to temp]
    B -->|exception| X[best-effort unlink temp]
    X --> Y[re-raise; record untouched]
    B -->|clean| C[reopen O_RDWR + fsync]
    C --> D[chmod from target]
    D --> E{os.replace}
    E -->|winerror 32/33| F[sleep, retry: ~50ms total]
    F --> E
    E -->|other PermissionError| Y2[raise immediately]
    E -->|ok| G[published]

The retry's blast radius, stated honestly

The retry is the only place this change can make concurrency worse, so it is deliberately narrow. Permanent causes — a read-only target, a directory ACL that permits rewriting a file but denies creating or deleting children — raise on the first attempt (backend/src/grimoire/store/atomic.py:61). Only ERROR_SHARING_VIOLATION and ERROR_LOCK_VIOLATION retry, because only those are transient.

The reason this matters: append_message is an unlocked read-modify-write. Every millisecond spent retrying is a millisecond in which another writer can complete, after which the retry would publish stale content over it. Capping total backoff at ~50 ms bounds that window; it does not eliminate the pre-existing race, which is out of scope and filed as a follow-up.

1. The image_path mtime tie-break is scope expansion. backend/src/grimoire/store/assets.py:54 changes what an existing read returns. It is necessary — reordering put_image without it introduces a stale-read window that the old delete-first ordering did not have — but it is a semantic change to a function this issue never mentioned. 2. sheets.seed now reads whole files into memory. backend/src/grimoire/store/sheets.py:536 replaced shutil.copy2 with atomic.write_bytes(dst, p.read_bytes()). Correct, and sheet JSON is small — but it is a read-all-then-write where a streaming copy used to be, and it drops copy2's metadata preservation. Fine for these files; would not be fine for large binaries.

Invariant impact

  • Strengthened: "a store record on disk is always a complete record." Previously untrue for ~100 write sites; now enforced everywhere and guarded against regression.
  • Unchanged: "concurrent writers to one record serialize." Still only true where a lock exists (rolls, proposals, audit, sheets). rolls.py's docstring previously credited the temp-file pattern for this; corrected at backend/src/grimoire/store/rolls.py:11 to credit the lock.
  • Newly possible failure: os.replace can raise PermissionError where an in-place rewrite would have succeeded — a concurrent reader on Windows, or a directory ACL permitting file-write but not child-create. Deliberate trade: a rare surfaced error instead of a silent truncation.
  • New litter: a hard power loss can orphan a .tmp. Invisible to the glob("*.md") listers, but store/assets.py:64, store/overlay.py:332 and store/campaigns.py:222 use bare iterdir()/rglob("*") and would see one — overlay's emptiness check would read a stray temp as non-empty. Documented, not fixed.
