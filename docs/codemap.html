What grimoire is

A local-first, single-user toolkit for running solo tabletop RPG campaigns with an LLM as game master. A FastAPI backend and a React/Vite frontend sit over a filesystem-as-database: every world, campaign, character and scene transcript is a Markdown or JSON file under the resolved data root, deliberately outside the repository. That root is GRIMOIRE_HOME if set, else the user-chosen path in the bootstrap pointer, else ~/.grimoire (backend/src/grimoire/store/paths.py:42-50) — so ~/.grimoire is the desktop default, not the location. Android and any relocated store resolve elsewhere; backup and migration work must follow home(), not the literal path. The same backend is packaged verbatim into an Android WebView shell, so no backend code may assume a repo checkout or a desktop home directory.

Architecturally it is a layered monolith with an unusually disciplined persistence layer. The interesting engineering is not the HTTP surface — it is the four mechanisms protecting a store that holds the one asset the app cannot regenerate: a scene transcript. Those are crash-safe writes, per-campaign locking, copy-on-write campaign-over-world resolution, and an idle-bounded streaming LLM facade.

Key decisions & constraints

Filesystem as the database

No SQL, no ORM. Records are Markdown with frontmatter plus JSON sidecars (backend/src/grimoire/store/__init__.py:1). This buys human-editable, sync-friendly, diffable data — and costs the app every guarantee a database would have given for free, which is precisely what backend/src/grimoire/store/atomic.py, backend/src/grimoire/store/locks.py and backend/src/grimoire/store/overlay.py exist to rebuild by hand.

The LLM gateway is kept store-free

backend/src/grimoire/llm.py:132-142 takes its timeout as a number or a callable, specifically so the gateway never imports the store. Deliberately acyclic, and it also lets a Configuration-page change take effect without a restart.

Android forces portability constraints

All filesystem access goes through store.paths, prompts.templates_dir() and main.dist_dir(), each env-overridable (backend/src/grimoire/prompts.py:17-26, backend/src/grimoire/main.py:22-30). Base dependencies must stay Android-installable, and pydantic usage stays v1/v2-agnostic.

Prompts are data, not code

Every authored instruction sent to a model lives in templates/ and renders through a 36-line module (backend/src/grimoire/prompts.py) with StrictUndefined and Jinja auto-reload. Prompts are editable live — which is exactly why the eval suite exists. Not everything in the request comes from a template, though: build_messages appends the persisted conversation history verbatim (backend/src/grimoire/store/context.py:652), and build_director_messages appends the caller's note as the final user message (backend/src/grimoire/store/context.py:668). And the provider adapters transform the request again on the way out: backend/src/grimoire/claude_agent.py:24-29 flattens every turn into a [role] transcript and appends an [assistant] cue, while backend/src/grimoire/openai_compatible.py:54-80 folds system text into user turns. Auditing what a model actually sees — for behaviour or for privacy — means reading templates/, the two context-builder additions, and the adapter for the selected provider.

Evaluation

The project treats prompt behaviour as testable. evals/ defines four pass/fail hypotheses — scene-length budget, roll-fence protocol, the absorb contract, and owned-lore containment — scored by deterministic graders (evals/graders.py) against checked-in recordings in evals/recordings/.

The replay suite is offline and runs inside pytest. backend/tests/test_eval_graders.py proves each individual check fires, and each recorded counterexample (evals/recordings/roll-fence.unclosed.md, evals/recordings/absorb.truncated.json) makes its case fail — so the graders cannot silently rot into always-pass. Whether a model still obeys a reworded instruction is only answered by the opt-in evals/run.py --live.

Seams

The user's turn is durable before the model is ever called. backend/src/grimoire/routes/scenes.py:143 appends the user message, and only then does line 144 build the context. So if context assembly or the provider fails, the transcript already contains the player's turn with no reply — the assistant finalizer is not the only mutator on this path. Macros are deliberately expanded once at persist time (backend/src/grimoire/routes/scenes.py:139-142) so a player's {{roll:1d20}} cannot re-roll on every later context build.
On the director-note branch the input is ephemeral — the reply is not. A pcless scene or an empty send takes backend/src/grimoire/routes/scenes.py:128-134, where the note steers one generation and is never written to the transcript. But that branch still returns _chat_stream (backend/src/grimoire/routes/scenes.py:134), which is the ordinary persisted-turn strategy: it watches roll fences and persists the model's narration through _persist_reply exactly as a normal turn does (backend/src/grimoire/routes/streaming.py:149-172). backend/tests/test_routes.py:3724-3726 pins both halves — stored messages exist and are all assistant-role, and the note text appears in none of them.
Ordering is the guarantee, not atomicity. backend/src/grimoire/routes/streaming.py:125-141 is explicit that finalize is not transactional: the proposal is written under one lock, the lock is released, then _persist_reply re-takes it. Contention on that second acquisition leaves a proposal on disk with no narration — the sanctioned direction. The invariant actually held is narration is never persisted without its proposal, never the reverse.
The idle bound is deliberately not a total bound. backend/src/grimoire/llm.py:84-104 bounds the gap between deltas, so a slow-but-progressing generation is never cut mid-prose. Empty chunks are provider heartbeats: they reset the wait and are dropped rather than forwarded (backend/src/grimoire/llm.py:118). A total-duration ceiling exists only where a caller imposes one.
Two disclosed crash windows. backend/src/grimoire/routes/streaming.py:5-24 documents both — a crash at the initial fence loses the last narration beat but leaves an adjudicable proposal; a crash at a follow-up fence loses the follow-up check. Both are bounded and non-corrupting. Full cross-file journaling was rejected as disproportionate for a local single-user store, which is a defensible call, but it is an accepted risk rather than an absent one.
A partial reply can be lost with no indication that it was lost. At backend/src/grimoire/routes/streaming.py:101-108, StoreBusy raised while persisting a partial reply is swallowed — the response has already begun streaming, so the global 409 handler cannot reach it. An error frame does follow, but it carries only the original LLM failure: backend/src/grimoire/routes/streaming.py:109 emits exc.detail and exc.kind from the LLMError, with nothing about the failed save. So the user learns the generation failed and not that the text they watched stream is gone. The code's own comment — "the frame below still tells the user why" — is true of the LLM error and overstates what the frame conveys about persistence.
Blocking work is pushed off the event loop on purpose. backend/src/grimoire/routes/streaming.py:111-124 runs finalize in a threadpool because its cross-process lock retry can sleep up to the lock timeout; inline, that would freeze every unrelated request on the backend. Note the list(...) — materializing inside the worker so a lazy generator body cannot leak StoreBusy past the handler.

Seams

The lock ordering is documented in exactly one place. backend/src/grimoire/store/locks.py:1-60 states the hierarchy: module-edit lock → campaign locks in sorted cid order → audit baseline lock / rolls lock. hold_all (backend/src/grimoire/store/locks.py:265) enforces the sort, so the two multi-campaign holders cannot deadlock against each other. The docstring notes they previously agreed only by accident.
The lock domain is a hand-maintained list, and it has been wrong before. backend/src/grimoire/store/locks.py:1-14 says it outright: a campaign-scoped mutator that keeps a private registry is invisible to the domain and silently outside the exclusion — which is what happened to rolls until it joined. Nothing mechanically enforces membership; the guarantee rests on this docstring being read.
The expensive work happens outside the campaign locks. backend/src/grimoire/store/module_edit.py:564-585 copies, mutates, loads and validates the staged pack, then returns early on validation errors or a valid dry run, before _campaign_locks() is entered at backend/src/grimoire/store/module_edit.py:586. Note the two early exits differ: a pack with errors returns ok=false, while a valid dry run returns a successful preview (ok=true) via backend/src/grimoire/store/module_edit.py:583-585. Neither takes a campaign lock — but staging is not unprotected: the module-edit lock _M is held across the whole function (backend/src/grimoire/store/module_edit.py:564).
Migration runs inside the lock, before the journal is cleared. backend/src/grimoire/store/module_edit.py:599-600 runs _run_migration and only then unlinks the journal, still holding every campaign lock. So the every-campaign hold covers swap plus migration, not swap alone — and a crash between them is exactly what recover() replays, which is why the journal records the migration alongside the nonce (backend/src/grimoire/store/module_edit.py:592-594).
Locks protect one machine, not one store — and not every mutation on that machine. Both locks are OS file locks as well as in-process ones, so actors on one machine under one OS user are excluded (backend/src/grimoire/store/module_edit.py:4-18). Two devices sharing a synced folder are not, and cannot be by any filesystem lock. The docstring also lists what the lock does not cover on a single machine (backend/src/grimoire/store/locks.py:64-68) — see the Invariants tab. Since the Configuration page actively encourages pointing the store at a synced folder, this is the gap most likely to be met in real use.
Startup degrades to serving, not failing. backend/src/grimoire/main.py:33-55 guards each startup step separately and logs at WARNING on contention, because all three steps are idempotent and re-run later. Startup is also the one place the global 409 handler cannot reach.

Seams

Nothing is written until a human approves it. The extraction pass stages dossier and audit edits rather than applying them (backend/src/grimoire/routes/scenes.py:435-441), so a partial or malformed model response costs a token and nothing else. This is a structural improvement over a single write-as-you-go pass.
One lock hold covers all four writes, and the reason is written down. backend/src/grimoire/routes/scenes.py:471-483 explains that per-write locking would return 409 after the chronicle record and timeline events were already durable — and the retry that 409 invites would append the timeline events twice. Holding across the sequence means a busy response arrives before the first write, so retrying is safe.
One write lands before the ledger reservation, deliberately. backend/src/grimoire/routes/scenes.py:522-524 writes the chronicle record, and only then does backend/src/grimoire/routes/scenes.py:528 reserve the token. The comment in between explains the choice: the chronicle entry is keyed by scene id and merely overwrites, so replaying it is harmless, while every append below the reservation is not. The consequence is a real if benign window — a crash between the two leaves a chronicle write with no ledger entry, and the next attempt redoes it. There is a second window at the far end: backend/src/grimoire/routes/scenes.py:533 marks the token done only after apply_edits, so a crash between them leaves every approved edit applied but the token reserved-and-incomplete, and the retry gets commit_incomplete rather than a replay of the result.
Non-idempotency is handled by a commit ledger, not by hoping. Absorb is explicitly not idempotent — lore edits append and plot movements add a beat (backend/src/grimoire/routes/scenes.py:413-416). A commit_token minted with the staged result (backend/src/grimoire/routes/scenes.py:449) is reserved before the first non-idempotent write (backend/src/grimoire/routes/scenes.py:526-528), and the ledger distinguishes four cases: clean replay, scene mismatch, body-changed-after-commit, and reserved-but-never-completed — each with its own 409 and a message telling the user what to do (backend/src/grimoire/routes/scenes.py:489-521).
Widest blast radius in the app. backend/src/grimoire/store/absorb.py:11-14 imports eighteen store modules — appearances, campaigns, characters, chronicle, dossiers, entities, plot, relationships, sheets and more. One malformed model response is parsed into edits across all of them, which is why the absorb eval case checks that every required section is present and that the result materializes into applicable edits (evals/recordings/absorb.truncated.json is the counterexample that must fail).
The staged phases never raise, but they do not fail silently either. Dossier staging and the mechanics audit each own their failure boundary rather than aborting the absorb (backend/src/grimoire/routes/scenes.py:435-441) — and both report what happened as explicit status rather than as an absent result. _stage_dossiers returns failed, degraded or ok with a reason and a per-NPC breakdown (backend/src/grimoire/routes/scenes.py:380-388), and _run_audit returns mechanics.status of failed or skipped with a reason and the sheets it dropped (backend/src/grimoire/routes/scenes.py:273-304). A failed phase is therefore distinguishable in the review panel from a phase that genuinely had nothing to change — which is the point of the design.

But the file graph is not acyclic — the store SCC is real coupling. A concrete back-edge: backend/src/grimoire/store/modules.py:18 imports module_display at module load, while backend/src/grimoire/store/module_display.py:65 and :98 import back from modules inside functions, each annotated "deferred: modules imports us". That deferral is the workaround that makes the pair importable, and it is a marker of genuine mutual dependency rather than of a clean layering.
The store's internal "cycle" is the package-__init__ aggregation pattern. backend/src/grimoire/store/__init__.py:6-13 imports all 60-odd submodules, and each submodule imports siblings via from . import ... — which re-enters the partially-initialized package. Python resolves this because submodule binding does not require __init__ to have finished. It works, and it gives callers one flat store.x namespace (fan-in 153, the highest in the codebase). The cost is real but narrow: import order inside backend/src/grimoire/store/__init__.py is load-bearing, and a new module-level statement that reads a name defined later in __init__ would fail at import time rather than at its call site.

Data ownership

Every user record lives under the data root, never in the repo. Two kinds of persistent state deliberately sit outside it, which matters for backup, cleanup and any data-ownership audit:

  • the bootstrap pointer ~/.grimoire.json, which cannot live inside the directory it names (backend/src/grimoire/store/paths.py:16-38);
  • process lock files, in ~/.local/state/grimoire/locks or the Windows AppData/Local equivalent (backend/src/grimoire/store/proclock.py:90-97) — state that must persist and must not be swept, since a cleaner unlinking a held lock would split two processes onto different inodes with both believing they hold it.

Failure handling

No bare except: anywhere in backend/src — but "narrow" is only half the story. Two distinct patterns coexist, and conflating them would misread the failure boundaries:
  • Narrow named catches, where the handler names the exact failure it expects: backend/src/grimoire/store/atomic.py:114 and :187 (cleanup paths), backend/src/grimoire/store/fence.py:127 (a malformed fence body falls back rather than killing a turn), backend/src/grimoire/store/suggest.py:104.
  • Deliberate broad containment, where except Exception is used on purpose to stop one corrupt record from taking down a whole build. These are numerous — backend/src/grimoire/store/audit.py:101, backend/src/grimoire/store/absorb.py:699, backend/src/grimoire/store/context.py:364 and others — and every one carries a noqa: BLE001 with a stated reason ("garbled state: omit, don't crash the context build"; "never fail the caller").
The second pattern is a design decision, not sloppiness: a single unreadable JSON file degrades one section of a prompt instead of failing the turn. But it does mean a systematically corrupt record can be silently omitted from every prompt with nothing logged, and the backend/src/grimoire/store/context.py instances sit directly on the play path.
Errors are handled far from their cause by design. Two app-level handlers (backend/src/grimoire/main.py:71-81) convert HTTPException and StoreBusy centrally, which is why ~35 lock call sites carry no error handling. The one place this cannot reach is a response that has already started streaming — handled explicitly at backend/src/grimoire/routes/streaming.py:96-110 and :125-141.
One deliberate silent loss. backend/src/grimoire/routes/streaming.py:101-108 swallows StoreBusy while persisting a partial reply after an LLM failure. An error frame follows, but it reports only the original LLM failure — nothing says the save failed. Correct given the constraint, but it is a silent data-loss path reachable by ordinary contention.
Two nominal read paths mutate the filesystem. backend/src/grimoire/store/assets.py:251 (image_path) and backend/src/grimoire/store/assets.py:275 (list_images) both call _heal_stranded_promotion (backend/src/grimoire/store/assets.py:173), which renames files to rescue an avatar stranded by a pre-#253 crash. The recovery is well-argued — the alternative is serving a 404 over a file that exists — but a GET that renames on disk is a surprise for any caller reasoning about read/write separation, and it is not the only read that mutates. Two more are reachable from ordinary GETs on a fresh store: backend/src/grimoire/store/config.py:53 writes a default config.md when none exists, and backend/src/grimoire/store/llm_connections.py:191 (ensure_migrated) can create the connections directory, seed records and drop a .migrated marker. Worth knowing before treating any GET as safe for a backup or audit snapshot.
Custom-calendar plugin failures are silent. backend/src/grimoire/store/calendars/plugins.py:47 catches bare Exception around exec_module and only un-registers the half-imported module. A user's homebrew calendar with a syntax error simply never appears, with no log line and no surfaced error. Since these plugins live outside the repo by design, the user has no other channel telling them why their calendar vanished.
Timeouts are present and bounded; retries are not unbounded. The LLM idle bound defaults to 120s (backend/src/grimoire/llm.py:19) and is overridable live from config. Lock acquisition raises StoreBusy after 30s (backend/src/grimoire/store/locks.py:89), and hold_all uses one deadline across N locks rather than N × timeout, avoiding a convoy (backend/src/grimoire/store/locks.py:278-286). Provider cleanup has its own 5s grace before abandonment (backend/src/grimoire/llm.py:24).

Concurrency

Genuinely concurrent, on three axes, and the code treats all three seriously:

  • Async event loop — SSE streaming. Blocking store work is pushed to a threadpool precisely because lock waits would otherwise freeze every unrelated request (backend/src/grimoire/routes/streaming.py:111-124).
  • In-process threads — re-entrant locks let higher-level mutators compose lower-level ones (backend/src/grimoire/store/locks.py:238).
  • Cross-process — OS file locks added for a second backend against a synced store (backend/src/grimoire/store/module_edit.py:4-18).
Abandonment over blocking, deliberately. backend/src/grimoire/llm.py:50-71 refuses to await a cancellation it requested, because an upstream that ignores CancelledError would recreate the indefinitely-held request the module exists to prevent. The comment's own summary — "a detached task is a leak we can live with; a wedged request is not" — is the right trade for this app, but it does mean a pathological provider can strand tasks for the life of the process.

Risk ranking

1 · No CI configuration exists in the repository. There is no .github/workflows/. pytest, vitest, tsc -b, scripts/verify_templates.py and the eval suite all run only when a human remembers. This is the single highest-leverage gap: the project has built better-than-average guard harnesses and then left their execution to discipline. templates/ edits are the sharpest case — Jinja auto-reload means a bad edit takes effect live, with no restart and no code change.
2 · Synced-folder concurrency is unprotectable and actively recommended. CLAUDE.md suggests pointing the store at a synced folder to share a library across devices; backend/src/grimoire/store/module_edit.py:4-18 states that two devices cannot be excluded by any filesystem lock. Conflict-copy resolution is left to OneDrive/Dropbox on their own schedule (backend/src/grimoire/store/atomic.py:20-21). Blast radius is an irreplaceable transcript.
3 · Four campaign mutators sit outside the lock domain right now, by the module's own admission. backend/src/grimoire/store/locks.py:64-68 names them: rename_campaign, set_campaign_response, touch and delete_campaign take no lock at all. Each is an unlocked read-modify-write on campaign metadata (backend/src/grimoire/store/campaigns.py:344-374), so two processes updating one campaign can silently overwrite each other, and a delete can race a concurrent mutation. Atomic replacement guarantees each write lands whole; it does not prevent a lost update. This is the same class of gap as the rolls omission recorded at backend/src/grimoire/store/locks.py:1-14, except these are current rather than historical — and because the list is prose, nothing stops the set from growing. A guard test in the style of backend/tests/test_overlay_guard.py would turn the codebase's most dangerous convention into an enforced one.
4 · backend/src/grimoire/store/module_edit.py concentrates the most branching in the app. 1,134 lines and 332 branches — the highest branch count in the codebase — carrying staging, validation, journaling, crash recovery and publication together. Its churn is comparatively low (19 commits in 24 months, seventh on the combined ranking), so this is complex-but-stable code rather than a churn hotspot; the risk is concentration, not volatility. It is also one of only two multi-campaign lock holders, so a defect there is a whole-store defect — the other is the world-module rebind route (backend/src/grimoire/routes/worlds.py:78-90), which gathers every campaign bound to a world and holds them together through hold_all (backend/src/grimoire/store/locks.py:44-46).
5 · Android portability rules are convention-only. The pydantic v1/v2-agnostic rule and the "no Path.home()" rule are documented in CLAUDE.md and honoured in current code, but no test or lint rule asserts either. A violation passes every check in the repository and surfaces as a broken APK build.

Closed since the previous atlas

Findings the last atlas raised that this one deliberately does not carry forward — recorded here because "the risk we flagged is fixed" is information a fresh atlas cannot otherwise express.

Locks were in-process only; they are now cross-process. The previous atlas's top risk was that threading.RLock protects nothing across processes while the product recommends a shared data directory. Both the campaign lock and the module-edit lock are now OS file locks as well (backend/src/grimoire/store/module_edit.py:4-18), and a StoreBusy handler converts contention into a 409 centrally (backend/src/grimoire/main.py:77-81). Partially closed: one machine under one OS user is now covered for the mutators inside the lock domain. Two devices over a synced folder still are not (risk #2), and four campaign mutators still take no lock at all (risk #3).
Absorb no longer commits early phases before later ones run. The previous atlas flagged absorb as a long, non-atomic, non-idempotent multi-phase write whose prose edits landed before the dossier and audit phases. Extraction now stages everything and writes nothing (backend/src/grimoire/routes/scenes.py:435-441); the commit is a separate reviewed call that holds one campaign lock across all four writes and is protected by a commit ledger (backend/src/grimoire/routes/scenes.py:471-528). Re-absorption is refused by default before a token is spent (backend/src/grimoire/routes/scenes.py:413-416).
Absorb failures now reach the user. apply_edits returns a failures list alongside applied (backend/src/grimoire/routes/scenes.py:532-533), and each ledger 409 carries a message naming the recovery step. The previous atlas's "no remediation path" finding is substantially addressed, though remediation is still "reload and edit the records directly" rather than a retry of the failed edit.
The old monolithic routes module stayed gone. Split into 14 route modules; nothing in backend/src/grimoire/routes/ now exceeds 661 lines, and the top hotspot has moved to the store.

Misleading and overloaded names

module means three different things. A Python module; a mechanics data pack (backend/src/grimoire/store/modules.py:1 — "a declarative data pack, JSON + markdown, no code plugins"); and a grouping node in this atlas's own dependency graph. The docstrings say "module pack" where precision matters, but symbol names do not: module_edit.recover() recovers a pack publication journal, and backend/src/grimoire/store/modules.py is a Python module about non-Python modules. This is the term most likely to mislead a newcomer reading backend/src/grimoire/store/module_edit.py cold.
lore is both a record kind and a whole subsystem. As a kind it is one of five in ENTITY_KINDS (backend/src/grimoire/store/entities.py:17), sitting alongside locations and items. As a subsystem, "world-info" is the SillyTavern-derived keyed-activation mechanism that decides which entries reach the prompt (backend/src/grimoire/store/context.py:25-42), and backend/src/grimoire/store/lorebook.py:1 translates world-info into entities. So three names — lore, world-info, lorebook — cover two concepts with a partial overlap. The owned-lore eval case is about the world-info containment rule, not about the lore kind.
store.home() does not return the user's home directory. It returns the grimoire data root — ~/.grimoire by default, but overridable by GRIMOIRE_HOME or the bootstrap pointer (backend/src/grimoire/store/paths.py:42-50). Since the Android portability rule is specifically "never assume a desktop ~", a function named home() that must not mean Path.home() is an unfortunate collision — and Path.home() genuinely does appear in the same file — at backend/src/grimoire/store/paths.py:13 for the default root and backend/src/grimoire/store/paths.py:23 for the bootstrap pointer.
sync.md is unrelated to folder syncing. It holds base hashes for materialized overlay records (backend/src/grimoire/store/overlay.py:14). The codebase separately discusses OneDrive/Dropbox "sync" as a concurrency hazard (backend/src/grimoire/store/atomic.py:20-21) and recommends a synced folder for sharing a library. Same word, two unrelated meanings, both load-bearing — worth a rename or at least a cross-reference.
Naming conventions otherwise hold across the tree. cid/sid for campaign and scene ids, *NotFound for lookup failures, _-prefixed helpers as module-private, and exception names that match their domains — CampaignNotFound, DiceError, WorldNotFound.
The store's exception re-export is not complete, so the import path still matters. backend/src/grimoire/store/__init__.py:14-33 re-exports the store's own record errors, so a caller catching CampaignNotFound or DiceError need not know the defining submodule. Two of the errors a caller is most likely to want are not in that block: StoreBusy stays under backend/src/grimoire/store/locks.py:92, and LLMError lives outside the store entirely in backend/src/grimoire/llm_errors.py. Both are deliberate — LLMError is kept out of the store to keep the LLM gateway's imports acyclic — but it means the convenience is partial, and "import it from store" is not a rule you can follow blindly.
