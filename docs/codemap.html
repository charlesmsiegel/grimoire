A local-first writing tool that happens to be an LLM client

grimoire is a single-user application for running long-form tabletop / roleplay campaigns with an LLM as the narrator. It is a layered monolith: a FastAPI backend (backend/src/grimoire, 300 routes) serving a React SPA (frontend/src) that the same process also hosts as static files.

The defining architectural choice is that there is no database. The system of record is a directory of Markdown and JSON files that lives outside the repository, rooted at ~/.grimoire and resolved by backend/src/grimoire/store/paths.py:47. Everything else follows from that: writes must be crash-safe by hand (backend/src/grimoire/store/atomic.py), concurrency must be serialized by hand (backend/src/grimoire/store/locks.py), and a campaign that inherits from a world needs copy-on-write resolution by hand (backend/src/grimoire/store/overlay.py).

The second defining choice is that the same backend ships three ways — a desktop dev server, a packaged local app, and an Android WebView shell that runs this exact Python under Chaquopy. That is why filesystem access and template lookup are funnelled through resolvers rather than repo-relative paths.

Key decisions and constraints

Files, not a database

Records are Markdown with frontmatter, readable and editable outside the app, and syncable by pointing home() at a synced folder. The cost is that atomicity, locking, and inheritance are all application code.

Android is a packaging target, not a port

android holds ~535 lines of Kotlin and packages backend/src verbatim. That constraint is why base dependencies must stay pure-Python, pydantic usage stays v1/v2-agnostic, and paths resolve through environment overrides rather than the checkout layout.

Prompts are data

All prompt text lives in templates and is rendered through backend/src/grimoire/prompts.py with StrictUndefined, so a template referencing a variable nobody passes fails loudly instead of rendering an empty string.

Architecture enforced by tests that read the AST

Nine guard tests (8,416 lines) parse the package's own source to hold rules the type system cannot: every write goes through atomic, every campaign mutator takes the lock, no overlay bypass, no cycles. See Invariants & Risks.

Evaluation

The repo has a real offline eval harness at evals/run.py, with evals/graders.py and evals/cases.py, that runs inside pytest: it renders the assembled prompts and asserts that the budget, reply-format and roll-protocol sections survive verbatim, and that the graders still score recorded output correctly. Whether a model obeys a reworded instruction is only answered by evals/run.py in its live mode, which is opt-in and makes real API calls. The Measurement document grades this in detail; the short version is that the harness measures prompt assembly well and model behaviour not at all offline, and is explicit about the difference.

Two caveats about the automated tabs on this page. The LLM Ops tab reports zero backend call sites: it recognizes vendor SDK method names, and grimoire calls OpenRouter over raw httpx in backend/src/grimoire/openrouter.py, so the real call sites are invisible to it. The Coverage tab reflects the frontend only — the backend has no coverage tooling configured.

Three flows carry almost all of the risk

A scene turn is the only flow that writes an artifact the system cannot regenerate — a transcript. Record resolution is the flow every read passes through. Store writes are the flow that decides whether a crash costs you a file. Everything else in 300 endpoints is CRUD over those three.

Seams

  • The player's post is written before the reply is possible. backend/src/grimoire/routes/streaming.py:430 documents the window and closes it with an undo_user_post callback — but only when the turn produced nothing. A partial reply deliberately keeps both halves.
  • Turn ownership is a process-local dict, not a lock. backend/src/grimoire/routes/streaming.py:72 hands out a token under the GIL; the abort path re-checks both the token and the transcript length (backend/src/grimoire/routes/streaming.py:79) because each catches a different intruder. The claim was moved inside the campaign lock after review found the gap.
  • The abort write runs during teardown. backend/src/grimoire/routes/streaming.py:83 shields the cancel scope, because inside a cancelled scope the next await would re-raise before the write could start. Its except Exception: pass is deliberate and argued in the docstring.
  • A roll fence is not crash-atomic across files. The module header discloses two bounded windows between the proposal record and the transcript, and records that full journaling was rejected as disproportionate. This is a stated accepted risk, not an oversight.
  • Sidecar failure is swallowed on purpose. backend/src/grimoire/routes/streaming.py:113 catches OSError from alternates.reconcile so a full disk cannot turn a landed generation into a reported failure that invites a duplicate retry.

Data ownership

Every record in the store has exactly one writer path. All writes funnel through backend/src/grimoire/store/atomic.py, and campaign-scoped state additionally serializes on campaign_lock(cid). Three declared exceptions, and one frozen backlog. backend/src/grimoire/store/locks.py:248 lists modules deliberately outside the domain with a stated reason each, and backend/src/grimoire/store/locks.py:298 holds UNREVIEWED — a backlog that the guard permits to shrink but not grow. That is an honest representation of partial work, but the entries in it are, by definition, campaign-scoped mutators nobody has yet confirmed are safe.
Multi-lock acquisition has exactly one legal form. backend/src/grimoire/store/locks.py:610 (hold_all) sorts the ids and applies a single deadline across all of them rather than LOCK_TIMEOUT per lock; backend/tests/test_lock_order_guard.py fails any other function whose shape could hold two. The comment records that two holders once acquired locks in different orders and wedged permanently.

  • bad The play screen is a layer unto itself. frontend/src/routes/CampaignView.tsx:251 opens a single function component that does not close until line 4236 — roughly 3,985 lines, 28 useState calls and 64 hook calls in one function.   • warn Route modules reach into store submodules directly. Cycles

There are none to explain. The dependency analysis found zero import cycles at every scope, with 1,510 of 1,510 first-party Python imports and 474 of 476 TypeScript imports resolved — so this is a measured result over a graph that was actually built, not an artifact of a sparse one. backend/tests/test_import_guard.py is what keeps it true, and it additionally forbids the subtler failure: a cross-package import inside store must bind a submodule (from ..campaigns import read), never a name, because binding a function by value silently defeats any test that patches it.

The invariants are unusually well enforced — by tests that read the source

Most codebases record their architectural rules in comments and hope. This one compiles nine of them into tests that parse the package's own AST and fail the build. That changes what is worth worrying about here: the backend's structural risks are largely closed, and the live risks sit in the frontend, in one deliberately-accepted crash window, and in a frozen backlog that the guards permit to exist.

Failure handling

  • Swallowing is deliberate and argued, not casual. The broad except Exception handlers I read each carry a docstring explaining what would be worse: backend/src/grimoire/store/campaigns/read.py:329 (a lost activity stamp must not fail a completed write), backend/src/grimoire/routes/streaming.py:83 (a failed rescue must not replace the teardown exception), backend/src/grimoire/store/climates/__init__.py (one bad preset must not abort the registry scan). The merged doctor reports still count 7 empty_catch and 5 swallowed_error findings; they are worth reading individually rather than as a class.
  • Fail-soft reads are inventoried. backend/src/grimoire/store/failsoft.py exists specifically to name the three readers where answering an unreadable file with an empty value would add content rather than remove it — deleted records resurrecting from the world. That is the right instinct applied to the right cases.
  • One handler covers ~35 lock sites. StoreBusy becomes a 409 at backend/src/grimoire/main.py:241 rather than being caught per call site.
  • Streams have a heartbeat but the facade owns the timeout. backend/src/grimoire/llm.py emits an SSE comment every 15s so a silent model is distinguishable from a dead connection, with a 120s default timeout for clients that inject none.

Concurrency

The app is a single local ASGI process with threads: sync route bodies get Starlette's thread pool, and blocking store work is pushed off the event loop explicitly (anyio.to_thread.run_sync in the activity middleware and the backup ticker at backend/src/grimoire/main.py:102). Mutual exclusion is per campaign, with a 30s timeout (backend/src/grimoire/store/locks.py:323) and a single-deadline multi-lock helper at backend/src/grimoire/store/locks.py:610. Cross-process races are explicitly out of scope in two documented places — the activity stamp's high-water compare and the atomic write's durability note — on the grounds that this is a local single-user app.

Naming drift worth knowing

  • cid is overloaded on the wire. Under /api/campaigns/ it is a campaign id; under /api/worlds/{wid}/characters/{cid} it is a character id. The activity middleware at backend/src/grimoire/main.py:162 has to match on the path prefix rather than the parameter name for exactly this reason, and says so.
  • "Absorb" means two things in the repo's history. The runtime verb above, and the offline transcript importer backend/scripts/ingest_scene.py. They are separate code paths; only the first is a model call made during play.
  • "Sync" is not cloud sync. sync.md holds base hashes for materialized records so a campaign copy can tell whether its world original moved underneath it.
