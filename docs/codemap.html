A single-user worldbuilding and roleplay tool whose database is a folder of Markdown

grimoire runs a FastAPI backend and a Vite/React frontend against a store that is literally files — Markdown-with-frontmatter for prose records, JSON for structured state, rooted wherever store.home() resolves (backend/src/grimoire/store/paths.py:42). No database, no ORM, no transactions. The upside is that a user's library is portable, greppable, and syncable; the cost is that every consistency property normally bought from a database has to be hand-built here, and the interesting findings in this atlas are almost all in that gap.

The domain has two axes. Worlds hold reusable canon (characters, locations, lore); campaigns instantiate a world and accumulate play — scenes, appearances, a chronicle, sheets. A campaign reads through an overlay: its own copy if it has one, the world's otherwise. That indirection is the single most load-bearing idea in the codebase, and also the one most often bypassed.

Decisions worth knowing before you judge the code

  • Files over a database, deliberately. Records are portable and diffable; the README encourages pointing the store at a synced folder to share a library across devices. That decision is the direct cause of risks #1 and #2 below — it is a trade, not an oversight, but the trade's cost is unpaid in places.
  • Campaigns copy-on-write from worlds. A campaign starts thin and materializes records only when edited. Anything that reads campaign data without going through overlay silently sees a partial world.
  • pydantic stays v1/v2-agnostic and base deps stay Android-installable. Per CLAUDE.md — the Android app packages backend/src verbatim via Chaquopy, so a compiled desktop-only dependency breaks a platform that has no CI here.
  • Test share is 48.9% of LOC and the suite is ~2,082 tests. This is a well-tested codebase by volume; the gaps below are concurrency and crash-recovery properties that tests of this shape cannot easily reach.

What this atlas cannot see

  • 219 Jinja templates are invisible to the dependency graph. 95 files were excluded as unrecognized languages, 57 of them .j2. Those templates are the LLM behavior — a prompt change is a behavior change with no import edge and no type signature. Treat the Dependencies tab as covering the Python/TS skeleton only.
  • No coverage tab. No parseable artifact exists in the repo (no Cobertura XML, LCOV info, or Go coverage profile). Coverage was not generated for this atlas — running the suite to manufacture a number would misrepresent when it was measured. Line-level coverage is genuinely unknown.
  • No eval harness. There is no benchmark or eval infrastructure for LLM output quality — tracked as issue #246. For a product whose core value is model output, that is a notable absence rather than a missing tab.
  • Cycle counts move with module granularity, so read them with the depth attached. At this edition's grouping (12 modules) there is one module-level cycle, plus three file-level ones (issues #238, #239) — see Boundaries. Split one level finer (18 modules) and a second real one appears: grimoire ⇄ grimoire/store, because eight store modules import grimoire.prompts while the root imports the store. It is invisible above only because both sides collapse into one backend node. A cycle wholly inside one module never appears as an edge at any depth.

Three flows carry the product, and each has one seam worth staring at

Play (send a message, get a reply), absorb (turn a finished scene into durable campaign state), and record write (how anything reaches disk). The third is now uniform; the first two are where the unpaid cost of "files instead of a database" actually lands.

1. Play — the message round trip

sequenceDiagram
    participant U as Frontend
    participant R as routes.py
    participant S as store.scenes
    participant C as store.context
    participant L as LLM provider
    U->>R: POST /campaigns/{cid}/scenes/{sid}/chat
    R->>S: append_message(user text) [campaign lock]
    R->>C: build context (cast, chronicle, sheets, style)
    C->>R: assembled prompt
    R->>L: stream completion
    L-->>R: tokens
    R-->>U: SSE frames
    R->>S: append_reply(segments + turn_sizes) [campaign lock]
    Note over S: transcript and boundary list land in ONE write

The seam: two appends, one lock — and only within a process

Both appends in this flow are read-modify-writes of the whole transcript file. Until #254 neither took a lock: writer A read the transcript, writer B read it, appended and published, then A appended to its stale copy and published — B's message gone, silently, with a well-formed file at every instant. The atomic write is precisely why nothing noticed; both writes were individually complete.

Every scene mutator now runs under locks.campaign_lock(cid) via @_serialized (backend/src/grimoire/store/scenes.py:115), with the read inside the lock. append_message (backend/src/grimoire/store/scenes.py:397) and append_reply (backend/src/grimoire/store/scenes.py:471) share it, so the ordinary case — a user typing while a reply is persisted — no longer loses either message.

What is still open: the lock is a threading.RLock, so this holds within one process only. Two backend processes on a synced store race exactly as before (#234), and that is the configuration the README encourages.

One thing this flow gets right and is easy to miss: append_reply persists the segments and the turn_sizes boundary list in a single write. Splitting them would let a crash leave the boundary list describing a transcript that no longer exists, and reroll would then delete blocks belonging to an older generation. Four tests pin this specifically.

2. Absorb — scene becomes campaign state

sequenceDiagram
    participant R as routes.py
    participant L as LLM
    participant A as store.absorb
    participant D as dossiers
    participant AU as store.audit
    R->>L: absorb prompt (transcript + state snapshot)
    L-->>R: structured edits
    R->>A: materialize(cid, sid, parsed)
    Note over A: chronicle, state, relationships, plot, groups COMMIT here
    R->>D: _refresh_dossiers (per NPC)
    D-->>R: exception

    R->>AU: run audit
    Note over R: response carries mechanics + dossiers status

The seam: a multi-phase write with no rollback and no idempotency key

store.absorb.materialize commits prose edits at backend/src/grimoire/routes.py:3172 — before the dossier phase and audit run. If the process dies during the dossier phase, the campaign has absorbed the scene while some NPCs still carry pre-scene dossiers. There is no "already absorbed" guard, so re-running re-applies everything from scratch. Issue #235.

Resolved: the dossier phase no longer swallows its failures. The loop that discarded every exception with a bare continue is now _refresh_dossiers (backend/src/grimoire/routes.py:3115), built to the same shape as the audit helper 40 lines above it: it still never fails absorb, but returns {status, reason, refreshed, failed} on the response (backend/src/grimoire/routes.py:3182) and the scene inspector renders the failures (frontend/src/routes/CampaignView.tsx:777). It also closed an escape the old code had — scene_cast ran outside the try, so an unreadable cast 500'd the endpoint. Issue #236, resolved on branch fix-236-dossier-refresh-errors.

3. Record write — now the one uniform path

flowchart LR
    A[any store module] --> B["atomic.write_text / write_bytes"]
    B --> C{target read-only?}
    C -->|yes| D[PermissionError, no temp created]
    C -->|no| E[mkstemp beside target]
    E --> F[write through that fd]
    F --> G[fsync, close]
    G --> H[carry mode, group, xattrs]
    H --> I[os.replace]
    F -.exception.-> J[unlink temp, record untouched]

Every byte the package writes goes through backend/src/grimoire/store/atomic.py:193. The temp's pathname is never handed out — the descriptor mkstemp returns is written through directly — so there is no interval in which the temp can be swapped for a symlink. backend/tests/test_atomic_guard.py fails the build if a raw write reappears anywhere in the package without a reasoned atomic-ok marker.

This was risk #1 in the previous atlas and is resolved (#233, merged at fd38a84a). Scene transcripts were being rewritten with a plain write_text on every message. Two things are worth carrying forward rather than filing away: the guarantee is atomicity, not durability — a power cut can still lose the last write, it just cannot shred the file — and the retrofit's own review turned up four further defects in the fix, three of them in code written to address earlier review rounds.

Sync — the flow most likely to surprise a reader

World edits reach a campaign through a three-hash comparison (world / base / mine) in backend/src/grimoire/store/sync.py:33, with content hashes standing in for revision numbers (backend/src/grimoire/store/entities.py:130). There is no timestamp ordering and no vector clock: a record is "changed" if its hash differs from the recorded base. That is sound for a single writer and undefined for two — see risk #2.

Most concerns have one owner; the ones that don't are the findings

This codebase is unusually disciplined about single ownership — durability, Markdown serialization, path resolution, and campaign locking each have exactly one home. The exceptions cluster in one place: the HTTP layer reaching past the store, which is both a boundary violation and the reason two separate bugs went unnoticed.

Cycles

Correction from the previous atlas, not a regression. The last edition reported "zero module-level cycles across 18 modules"; at this edition's module granularity the graph resolves to 12 modules, 1,272 import edges, and one module-level cycle: frontend/src/components ⇄ frontend/src/routes. The edge pair is not new — the earlier count merged those two directories into a single frontend module, which hid it. Re-measured on both the branch and mainline with identical results, so nothing in this edition's changes caused it.

Three file-level cycles are tracked. Two are known issues: the module-editor components form a five-file cycle (issue #238), and the LLM providers cycle through LLMError in llm.py (issue #239). The third is the store package's 60-file __init__ re-export knot, which is structural rather than accidental. Read the Dependencies tab as "one cycle between subsystems, three within them".

Durability closed, then in-process concurrency; the cross-process gap remains

Two editions ago the headline was scene transcripts rewritten non-atomically on every message (#233). This one closes the sequel: those same writes took no lock, so concurrent appends lost a message inside a single process (#254). What remains is narrower but unchanged in kind — this codebase reliably makes each individual write correct, and protects sequences of them only within one process. Every risk below is a multi-step operation with no serialization, no rollback, or both.

Failure handling

No silent-swallow site remains on the main flow. The dossier refresh loop that discarded every exception with a bare continue now reports each outcome as a status the UI renders (backend/src/grimoire/routes.py:3115), matching the audit helper it sits next to. Both absorb side-phases now have the same contract: never fail the request, always name what failed. Issue #236, resolved on branch fix-236-dossier-refresh-errors.

The custom-calendar loader swallows import failures too (backend/src/grimoire/store/calendars/plugins.py), but there the retry-next-call behavior is documented and reasonable for a plugin system.

Worth crediting: the codebase writes unusually good why comments, and several of the trickiest invariants (turn-size boundaries, lock ordering, the two-actor module-edit threat model) are explained at their definition rather than left for a reader to reconstruct.

Concurrency

The locks are in-process; the product advertises multi-process use. threading.RLock protects nothing across processes, yet the README recommends pointing the data directory at Dropbox or iCloud to share one library across devices, and the same store is reachable from the desktop app and the Android APK. Two devices — or two backend processes on one machine — editing one campaign have no mutual exclusion at all, and because most records are rewritten whole rather than merged, the loser's edit is silently overwritten.

The threat model documented in backend/src/grimoire/store/module_edit.py:4-10 names exactly two actors, User and LLM, both inside one process. The sync-folder scenario adds a third the design does not account for.

Within one process the domain is now coherent: sheets, proposals, audit, module publication and every scene mutator serialize on the same campaign_lock(cid). Two registries still sit outside it — rolls.py (#255) and the per-image lock in backend/src/grimoire/store/assets.py:45, the latter deliberately, since it guards a different unit.

Risk ranking

1. Cross-process and cross-device writers have no protection. Given a documented, encouraged sync-folder workflow, last-writer-wins on whole-file rewrites is a data-loss path with no detection and no user-visible symptom. Now the whole of the concurrency risk, and it moved up. #254 closed the in-process half for scenes, which leaves this as the only remaining way to lose a transcript message — and the harder half, since a threading.RLock cannot be extended across processes. #234.

2. Absorb is a long, non-atomic, non-idempotent multi-phase write. Prose edits commit before the dossier phase and audit run (backend/src/grimoire/routes.py:3172); there is no absorbed-already guard, and a re-run re-applies everything. Interrupted absorbs leave campaigns in states no code path expects. #235.

3. routes.py is 3,511 LOC with 567 branches and 161 commits — the top hotspot by a factor of four. Its churn×complexity score is 91,448 against 20,976 for the next file. It holds all 252 endpoints plus streaming, the fence protocol, the proposal-healing invariant and audit orchestration. Two of this atlas's boundary violations live here because there is nowhere better to put them. Splitting by domain is mechanical and would shrink the review surface of every future change. #241.

4. Absorb's reported failures have no remediation path. With #236 fixed, the user is now told when a dossier refresh failed — but the only way to retry one is to absorb another scene. The mechanics audit has both a standalone endpoint (backend/src/grimoire/routes.py:3186) and a Retry validation button; the dossier notice is read-only. A visible failure the user cannot act on is a smaller problem than an invisible one, but it is the natural follow-up.

Resolved since the last atlas. Risk #1 was "scenes.append_message takes no lock at all" — fixed by #254. Every scene mutator now runs under the campaign lock with the read inside it (backend/src/grimoire/store/scenes.py:115), and the tests widen the read→write window so the old behaviour fails on every run rather than one in a thousand. Note the pairing with #233 below: making the write atomic is what made this lost update silent, because both racing writes were individually complete and well-formed. Atomicity and serialisation are different properties, and shipping one can disguise the absence of the other. The fix is bounded on purpose — it closes the in-process half only, which is why #234 moved to the top rather than leaving with it.

Risk #5 was "silent dossier failures" — fixed on branch fix-236-dossier-refresh-errors (#236): the loop became _refresh_dossiers, returning the same status/reason/dropped shape the audit already used, and the scene inspector renders it. Risk #1 was "scene transcripts are rewritten non-atomically on every message" — fixed in #233 (merged fd38a84a). All ~100 write sites publish by rename through one helper, and a guard test keeps it that way. Two smaller findings went with it: put_image deleted the old image before writing the new one, and routes.py was writing a campaign record with a raw write_text from the HTTP layer.

Also resolved: #237 — the campaign climate record had four touchpoints across three layers and no owning module. It now has one (backend/src/grimoire/store/campaign_climate.py), and the HTTP layer no longer reads or writes that file. Consolidating the readers found a live defect rather than only tidying: the climate-referrer scan, which feeds the editor's delete/revert warning, reported campaigns with no stored default as using no climate at all, though they resolve to the shipped preset on every turn — and the editor never asked for referrers on the revert path, so reverting a customized preset warned about nothing.

One process observation worth carrying: that fix took five review rounds, and three of its four P1 defects were introduced while fixing earlier findings — a symlink window opened by closing a file descriptor, a process-global umask mutation, and two successive incomplete fixes to the same image-cleanup race. Changes in this area are unusually good at looking finished before they are.

Names that will mislead you

atomic.py does not mean transactional. It guarantees per-file atomicity — a reader sees the whole old version or the whole new one. It does not give you multi-file consistency, and it does not give you durability across a power cut. Both limits are stated at backend/src/grimoire/store/atomic.py:8-21, and both have been over-read at least once already.

locks.campaign_lock is not the lock. Its docstring enumerates who takes it, and that list is incomplete: rolls.py keeps a private registry (#255), and backend/src/grimoire/store/assets.py:45 has its own per-image lock added for a different reason. "Campaign-scoped mutation serializes here" is true of most callers, not all.

playstate vs playing vs plotmap. Three similarly-named modules holding different things: playstate.py is per-character campaign play-state stored beside the character copy; playing.py is the campaign's played-greeting set; plot.py/plotmaps are authored plot threads. Nothing in the names distinguishes them.

"Character" is two things. A world character (canon, shared) and a campaign character (a materialized copy with its own version lock and play-state). overlay.read_character resolves across both; characters.read_character takes an explicit root and does not. Calling the wrong one is a silent partial read, not an error.

Templates are named for their prompt role, not their caller. The 219 .j2 files under the templates directory (backend/src/grimoire/prompts.py:17) are organized by flow (an absorb system prompt, an audit system prompt) rather than by caller, so finding which code path renders a given template means grepping for the template name, not following imports. There are no import edges to follow.
