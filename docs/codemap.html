What this is

grimoire is a local-first, single-user AI tabletop-RP companion: a FastAPI backend and a React SPA served from one process, where the durable state is not a database but a tree of markdown-with-frontmatter and JSON files under ~/.grimoire. A world holds characters, lore and locations; a campaign layers copy-on-write edits over a world and accumulates scenes, which are LLM-generated prose.

Architecturally it is a layered monolith with an unusually thick data layer. backend/src/grimoire/store is 79 files and 15.5k lines — simultaneously the persistence layer, the domain model, and the prompt-assembly engine. The two thin layers on either side of it (routes/ at 3.9k lines, backend/src/grimoire/llm.py plus three providers) are deliberately kept small and acyclic; the store is where all the weight and all the coupling live.

Two things make it unlike a typical CRUD app. First, the product is LLM prose, so templates/ is a real architectural layer: every string sent to a model lives in Jinja templates outside the code, editable live. Second, the same source runs on Android inside a Chaquopy WebView shell, which turns portability rules (no repo-layout assumptions, pydantic v1/v2-agnostic) into hard constraints enforced by tests.

Key decisions & constraints

Storage

Filesystem as database. No SQL, no ORM, no migrations table — records are markdown with YAML frontmatter, plus JSON for structured state. The payoff is that a user's library is a plain folder they can sync, diff, and read without the app; the cost is that every consistency guarantee a database would give you has to be hand-built, which is what backend/src/grimoire/store/atomic.py, backend/src/grimoire/store/locks.py and backend/src/grimoire/store/overlay.py are.

Copy-on-write campaigns. A campaign materializes a record only when it diverges from its world (backend/src/grimoire/store/overlay.py:43). Tombstones in deleted.json handle campaign-side deletion of an inherited record.

Concurrency

The campaign is the unit of mutual exclusion. One lock domain covers scenes, sheets, audit baselines, proposals and the roll log, because a module-pack swap must exclude a proposal derived from the pack it replaces (backend/src/grimoire/store/locks.py:238).

Cross-process, not just cross-thread. OS advisory file locks live outside the store, keyed off the account database rather than $HOME, so two backends of the same user cannot pick different lock files.

Prompts as data

Every model-facing string lives in templates/ and renders through backend/src/grimoire/prompts.py:17, with Jinja auto-reload so edits take effect live. Two harnesses keep code and templates honest: scripts/verify_templates.py checks byte-for-byte agreement, and evals/run.py checks that the assembled prompt still contains the instructions verbatim.

Android portability

The APK packages the backend and frontend verbatim, which forbids three things in backend code: repo-layout assumptions (hence GRIMOIRE_DIST / GRIMOIRE_TEMPLATES resolvers), compiled desktop-only dependencies in the base dependency set, and pydantic v2-only APIs. All three are enforced mechanically rather than by convention.

Evaluation

The project does have eval infrastructure, which is rarer than it should be. evals/ defines four pass/fail cases — scene length budget, roll-fence parseability, absorb contract completeness, owned-lore containment — each a stated hypothesis about model behaviour rather than a subjective quality score.

Two modes, and the distinction matters when reading results: replay scores 10 checked-in recordings under evals/recordings, is deterministic and offline, and runs inside pytest via backend/tests/test_evals.py and backend/tests/test_eval_graders.py. That proves the graders fire and the instructions survive in the assembled prompt — it does not prove a live model still obeys them. Only evals/run.py --live answers that, and it is opt-in.

unverified The checked-in recordings appear to be hand-authored counterexamples rather than captured live output, so the replay suite's pass rate measures grader correctness, not model compliance. Treat a green replay run as a lint pass, not as evidence about the current model.

Three flows carry the risk

Almost every hard problem in this codebase lives in one of three places: streaming a model reply that may interrupt itself with a dice-roll request, resolving a campaign record that may or may not exist on disk, and absorbing a finished scene into durable state. Each is diagrammed below as implemented — including the failure branches, which is where the interesting design is.

Flow 1 — A scene turn, with roll-fence interruption

The main request path. A player sends a message; the model streams prose back; if the model decides a dice roll is needed it emits a ```roll fence, which cuts the stream and turns into a pending proposal the player must adjudicate.

Seams

  • The proposal and its narration are two separate lock acquisitions, not one transaction. backend/src/grimoire/routes/streaming.py:157-160 writes the proposal inside campaign_lock, releases it, then calls _persist_reply, which takes the lock again. Contention on that second acquisition leaves a proposal on disk with no narration. The code says so explicitly and calls it the sanctioned direction — the reverse order would lose data instead. Worth knowing before you "fix" it.
  • Once the response has started, the global 409 handler is unreachable. backend/src/grimoire/main.py:77 converts StoreBusy into a 409, but SSE headers are already sent by the time finalize runs, so backend/src/grimoire/routes/streaming.py:125 catches it separately and emits an error frame. A missed catch here truncates the stream with no error at all.
  • Persisting happens in a worker thread on purpose. backend/src/grimoire/routes/streaming.py:124 wraps finalize in run_in_threadpool and materializes it with list(). Inline, the lock's retry sleep would block the event loop for the full timeout — freezing every other live stream, not just the contended campaign.
  • The idle bound is on silence, not on total duration. backend/src/grimoire/llm.py:84 resets its wait on any provider frame, including empty keep-alives and reasoning tokens. A slow-but-progressing generation is never cut off; a genuinely infinite one is only bounded if the provider stops sending frames. Callers that need a wall-clock ceiling impose it themselves.
  • Fence watching covers persisted turns only. _ephemeral_stream at backend/src/grimoire/routes/streaming.py:203 is deliberately untouched, so a roll fence emitted during an opener or director note is streamed as literal text rather than becoming a proposal.

  G["caller edits X"] --> H["record sync base in sync.md FIRST"]
  H --> I["copy the record — its last write is the commit point"]
  I --> J["now materialized: future reads take branch C"]

Seams

  • Base-before-copy is a deliberate crash-ordering choice. backend/src/grimoire/store/overlay.py:94 writes the sync base before the copy, because the harmless failure is base with no copy (self-healing — the record still reads through) and the catastrophic one is copy with no base (permanent silent divergence, since the sync engine only considers refs in the manifest).
  • Reading around this module fails silently. A missing character is a skipped cast entry, not an exception — which is why backend/tests/test_overlay_guard.py exists to flag any campaign root meeting an inheritable kind. Per the guard's own docstring this is the codebase's most repeated bug class.
  • Actors and flat records use different resolution rules. Flat records overlay per file; characters and PCs are whole-directory, keyed on character.md existing (backend/src/grimoire/store/overlay.py:43), so lock-purged versions stay purged. tagline.md is the one sidecar that overlays per file anyway — an exception documented in the module docstring and easy to miss.
  • A campaign's world may not exist. backend/src/grimoire/store/overlay.py:53 deliberately does not raise for a deleted world; every resolver just reads a path that holds nothing. Fail-soft, but it means a broken world reference degrades to "everything inherited is missing" rather than an error.

Flow 3 — Absorbing a finished scene

Turns a transcript into durable state: chronicle summary, lore edits, relationship and plot movement, refreshed dossiers, a mechanics audit. Three LLM calls under one shared wall-clock budget.

sequenceDiagram

Seams

  • Absorb is a proposal, not a write. backend/src/grimoire/routes/scenes.py:434 materializes edits in memory and returns them; the commit is a separate call keyed on commit_token. This exists because absorb is not idempotent — lore edits append and plot movements add a beat, so a replay would duplicate both.
  • Re-absorb is refused before spending a token (backend/src/grimoire/routes/scenes.py:413), which is the right order: the cheap check precedes the expensive call.
  • Two of the three LLM phases swallow their own failures by design. Dossier staging and the mechanics audit are documented as never raising, so a partial absorb degrades to fewer proposed edits rather than a 502. That is a deliberate trade, but it does mean a systematically failing dossier model shows up as silently missing proposals, not as an error — nothing in the response distinguishes "no dossier changes needed" from "the dossier call failed".
  • One budget spans all three calls. store.config.absorb_budget() bounds the whole sequence, unlike the per-call idle bound in backend/src/grimoire/llm.py. The two limits are independent and can interact: a healthy-but-slow first call can consume the budget the later phases needed.

This codebase is unusually disciplined about single ownership: writes, id validation, campaign resolution, lock mechanism and pydantic dialect each have exactly one owning module, and four of those rules are enforced by tests that parse the package's own AST rather than by convention. Boundary violations

1. The store package is one 63-file import cycle. backend/src/grimoire/store/__init__.py:5 imports 60 submodules to re-export them, and every submodule reaches its siblings with from . import ... — which resolves through that same package initializer. The result is a single strongly-connected component containing essentially the entire data layer, and a hub file with fan-in 153 and fan-out 59, by far the most connected file in the repo.

The practical cost is not runtime (Python resolves it fine) but comprehension and testability: there is no subset of the store you can import, reason about, or replace in isolation, and import order becomes load-bearing in ways nothing checks.

This is known, specified, and already tooled — but not yet done. A design and a 15-task plan for partitioning the store into layered packages are merged (docs/superpowers/specs/2026-07-30-store-import-layering-design.md, docs/superpowers/plans/2026-07-30-store-import-layering.md), along with a validator that reads the proposed function-to-file mapping out of the spec and checks it for cycles. Running scripts/validate_partition.py --graph today reports the post-refactor graph would be acyclic across packages. The implementation has not started: the store is still the flat 79-file layout. This is the single largest piece of planned-but-unlanded work in the repo.
2. The module-level cycle grimoire → routes → store → grimoire is a grouping artifact, not a real one. The Dependencies tab reports it because backend/src/grimoire is treated as one node, and that directory holds both the top of the stack (backend/src/grimoire/main.py) and the bottom (backend/src/grimoire/prompts.py, which seven store modules import). At file level there is no cycle: backend/src/grimoire/prompts.py imports only jinja2 and the standard library.

The smell it does point at is real but minor — grimoire/ mixes layers in one directory. backend/src/grimoire/llm.py is the counter-example done right: it sits at the same level but deliberately imports no store code, taking its config as an injected callable from backend/src/grimoire/routes/common.py:23.

3. backend/src/grimoire/store/context.py imports 21 sibling modules (backend/src/grimoire/store/context.py:16-22) and has the second-highest fan-out in the repo. That is inherent to what it does — a scene prompt genuinely needs cast, lore, weather, calendar, sheets, checks, relationships, plot and style — but it makes this file the one place where almost any store change can break prose generation, which is consistent with it being both a top-10 hotspot and a top-10 coverage risk.
4. One frontend request leaves the app entirely, straight from the browser. frontend/src/api/models.ts:11-12 calls fetch("https://openrouter.ai/api/v1/models") directly rather than going through frontend/src/api/client.ts, which is otherwise the SPA's single server surface (fan-in 94). Consequences worth knowing: the model catalogue is unavailable offline and on any deployment with a restrictive CSP, the request carries no grimoire error handling, and it is the one place the browser talks to a third party without the backend in between.

Failure handling

The dominant pattern is deliberate fail-soft: unreadable or malformed JSON in the store returns an empty value rather than raising, because the store is a folder the user can edit, sync, and corrupt. It appears at eight-plus sites including backend/src/grimoire/store/audit.py:42, backend/src/grimoire/store/changes.py:44 and backend/src/grimoire/store/commits.py:49. For most of them that is the right call. Two are different in kind:

A corrupt deleted.json silently resurrects every tombstoned record. backend/src/grimoire/store/overlay.py:74 returns an empty set on JSONDecodeError, and an empty tombstone set means "nothing was deleted" — so characters and lore the user deleted campaign-side reappear, inherited from the world again, with no error anywhere. Every other fail-soft site degrades toward less content; this one degrades toward more, which is the direction a user cannot detect.
A corrupt ~/.grimoire.json silently relocates the entire library. backend/src/grimoire/store/paths.py:33 falls back to {}, which drops the user's configured data_dir and reverts home() to the default ~/.grimoire. For anyone who pointed grimoire at a synced folder, the app then starts up looking empty. The pointer file is written atomically so this should be rare — but the failure mode is "all your worlds are gone", and it is reported as nothing at all.

Two absorb phases are documented as never raising. Dossier staging and the mechanics audit at backend/src/grimoire/routes/scenes.py:437-441 absorb their own failures so a partial result still returns. The cost: nothing in the response distinguishes "the model proposed no dossier changes" from "the dossier call failed", so a systematically broken phase looks like a quiet model.
Two nominal read paths mutate the filesystem, and one plugin loader swallows everything. backend/src/grimoire/store/assets.py:251 and backend/src/grimoire/store/assets.py:275 both self-heal a stranded promotion temp while serving what reads like a query — deliberate recovery for #253, but it means a GET can write. Separately, backend/src/grimoire/store/calendars/plugins.py:47 catches bare Exception around exec_module so a broken homebrew calendar cannot break the calendar list; the cost is that a plugin with a typo simply never appears, with no error surfaced to its author.
Timeouts are genuinely handled, which is unusual. Every LLM call is idle-bounded at the facade (backend/src/grimoire/llm.py:84) regardless of provider — including the Claude Agent SDK, which exposes no HTTP client to configure — and absorb adds a whole-sequence wall-clock budget on top. The bound counts provider activity rather than visible text, so long reasoning does not get killed as a stall. Cleanup is bounded too: a provider that will not unwind is abandoned rather than allowed to hold the caller (backend/src/grimoire/llm.py:50).

Concurrency

Single process, asyncio event loop, with blocking store work pushed to a threadpool. Three things are worth internalizing:

  • The campaign is the lock unit, covering scenes, sheets, audit baselines, proposals and rolls in one domain so a module-pack swap can exclude a proposal derived from the pack it replaces (backend/src/grimoire/store/locks.py:238).
  • Locks are cross-process, via OS advisory file locks kept outside the store and keyed off the account database rather than $HOME — because a synced store cannot host lock files and a rewritten environment would let two backends of the same user pick different ones (backend/src/grimoire/store/proclock.py).
  • Blocking calls never run inline on the event loop. backend/src/grimoire/routes/streaming.py:124 is explicit that an inline finalize would block every other live stream for the lock timeout, not just the contended campaign.

Startup is the one place the 409 handler cannot reach, so backend/src/grimoire/main.py:48 degrades a contended migration to a warning and boots anyway — all three steps are idempotent and re-run later.

Risk ranking

1. The store is a single 63-file import cycle, and the fix is specified but unstarted. No part of the data layer can be imported, tested, or replaced in isolation. The design, a 15-task plan, and a validator that proves the target graph is acyclic are all merged; the code is untouched. Every week this waits, the partition tables in the spec drift further from the modules they describe.
2. The lock domain is enforced by a docstring. A new campaign-scoped mutator that forgets campaign_lock is invisible to every test in the repo, and this exact bug has already shipped once. Blast radius is silent data loss on concurrent edits to a scene transcript — the one artifact the codebase says cannot be regenerated.
3. Fail-soft on corrupt JSON points the wrong way in two places. Tombstone loss resurrects deleted records; pointer loss hides the whole library. Both are silent. Both would be one log.warning away from being diagnosable.
4. A synced store still has no cross-device exclusion, and the product recommends syncing. CLAUDE.md suggests pointing the store at a synced folder to share a library across devices, but the lock module states plainly that a peer on another device is invisible and that "no filesystem lock on a sync-replicated store can do better" — the sync client resolves simultaneous edits with conflict copies on its own schedule (backend/src/grimoire/store/locks.py:58-63). This is a correctly-identified limit rather than a defect, and the module names the fix it would take (compare-and-swap on a content digest). It stays on the list because the recommended configuration is the unprotected one.
5. Complexity and untested surface are concentrated in four files. backend/src/grimoire/store/module_edit.py carries 332 branches in 1,134 lines — the highest branch count in the repo — and is the top coverage risk at 91.2%. Meanwhile coverage is backend-only: 90 files are unmeasured, including frontend/src/routes/CampaignView.tsx and frontend/src/components/CharacterEditor.tsx, the two largest churn-times-complexity hotspots in the whole codebase. Vitest tests exist for both; no coverage artifact does, so their real exercise level is unknown rather than low.
Minor, but free to fix: the lint gate omits W605 and there are two live instances. ruff check passes today, yet scripts/validate_partition.py:309 contains two invalid escape sequences that CPython already reports as a SyntaxWarning on import and that a future Python will make a hard error. The ruff config is deliberately narrow and says so, but its stated principle is "every selected rule maps to a real bug class" — W605 does, and it is currently unselected.

Overloaded names

module — game-mechanics data pack vs. Python module. highest confusion risk

In backend/src/grimoire/store/modules.py, backend/src/grimoire/store/module_edit.py and backend/src/grimoire/routes/modules.py, "module" means a game system data pack — sheets, checks, dice rules — that a campaign binds to. Everywhere else in the repo, including in those same files' import statements, it means a Python module. Sentences like "the module edit holds every campaign's lock across the swap" are about game packs, not code. There is no naming fix that is worth the churn now, but a reader should hold both senses in mind from the start.

materialize — two unrelated operations.

In the overlay it means copy an inherited record into the campaign so it can diverge (backend/src/grimoire/store/overlay.py:173, backend/src/grimoire/store/overlay.py:363). In absorb and audit it means turn parsed LLM output into a list of proposed edit objects (backend/src/grimoire/store/absorb.py:202, backend/src/grimoire/store/audit.py:324). The first writes to disk; the second explicitly does not. Same verb, opposite side effects.

proposal — a pending dice decision vs. a proposed edit.

backend/src/grimoire/store/proposals.py owns exactly one thing: the pending roll a player must adjudicate or decline, which lives in the campaign lock domain and has a supersede protocol. Absorb's output is also conversationally called a proposal — the route returns edits plus a commit_token — but shares no code, no storage, and no lifecycle with it. When a comment says "the proposal", check which one.

Names that read oddly but are right

absorb is invented rather than borrowed, and it earns its keep: no standard term covers "end this scene and fold its consequences back into world, campaign and character state". fence is markdown's own word for a code block, used precisely. overlay names the mechanism rather than the feature, which is the right choice for a module whose entire job is resolution order.

Two more worth calling out as good practice: safe_id says what it guarantees rather than what it rejects, and SYNCED_KINDS encodes an architectural rule as data that a test can read — the overlay guard consumes that tuple rather than re-listing the kinds.
