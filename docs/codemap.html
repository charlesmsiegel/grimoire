What this is

grimoire is a local-first, single-user AI tabletop-RP companion: a FastAPI backend and a React SPA served from one process, where the durable state is not a database but a tree of markdown-with-frontmatter and JSON files under ~/.grimoire. A world holds characters, lore and locations; a campaign layers copy-on-write edits over a world and accumulates scenes, which are LLM-generated prose.

Architecturally it is a layered monolith with an unusually thick data layer. backend/src/grimoire/store is 135 files and 19.8k lines — simultaneously the persistence layer, the domain model, and the prompt-assembly engine. The two thin layers on either side of it (routes/ at 14 files and 4.9k lines, backend/src/grimoire/llm.py plus three providers) are deliberately kept small and acyclic. Since the store-layering refactor the store is acyclic too: ten oversized modules became layered subpackages, every import sits at module scope, and a test enforces both.

The mechanism to internalize before anything else is the guard set: six tests that parse the package's own ASTs and fail the build when a convention is broken — writes outside atomic, campaign reads outside overlay, filesystem access outside the resolvers, pydantic v2-only APIs, an import inside a function body, and a campaign mutator outside the declared lock domain. Each carries a # <name>-ok: <reason> escape hatch where a marker with no reason fails deliberately, and each docstring states its own blind spots. With the facade snapshot they are 6,696 lines of test code, a third the size of the store package they mostly check. See Invariants & Risks for the full set and for the one place a guard's reach has shrunk.

Two things make it unlike a typical CRUD app. First, the product is LLM prose, so templates/ is a real architectural layer: every string sent to a model lives in Jinja templates outside the code, editable live. Second, the same source runs on Android inside a Chaquopy WebView shell, which turns portability rules (no repo-layout assumptions, pydantic v1/v2-agnostic) into hard constraints enforced by tests.

Key decisions & constraints

Storage

Filesystem as database. No SQL, no ORM, no migrations table — records are markdown with YAML frontmatter, plus JSON for structured state. The payoff is that a user's library is a plain folder they can sync, diff, and read without the app; the cost is that every consistency guarantee a database would give you has to be hand-built, which is what backend/src/grimoire/store/atomic.py, backend/src/grimoire/store/locks.py and backend/src/grimoire/store/overlay.py are.

Copy-on-write campaigns. A campaign materializes a record only when it diverges from its world (backend/src/grimoire/store/overlay.py:181). Tombstones in deleted.json handle campaign-side deletion of an inherited record (backend/src/grimoire/store/overlay.py:70).

Concurrency

The campaign is the unit of mutual exclusion. One lock domain covers scenes, sheets, audit baselines, proposals and the roll log, because a module-pack swap must exclude a proposal derived from the pack it replaces (backend/src/grimoire/store/locks.py:8).

Membership is declared, not described. DOMAIN_MODULES (8), OUTSIDE_DOMAIN (3, each with a reason) and UNREVIEWED (19, a backlog that may only shrink) name every campaign-mutating module, and backend/tests/test_lock_domain_guard.py re-derives the verdict from the ASTs and fails when the two disagree.

Cross-process, not just cross-thread. OS advisory file locks live outside the store, keyed off the account database rather than $HOME, so two backends of the same user cannot pick different lock files.

Store layering

Every import at module scope, and no cycles. backend/tests/test_import_guard.py enforces three rules in one AST scan: no import inside a function body, no cycle in the module-level graph, and — inside store/ — a cross-package import must bind a submodule and keep it as a module object. There are currently zero # import-ok: exemptions.

The facade is a compatibility layer, not a namespace. Its export list is frozen by a snapshot test precisely so the packages behind it can keep moving.

Prompts as data

Every model-facing string lives in templates/ and renders through backend/src/grimoire/prompts.py:36, with Jinja auto-reload so edits take effect live. Two harnesses keep code and templates honest: scripts/verify_templates.py checks byte-for-byte agreement, and evals/run.py checks that the assembled prompt still contains the instructions verbatim.

Android portability

The APK packages the backend and frontend verbatim, which forbids three things in backend code: repo-layout assumptions (hence the GRIMOIRE_DIST / GRIMOIRE_TEMPLATES resolvers at backend/src/grimoire/main.py:22 and backend/src/grimoire/prompts.py:19), compiled desktop-only dependencies in the base dependency set, and pydantic v2-only APIs. All three are enforced mechanically rather than by convention.

Evaluation

The project does have eval infrastructure, which is rarer than it should be. evals/ defines four pass/fail cases — scene length budget, roll-fence parseability, absorb contract completeness, owned-lore containment — each a stated hypothesis about model behaviour rather than a subjective quality score.

Two modes, and the distinction matters when reading results: replay scores checked-in recordings under evals/recordings, is deterministic and offline, and runs inside pytest via backend/tests/test_evals.py and backend/tests/test_eval_graders.py. That proves the graders fire and the instructions survive in the assembled prompt — it does not prove a live model still obeys them. Only evals/run.py --live answers that, and it is opt-in.

unverified The checked-in recordings appear to be hand-authored counterexamples rather than captured live output, so the replay suite's pass rate measures grader correctness, not model compliance. Treat a green replay run as a lint pass, not as evidence about the current model.

Three flows carry the risk

Almost every hard problem in this codebase lives in one of three places: streaming a model reply that may interrupt itself with a dice-roll request, resolving a campaign record that may or may not exist on disk, and absorbing a finished scene into durable state. Each is diagrammed below as implemented — including the failure branches, which is where the interesting design is. The store-layering refactor moved the participants (the flat context, scenes and absorb modules are packages now) but changed none of these flows' behaviour.

Flow 1 — A scene turn, with roll-fence interruption

The main request path. A player sends a message; the model streams prose back; if the model decides a dice roll is needed it emits a ```roll fence, which cuts the stream and turns into a pending proposal the player must adjudicate.

Seams

  • The proposal and its narration are two separate lock acquisitions, not one transaction. backend/src/grimoire/routes/streaming.py:157-160 writes the proposal inside campaign_lock, releases it, then calls _persist_reply, which takes the lock again through _serialized. Contention on that second acquisition leaves a proposal on disk with no narration. The code says so explicitly (backend/src/grimoire/routes/streaming.py:150-153) and calls it the sanctioned direction — the reverse order would lose data instead. Worth knowing before you "fix" it.
  • Once the response has started, the global 409 handler is unreachable. backend/src/grimoire/main.py:77 converts StoreBusy into a 409, but SSE headers are already sent by the time finalize runs, so backend/src/grimoire/routes/streaming.py:125 catches it separately and emits an error frame. A missed catch here truncates the stream with no error at all.
  • Persisting happens in a worker thread on purpose. backend/src/grimoire/routes/streaming.py:124 wraps finalize in run_in_threadpool and materializes it with list(). Inline, the lock's retry sleep would block the event loop for the full timeout — freezing every other live stream, not just the contended campaign.
  • The lock the persist takes is the scene decorator's, and it is reentrant. backend/src/grimoire/store/scenes/locking.py:18 is now its own module — deliberately not folded into backend/src/grimoire/store/scenes/serialize.py, whose similar name means transcript marshalling, not serialization of writers. Its docstring states the bug it exists to prevent: an unlocked read-modify-write of a whole transcript loses a message with no error and no trace, and a transcript is the one artifact in the app that cannot be regenerated. Since 92452f6 the lock-domain guard resolves @locking._serialized across that file boundary, so all 18 applications of it are checked rather than read as unserialized — the decorator's own def is put through the same test a same-file decorator gets.
  • The idle bound is on silence, not on total duration. backend/src/grimoire/llm.py:84 resets its wait on any provider frame, including empty keep-alives and reasoning tokens. A slow-but-progressing generation is never cut off; a genuinely infinite one is only bounded if the provider stops sending frames. Callers that need a wall-clock ceiling impose it themselves.
  • Fence watching covers persisted turns only. _ephemeral_stream at backend/src/grimoire/routes/streaming.py:203 is deliberately untouched, so a roll fence emitted during an opener or director note is streamed as literal text rather than becoming a proposal.

  • Base-before-copy is a deliberate crash-ordering choice. backend/src/grimoire/store/overlay.py:102-115 writes the sync base before the copy, because the harmless failure is base with no copy (self-healing — the record still reads through) and the catastrophic one is copy with no base (permanent silent divergence, since the sync engine only considers refs in the manifest).

Sharp edges, and the blunt one that got ground down

The cycle that was, and the measurement that inflated it

Closed: the store is no longer one import cycle. Two atlases ago the store package — reported then as a single 63-node import cycle — was the repo's top structural risk. That finding is closed and stays closed; it is kept here only because the number itself was partly wrong and the correction is reusable. Ten oversized modules — campaigns, worlds, scenes, appearances, modules (which absorbed the old flat module_display), sheets, audit, module_edit, absorb, context — are now subpackages, 67 files where there were 11. Re-derived against the current tree: 0 module-scope import cycles, 0 imports inside a function body anywhere under backend/src/grimoire/, and 0 # import-ok: exemptions.
Two thirds of that "63" was a measurement artifact, and the correction is worth carrying. The number came from attributing from . import scenes to the package grimoire.store rather than to grimoire.store.scenes. With the package as a node, backend/src/grimoire/store/__init__.py importing dozens of submodules while each submodule reached its siblings relatively collapsed the entire data layer — plus files under calendars/, climates/ and weather/ that were never involved — into one component. Resolved to actual submodules, the pre-refactor tree had one true module-scope cycle: scenes → scene_refs → audit → scenes. What the other 53 sites bought was deferral, not decoupling: each in-function import postponed an edge that would otherwise close a loop, and hoisting all of them yields a 15-module component. That 15 is what the refactor actually cut.

Concretely reproducible, and re-measured at this commit: the unmodified graph builder reports a 114-node component on the current tree, up from the 63 it reported before the split, because more subpackages mean more from . import x lines feeding the same false node. The builder used for this atlas resolves those to submodules — the same rule backend/tests/test_import_guard.py:91-92 applies (out.add(cand if cand in MODULES else target)) — and reports no file-level cycle at all. That agrees with the guard, which is the authoritative check: running its own _cycles() over its own graph of 157 grimoire modules (135 of them under store/) returns an empty list. If a re-run of this analysis disagrees, the builder is wrong, not the code.

The rule that replaced it is narrower than "no cycles", on purpose. backend/tests/test_import_guard.py adds a third rule that the cycle check provably cannot catch: inside store/, a cross-package import must bind a submodule and keep it as a module object — from ..campaigns import read then read.world_refs(). Binding a name off a package (from ..campaigns import world_refs) raises at import time if that package's __init__ is still running; binding a function off a leaf module (from ..campaigns.read import world_refs) silently defeats any test that patches it, which fails green rather than red. Both leave the file graph perfectly acyclic (backend/tests/test_import_guard.py:9-15), which is exactly why the rule is checked separately. Package initializers are exempt because re-exporting is their job (backend/tests/test_import_guard.py:136-139).

Concurrency

Single process, asyncio event loop, with blocking store work pushed to a threadpool. Three things are worth internalizing:

  • The campaign is the lock unit, covering scenes, sheets, audit baselines, proposals, the roll log and the module-pack swap in one domain so a module edit can exclude a proposal derived from the pack it replaces (backend/src/grimoire/store/locks.py:1-12).
  • Locks are cross-process, via OS advisory file locks kept outside the store and keyed off the account database rather than $HOME — because a synced store cannot host lock files and a rewritten environment would let two backends of the same user pick different ones (backend/src/grimoire/store/proclock.py).
  • Blocking calls never run inline on the event loop. backend/src/grimoire/routes/streaming.py:124 is explicit that an inline finalize would block every other live stream for the lock timeout, not just the contended campaign.

Startup is the one place the 409 handler cannot reach, so backend/src/grimoire/main.py:52 degrades a contended migration to a warning and boots anyway — all three steps are idempotent and re-run later. Note also that backend/src/grimoire/store/failsoft.py keeps deliberately-unlocked module state; its docstring explains why that is safe (every operation is a single mapping call) and why the obvious eviction spelling is not.

Overloaded names

module — game-mechanics data pack vs. Python module. highest confusion risk

In backend/src/grimoire/store/modules/, backend/src/grimoire/store/module_edit/ and backend/src/grimoire/routes/modules.py, "module" means a game system data pack — sheets, checks, dice rules — that a campaign binds to. Everywhere else in the repo, including in those same files' import statements, it means a Python module. The store split made both senses more visible at once: store/modules/ is now a Python package whose contents are about game packs. Sentences like "the module edit holds every campaign's lock across the swap" are about game packs, not code.

materialize — two unrelated operations.

In the overlay it means copy an inherited record into the campaign so it can diverge (backend/src/grimoire/store/overlay.py:181, backend/src/grimoire/store/overlay.py:371). In absorb and audit it means turn parsed LLM output into a list of proposed edit objects (backend/src/grimoire/store/absorb/materializer.py:57, backend/src/grimoire/store/audit/apply.py:80). The first writes to disk; the second explicitly does not. Same verb, opposite side effects.

proposal — a pending dice decision vs. a proposed edit.

backend/src/grimoire/store/proposals.py owns exactly one thing: the pending roll a player must adjudicate or decline, which lives in the campaign lock domain and has a supersede protocol. Absorb's output is also conversationally called a proposal — the route returns edits plus a commit_token — but shares no code, no storage, and no lifecycle with it. When a comment says "the proposal", check which one.

serialize — marshalling vs. mutual exclusion. New with the scene split, and the code says so itself.

backend/src/grimoire/store/scenes/serialize.py is transcript marshalling. _serialized, in backend/src/grimoire/store/scenes/locking.py:18, runs a mutation under the campaign lock. They are unrelated, and backend/src/grimoire/store/scenes/locking.py:3-8 exists as its own file specifically so the decorator does not end up in a corner of the same-sounding module.

Filenames that dodge a collision on purpose

Three submodules are named one letter off the obvious choice, and the reason is mechanical rather than stylistic: sheets.read, module_edit.rename and absorb.materialize are public functions on the facade, so a submodule of the same name would be overwritten the moment the package re-exports the function — and a later from ..sheets import read would bind the function, with read.list_refs(...) failing at call time having passed both the import and the cycle check. Hence backend/src/grimoire/store/sheets/reader.py, backend/src/grimoire/store/module_edit/renaming.py and backend/src/grimoire/store/absorb/materializer.py, while backend/src/grimoire/store/campaigns/read.py and backend/src/grimoire/store/worlds/read.py keep the plain name because no facade function claims it there. The collision is caught at its source by backend/tests/test_import_guard.py:258, which imports every package and asserts each same-named attribute is still a module object.

backend/src/grimoire/store/modules/display.py is the one rename with a compatibility tail: the old flat module_display was never in the facade's __all__, but it was reachable through dir(store) as a side effect of another module importing it. backend/src/grimoire/store/__init__.py:29-34 aliases it back explicitly and says why, and the dir() half of the API snapshot is what would have caught its silent disappearance.

Names that read oddly but are right

absorb is invented rather than borrowed, and it earns its keep: no standard term covers "end this scene and fold its consequences back into world, campaign and character state". fence is markdown's own word for a code block, used precisely. overlay names the mechanism rather than the feature, which is the right choice for a module whose entire job is resolution order.

Two more worth calling out as good practice: safe_id says what it guarantees rather than what it rejects, and SYNCED_KINDS encodes an architectural rule as data that a test can read — the overlay guard consumes that tuple rather than re-listing the kinds.
