What grimoire is

A local-first, single-user app for AI-driven collaborative storytelling: a FastAPI backend plus a Vite/React SPA that let one person run roleplay campaigns against a language model. Its defining architectural choice is that the filesystem is the database — worlds, campaigns, characters and every scene transcript are plain Markdown and JSON under a user-chosen data root, with no schema, no migrations table and no server-side session.

Two further choices shape almost everything else. Every prompt is a Jinja2 template under templates/, rendered by backend/src/grimoire/prompts.py, so no prompt text is hard-coded in Python. And a campaign is a copy-on-write overlay on a world (backend/src/grimoire/store/overlay.py): a campaign materializes a record only when it diverges, and reads through to the world otherwise.

Key decisions & constraints

Filesystem as database

No DB, no ORM, no transactions. Records are Markdown-with-frontmatter or JSON; content hashes (backend/src/grimoire/store/entities.py:130) stand in for revision numbers, and a three-hash comparison (world / base / mine) drives world-to-campaign sync at backend/src/grimoire/store/sync.py:33. The upside is that a user's library is portable and greppable; the cost is that multi-file updates have no atomicity.

Prompts are data, and so are game mechanics

Prompt text lives in templates/ with Jinja auto-reload (backend/src/grimoire/prompts.py:28-32), so editing a prompt needs no restart. Mechanics modules follow the same instinct one step further: they are declarative data packs, explicitly not code plugins, so importing someone else's module never executes their code (backend/src/grimoire/store/modules.py:1-7).

Calendars are the deliberate exception

Custom calendars are Python plugins, imported with exec_module from the user's data directory (backend/src/grimoire/store/calendars/plugins.py:45-47). The code comments treat this as intentional given a single-user local app, and the module docstring for modules explicitly contrasts itself with it. Worth knowing before anyone proposes a "share your calendar" feature.

Provider-agnostic LLM access, pydantic-version-agnostic models

Three providers sit behind one facade (backend/src/grimoire/llm.py:13-38), selected per stored connection. Separately, the Android build may pin pydantic 1.x, so the codebase avoids v2-only APIs and dumps models through one shim at backend/src/grimoire/routes.py:25-30.

Evaluation artifacts

There is no eval or benchmark suite in this repository — no evals/ tree, no benchmark job, no scored regression harness for prompt or model output quality. Correctness assurance is entirely conventional testing: 88 pytest modules and 49 vitest files, about 48% of all counted lines. For a system whose primary output is LLM prose, the absence of any output-quality measurement is a genuine gap rather than an oversight worth papering over; the closest thing that exists is scripts/verify_templates.py, which checks the template/variable contract, not generation quality.

Three flows carry the system

Playing a turn, absorbing a finished scene, and resolving a campaign record against its world. Everything else in the 252-route surface is CRUD around these. All three share one property that shapes their risk profile: they perform multi-file writes with no transaction, so every diagram below is really a diagram of where a crash can leave the store half-updated.

Flow 1 — playing a turn

The hot path. A user sends text, the model streams back, and a fence watcher intercepts any ```roll block mid-stream so the app can turn it into a durable dice proposal instead of letting the model narrate its own dice result.

Seams

The proposal is written before the narration it belongs to. In backend/src/grimoire/routes.py:2538-2546 the finalizer mints the proposal record inside the sheets lock and only then calls _persist_reply outside it. A crash between the two leaves a pending dice proposal attached to a scene whose transcript does not contain the narration that led to it. The code comments acknowledge this ordering as deliberate — a transcript ending at a mechanical decision point always has a recoverable proposal — so the residual risk is a proposal without its lead-in, not the reverse.
A hand-written invariant guards proposal retirement, enforced only by convention. backend/src/grimoire/routes.py:2505-2530 documents the rule in a 25-line docstring: a record with a projectable resolution must never be retired or replaced before its projection completes, so every such path calls _heal_current_proposal first. Five call sites currently honour it (backend/src/grimoire/routes.py:2543, backend/src/grimoire/routes.py:2575, backend/src/grimoire/routes.py:2992, backend/src/grimoire/routes.py:3019, backend/src/grimoire/routes.py:3033). Nothing in the code enforces it — a fifth retirement path added later that forgets the call silently orphans a completed roll.
Partial replies persist on upstream failure in one path but not the other. _chat_stream passes an on_error that keeps whatever narration arrived before an LLMError (backend/src/grimoire/routes.py:2552-2554); _continuation_stream deliberately passes none, dropping the partial (backend/src/grimoire/routes.py:2583-2586). Both choices are defended in comments, but a reader tracing "why did my text vanish" needs to know which stream they were in.
No timeout is set at this layer. The route awaits client.stream without a deadline of its own; whatever timeout exists comes from the provider client's httpx configuration. A hung upstream holds the SSE connection open indefinitely from the route's point of view.

Flow 2 — absorbing a finished scene

The heaviest operation in the app: one extraction call, then one LLM call per present NPC to refresh dossiers, then a mechanics audit. It is the only route that issues an unbounded number of model calls.

Seams

Absorb is a long non-atomic write sequence with no rollback. store.absorb.materialize at backend/src/grimoire/routes.py:3132 commits chronicle, state, relationship, plot and group edits to disk before the dossier loop and audit run. If the process dies during the dossier loop, the campaign has absorbed the scene but some NPCs still carry pre-scene dossiers, and re-running absorb re-applies the prose edits from scratch. There is no idempotency key and no "absorbed" guard on the route.
Dossier failures are invisible. The per-NPC loop swallows every exception with a bare continue at backend/src/grimoire/routes.py:3143-3144 and reports nothing in the response payload. A user whose dossiers silently stopped updating — because of a rate limit, a parse failure, or a bad character record — gets a successful-looking absorb with no signal. Contrast this with the audit step immediately below it, which threads a structured mechanics.status of ok/degraded/failed back to the UI (backend/src/grimoire/routes.py:3107-3111). The audit's design is the right one; the dossier loop predates it.
The audit's blanket exception handler is correct but broad. backend/src/grimoire/routes.py:3103-3105 catches bare Exception around the entire audit pipeline, by explicit design ("never fail absorb"). It converts any bug in backend/src/grimoire/store/audit.py into a user-visible "audit failed" string rather than a crash — good for availability, but it also means a genuine programming error in the audit path will never surface as a traceback in normal use.
Cost is unbounded in the number of NPCs. One extraction call plus N dossier calls plus one audit call, all sequential, all awaited inside a single HTTP request. A large scene cast makes this a multi-minute request with no progress reporting.

Flow 3 — resolving a record through the campaign overlay

The rule that makes campaigns cheap: read through to the world, materialize on write. Getting this wrong is the codebase's most repeated bug class, so it is worth being able to draw.

Seams

Read-through is opt-in, not enforced. Correctness depends on every campaign-scoped read going through backend/src/grimoire/store/overlay.py rather than reading the campaign root directly. Nothing prevents a new route from calling store.campaigns.campaign_root(cid) and reading a file itself — and two places already do exactly that for climate.json (backend/src/grimoire/routes.py:2018 and backend/src/grimoire/routes.py:2082). A record read that way is invisible to inheritance and to tombstones.
Materialization writes two files and can be interrupted between them. _materialize_flat copies the record, then reads, mutates and rewrites the campaign manifest (backend/src/grimoire/store/overlay.py:73-90). A crash between the copy and the manifest write leaves a materialized record with no recorded sync base, which the three-hash comparison in backend/src/grimoire/store/sync.py:97-100 will then classify differently than it should. The same two-step shape appears in materialize_actor (backend/src/grimoire/store/overlay.py:289-308), where it spans an entire directory copy.
A missing world is handled by resolving to a path that holds nothing. wroot_of deliberately never raises when a campaign's world was deleted or its world meta is empty (backend/src/grimoire/store/overlay.py:31-38) — every resolver then simply finds no records there. This is a defensible choice, well documented in place, but it converts a data-integrity problem into silently empty lists rather than an error the user sees.

The layering is real; the module boundaries inside the store are not

Grimoire's vertical boundary is genuinely clean: prompt text lives only in templates/, LLM calls happen only in the route layer, and stores are pure file I/O. The horizontal boundary — between the ~60 modules inside backend/src/grimoire/store/ — has largely dissolved. All 41 top-level store modules sit in a single import cycle, and the codebase's own answer to that pressure is a documented convention of function-level imports rather than a dependency direction.

Boundary violations

The route layer performs filesystem I/O. Besides the climate.json pair above, backend/src/grimoire/routes.py:785-794 opens a raw file descriptor and unlinks a temp file for module import. These are the only places the HTTP layer touches the disk directly; everything else goes through store. Small in volume, but they are precedent — and the climate.json read is exactly the campaign-root-direct-read pattern the overlay design exists to prevent.
The lock that governs all campaign mutation lives in the sheets module. sheets.lock_for(cid) (backend/src/grimoire/store/sheets.py:618-627) is the single serialization point for sheet writes, proposal transitions, audit application and module publication. Both backend/src/grimoire/store/proposals.py:28-34 and backend/src/grimoire/store/module_edit.py:4-10 document borrowing it and explain why the domains must be unified. The reasoning is sound; the placement means a reader looking for the app's concurrency model has no reason to open backend/src/grimoire/store/sheets.py to find it.

What the three import cycles actually mean

benign The 41-module store cycle

The dependency analyzer reports every module under backend/src/grimoire/store/ in one cycle. This is largely an artifact of Python package semantics: from . import campaigns inside a submodule imports the package, and backend/src/grimoire/store/__init__.py:5-12 imports all 60-odd submodules eagerly to build the flat store.* namespace. That alone would make every submodule cyclic with the package regardless of the real dependency direction.

The part that is not an artifact is what the codebase had to do to keep it working: at least 20 function-level imports exist purely to break genuine cycles, each annotated. Representative cases — backend/src/grimoire/store/campaigns.py:141 ("campaigns is imported by these"), backend/src/grimoire/store/appearances.py:201 ("scenes and appearances is already a lazy pair"), backend/src/grimoire/store/module_display.py:65 ("deferred: modules imports us"), backend/src/grimoire/store/proposals.py:33, backend/src/grimoire/store/chronicle.py:84. The comments are excellent and the pattern is applied consistently, but it is a workaround holding a layering problem in place: campaigns, scenes, appearances and overlay are genuinely mutually dependent, and the top four fan-in modules (backend/src/grimoire/store/__init__.py at 114, backend/src/grimoire/store/campaigns.py at 64, backend/src/grimoire/store/worlds.py at 51, backend/src/grimoire/store/characters.py at 46) are all also fan-out participants.

deliberate and documented The LLM provider cycle

backend/src/grimoire/llm.py ↔ backend/src/grimoire/openrouter.py / backend/src/grimoire/claude_agent.py / backend/src/grimoire/openai_compatible.py. The providers import LLMError from backend/src/grimoire/llm.py at module scope; backend/src/grimoire/llm.py imports the providers inside LLMClient.__init__ instead, with the reason stated in place at backend/src/grimoire/llm.py:18-21. The clean fix — a shared errors.py holding LLMError — would cost one small file and remove the cycle entirely. This is the cheapest cycle in the codebase to eliminate.

worth fixing The module-editor component cycle

Five frontend files cycle: frontend/src/components/ModuleEditor.tsx imports the four section components, and each of them imports shared helpers back out of frontend/src/components/ModuleEditor.tsx — see frontend/src/components/ModuleSchemaEditor.tsx:3, frontend/src/components/ModuleContentEditor.tsx:5, and the corresponding lines in frontend/src/components/ModuleRulesEditor.tsx and frontend/src/components/ModuleDisplayEditor.tsx. The shared pieces are useModuleDryRun, ErrorList, ImpactConfirm and the SaveFn type, all defined at frontend/src/components/ModuleEditor.tsx:13-129 above the component itself. Extracting those four exports into a moduleEditShared.ts would break the cycle with no behaviour change; as it stands, bundlers resolve it but the initialization order is load-order dependent.

The store assumes one writer, one process, and no crashes

Grimoire's correctness rests on a small set of assumptions about how its files are touched. Most are enforced somewhere and documented well — this codebase writes unusually good "why" comments. The gap is that the strongest guarantees (atomic writes, a serialization lock, a heal-before-retire rule) were added with the newer mechanics subsystem and were never retrofitted onto the older core, so the oldest and most-written data — scene transcripts — has the weakest durability guarantees in the system.

Failure handling

Two silent-swallow sites, one of them on the main flow. The dossier refresh loop discards every exception with a bare continue and reports nothing (backend/src/grimoire/routes.py:3143-3144) — a user can lose dossier updates indefinitely without a single visible symptom. The custom-calendar loader does the same on import failure (backend/src/grimoire/store/calendars/plugins.py:48-49), though there the retry-next-call behaviour is documented and reasonable for a plugin system.
The audit pipeline is the pattern to copy. _run_audit wraps its whole pipeline in one failure boundary and converts any exception into a structured status the UI renders — status of ok / degraded / failed, plus reason, warnings and dropped (backend/src/grimoire/routes.py:3073-3111). Failures degrade visibly instead of vanishing. The dossier loop sitting twenty lines above it does the opposite.
Reads are permissive, writes are strict — deliberately. Several modules state this contract explicitly: backend/src/grimoire/store/sheets.py:1-9 ("read/coverage never raise on malformed sheet content; writes validate strictly"), and backend/src/grimoire/store/paths.py:25-33 silently returns an empty dict for an unparseable bootstrap pointer. This keeps a corrupted file from bricking the app, at the cost of corruption being invisible until a write fails.
No request-level timeouts. Neither the streaming routes nor the awaited client.complete calls set a deadline; whatever bound exists comes from each provider's httpx client. Absorb — which issues one call per present NPC sequentially — has no ceiling on total duration.

Concurrency

The backend is a normal async FastAPI app: streaming endpoints are async generators, and most store work is synchronous file I/O executed inline. Shared mutable state is small and explicit — a per-campaign RLock registry (backend/src/grimoire/store/sheets.py:614-627), a global module-edit lock, and a module-level LLMClient singleton created at import (backend/src/grimoire/routes.py:21-22). Lock ordering is disciplined: backend/src/grimoire/store/module_edit.py:4-10 states the rule that a publishing writer takes the global edit lock and then every campaign lock, and that LLM play flows hold their single campaign lock across resolve/load/compute so they never see a half-published pack.

The locks are in-process, but the product advertises multi-process use. threading.RLock protects nothing across processes, yet the README explicitly recommends pointing the data directory at Dropbox or iCloud to share one library across devices, and the same store is reachable from the desktop app and the Android APK. Two devices — or two backend processes on one machine — editing one campaign have no mutual exclusion at all, and because most records are rewritten whole (rather than merged), the loser's edit is silently overwritten. The threat model in backend/src/grimoire/store/module_edit.py:4-10 names exactly two actors, User and LLM, both inside one process; the sync-folder scenario adds a third the design does not account for.

Risk ranking

1. Scene transcripts are rewritten non-atomically on every message. backend/src/grimoire/store/scenes.py:316-323 reads the whole scene, appends a block, and writes the whole file back with write_text. A crash, a full disk, or a sync-client conflict mid-write truncates the file — and a scene transcript is the single piece of user data in this app that cannot be regenerated. The fix already exists in the codebase (the temp-file + os.replace helper pattern used by six other modules); it simply has not been applied here. Highest likelihood × highest blast radius.
2. Concurrent writers across processes or devices have no protection. Given a documented, encouraged sync-folder workflow, last-writer-wins on whole-file rewrites is a data-loss path with no detection and no user-visible symptom.
3. Absorb is a long, non-atomic, non-idempotent multi-phase write. Prose edits commit before the dossier loop and audit run (backend/src/grimoire/routes.py:3132), there is no absorbed-already guard, and a re-run re-applies everything. Interrupted absorbs leave campaigns in states no code path expects.
4. backend/src/grimoire/routes.py is a 3481-line file with 563 branches and 156 commits — the top hotspot by a factor of four. It holds all 252 endpoints plus the streaming machinery, the fence protocol, the proposal-healing invariant and the audit orchestration. The hand-maintained invariant in point 3 of the Flows tab lives here precisely because there is nowhere better to put it. Splitting by domain (campaigns / worlds / modules / config) is mechanical and would cut the review surface of every future change to this file.
5. Silent dossier failures. Low blast radius per occurrence, but unbounded in time — nothing ever tells the user their campaign memory stopped being refreshed. Cheap to fix by mirroring the audit's status-reporting shape.
