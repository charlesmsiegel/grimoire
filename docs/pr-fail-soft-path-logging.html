Two silent fail-soft reads now report themselves

Nothing about what the store does with a corrupt file changes: a malformed <campaign>/deleted.json still reads as "no tombstones", and a malformed ~/.grimoire.json still reads as "no configured data dir". The change is that both now emit a WARNING naming the file and the consequence, where before they returned the empty value in silence.

Those two reads were singled out because their fallback fails in the direction a user cannot see. An empty tombstone set means nothing was deleted, so records deleted campaign-side reappear inherited from the world (backend/src/grimoire/store/overlay.py:69-83). An empty pointer drops data_dir, so a library kept in a synced folder opens empty at ~/.grimoire (backend/src/grimoire/store/paths.py:26-38). Every other fail-soft read in the store degrades toward less content, which a user notices; these two degrade toward more content and a wrong location.

The logging lives in one new module, backend/src/grimoire/store/failsoft.py, not because two call sites justify an abstraction on their own, but because both need the same non-obvious thing — warnings deduplicated per file version. Measured on this tree, a 20-character listing costs 41 deleted() calls and 224 _read_pointer() calls, so an unconditional log.warning would answer one corrupt file with hundreds of identical lines per page load.

Two undisclosed-by-the-issue behaviour changes, both widening the fallback.

1. overlay.deleted() previously caught only (json.JSONDecodeError, OSError). It now goes through read_json, which catches ValueError — so a <campaign>/deleted.json that is not valid UTF-8 now falls soft with a warning instead of propagating UnicodeDecodeError out of every campaign read. backend/src/grimoire/store/failsoft.py:125. This is strictly more fail-soft and matches what paths._read_pointer already did, but it is a behaviour change, not logging.

2. Both sites lost their path.exists() pre-check; read_json reads straight through and treats FileNotFoundError as absence (backend/src/grimoire/store/failsoft.py:121-124). Same answer, one fewer syscall, and the exists-then-read TOCTOU is gone — a file deleted between the two calls used to raise.

Classification: bugfix (observability), not a feature. No route, schema, payload or on-disk format is touched. Three source files, three test files, one directory pair. Nothing unrelated is bundled in.

What did not change, where a reader might expect it to

  • The other fail-soft sites stay silent. audit, changes, commits and the rest keep their bare except: return {}. That is deliberate and argued in backend/src/grimoire/store/failsoft.py:56-58 — they degrade toward less content, which a user can see, and making them chatty would bury these two. A reviewer who wants a general "all fail-soft reads log" rule should say so; this change explicitly declines it.
  • Nothing surfaces in the UI. data_dir_info() (backend/src/grimoire/store/paths.py:95-106) still reports source: "default" for a corrupt pointer, indistinguishable from an unconfigured one. The Configuration page therefore still shows a user with a broken pointer exactly what it shows a user who never set one. The log is now the only channel.

That is pre-existing, and it is now at least preceded by a warning — but the destructive overwrite itself is untouched.

What moved

  • The exists() probe is gone. The read happens first and FileNotFoundError is what "absent" means now (backend/src/grimoire/store/failsoft.py:121-124). One fewer syscall on a call made 41 times per 20-record listing, and the exists-then-read race disappears.
  • A stat() is added, but only on the failure path (backend/src/grimoire/store/failsoft.py:85-90). An intact file costs no extra syscall.
  • The shape check moved into the helper. isinstance(data, list) used to live in deleted() and silently produced the same empty set as a parse error; it now takes the same warning (backend/src/grimoire/store/failsoft.py:128-130).
  • Error propagation widened once: UnicodeDecodeError used to escape deleted(), and is now absorbed with a warning (backend/src/grimoire/store/failsoft.py:125).

Flow 2 — home() over a corrupt bootstrap pointer

Same shape, higher stakes and much higher call volume: home() re-reads the pointer on every path resolution — 224 times in a single 20-character listing on this tree — so this is the flow the de-dup exists for.

What moved

  • The corrupt edge is the one that used to be indistinguishable from missing. It now carries a warning naming the pointer path and the directory the store falls back to (backend/src/grimoire/store/paths.py:35-38).
  • The message is built on every call, warning or not — the f-string at backend/src/grimoire/store/paths.py:37-38 interpolates DEFAULT_HOME unconditionally. On a path taken 224×/listing that is real but tiny work (~200 ns) next to the file read it accompanies (~50 µs); a lazy message would complicate the API for <0.5% of the call's cost. Flagged so the reviewer can disagree deliberately.
  • Recovery path is unchanged and now proven: setting a new location from the Configuration page rewrites the pointer whole, so the warning stops (backend/tests/test_data_dir.py:149-159).
No flow changes for an intact store. On the success path read_json adds exactly one dict pop (backend/src/grimoire/store/failsoft.py:131) and removes one exists() syscall. Every route, lock boundary, and materialization order is untouched.

backend/src/grimoire/store/failsoft.py the only file worth arguing about

132 lines, 58 of them module docstring, 2 public-ish functions. The code is small enough to be obviously right; the question is whether it should exist at all for two call sites.

It earns its keep on the de-dup, not on the JSON parsing. Two inline log.warning calls would have been fewer lines, and would have emitted 41 and 224 identical warnings per 20-record listing respectively — measured, not estimated. Any dedup strategy has to live somewhere, and duplicating a stat-signature cache in both overlay and paths is worse than sharing it.

backend/src/grimoire/store/failsoft.py — lines 64–69
+ def _warn(path: Path, detail: str, consequence: str) -> None: + signature = _signature(path) + if signature is not None and _warned.get(path) == signature: + return + _warned[path] = signature + log.warning("%s is unusable (%s) -- %s", path, detail, consequence)

Checks that hold: the cache is keyed per path, so one corrupt file cannot mask another (backend/tests/test_failsoft.py:179-187); a changed file re-warns (backend/tests/test_failsoft.py:91-101); an unstattable file re-warns every time rather than being suppressed once by a None that matches itself — that is what the signature is not None guard buys, and the comment at backend/src/grimoire/store/failsoft.py:70-77 says so.

backend/src/grimoire/store/overlay.py clean

The one thing to check is that the empty-list case still returns an empty set rather than tripping over None: set(refs) if refs else set() at backend/src/grimoire/store/overlay.py:83 handles None, [] and a populated list identically to the old code.

Invariant impact

  • Strengthened, in documentation: the store's fail-soft convention was prose spread across eight-plus sites. backend/src/grimoire/store/failsoft.py:1-58 now states the rule and its exception — silence is right when the fallback holds less content than the file did — and names the two sites that fail the other way. Nothing enforces it mechanically; this repo does write AST guards (backend/tests/test_paths_guard.py, backend/tests/test_overlay_guard.py), so a future guard could.
  • Unchanged: the copy-on-write overlay invariants (backend/src/grimoire/store/overlay.py:1-29) are untouched — a corrupt tombstone file still resurrects records, exactly as before. This change makes the violation audible, not impossible.
  • New assumption in one more place: "a corrupt file returns the empty value" is now partly failsoft's responsibility rather than each caller's. Anything routed through it inherits the warning too, which is why the module docstring explicitly forbids adding callers without the same argument.

Verdict — mergeable

The change does what it claims, preserves every fallback value, and is covered by tests that assert both the fallback and the report. Nothing here is a must-fix.

Should-fix / consider

  1. Surface the corrupt pointer in the Configuration page, not only the log. data_dir_info() at backend/src/grimoire/store/paths.py:95-106 still reports source: "default" for a corrupt pointer — identical to a user who never configured one. The user staring at an empty library is looking at that page, not at stderr. Deliberately out of this change's scope; worth a follow-up issue.
  2. add_deleted destroys the corrupt file it just warned about — reproduced. backend/src/grimoire/store/overlay.py:86-87 rewrites <campaign>/deleted.json from deleted(cid), which is the empty set when the file is corrupt. Sequence: two records deleted, the file truncated by a sync conflict, then one more campaign-side delete — the file is rewritten as ["lore/gamma"], the first two records are permanently back, the file is valid JSON again, and the warning never fires for that campaign again. Pre-existing and untouched here, but it caps how much the warning is worth: for the commonest corruption it fires once and then the evidence is gone. Deliberately not fixed in this change — refusing the write, or quarantining the bad file, is a product decision about delete semantics, not logging.
