Overview

Grimoire is a local-first, single-player AI roleplay studio — think SillyTavern, rebuilt around a clean worlds → campaigns → scenes hierarchy with git-friendly plaintext storage and a streaming chat engine backed by OpenRouter.

The core idea in three sentences:

  1. You build a World: a reusable library of character cards, player personas (PCs), lore & location entries, and greetings.
  2. You spin up a Campaign from a world — a deep copy that you can play and diverge, while still pulling curated updates back from the world via a three-way sync.
  3. Inside a campaign you play Scenes: you add a cast, type a message, and the context builder assembles every relevant piece — character definitions, personas, and keyword-activated world-info — into the message list that streams to the model.

Everything is stored as Markdown + YAML-ish frontmatter and JSON under ~/.grimoire/. There is no database — the filesystem is the database, which makes the whole library diffable, portable, and inspectable.

Three things to internalize from this diagram:

On-Disk Data Model

All state lives under ~/.grimoire/ (override with $GRIMOIRE_HOME). Two top-level trees: worlds/ (the reusable library) and campaigns/ (playable instances). Files are Markdown-with-frontmatter for human-editable content and JSON for structured graphs/state.

A campaign is a partial deep-copy of its world: only the actors/entities you actually pull in are materialized, each pinned to a specific version + a "base" hash for sync.

A Scene transcript (scenes/<sid>.md)

The chat log is plain Markdown — role-labeled blocks the store parses back into messages. This is why your roleplay is greppable.

---
title: 'Meeting Seraphine'
model: 'anthropic/claude-opus-4.1'
created: '2026-06-24T14:30:00Z'
updated: '2026-06-24T15:45:00Z'
dismissed: 'goblin-king,the-warden'
---

**Grimoire:** You push open the tavern door…

**You:** I scan the room for the hooded figure.

**Grimoire:** Seraphine's eyes meet yours from the corner booth…
Format note: frontmatter.py implements a deliberately small YAML-ish parser (string scalars only, custom single-quote escaping) so there's no heavy YAML dependency. **You:** / **Grimoire:** markers (see scenes.py) delimit user vs. assistant turns.

Worlds vs. Campaigns — the central distinction

This separation is the spine of the whole app, so it's worth making explicit.

WorldCampaign
RoleAuthoring library / templatePlayable, divergent instance
ContainsCharacters, PCs, lore, locations, greetings, tags, plotmapScenes (chat), a copy of the actors/entities actually used, play-state
Created fromScratch / importsPOST /campaigns with a world id
MutationEdited freely in the World editorDiverges as you play & edit locally
Reconciliation—Pulls world edits via three-way sync

Because the campaign holds its own copy of every actor (pinned to a version + a base hash), editing a world character later doesn't silently rewrite an in-progress campaign. Instead it surfaces as a pending "incoming" change you accept or reject.

Key details in this flow

  • The user message is persisted before building context (routes.py post_chat), so the new turn is part of the history the context builder sees.
  • The assistant reply is persisted by the server, not the client — inside _chat_stream's generator, deltas are accumulated and append_message(assistant, …) runs when the stream completes (or partially, on error, so nothing is lost).
  • retry is the same path minus the append: it just rebuilds messages from existing history and re-streams.
  • Errors are normalized by openrouter.py into {kind, detail} (missing_key, auth, rate_limit, network, bad_response) and forwarded as an SSE error event — the UI shows a readable banner + Retry.

★ The Context Builder

This is the heart of Grimoire. store/context.py turns a scene's cast + activated world-info into the exact messages[] list sent to the model — SillyTavern-faithful in ordering.

Why it matters: Prompt order is the product. The same cards in a different order produce a different roleplay. build_messages() is small (~65 lines) but every line encodes a deliberate decision about what the model sees and when.

[
  { role: "system",    content: <assembled system block, substituted> },   # if non-empty

The post_history_instructions slot (a.k.a. depth-0 / "UJB" in SillyTavern) is appended after the conversation. This is the classic trick for instructions that must not be drowned out by a long history — they sit closest to the generation point.

World-Info activation

World-info (lore + locations entries) is selected, not dumped. The activate() function is intentionally the single swap point for smarter retrieval later (embeddings, etc.). Today the rule is keyword-based, faithful to SillyTavern:

  • Keyless entries → always on. An entry with no keys is unconditional background lore.
  • Keyed entries → conditional. Included only if any key matches as a whole word (case-insensitive) within recent_text.
  • recent_text = the last context_scan_depth messages (config, default 8) joined together. Depth 0 is special-cased to mean "no scan window" (so keyed entries simply won't fire) — guarding against history[-0:] meaning the whole list.
# context.py — the activation rule
def activate(entries, recent_text):
    out = []
    for e in entries:
        keys = e.get("keys") or []
        if not keys:                       # keyless = always-on
            out.append(e); continue
        if any(re.search(rf"\b{re.escape(k)}\b", recent_text, re.IGNORECASE)
               for k in keys):             # whole-word, case-insensitive
            out.append(e)
    return out

Token substitution

{{user}} and {{char}} placeholders in any card/lore text are replaced with the actual names of the scene's current cast before sending:

TokenReplaced with
{{user}}Comma-joined names of all player-role actors in the scene
{{char}}Comma-joined names of all npc-role actors in the scene

Substitution is case-insensitive and skips empty values — a player-less scene leaves {{user}} literal rather than substituting an empty string. The replacement uses a function callback so card text containing \1-style sequences is inserted verbatim (no regex group expansion footgun).

The Opener — a parallel, ephemeral build

Starting a fresh scene from a prompt uses a second builder, build_opener_messages(). It's deliberately character-less and world-informed:

What goes in

  1. A fixed instruction: "Write the opening narration… second person… don't act for the player."
  2. Only the player persona blocks (no NPC cards).
  3. World-info activated against the prompt itself (not history — there is none yet).

What's different

  • Ephemeral: streams via _ephemeral_stream and is not persisted — the user previews and decides.
  • The user message is the raw prompt (substituted).
  • Lets you set a vivid scene before any NPC has "appeared."

World → Campaign Sync

Because a campaign owns copies of its actors/entities, world edits don't auto-propagate. store/sync.py implements a three-way merge per ref to classify what changed and let you accept/reject.

For each ref (a kind/id like lore/the-pact or characters/seraphine) three content hashes are compared:

HashMeaning
worldThe world entity's current hash (or None if deleted)
baseThe hash recorded when the campaign last synced this ref (the manifest / appearance base)
mineThe campaign's current copy hash (may have diverged through local edits)

    Q1 -- no --> Q2{mine is None?}
    Q2 -- yes --> NEW["status: NEW
not in campaign yet"]
    Q2 -- no --> Q3{mine == base?}
    Q3 -- yes --> UPD["status: UPDATE

NEW — exists in world, absent in campaign UPDATE — safe fast-forward CONFLICT — diverged both ways

Accept vs. reject are the same operation with one flag (_advance(..., copy=)):

  • accept(refs) → copy=True: overwrite the campaign copy with the world version and advance the base hash.
  • reject(refs) → copy=False: keep your copy, but advance the base hash so the change stops nagging.

Entities (lore/locations) track their base in sync.md; actors (characters/pcs) track it in appearances.json. campaigns_for_world() rolls up pending counts so the World view can badge each campaign with new update conflict.

Greetings & the Plotmap

Greetings are pre-written scene openers tied to a character+version, optionally gated by player tags and chained into a directed graph (the plotmap) that models story progression.

A greeting

  • character + version it belongs to
  • body — the opening message
  • requires_tags + predecessor_join (all/any) — gating
  • Imported in bulk from a card's first_mes + alternate_greetings

The plotmap (plotmap.json)

  • leads_to — greetings unlocked after this one is played
  • excludes — greetings made unavailable (mutually-exclusive branches)
  • playing.py computes available greetings from played.json + player tags

Starting a scene from a greeting (playing.start_from_greeting) does three things atomically: makes the character appear in the scene, records the greeting as played, and appends its body as the first assistant message.

Character Cards

Characters use the SillyTavern Character Card V3 shape (spec: "chara_card_v3"). store/cards.py handles import/export across three carriers — all in pure stdlib (no Pillow):

FormatHow the card travels
jsonPlain V3 JSON file
pngJSON base64-embedded in a PNG tEXt chunk (ccv3) — the iconic "character card image"
charxZIP archive containing card.json (+ optional embedded assets)

to_v3() normalizes older V2/bare cards up to V3 without mutating the input. Characters are versioned: a character folder holds many <vid>.json cards (e.g. default, corrupted, future) plus a default_version pointer. Per-version images live under assets/<vid>/ and are served (not hashed into sync). A card's embedded character_book can be lifted into editable world lore via the lorebook importer.

Cast & Appearances

appearances.json is the source of truth for who is in a campaign. When you add an actor to a scene (appear()), it:

  1. Locks the version & role. Re-appearing the same actor with a different version/role raises AppearError — an actor is consistent across the whole campaign.
  2. Copies the actor from world → campaign (card/persona + meta + assets) and records the base hash for sync.
  3. Appends the scene id to the actor's scenes list (so one actor can span scenes).

Two derived features ride on this state:

  • Cast / roster — scene_cast() and roster() drive the CastPanel UI and feed the context builder.
  • Suggestions — suggestions() scans the text of in-scene characters' cards for whole-word mentions of other world characters not yet present (minus dismissed ones), surfacing "you mentioned X — add them?" prompts.

The SSE Streaming Loop (frontend)

The mirror image of the server's _chat_stream. CampaignView owns three pieces of state: messages (committed turns), streaming (the in-flight assistant text), and busy/error.

flowchart LR
    subgraph send["send() — CampaignView"]
      I["input + Enter"] --> APP["optimistic push
user message"]
      APP --> RS["runStream(start)"]
    end
    RS --> SP["streamPost()
client.ts"]
    SP --> PARSE["parseSSEChunk()
stream.ts"]
    PARSE -->|"{delta}"| ACC["acc += delta
setStreaming(acc)"]
    ACC --> RENDER["live render
+ cursor"]
    RENDER -.next token.-> PARSE
    PARSE -->|"{done}"| FIN["push final assistant msg
clear streaming"]
    PARSE -->|"{error}"| ERR["error banner + Retry"]

    style ACC fill:#e3d4f5,stroke:#5e3f8c,stroke-width:3px,color:#1c1208
  1. send() optimistically appends the user message and calls runStream(onEvent => api.chat(cid, sid, content, onEvent)).
  2. streamPost() POSTs, then reads res.body as a byte stream, decoding into a buffer.
  3. parseSSEChunk() splits on \n\n, JSON-parses each data: line into a ChatEvent, and fires onEvent.
  4. Each delta accumulates into acc and re-renders via setStreaming(acc) — that's the live typing effect.
  5. On done, the accumulated text is committed to messages and streaming is cleared; on error, a readable banner appears with a Retry button.
