Overview

Grimoire is a local-first, single-player AI roleplay studio — think SillyTavern, rebuilt around a clean worlds → campaigns → scenes hierarchy with git-friendly plaintext storage, a streaming chat engine backed by OpenRouter, and a continuity engine that remembers what happened after every scene.

The core idea in four sentences:

  1. You build a World: a reusable library of character cards, player personas (PCs), lore & location entries, greetings, tags, and a calendar.
  2. You spin up a Campaign from a world — a full deep copy that you play and diverge, while still pulling curated world updates back through a three-way sync.
  3. Inside a campaign you play Scenes: script-format transcripts where every post carries a speaker, and the context builder assembles cards, personas, keyword-activated world-info, and continuity state into the message list that streams to the model.
  4. When a scene ends you absorb it: an LLM pass extracts a summary, character-state changes, relationship shifts, and plot-thread movements; you review the proposed edits and the accepted ones are written back — and fed into every future scene's prompt.

Everything is stored as Markdown + YAML-ish frontmatter and JSON under ~/.grimoire/. There is no database — the filesystem is the database, which makes the whole library diffable, portable, and inspectable. And every string sent to the LLM lives in a top-level templates/ directory of Jinja2 files, editable without touching code.

Four things to internalize from this diagram:

  • The store layer is the whole model. Routes are thin: validate input, catch *NotFound exceptions, map to HTTP codes. All real logic lives in store/.
  • context.py gathers, templates/ speaks. Store modules produce data dicts; every literal string the model sees is a Jinja2 template. Editing a template changes the app's prompts live (auto-reload), no restart.
  • The continuity engine closes a loop. Scenes feed absorb, absorb writes chronicle/state/relationships/plot files, and those files feed the next scene's context.
  • Streaming is one-way SSE. Chat, retry, regenerate, opener, chub-gallery downloads, and image localization all stream text/event-stream frames.

A Scene transcript (scenes/012--2026-06-24--meeting-seraphine.md)

The chat log is a plain-Markdown script: every message is a **<Speaker>:** block. Scene filenames follow the grammar <number>--<date>--<title-slug> (number first, zero-padded, so filename order = play order; the date section appears once the scene has an in-world date).

---
title: 'Meeting Seraphine'
created: '2026-06-24T14:30:00Z'
…plus: pcless flag, in-world date & location history,
 dismissed cast suggestions, absorbed one-liner/summary…
---

**You:** I scan the room for the hooded figure.

**Seraphine Vale:** "You're late," she murmurs, not looking up…

**Grimoire:** The tavern's hush deepens as the door swings shut.
Format notes: frontmatter.py implements a deliberately small YAML-ish parser (string scalars only) so there's no heavy YAML dependency. Roles are derived, not stored: a message is user-side iff its speaker is You or matches a role=player cast name (scenes.py). One model reply is split into per-speaker posts when it contains multiple **Name:** blocks.

Worlds vs. Campaigns — the central distinction

This separation is the spine of the whole app, so it's worth making explicit.

WorldCampaign
RoleAuthoring library / templatePlayable, divergent instance
ContainsCharacters, PCs, lore, locations, greetings, tags, plotmap, calendar, taglinesScenes, a full copy of the world's records, play-state, and the continuity files (chronicle, relationships, plot, changes, dossiers)
Created fromScratch / imports (cards, chub.ai, lorebooks)POST /campaigns with a world id — deep-copies every record and stamps world_copy: full
MutationEdited freely in the World editorDiverges as you play; most records are editable at campaign scope too (see sync)
Reconciliation—Pulls world edits via three-way sync (lore, locations, greetings, plotmap, whole actors)

Because the campaign holds its own copy of everything (each ref pinned to a recorded "base" hash), editing a world record later never silently rewrites an in-progress campaign — it surfaces as a pending incoming change you accept or reject. Pre-full-copy campaigns are lazily backfilled on first touch (ensure_campaign_copy), which never clobbers an existing campaign copy.

Key details in this flow

  • The user message is persisted before building context, so the new turn is part of the history the context builder sees. If exactly one player is seated, the message is stamped with that PC's name as its speaker.
  • An empty send is a turn too. Empty input (or any input in an offscreen scene) becomes an ephemeral director note — sent as the final user message of that one call, never written to the transcript. The default note is templates/scene/director_note.j2 ("Continue the scene.").
  • The reply is persisted by the server — _persist_reply splits one model reply containing several **Name:** blocks into separate per-speaker assistant posts, so the frontend re-fetches the scene when the stream ends and renders each speaker under its own plate.
  • retry re-streams from current context; regenerate drops the trailing assistant run first and optionally injects a one-shot guidance system message (scene/regenerate_guidance.j2) — the guided-reroll popover.
  • Errors are normalized by openrouter.py into {kind, detail} (missing_key, auth, rate_limit, network, bad_response) and forwarded as an SSE error event — the UI shows a readable banner + Retry.

The Prompt Template Layer

Every string grimoire sends to an LLM lives in the top-level templates/ directory as Jinja2. Nothing prompt-shaped is hard-coded. grimoire/prompts.py is a ~25-line renderer (StrictUndefined, auto-reload) — edit a template and the running app's prompts change immediately.

Layout conventions

  • One folder per LLM call, one file per message part: system.j2 + user.j2.
  • Variants live in subfolders — scene/opener_instruction/{standard|offscreen}.j2, scene/sections/story_so_far/{full|compact}.j2 — selected by a variable.
  • snippets/ holds shared line formats (transcript lines, relationship lines, plot-thread lines).
  • Files starting with _ are macro libraries (e.g. scene/_persona_blocks.j2).

The five calls

  • scene/ — the context builder (chat / retry / regenerate / director / opener)
  • absorb/ — end-of-scene extraction
  • dossier/ — per-NPC dossier refresh (inside absorb)
  • tagline/ — one-line character blurb generator
  • scene_suggestions/ — next-scene premises + greeting ranking
Keeping templates honest: scripts/verify_templates.py checks the wiring (each builder passes the documented variables to the right template) against a throwaway store exercising every section — it never pins template text, so editing a prompt cannot fail it. templates/README.md documents each template's variable contract.

★ The Context Builder

The heart of Grimoire. store/context.py turns a scene's cast + continuity state + activated world-info into the exact messages[] list sent to the model. The module gathers data; templates/scene/system.j2 owns the text and section order.

Why it matters: Prompt order is the product. The same cards in a different order produce a different roleplay. One _assemble() pass feeds four different builders — build_messages (chat/retry/regenerate), build_director_messages, build_opener_messages, and context_sections (the inspector's token breakdown) — so what you inspect is exactly what the model sees.

The post_history_instructions slot (a.k.a. depth-0 / "UJB" in SillyTavern) is appended after the conversation — the classic trick for instructions that must not be drowned out by a long history. Openers go one further: the shape rules render after even that, right at the generation point.

World-Info activation

World-info (lore + location entries) is selected, not dumped. activate() is intentionally the single swap point for smarter retrieval later. The rules today:

  • Owned entries are gated first. An entry whose owners list is non-empty stays silent unless one of its owners (a kind:id ref — character, PC, or the current location) is present in the scene. Secrets tied to a character never leak into scenes they're not in.
  • Keyless entries → always on (once owner-gating passes) — unconditional background lore. Exception: a keyless location never rides world-info; it surfaces only as the Current setting when the scene is actually there.
  • Keyed entries → conditional. Included only if any key matches as a whole word (case-insensitive) within recent_text — the last context_scan_depth messages (config, default 8; depth 0 is special-cased to "no scan window"). For openers, the prompt text stands in for the missing history.
# context.py — the activation rule
def activate(entries, recent_text, present=frozenset()):
    out = []
    for e in entries:
        owners = e.get("owners") or []
        if owners and not any(o in present for o in owners):
            continue                       # owned but no owner in scene -> never leak
        keys = e.get("keys") or []
        if not keys:                       # keyless = always-on
            out.append(e); continue
        if any(re.search(rf"\b{re.escape(k)}\b", recent_text, re.IGNORECASE)
               for k in keys):             # whole-word, case-insensitive
            out.append(e)
    return out

Token substitution

{{user}} and {{char}} placeholders in any card/lore text are replaced with the actual names of the scene's current cast before sending. This is a data transformation applied by code (context._substitute) — never by templates.

TokenReplaced with
{{user}}Comma-joined names of all player-role actors in the scene (in a pcless scene: the campaign's player actors — the reference cast)
{{char}}Comma-joined names of all npc-role actors in the scene

Substitution is case-insensitive and skips empty values — a player-less mapping leaves {{user}} literal rather than substituting an empty string. The replacement uses a function callback so card text containing \1-style sequences is inserted verbatim. At import time, {{char}} is additionally baked into the character's own name field so cards read naturally in editors.

Openers — full-context, ephemeral, shape-ruled

Starting a fresh scene from a prompt uses build_opener_messages(). It is no longer a stripped-down build — it sees everything:

What goes in

  1. An opener instruction prepended to the full 16-section system block (opener_instruction/standard.j2: second person, don't act for the player; offscreen.j2: third person, NPCs only).
  2. The full Story so far recap — complete summaries of the last 5 scenes.
  3. World-info activated against the prompt itself (no history yet).
  4. The (substituted) prompt as the user message.

What's different

  • Ephemeral: streams via _ephemeral_stream, never persisted. The UI previews it; Use adopts it as the scene's first post (POST …/first-post), or Save as greeting keeps it for later.
  • Shape rules go last: opener_shape.j2 rides the final system message — cap of five paragraphs, one per present character plus narration, each under its **Name:** marker — placed after everything so it outranks the big system block.

Offscreen (PC-less) scenes — director mode

A scene created with pcless: true has no player seated (seating a player 409s). The model plays all the NPCs; you direct:

  • The system block adds the Offscreen scene instruction and the Absent player characters reference section, so NPCs can talk about the PCs without them present.
  • Every user input becomes an ephemeral director note (build_director_messages) — steering that is followed but never acknowledged in fiction, and never stored in the transcript. Blank input sends "Continue the scene."
  • Greetings carry a matching pcless flag: offscreen scenes can only start from offscreen greetings (and vice versa — starting a pcless greeting in a fresh scene flips the scene offscreen).

Scenes Are Scripts

Transcripts moved from a two-role chat log to a script grammar with named speakers — the enabler for multi-NPC scenes, speaker plates in the UI, and per-NPC posts.

The grammar (scenes.py)

  • Every message starts **<Speaker>:** at the top of the body or after a blank line (bold text inside a paragraph stays content).
  • Reserved labels: **You:** (user) and **Grimoire:** (assistant narration). Anything else is a named speaker.
  • Role is derived: user-side iff the speaker is "You" or matches a role=player cast member. match_name() resolves labels by case-insensitive exact match, else a unique word-boundary prefix ("Winifred" names "Winifred Vance"; ambiguous prefixes name no one).
  • One model reply with several **Name:** blocks is split into per-speaker posts on persist; the trailing assistant run is what reroll replaces.

Scene ids (scene_ids.py)

  • Grammar: <number>--<date-slug>--<title-slug>.md; the date section appears once the scene has an in-world date (first set_datetime renames the file).
  • Number first + zero-padding (min width 3, campaign-wide re-pad) ⇒ lexicographic filename order = play order.
  • Renames cascade: scene_refs.repoint() fixes every store that references scene ids (chronicle, plot, changes, appearances, played).
  • Legacy files are migrated once at startup (migrations.migrate_scene_ids).

Calendars & In-World Dates

The store/calendars/ package gives scenes real in-world dates on a provider registry, so fictional calendars can slot in later without touching anything else.

  • A fixed-day integer axis (proleptic Gregorian ordinal) underlies every provider, so dates from different calendars are orderable and arithmetic is exact. Time-of-day (Thh:mm) is handled calendar-agnostically.
  • gregorian is the only shipping provider — region holidays via the holidays PyPI package plus custom fixed or nth-weekday rules. calendar.json ({primary, secondary, confirmed}) is world-scoped and copied into each campaign.
  • today_facts() merges primary + secondary calendars into the prompt's Today section: friendly date, weekday, holidays today, next holiday within UPCOMING_WINDOW_DAYS = 30 — plus each cast member's age and birthday-today flag (characters/PCs carry a birthdate).
  • Scene datetime is a history (GET/PUT …/datetime); a suggested pre-fill comes from the creation-time hint or the last chronicle date, and the wizard/chooser/inspector all pre-fill it.

Taglines & Dossiers — the off-scene cast directory

Two tiers of "who else exists," so the model can pull absent characters in sensibly (prompt section 15, # Other characters in this world):

Tagline world-level · per character

characters/<cid>/tagline.md — one sentence. Generated on demand from the card (templates/tagline/) or hand-written; deliberately not hash-tied to the card so hand-written taglines never "expire." Feeds tier 2: Known to exist — every world character not yet in the campaign, with available version ids.

Dossier campaign-level · per character

campaigns/…/characters/<cid>/dossier.md — a standing paragraph: who they are and where things stand in this campaign. Auto-refreshed by an extra LLM call per present NPC during every absorb (prior dossier + transcript in). Feeds tier 1: Active in this campaign, elsewhere.

Scene Suggestions & the New-Scene Chooser

The + New Scene button opens a chooser modal (PC mode vs. offscreen mode first), which combines deterministic availability with one LLM call:

  • suggest.build_snapshot() gathers: the current in-world date + upcoming holidays/birthdays, open plot threads, cast absent from the last 5 absorbed scenes (with taglines), available cast and locations.
  • One call to templates/scene_suggestions/ returns generated premises ({title, premise, cast, location, date} — id-validated against the snapshot), a ranking of startable greetings (only when more than two are available), and an estimated next_date.
  • The chooser shows ~4 cards: top-ranked greetings + generated premises. Picking a greeting runs start-from-greeting (which retitles the scene after the greeting); picking a premise creates the scene, seeds its whole cast in one batch call, sets the location, and pre-fills the opener prompt with the premise.
  • A failed seed deletes the half-created scene before surfacing the error — no orphans.

Accept vs. reject are the same operation with one flag (_advance(…, copy=)): accept overwrites the campaign copy with the world version (flat file write; whole-dir rmtree+copytree for unpicked actors, so deleted versions propagate; just the locked version file for locked actors) and advances the base hash; reject only advances the base ("keep mine, stop nagging"). campaigns_for_world() rolls up pending counts so the World view can badge each campaign with new update conflict.

Version locking — one door, three keys

An actor's campaign life has two phases. Unpicked: all versions ride along, world changes arrive whole-dir via sync. Locked: exactly one version, tracked per-version. All three entry points route through the same _lock():

  • appear() — first time an actor is seated in a scene (lazy pick). Re-appearing with a different version/role raises AppearError.
  • pick_version — explicit pick from the campaign's world pages (409 if already locked).
  • start_from_greeting — casting the greeting's characters.

Locking purges every sibling version, points default_version at the pick, and migrates the sync base from sync.md to appearances.json. Later, import_version can swap the locked version for a different world version (requires an existing lock — until you pick, world changes come via sync).

What's editable at campaign scope

The campaign's world pages (/campaigns/:cid/world) edit the campaign copy: full CRUD for lore, locations, greetings (+ plotmap edges + marks), PCs (including campaign-local creation), and characters (edit versions; creating a new version 409s once locked). Tags stay world-only — campaign PC tags are free strings.

Greetings & the Plotmap

Greetings are pre-written scene openers tied to a character+version, optionally gated by player tags and chained into a directed graph (the plotmap) that models story progression.

A greeting

  • character + version it belongs to; optional co-cast via present
  • body — markdown, may embed localized images
  • requires_tags + predecessor_join (all/any) — gating
  • pcless — an offscreen greeting
  • Imported in bulk from a card's first_mes + alternate_greetings, or authored (incl. saving a generated opener)

Marks & availability (playing.py)

  • played.json holds three sets: played (actually started), completed / skipped (off-screen marks you set by hand)
  • Availability treats played ∪ completed as done; skipped greetings are dropped and pruned from predecessor joins — the plot routes around them
  • ?after= flags greetings unlocked by a just-finished scene's greeting (they sort first in the chooser)

Starting a scene from a greeting (playing.start_from_greeting) casts every listed character (locked version wins), records the greeting as played, appends its body as the first assistant post, retitles the scene to the greeting's name (the response carries the new scene id), and enforces the pcless pairing rules.

pngJSON base64-embedded in a PNG tEXt chunk — the iconic card image. Real PNGs can carry duplicate chara chunks (stale + current), so the reader scans every chunk and prefers the first rather than dict-ing by keyword.
charxZIP archive containing card.json (+ optional embedded assets)

to_v3() normalizes older V2/bare cards up to V3 without mutating the input. Characters are versioned: many <vid>.json cards per character plus a default_version pointer. A card's embedded character_book can be lifted into editable world lore via the lorebook importer.

chub.ai integration (store/chub.py + fetch.py)

  • Read-only client for chub's undocumented API: paste a URL (or bare creator/slug) → import_from_chub fetches the card PNG, overlays the current API definition over the possibly-stale PNG payload, and optionally pulls the project gallery (streamed per-image SSE progress) and linked lorebooks.
  • chub_source is per-version, so one character can hold linked variants; one-click Re-download updates a linked version in place, and a bulk script re-downloads every linked character.
  • fetch.py is the safety layer: SSRF guard (private/loopback ranges blocked, re-checked per redirect hop), 100 MB cap, magic-byte image sniffing, best-effort semantics (returns None, never raises into happy paths).
  • Image localization (localize.py): scans card fields / greetings for remote image refs (markdown, <img>, data-URIs, bare URLs), downloads them into version assets, and splices local URLs back in — streaming progress, and completed field rewrites survive a mid-stream disconnect.

Images & Assets

store/assets.py is a per-record image store — <kind>/<id>/assets/<version>/<name>.<ext> — shared by characters (per version), entities, and greetings (version default). Images are deliberately not hashed into sync.

Slots & operations

  • avatar is the primary slot; gallery_N for the rest.
  • Promote = a three-way rename swap (nothing lost) at both world and campaign scope.
  • Crop focus: focus.json sidecar stores a 0–100 position along the avatar's long axis (the AvatarFocusPicker); any avatar write clears it.
  • Image subjects: subjects.json per greeting records which characters appear in each image — powering the "Appears in" gallery on character pages, copy-image-to-character, and the untagged-image tagging queue.

Serving & caching

  • Bare URL → Cache-Control: no-cache + ETag (mtime/size) for 304 revalidation.
  • ?v=<version> → immutable, max-age=1y (the frontend appends the version token).
  • ?w=N → lazily cached WebP thumbnail (thumbs.py, under .cache/thumbs/ — derived data, safe to delete) so grids never ship full-res art.
  • statcache.py memoizes content hashes/summaries keyed on file stat signatures, with a git-style 1-second racy-clean guard.

Themes

Three token sets in theme/themes/ — codex (default: light parchment, hard 2–3px rules, offset block shadows, red accent), manuscript (dark brown/gold), astral (near-black indigo, cyan, starfield). ThemeProvider applies a theme by writing CSS custom properties onto :root (colors, rule widths, shadows, fonts, background --fx). Fonts are self-hosted via @fontsource (Big Shoulders Display / Newsreader / JetBrains Mono for codex; Cormorant + EB Garamond for manuscript; Cinzel / Spectral / Space Mono for astral).

CampaignView anatomy (the play screen)

  • Sub-header: campaign name, World ▸ name ↗ link, Changes toggle, End scene button.
  • Scene rail: numbered scenes (offscreen ones badged), + New Scene → chooser, footer date button → calendar config.
  • Transcript: consecutive same-speaker messages group into a run under one plate (portrait + name + pc/npc chip); speaker labels fuzzy-match the cast like the backend does; clicking a plate opens the RecordDrawer. Double-quoted spans get theme quote colors via a rehype plugin. Gutter icons: ✎ edit, ↻ guided reroll (popover) on the last post.
  • Composer: Enter sends; empty input reads Continue ▶ (ephemeral NPC round); offscreen scenes show a 🎬 director-note placeholder.
  • SceneInspector: story-so-far one-liners, active-cast portrait rows, location (+ move), in-world date (+ advance), and the Context breakdown — the exact prompt sections with token counts and a % bar against the model's context length (catalog fetched once per page load).
  • Empty scene → CastPanel: setting/date pickers (pre-filled with the suggested date), add-to-scene, and the opener box (generate → preview → Use or Save as greeting).

The API layer is a single facade in api/client.ts: request() (JSON + ApiError{status, detail, kind}), requestForm() (multipart), streamPost() (SSE driver), plus in-flight GET de-duplication and a config cache — opening a scene fires identical GETs from several components, and they coalesce.

The SSE Streaming Loop (frontend)

The mirror image of the server's _chat_stream. CampaignView owns messages (committed posts), streaming (the in-flight blob), and busy/error.

  1. send() optimistically appends the user message and calls runStream(onEvent => api.chat(cid, sid, content, onEvent)).
  2. streamPost() POSTs, reads res.body via getReader() + TextDecoder; parseSSEChunk() splits on \n\n, JSON-parses each data: line into a ChatEvent, ignoring malformed fragments.
  3. Each delta accumulates into acc → setStreaming(acc) — the live typing effect under a provisional plate with a blinking cursor.
  4. On done, the view re-fetches the scene — the server persisted the reply as per-speaker posts, so the one streamed blob is replaced by split messages with speakers. On error, a readable banner + Retry.
  5. The same plumbing drives LocalizeEvent and ChubGalleryEvent progress streams (image localization, gallery downloads).

Recurring patterns to recognize: (1) path-safety guards reject ""/./../slashes everywhere; (2) content hashing (SHA-256 of file text, statcache-memoized) powers all sync; (3) frontmatter + body is universal for human-editable records; (4) campaigns copy-everything and remember base hashes; (5) continuity reads fail open — a garbled JSON omits its prompt section, never crashes a chat.
