Move the per-campaign lock registry out of sheets.py into store/locks.py (#245)

base main @ df0cff60 → 1816399c · +262/−103 · generated 2026-07-28

Nothing executes differently. One name and one file changed.

The process-wide registry of per-campaign RLocks moved out of backend/src/grimoire/store/sheets.py into a new 52-line module backend/src/grimoire/store/locks.py, and the accessor was renamed lock_for(cid) → campaign_lock(cid). All thirteen acquisition sites across seven modules were repointed. The registry body is byte-identical logic: same _registry_guard, same setdefault, same RLock — so the same single lock object is still handed to every caller for a given campaign id.

The reviewable question is therefore not "does it work" but "did every borrower come along". If one had been missed, that borrower would land on a different lock and the unified domain would split silently — sheets and proposals would stop excluding each other, and a module publish could swap a pack out from under a proposal mid-derivation. The diff repoints all of them, and three new tests fail loudly if a future change re-splits the domain.

The one flow a reviewer should still picture

The reason the domain must stay unified — unchanged by this PR, but it is what the new tests defend:

sequenceDiagram
  participant U as User (module edit)
  participant ME as module_edit
  participant LK as locks.campaign_lock
  participant LLM as LLM play flow
  U->>ME: publish edited pack
  ME->>ME: acquire _M (module-edit lock)
  ME->>LK: acquire every campaign's lock
  Note over ME,LK: ordering rule: _M before campaign locks
  LLM-->>LK: proposals.new(cid, ...) blocks here
  ME->>ME: swap pack directory
  ME->>LK: release
  LLM->>LK: acquires, derives against the NEW pack

If any borrower were on a different lock object, the dashed arrow would not block and the LLM flow could persist a proposal derived from a pack that no longer exists. backend/tests/test_locks_store.py:90-113 asserts the block for sheet writes, proposal creation and baseline capture; each was confirmed to fail when its module is given a private lock.

Tests: this is the part worth reading

A rename-only PR normally gets rename-only tests. This one adds a file that would fail on a future re-split, which is the failure mode the issue's design is guarding against:

backend/tests/test_locks_store.py — lines 25–36
+def _blocks_while_held(cid, call) -> bool: + """True if `call` cannot start while campaign_lock(cid) is held here.""" + done = [] + with locks.campaign_lock(cid): + t = threading.Thread(target=lambda: (call(), done.append(1))) + t.start() + t.join(timeout=0.3) + blocked = not done + t.join(timeout=5) + assert done, "the call never completed once the lock was released" + return blocked

Three tests use it — backend/tests/test_locks_store.py:90, 96 and 104 — asserting that sheet writes, proposal creation and baseline capture each block behind the campaign lock. The trailing assert done is what keeps it from being a tautology: a call that never completes fails rather than reading as “blocked”.

The domain tests were mutation-checked, not just observed passing. Giving proposals a private RLock fails test_proposals_serialize_on_the_campaign_lock; giving audit.capture_baseline one fails its test; giving sheets one fails both its domain test and the placement test. Each was run and confirmed red before being restored. A reviewer does not have to take the tests' word for it.

The remaining coverage: registry stability and reentrancy (backend/tests/test_locks_store.py:41), per-campaign isolation with a timed acquire proving no cross-blocking (50), an 8-thread barrier race against a cold registry proving the setdefault is doing real work (62), and two placement tests that reject both a re-implemented registry and a borrower that merely imports the name into its own namespace (120, 132).
