# Device sync: pairing and peer transfer

**Status:** first slice of [App-Managed Device Sync](roadmap/sprints/app-managed-device-sync.md) (Wave 4, #028), implemented as `grimoire.peersync` over 019's [revision and conflict core](SYNC.md). Two **paired** libraries synchronize over one **authenticated** connection, and the transfer reports `synced`, `conflicts` or `incomplete`. It is headless: there is no pairing screen, no discovery, no background sync and no encryption yet. The proving test runs the serving device in its own process on loopback (`backend/tests/test_peersync.py`). Like 019, a green suite proves this contract, not a working phone app.

## What it guarantees

- **019 decides, unchanged.** A transfer is 019's `plan_sync` and `apply_sync` with one library replaced by a checked stand-in for the other device (below). Every merge rule, keep-both conflict, held family and crash guarantee in [SYNC](SYNC.md) holds as written there; this layer adds no rule of its own about content.
- **Only paired devices talk.** Both sides prove they hold the pairing's 32-byte key before anything about either library is sent. A device that is not paired, holds another key or names another device is refused with nothing exchanged and nothing written.
- **A peer is never an owner.** A paired device writes only as its peer principal, `app:peer:<device>`, through this library's own grants to it. It can supply no approval, issue no grant and touch no reserved root (`secrets`, the `authority` ledgers, `config`), its identity or another pair's sync state ([tool authority](TOOL_AUTHORITY.md#requirements-on-later-sprints)).
- **Complete means verified.** `synced` is reported only for a pass in which every write, blobs and placements included, was committed and re-read on **both** devices with the planned bytes, and which then found nothing left to write and no conflict.
- **A failure is never half a step.** Each 019 step that lands on the serving device is one 010 transaction there. A dropped connection, a refusal or a stale snapshot leaves both libraries exactly as a crash at that point of a local 019 sync would, and the next transfer converges.
- **One chat stays one chat.** The world-less chat, its play scope, bindings, actors and pictures travel as 019 records; derived navigation indexes never travel and are rebuilt on each device, so a list by character on one device and a list by campaign on the other find the same chat ID ([chat model](roadmap/CHAT_MODEL.md)).

## Pairing

`pair(store, authority, peer, key, granted_by=human)` records the pairing on one library; the same key is entered on the other device for its pairing with this one. `new_pairing_key()` draws the key. Pairing is a direct human action, so `granted_by` must be a `human:` principal.

- The key lives in `secrets/peers/<device>.json`, a reserved root that no grant reaches, the store's scan never lists, and no transfer ever sends.
- Pairing grants `app:peer:<device>` `APPLY` on `sources`, `campaigns`, `kept` and `assets`: what 019 synchronizes. The grants are issued **before** the key is written, so an interrupted pairing leaves grants that no connection can use. Their IDs are named for the key, so pairing again with a new key never reuses an ID (grant IDs are never reused, per 010b).
- Pairing again replaces the key and revokes the old grants. Pairing again with a key this library already used and ended is refused: pick a new key.
- Either end stops at its next request or step once it is no longer paired: the initiating device checks its own pairing before each pass and before each step it sends, so unpairing a lost device mid-transfer sends it nothing more (`incomplete`, `not_paired`).
- `unpair(store, authority, peer)` erases the key first (the record keeps only `revoked`), then revokes every grant to the peer's principal, so an interrupted unpair leaves grants no connection can use, never a working key. A session that was already open ends at its next request: before every snapshot and every commit the server checks again that the session's key is still the pairing's and that the peer still holds a grant, and refuses with `not_paired` otherwise.

## How a transfer works

`transfer(store, authority, peer, address)` runs on the initiating device; `PeerServer(store, authority)` (or `python -m grimoire.peersync serve LIBRARY --owner human:you`) answers on the other. Either device can initiate.

1. **Handshake.** The client sends its device ID, the device it wants and a fresh nonce. The server answers with its own nonce and an HMAC proof over both IDs and both nonces; the client checks it and answers with its own proof. Each direction then has its own session key derived from the pairing key and that transcript. Every later frame carries a sequence number and an HMAC-SHA256 tag, so a forged, altered, replayed, reordered or reflected frame ends the connection (`TransportError`).
2. **Snapshot.** The server sends the grants it gives the client's principal, its device identity and this pair's archive and pending marker (each root and the shards it lists, never a stale or planted shard while that root and its shards are a valid document: a later write of such a name is checked against this device's own copy, its root's compare-and-swap guarding the document; when they are not, every shard of that kind as it stands, so the mirror reads the same paths as uncertain as this device would) and its kept-version record, every entry under `sources`, `campaigns` and `assets` exactly as on disk, and of `.conflicts` only the kept-version slots 019 reads to pick the next free one, under every spelling the store takes for one (recovery leftovers there, such as a discarded journal's staged files or ledger batches moved aside, never leave the device; a slot it cannot send goes as an empty placeholder, so it still counts as taken, and a file or link where `.conflicts` or a slot folder belongs goes as one too, so the mirror refuses a keep there as the server will) (an entry it cannot send as itself, such as a link, an unreadable or oversized file or a pipe, is sent as *blocked* when its own scan reports it blocked, and left out when the scan skips it, as 019 does), and its own canonical scan, with the reason it gives each blocked entry. The mirror reproduces every blocked entry as a dangling link, so once its blocked paths match, its scan reports each with the server's reason (`unreadable`, a look-alike spelling) and 019 decides as it would locally. Paths deeper than the walk goes (64 folders; no record is more than 32 parts deep) are left out of both scans.
3. **Mirror.** The client rebuilds those folders as a scratch library and refuses to use it (`MirrorMismatch`) unless it scans exactly as the server's scan does: the same record files with the same bytes, the same blocked paths, blobs and cross-kind pairs. Everything 019 plans from is in that scan. A path outside the synchronized roots, `..`, a sync file of another pair or a snapshot over the client's limits ends the session; an entry this filesystem cannot hold, or one that would resolve outside the mirror, makes the pass `MirrorMismatch` after the snapshot has been read to its end. The server re-reads the pairing for each request against the key the session proved, so pairing again with a new key ends sessions of the old one too.
4. **Plan and apply.** 019 plans between the client's library and the mirror. As `apply_sync` commits each step on the mirror, an observer sends the same writes to the server, which commits them as one transaction under the client's principal, re-reads each file and answers with a digest of their etags (one reply fits any step). Only when it matches the plan does 019 go on, so both real devices are written in 019's own order: data on each side, verify, kept-version records (028: every conflict the sync ended is taken out of conflict on both devices before either archive step, so a connection dropped after one never leaves a kept copy dismissable), archives, pending markers.
5. **One answer per step.** The client streams a step's writes without waiting and reads one reply, at its `commit`. A write the server refuses while they arrive (the step is over its limits, a blob cannot be staged) poisons the step: the rest of it is dropped unread and the commit is answered with that refusal, so nothing of the step is written and the two ends stay in step. Blob bodies are spooled to a private temporary folder as they arrive; other bodies are held in memory, at most 1 GiB per step.
6. **Passes.** A pass that wrote something is followed by another, up to four. A refusal (`stale` when the serving device changed since its snapshot, `denied` when a grant was revoked) or a mismatch makes the next pass plan again from both devices as they now are.

### The report

`TransferReport(peer, status, reason, passes)`:

- `synced`: the last pass completed, wrote nothing and found no conflict.
- `conflicts`: it completed with 019 conflicts (`report.conflicts`), each device keeping the other's version under `.conflicts`. `held` families count here, as in 019.
- `incomplete`: no pass completed quietly. `reason` says why: `unreachable`, `disconnected`, `not_paired` (the pairing ended mid-transfer), the last refusal or mismatch, a 019 or store error that would recur (`ArchiveTooLarge`, say), or that every pass still wrote something.

`NotPaired` (this library holds no pairing) and `AuthenticationFailed` (with `code`: `unauthenticated`, `not_paired`, `wrong_device`, `protocol`) are raised before anything is exchanged.

## Per-device IDs

The audit left actor numbering with 028. 107 numbered a new actor by the first free number in its campaign, so two devices continuing one campaign offline both created `mara-1`, and 019 then merged two different actors into one file. A library with a device identity now numbers new actors `<entity>-<tag>-<n>` (`mara-3f2a91c0-1`), where the tag is the first eight hex digits of the SHA-256 of the device ID. Two devices never draw the same ID without coordinating, which offline work cannot. A library that was never identified has never synced and keeps `<entity>-<n>`, so existing libraries read exactly as before. A damaged or unreadable identity file (a link or folder included) refuses the new actor (`InvalidBinding`, reason `device_identity`) rather than falling back to the numbering that collides. Every other rule of [taken instance IDs](CHATS.md#taken-instance-ids) still applies on top.

034's unique items use the same tag (`chatstore.device_tag`): a new item is `<base>-<tag>-<n>` (`longsword-3f2a91c0-1`) on an identified library and `<base>-<n>` otherwise, and a damaged or unreadable identity (a link or folder included) refuses the creation (`PossessionRefused`, reason `device_identity`). An instance of an `individual` definition (one particular artifact) is tagged by its definition instead, with the first eight hex digits of the SHA-256 of its unpinned source ref (`starfall-0f8a3e79-1`): it may exist once per campaign, so two devices that each made it offline collide on one file, which 019 keeps both of as a conflict, while two different artifacts that share an entity id never meet. A creation planned before the library was identified is stale at commit, so it is never written under the plain number. Items and actors already made keep their IDs ([POSSESSIONS](POSSESSIONS.md#service-grimoirepossessionstorepossessionlibrary)).

## Known limits

- **Loopback only, not encrypted.** Frames are authenticated, not encrypted: anyone who can read the path reads the library's records. `PeerServer` therefore refuses any address that is not a loopback IP. Encrypted transport, LAN discovery and a user-chosen remote endpoint or relay are later milestones of this sprint.
- **One step must fit.** 019 commits each device's data as one step, and the server takes a step of at most 200,000 writes and 1 GiB of record bodies (blobs aside, 8 GiB in all). A first sync of a library past either limit to an empty device is refused as `too_large` on every pass, so it stays `incomplete`; splitting 019's data step is a later 028 decision.
- **Whole snapshots.** Each pass sends the serving library whole and the mirror is rebuilt in a temporary folder (default limits: 250,000 entries, 8 GiB). Incremental snapshots and fetching blobs only when needed come later; until then a large library transfers slowly.
- **Blocked entries need links.** A blocked entry is reproduced in the mirror as a dangling symbolic link. Where links cannot be made (Windows without the privilege), a library with a blocked entry cannot be mirrored and the transfer is `incomplete` with `MirrorMismatch`.
- **Waiting.** The handshake must finish within 10 seconds and no handshake frame may exceed 4 KiB, so a local process that never authenticates cannot hold the server's one connection slot; nothing it sends stops the server. Once authenticated, either end may go quiet for up to 10 minutes (the client rebuilding the mirror and committing its own side before the first step; the server committing a large step). There are no keepalives yet: a step that takes longer ends the transfer as `incomplete`. The server takes one connection at a time, so local processes that open many connections and send nothing can each hold it for the 10-second handshake limit and delay a real transfer past its own timeout.
- **Names the client's filesystem cannot hold.** The mirror reproduces every entry under the synchronized roots, records or not. A file a Linux server holds that a Windows or macOS client cannot create (`notes?.txt`, `CON`, two names differing only in case, a trailing dot on Windows) makes every pass `MirrorMismatch`, though a local 019 sync would skip it; the snapshot is still read to its end, so the connection stays usable. A name holding `:` or `\` (a Finder name like `notes 10:30.txt`) is never sent: no synchronized record is spelled so, and the client could not tell it from a path that escapes its mirror.
- **Paired device IDs are visible locally.** Any local process can learn whether a device ID is paired with the serving library: an unpaired one is refused with `not_paired` before any proof, a paired one gets a challenge. It learns nothing else.
- **A peer is trusted as a device of the same user.** Its writes use a *trusted* handle for its peer principal, as 019's local sync does for each library. [Tool authority](TOOL_AUTHORITY.md) requires an untrusted handle for code that parses imported content or model output; the sync engine does neither, it copies records byte for byte and decides only from etags and its own bookkeeping. An untrusted handle would need an owner's approval for every synchronized write, which no unattended sync can have. Within its grants it can write any record content, and like any 019 writer it can claim any `previous` lineage through `put_exact` and write its own pair's markers ([SYNC](SYNC.md#limits)). Pairing is the user's decision that the other device is theirs; unpairing ends it.
- **Still owed by 028** (each listed under [Inherited from 019](roadmap/sprints/app-managed-device-sync.md#inherited-from-019)): merge rules for 021 accepted events and wrap-ups and 023 holdings (still `held`), merging two devices' knowledge logs, deletion propagation, resolving a conflict over the transport, and background sync. The merges and deletion propagation are due before Sprint 044 ([Milestone: merges before 044](roadmap/sprints/app-managed-device-sync.md#milestone-merges-before-044)). Dismissing kept versions and sharded archives are done ([SYNC](SYNC.md#keep-both)). A peer's replayed step is refused (`invalid`) when it adds a dismissal, records as delivered a version that no keep op of the same step writes on this device as the first copy of those bytes at its path (the data step carries the record with its keeps), drops a `resolve` hold whose slot still stands or cannot be read (an unreadable slot also makes no keep beside it a first copy), writes a shard that no root written in the same step lists, or writes an archive or marker root that, with its shards (those written in the step and the listed ones already on disk), is not a valid document of this pair.
