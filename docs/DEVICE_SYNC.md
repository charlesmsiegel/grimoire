# Device sync: pairing and peer transfer

**Status:** first slice of [App-Managed Device Sync](roadmap/sprints/app-managed-device-sync.md) (Wave 4, #028), implemented as `grimoire.peersync` over 019's [revision and conflict core](SYNC.md). Two **paired** libraries synchronize over one **authenticated** connection, and the transfer reports `synced`, `conflicts` or `incomplete`. It is headless: there is no pairing screen, no discovery, no background sync and no encryption yet. The proving test runs the serving device in its own process on loopback (`backend/tests/test_peersync.py`). Like 019, a green suite proves this contract, not a working phone app.

## What it guarantees

- **019 decides, unchanged.** A transfer is 019's `plan_sync` and `apply_sync` with one library replaced by a checked stand-in for the other device (below). Every merge rule, keep-both conflict, held family and crash guarantee in [SYNC](SYNC.md) holds as written there; this layer adds no rule of its own about content.
- **Only paired devices talk.** Both sides prove they hold the pairing's 32-byte key before anything about either library is sent. A device that is not paired, holds another key or names another device is refused with nothing exchanged and nothing written.
- **A peer is never an owner.** A paired device writes only as its peer principal, `app:peer:<device>`, through this library's own grants to it. It can supply no approval, issue no grant and touch no reserved root (`secrets`, the `authority` ledgers, `config`), its identity or another pair's sync state ([tool authority](TOOL_AUTHORITY.md#requirements-on-later-sprints)).
- **Complete means verified.** `synced` is reported only for a pass in which every write, blobs and placements included, was committed and re-read on **both** devices with the planned bytes, and which then found nothing left to write and no conflict.
- **A failure is never half a step.** Each 019 step that lands on the serving device is one 010 transaction there. A dropped connection, a refusal or a stale snapshot leaves both libraries exactly as a crash at that point of a local 019 sync would, and the next transfer converges.
- **One chat stays one chat.** The world-less chat, its play scope, bindings, actors and pictures travel as 019 records; derived navigation indexes never travel and are rebuilt on each device, so a list by character on one device and a list by campaign on the other find the same chat ID ([chat model](roadmap/CHAT_MODEL.md)).

## Pairing

`pair(store, authority, peer, key, granted_by=human)` records the pairing on one library; the same key is entered on the other device for its pairing with this one. `new_pairing_key()` draws the key. Pairing is a direct human action, so `granted_by` must be a `human:` principal.

- The key lives in `secrets/peers/<device>.json`, a reserved root that no grant reaches, the store's scan never lists, and no transfer ever sends.
- Pairing grants `app:peer:<device>` `APPLY` on `sources`, `campaigns`, `kept` and `assets`: what 019 synchronizes. The grants are issued **before** the key is written, so an interrupted pairing leaves grants that no connection can use. Their IDs are named for the key, so pairing again with a new key never reuses an ID (grant IDs are never reused, per 010b).
- Pairing again replaces the key and revokes the old grants. Pairing again with a key this library already used and ended is refused: pick a new key.
- Either end stops at its next request or step once it is no longer paired: the initiating device checks its own pairing before each pass and before each step it sends, so unpairing a lost device mid-transfer sends it nothing more (`incomplete`, `not_paired`).
- `unpair(store, authority, peer)` erases the key first (the record keeps only `revoked`; it is written for a peer never paired too, such as one 019 synced directly, since an ended pairing is also how the owner tells the scene that a lost peer's open conflicts no longer hold a chat, [SCENES](SCENES.md#storage-and-sync)), then revokes every grant to the peer's principal, so an interrupted unpair leaves grants no connection can use, never a working key. A session that was already open ends at its next request: before every snapshot and every commit the server checks again that the session's key is still the pairing's and that the peer still holds a grant, and refuses with `not_paired` otherwise.

## How a transfer works

`transfer(store, authority, peer, address)` runs on the initiating device; `PeerServer(store, authority)` (or `python -m grimoire.peersync serve LIBRARY --owner human:you`) answers on the other. Either device can initiate.

1. **Handshake.** The client sends its device ID, the device it wants and a fresh nonce. The server answers with its own nonce and an HMAC proof over both IDs and both nonces; the client checks it and answers with its own proof. Each direction then has its own session key derived from the pairing key and that transcript. Every later frame carries a sequence number and an HMAC-SHA256 tag, so a forged, altered, replayed, reordered or reflected frame ends the connection (`TransportError`).
2. **Snapshot.** The server sends the grants it gives the client's principal, its device identity and this pair's archive and pending marker (each root and the shards it lists, never a stale or planted shard while that root and its shards are a valid document: a later write of such a name is checked against this device's own copy, its root's compare-and-swap guarding the document; when they are not, every shard of that kind as it stands, so the mirror reads the same paths as uncertain as this device would) and its kept-version record, the pair's base cache entries a ledger merge may need (028: each ledger file its archive records as agreed that it no longer holds as agreed; one it still holds is its own base), every entry under `sources`, `campaigns` and `assets` exactly as on disk, and of `.conflicts` only the kept-version slots 019 reads to pick the next free one, under every spelling the store takes for one (recovery leftovers there, such as a discarded journal's staged files or ledger batches moved aside, never leave the device; a slot it cannot send goes as an empty placeholder, so it still counts as taken, and a file or link where `.conflicts` or a slot folder belongs goes as one too, so the mirror refuses a keep there as the server will) (an entry it cannot send as itself, such as a link, an unreadable or oversized file or a pipe, is sent as *blocked* when its own scan reports it blocked, and left out when the scan skips it, as 019 does), and its own canonical scan, with the reason it gives each blocked entry. The mirror reproduces every blocked entry as a dangling link, so once its blocked paths match, its scan reports each with the server's reason (`unreadable`, a look-alike spelling) and 019 decides as it would locally. Paths deeper than the walk goes (64 folders; no record is more than 32 parts deep) are left out of both scans.
3. **Mirror.** The client rebuilds those folders as a scratch library and refuses to use it (`MirrorMismatch`) unless it scans exactly as the server's scan does: the same record files with the same bytes, the same blocked paths, blobs and cross-kind pairs. Everything 019 plans from is in that scan. A path outside the synchronized roots, `..`, a sync file of another pair or a snapshot over the client's limits ends the session; an entry this filesystem cannot hold, or one that would resolve outside the mirror, makes the pass `MirrorMismatch` after the snapshot has been read to its end. The server re-reads the pairing for each request against the key the session proved, so pairing again with a new key ends sessions of the old one too.
4. **Plan and apply.** 019 plans between the client's library and the mirror. As `apply_sync` commits each step on the mirror, an observer sends the same writes to the server, which commits them as one transaction under the client's principal, re-reads each file and answers with a digest of their etags (one reply fits any step). Only when it matches the plan does 019 go on, so both real devices are written in 019's own order: data on each side, verify, kept-version records (028: every conflict the sync ended is taken out of conflict on both devices before either archive step, so a connection dropped after one never leaves a kept copy dismissable), archives, pending markers.
5. **One answer per step.** The client streams a step's writes without waiting and reads one reply, at its `commit`. A write the server refuses while they arrive (the step is over its limits, a blob cannot be staged) poisons the step: the rest of it is dropped unread and the commit is answered with that refusal, so nothing of the step is written and the two ends stay in step. Blob bodies are spooled to a private temporary folder as they arrive; other bodies are held in memory, at most 1 GiB per step.
6. **Deletions (028).** A propagated deletion the serving device receives travels as one `delete` op per record (its path, the etag removed, the hold's slot, and the removed bytes as its body) in the data step, which commits each as `keep_version` (a hold) plus `delete_exact` in that one transaction, under the client's principal: it is authorized as `APPLY` on the record's address over the deletion document, which pairing's grants on `sources` and `campaigns` (and `kept` for the hold) already cover, so no new permission and no pairing migration. The confirmation re-reads the hold and the path's absence. When the client deletes a record the serving device deleted, the client's data commit asks first (`{"t": "check", "absent": [...]}`, under the client's lock): the serving device answers `confirmed` only if, under its own lock, it still lacks each of those records, and refuses `stale` otherwise, so the pass stops with nothing deleted and the next pass plans again. While it waits for that answer the client's library is marked held for a peer, as for a replayed deleting step, so two devices transferring to each other at once, each deleting in its own library, never wait on each other's library until the connection times out: each server refuses the other's `check` `busy` after `BUSY_WAIT`, and the next transfer makes both deletions. When the serving device deletes, the client checks its own library and keeps it locked until the step is replayed, so a record the person puts back on the client meanwhile waits for that step (and while such a step is out, this library's own server waits for it only `BUSY_WAIT` before refusing `busy`, as for a resolve). It is accepted only when its body is exactly the bytes it removes, never in a resolve session, and only once this pair's record on disk already holds those bytes, which 019's holds step commits first. The holds step (the commit names its step `holds`, and it writes this pair's `keeps.json` alone; no other sync step may add a hold) may add as `held` only a version that is the serving device's own current one at a path whose family propagates deletions: a peer that adds one without deleting only makes that version never dismissable, which fails closed. The serving device takes those bytes out of every other pair's `delivered` versions itself, in a commit of its own just before the data step, as for a resolve hold.
7. **Passes.** A pass that wrote something is followed by another, up to four. A refusal (`stale` when the serving device changed since its snapshot, `denied` when a grant was revoked) or a mismatch makes the next pass plan again from both devices as they now are.

### The report

`TransferReport(peer, status, reason, passes)`:

- `synced`: the last pass completed, wrote nothing and found no conflict.
- `conflicts`: it completed with 019 conflicts (`report.conflicts`), each device keeping the other's version under `.conflicts`. `held` families count here, as in 019.
- `incomplete`: no pass completed quietly. `reason` says why: `unreachable`, `disconnected`, `not_paired` (the pairing ended mid-transfer), the last refusal or mismatch, a 019 or store error that would recur (`ArchiveTooLarge`, say), or that every pass still wrote something.

`NotPaired` (this library holds no pairing) and `AuthenticationFailed` (with `code`: `unauthenticated`, `not_paired`, `wrong_device`, `protocol`) are raised before anything is exchanged.

## Resolving a conflict over the transport

`resolve_conflict(store, authority, peer, address, path, keep, expected)` ends one conflict a transfer reported, from either device, without opening both libraries in one process. Its arguments are 019's [`resolve`](SYNC.md#ending-a-conflict)'s: `keep` is the current etag of the version to keep, and `expected` gives each device's etag (`None`: absent) as the conflict was reported. It is 019's `resolve` itself, between this library and a mirror of the other device, so every rule and refusal of [Ending a conflict](SYNC.md#ending-a-conflict) holds unchanged: the receiver gets the chosen bytes with its replaced version kept under `.conflicts` as a *hold* (an aborted commit preserves it) and its pending marker updated in the same transaction. Before anything else of it is written, each device's kept-version record for the pair takes the path out of conflict (its deliveries and dismissals dropped), each in a commit of its own, so neither device's kept copy of the other's version is dismissable once the receiver may hold the winner's (it may be that version's last copy). Just before the data transaction, in a commit of its own, the hold is recorded as `held` in the receiver's kept-version record for the pair and taken out of every other pair's `delivered` versions, so `dismiss` never takes it for a delivered keep: not now, not after any later sync, and not after 010's recovery finished the hold's commit without a staged `.sync` file. Both archives then record the agreement, and both markers drop the path. It refuses while either device's marker for the pair is ignored. `keep=None` chooses the deletion (028), and only the device that holds the record starts it: that device receives in its own library (its version recorded as `held` and kept as a hold, the record removed, the marker written) and the serving device, the winner, is written only bookkeeping. The mirror is a snapshot, so just before the requester's data commit (under its own lock) it sends a `check` request naming every path the deletion removes; the serving device answers `confirmed` only if, under its own lock, it still lacks each of them, and refuses `stale` otherwise (the resolve is then `refused`, nothing deleted). Started on the device that lacks the record it is refused before anything is sent, with a reason naming the device to start it on; a serving device that holds the record refuses such a request (`invalid`), and no resolve step may delete anything there. A choice that would replace a definition revision the other device holds is refused before anything is sent too, with a reason that says to start this resolve on that device: there the device holding the conflicted revision is the receiver, and it replaces the revision as its owner (see the third bullet below).

- **Request.** The client sends `{"t": "resolve", "path", "keep", "expected"}`. The serving device checks that the path is a synchronized record, that `keep` is an etag and that `expected` names both devices, and that its own copy holds `expected[itself]` (else `stale`). A peer is not an owner, so it then admits only a choice of a version it already has or had: `keep` must be its own current etag (it is the winner, and only its bookkeeping is written), but not when the requester's expected etag is that same one (`no_conflict`: nothing to resolve). Otherwise it receives, and `keep` must be the requester's own expected etag (the version `resolve` copies) and also one of: the etag of a kept version of the path under its `.conflicts`, which the keep-both transfer that reported the conflict left there (a file that reads whole: one that cannot be read proves nothing, so it admits nothing); the version this pair's archive on the serving device (read as a sync reads it, one file or sharded) records as agreed (when one device changed a mutable record, such as a chat, and the copy of its edit to the other device, still at the agreed version, failed: `head_dependency`, `unapplicable`, or `denied` at planning or commit, keep-both kept nothing on the device that changed it, since the other holds the agreed version, and a denied write is never kept); or, for a blob it lacks, the blob's own name (its bytes are checked against it as they land). Anything else is `unknown_version`. Each refusal comes before anything is sent; otherwise it answers with an ordinary snapshot. A server that predates this request answers `protocol` and ends the session, as for any request it does not know: the report is `refused` with reason `unsupported`, and nothing is written on either device.
- **Steps.** The client rebuilds the snapshot as a mirror (checked as for a transfer) and runs `resolve` against it. Each commit `resolve` makes on the mirror is replayed on the serving device before `resolve` goes on, with the transfer's own `op` and `commit` frames, limits and confirmation digest, as one transaction under the client's peer principal, never the owner (`denied` when its grants do not reach a write). So both devices are written in `resolve`'s own order: each device's kept-version record with the conflict ended, the receiver's hold record (when it replaces a version of its own), its data, verify, archives, pending markers. When the serving device receives, its two record steps are sent only once the mirror has passed the data commit's own checks, then in order, each a commit of its own; its own record needs clearing no sooner, since once it receives it holds the winner's version live. When it is the winner, its record step goes at once, before the client's data commit. Before each step the serving device checks it against the request: the step that writes the path must find `expected[itself]` there (and the write itself compares etags), write exactly the bytes whose etag is `keep`, and hold the serving device's own current version beside it (`invalid` otherwise, and when the serving device is the winner: nothing at the path is written there); the steps before it may be the record's, which write this pair's `keeps.json` and nothing else while the path still holds `expected[itself]` (a record past `keeps.RECORD_LIMIT`, which this device never writes itself, is `invalid` in any step); every other step must find the chosen etag, so an archive never records an agreement that device no longer holds. Like a transfer's pass, a resolve costs one whole snapshot of the serving library.
- **One write only a resolve makes; one no peer makes.** A `keep` may carry `"hold": true`; the serving device accepts it only after a `resolve` request, only for the path it named, only in the step that replaces that path, and only holding its own current bytes there (`invalid` anywhere else, in every sync step, and in a step that does not write the path: a device that keeps its own version holds nothing, and a hold of its live bytes would only leave a kept copy that is never dismissable). The hold is recorded as a local `resolve` records it, never in the hold's own commit: 010's recovery may finish a partly published commit without a `.sync` file whose staged copy is gone or damaged, which would leave a slot the hold reused (bytes once delivered) listed as delivered, and so dismissable, though it is the only copy. So `resolve`'s commit of the pair's record holding those bytes is relayed as a step of its own just before the data step, and that step may add as `held` only the serving device's own current version of the path. The client sends it only once the mirror has passed the data commit's own checks, the serving device's grants included, so a resolve its mirror refuses writes nothing on the serving device. The step that carries the hold is refused (`invalid`, nothing written) unless the pair's record on disk already holds those bytes and any record the step writes still does; just before committing it, under the same lock and only once the step has passed every check its own commit makes, the peer's grants included (so a peer the path denies never changes those records), the serving device commits on its own the removal of those bytes from the `delivered` versions of every other pair's record it keeps, exactly as a local `resolve` does (the client sees only this pair's record and may write no other). If the data step then never lands, the record holds bytes the resolve did not take: that only fails closed, and a sync drops the entry once no slot holds those bytes. No step may add any other `held` version, nor record a hold as delivered. When the client receives, its own library commits the same records before its data commit, as a local resolve. So a version held by a resolve over the transport is never dismissable, as in [Keep-both](SYNC.md#keep-both). A `put` carrying `"replace"` (019's replace of an unreferenced definition revision) is refused (`invalid`) in every step, resolve or not. A kept version proves nothing about where its bytes came from (a plain sync step may keep any version of a path beside it), so a peer that could replace a revision with a kept version could rewrite an immutable revision with bytes of its choice. A revision is replaced only by the device that holds it, as owner: it starts the resolve, the other device is the winner, and the serving device writes only bookkeeping. The client refuses the other direction before connecting, with a reason naming the device to start it on.
- **Two devices resolving at once.** 019 commits the receiver's data with both libraries held, so a resolve holds its own library while it waits for the peer's answer. Two devices resolving against each other at once would each wait for the other's library until the connection timed out, freezing local writes meanwhile. So a serving device refuses a `resolve` request with `busy` while a resolve of its own library is in flight in its process, and a served commit that cannot take the library within one second while one is in flight is refused `busy` too, with nothing written (without one, a commit waits for the library as before). The client reports `refused` (`busy`) when that came before the receiver's data landed: retry once the other resolve is over.

`ResolveReport(peer, path, status, reason, receiver)`:

- `resolved`: `receiver` now holds the chosen version and both archives record the agreement. The next transfer finds the conflict gone on both devices.
- `refused`: the chosen version landed on neither device. What may stand is the bookkeeping a local resolve also commits before its data: the kept-version records with the conflict ended (those kept copies are then never dismissable) and the receiver's hold recorded (bytes it still has as its live record). That only fails closed. `reason` is 019's `ResolveRefused` (a stale expected etag, a held path, a deletion started on the device without the record or one something still needs, an ignored marker, a grant that refuses the receiver's write, ...), or the serving device's refusal of the request or of any step up to the receiver's data (`stale`, `no_conflict`, `unknown_version`, `busy`, `denied`, `invalid`), or `unsupported`.
- `incomplete`: `unreachable`, `disconnected`, `not_paired`, a mismatched mirror, or a refusal after the receiver's data landed. Each device is as a crash at that point of a local resolve leaves it. After the data landed, the receiver holds the chosen version with its own one held, marked in its pending marker, and the next transfer records the agreement; repeating the same resolve then is refused as stale.

### Ledgers over the transport (028)

A transfer merges two devices' ledgers exactly as a local sync does ([SYNC](SYNC.md#ledgers-028)), on the stand-in. The serving device receives ordinary steps: the merged ledger files, under its grants to the client's peer principal and each with its compare-and-swap, and its own bookkeeping. It accepts a write of a base cache entry (`peers/<peer>/bases/<key>.json`) only in the step that writes its own archive, for a path that archive records as agreed at exactly the entry's etag, and only when those bytes are its own current file at that path. A file changed there since the snapshot is refused as `stale` (a race, not a lie): the client plans again, and the next pass merges the change. The serving device then replaces its own entry, whatever the client's mirror held, so a peer can never plant a base. The snapshot's `end` says whether the serving device can store a cache entry at all (`bases`; every entry's name has one length), and where it cannot, the stand-in plans none. A cache entry is an optional copy: one the serving device cannot read (a folder where the file should be, say) is left out of its snapshot rather than failing it, and `end` names it (`unreadable_bases`), so the stand-in plans no write over it either; that merge may then need review.

A data step that lands a merged ledger on the serving device also carries, for each unit, the unit as the client's plan read it there (`unit` checks: paths and etags, and the blocked paths by name). The serving device lists its own unit under its lock, just before it commits, and refuses the step as `stale` if they differ, so an event it accepted after the snapshot is never merged past. The client plans again, as after a local `SyncInterrupted`. Proved in `backend/tests/test_peersync_ledger.py`.

`resolve_ledger_with(store, authority, peer, address, campaign, keep, token, decided_by=...)` ends a `merge_review` over the connection. It plans 019's `resolve_ledger` against the stand-in and replays its steps:
- `keep=MERGE` (`grimoire.sync.MERGE`) discards nothing.
- `keep=<peer>` (a device id, a string; `"merge"` is a device id too) discards this device's own changes to that ledger, so `decided_by` must be one of this library's owners.
- Keeping this device's ledger would discard the peer's changes, so it is refused here: decide it on the peer. The serving device therefore never receives a discard.

Limits:
- The transport resolves one review per connection, with no retry.

`NotPaired` and `AuthenticationFailed` are raised before anything is exchanged, as for a transfer. Proved in `backend/tests/test_peersync_resolve.py`: from either device (one against a server in its own process), a revision replace with its hold started on the device that holds the revision and refused from the other, a revision edited in place returned to the agreed version, a choice neither device holds refused rather than redirected, a chat edit the other device's owner did not authorize ended by keeping the agreed version (admitted only as the requester's own), a forged version a sync step kept beside a revision never replacing it, a stale etag on either side, the deletion chosen on the device that holds the record (and refused from the other, by a serving device that holds it, by one that holds it again by the time the deletion would commit, by one that predates `check`, and as a `delete` op in a resolve step; a write landing just after the `check` is never deleted or lost at the next transfer), an ignored marker, a withdrawn grant, unpairing mid-resolve, a forged or unheld version and a request for a path in no conflict, two devices resolving against each other at once, a data step refused after the record steps committed reported `refused` with only that bookkeeping standing, a connection dropped before and after each of the serving device's commits (its records first; once the data landed the client's kept copy of the other version is not dismissable), a connection dropped right after the client's own data commit leaving the serving winner's copy not dismissable, the serving device's own refusals, a server that predates the request, and the agreed version admitted from a sharded archive. Proved in `backend/tests/test_peersync_bookkeeping.py`: the replaced version held on either receiver (the serving device included) and refused by `dismiss`, then and after later transfers, even once the other device comes back to those bytes; a hold over bytes once delivered still held, on either receiver, after a power loss whose recovery loses any record staged with the hold; a hold on the serving device taken out of its other pairs' deliveries (and those left untouched when the hold's grants deny it); an unrecorded hold, a hold recorded only in its own step, a record step calling the version delivered or holding another version, and a hold in a sync step all refused; a device that keeps its own version refusing a hold of its live bytes (with its record, after it, or over a record an abandoned resolve left); a peer's record past the record cap refused; and a chosen version whose kept file cannot be read not admitted.

## Per-device IDs

The audit left actor numbering with 028. 107 numbered a new actor by the first free number in its campaign, so two devices continuing one campaign offline both created `mara-1`, and 019 then merged two different actors into one file. A library with a device identity now numbers new actors `<entity>-<tag>-<n>` (`mara-3f2a91c0-1`), where the tag is the first eight hex digits of the SHA-256 of the device ID. Two devices never draw the same ID without coordinating, which offline work cannot. A library that was never identified has never synced and keeps `<entity>-<n>`, so existing libraries read exactly as before. A damaged or unreadable identity file (a link or folder included) refuses the new actor (`InvalidBinding`, reason `device_identity`) rather than falling back to the numbering that collides. Every other rule of [taken instance IDs](CHATS.md#taken-instance-ids) still applies on top.

034's unique items use the same tag (`grimoire.devicetag.device_tag`, re-exported by `chatstore`): a new item is `<base>-<tag>-<n>` (`longsword-3f2a91c0-1`) on an identified library and `<base>-<n>` otherwise, and a damaged or unreadable identity (a link or folder included) refuses the creation (`PossessionRefused`, reason `device_identity`). An instance of an `individual` definition (one particular artifact) is tagged by its definition instead, with the first eight hex digits of the SHA-256 of its unpinned source ref (`starfall-0f8a3e79-1`): it may exist once per campaign, so two devices that each made it offline collide on one file, which 019 keeps both of as a conflict, while two different artifacts that share an entity id never meet. A creation planned before the library was identified is stale at commit, so it is never written under the plain number. Items and actors already made keep their IDs ([POSSESSIONS](POSSESSIONS.md#service-grimoirepossessionstorepossessionlibrary)).

020's knowledge-log batches use the same tag: an identified library writes `batch/<seq:010d>-<tag>.json`, so two devices appending to one campaign offline never write one batch, and a transfer merges their logs by copying, as 019 does locally ([SYNC](SYNC.md#knowledge-logs-028)); a damaged identity refuses the append (`device_identity`), and batches written before `identify` keep their names ([EVIDENCE](EVIDENCE.md#the-knowledge-log)).

021's accepted events use it too: a new event id, and the id of every 017 relation an acceptance (or 030's `adopt`) begins, end in `-<tag>` on an identified library (`e-…-3f2a91c0`), so two devices that each accept an effect offline write two events and two relations, never one id with two contents (which a merge of their ledgers could not tell apart). A damaged identity refuses the acceptance (`device_identity`), an acceptance planned before `identify` is stale at commit, and events accepted before keep their ids ([EFFECTS](EFFECTS.md#accepting), step 14). A new event on an identified library also records what it was accepted after (`after`, `grimoire.accepted-event/2`), and keeps doing so if the identity is lost for a while, so the ledger merge keeps causal order across any pair of devices ([LEDGER_MERGE](LEDGER_MERGE.md#events)).

035's played turns use the same tag: a new turn is `<chat_id>.<n:06d>-<tag>` on an identified library and `<chat_id>.<n:06d>` otherwise, a damaged identity refuses it (`device_identity`), and turns made before `identify` keep their IDs ([SCENES](SCENES.md#a-turn)). Since 028's turn merge a transfer carries turns like any mutable record ([SYNC](SYNC.md#played-turns-035-028s-turn-merge)): two paired devices that played one chat offline each receive the other's turn, the chat is forked on both until its owner chooses a branch on either device, and the next transfer carries that choice, so both go on from the same line ([SCENES](SCENES.md#forked-chats); proved in `backend/tests/test_peersync_turns.py`). A device that chose the other's branch plays its own set-aside numbers again under a replay tag, the first eight hex digits of the SHA-256 of `<tag>.<k>`.

## Known limits

- **Loopback only, not encrypted.** Frames are authenticated, not encrypted: anyone who can read the path reads the library's records. `PeerServer` therefore refuses any address that is not a loopback IP. Encrypted transport, LAN discovery and a user-chosen remote endpoint or relay are later milestones of this sprint.
- **One step must fit.** 019 commits each device's data as one step, and the server takes a step of at most 200,000 writes and 1 GiB of record bodies (blobs aside, 8 GiB in all). A first sync of a library past either limit to an empty device is refused as `too_large` on every pass, so it stays `incomplete`; splitting 019's data step is a later 028 decision.
- **Whole snapshots.** Each pass sends the serving library whole and the mirror is rebuilt in a temporary folder (default limits: 250,000 entries, 8 GiB). Incremental snapshots and fetching blobs only when needed come later; until then a large library transfers slowly.
- **Blocked entries need links.** A blocked entry is reproduced in the mirror as a dangling symbolic link. Where links cannot be made (Windows without the privilege), a library with a blocked entry cannot be mirrored and the transfer is `incomplete` with `MirrorMismatch`.
- **Waiting.** The handshake must finish within 10 seconds and no handshake frame may exceed 4 KiB, so a local process that never authenticates cannot hold the server's one connection slot; nothing it sends stops the server. Once authenticated, either end may go quiet for up to 10 minutes (the client rebuilding the mirror and committing its own side before the first step; the server committing a large step). There are no keepalives yet: a step that takes longer ends the transfer as `incomplete`. The server takes one connection at a time, so local processes that open many connections and send nothing can each hold it for the 10-second handshake limit and delay a real transfer past its own timeout.
- **Names the client's filesystem cannot hold.** The mirror reproduces every entry under the synchronized roots, records or not. A file a Linux server holds that a Windows or macOS client cannot create (`notes?.txt`, `CON`, two names differing only in case, a trailing dot on Windows) makes every pass `MirrorMismatch`, though a local 019 sync would skip it; the snapshot is still read to its end, so the connection stays usable. A name holding `:` or `\` (a Finder name like `notes 10:30.txt`) is never sent: no synchronized record is spelled so, and the client could not tell it from a path that escapes its mirror.
- **Paired device IDs are visible locally.** Any local process can learn whether a device ID is paired with the serving library: an unpaired one is refused with `not_paired` before any proof, a paired one gets a challenge. It learns nothing else.
- **A peer is trusted as a device of the same user.** Its writes use a *trusted* handle for its peer principal, as 019's local sync does for each library. [Tool authority](TOOL_AUTHORITY.md) requires an untrusted handle for code that parses imported content or model output; the sync engine does neither, it copies records byte for byte and decides only from etags and its own bookkeeping. An untrusted handle would need an owner's approval for every synchronized write, which no unattended sync can have. Within its grants it can write any record content, and like any 019 writer it can claim any `previous` lineage through `put_exact` and write its own pair's markers ([SYNC](SYNC.md#limits)). Pairing is the user's decision that the other device is theirs; unpairing ends it.
- **A write on the serving device just after its `check`.** The serving device holds its lock only while it answers a deletion's `check`, so a write of the record there between `confirmed` and the requester's data commit still lets the requester delete (its version held under its `.conflicts`). In a resolve the serving device then refuses the archive step (`stale`) and the resolve is `incomplete`; in a sync the archives record the tombstone. Nothing is lost and nothing is deleted over that write: the next transfer derives `deleted E` from the requester's pending marker and judges the write by the [decision table](SYNC.md#decision-table), so the deleted bytes written again are `resurrected` (row 12) and any other bytes are a new record at a deleted path, copied to the requester (row 13), exactly as if the write had come just after a finished resolve or sync (`test_a_record_written_on_the_serving_device_after_its_check_is_never_deleted_or_lost`).
- **Every paired device upgrades together for 028's deletions.** A serving device that predates the `check` request answers `protocol` and ends the session, so a resolve toward a deletion against it is `refused` with that `protocol` refusal as its reason, nothing deleted and only the kept-version bookkeeping a resolve commits first standing (which fails closed), and a transfer in which the client would delete what it deleted is `incomplete` (`protocol`) with nothing deleted. As with 028's other new peer writes (the named holds step, the `delete` op), every paired device must run the same version.

Proved over the transport in `backend/tests/test_peersync.py`: a deletion on either device is made on the other with its version kept there, and the next transfer is quiet; a record the deleting device (either one) puts back after the snapshot is never deleted; two transfers in opposite directions at once, each deleting in its own library, end on the busy wait rather than the connection's timeout; and a deletion the receiving device's grants refuse is one `denied` conflict, with nothing written then or on the next transfer. A peer's replayed step is refused (`invalid`) when it adds a dismissal, records as delivered a version that no keep op of the same step writes on this device as the first copy of those bytes at its path (the data step carries the record with its keeps), drops a `resolve` hold whose slot still stands or cannot be read (an unreadable slot also makes no keep beside it a first copy), adds a `held` version other than the serving device's own current version in a resolve's record step or a sync's holds step (no other sync step, and no step that writes the hold, adds one), carries a resolve hold that the pair's record did not already hold before the step, carries a hold in a step that does not replace the resolve's path, writes a shard that no root written in the same step lists, or writes an archive or marker root that, with its shards (those written in the step and the listed ones already on disk), is not a valid document of this pair.
