Judge 1

Theory: Grimoire models a long-running tabletop campaign as a library of plain markdown/JSON files the player owns, in which a language model narrates one scene at a time from a deliberately budgeted slice of that library, and every finished scene is distilled back into it so the next scene opens on an updated world. Because the file tree is the system of record and not a cache in front of one, crash-safe writes, scene-id referential integrity across sixteen ledgers, per-campaign serialization, and copy-on-write inheritance of world records by a campaign are the load-bearing concerns rather than incidental plumbing. Its second, meta-level theory is that the same code must run unchanged on every surface it ships to (desktop, dev server, Android WebView), so the invariants that keep it portable are expressed as executable guards over the package's own AST rather than as prose someone must remember.

Instead of: The other coherent reading is 'a chat UI with retrieval over a notes folder' — the store as an index, the campaign as conversation history, and the interesting engineering in retrieval. I rejected it because the code's centre of gravity is unmistakably the write-back rather than the read: absorb/, chronicle, dossiers, plot beats, facts, journal, provenance, undo and cascade are the largest and most carefully argued modules in the tree, and cascade.py exists solely to reason about which of them a cut post must reverse. Retrieval is by contrast a single declared swap point (context.activate) with embedding search as one interchangeable strategy behind it, which is the shape of a subordinate concern, not a central one.

Judge 2

Theory: Grimoire models an ongoing roleplay campaign as a library of plain files the player owns: a world holds a setting and its cast, a campaign is a copy-on-write divergence of that world which accumulates continuity (chronicle, dossiers, threads, relationships, in-world dates), and a scene transcript is the one artifact in the system that cannot be regenerated. The language model is a narrator whose entire input is an assembled, budgeted, inspectable prompt whose text lives outside the code as templates, and whose output is never authority — absorb returns staged proposals that only a human review turns into writes. Everything else in the repository (atomic writes, the per-campaign lock domain, nine AST guards, a frozen checked-in store, the Android WebView shell that packages the backend verbatim) exists to keep that file library readable and un-shredded across processes, versions and platforms.

Instead of: The other coherent reading is 'a chat client with roleplay features that happens to save markdown' — conversation primary, store a persistence detail. Rejected because the code's centre of gravity is the opposite: the provider is a thin swappable facade containing no prompt text at all (backend/src/grimoire/llm.py, backend/src/grimoire/prompts.py:1-6), while the irreplaceable transcript is what atomic writes, the campaign lock domain and a checked-in never-regenerated store fixture are all designed around. A third reading — 'an LLM agent that maintains a world' — is refused in the code's own words: the absorb review router states that nothing it computes is permission, and apply.py deliberately does not import it so that claim stays checkable by reading an import line.

Judge 3

Theory: grimoire models a long-running collaborative story as a library of plain files the user owns: every durable fact is a markdown/JSON record under one resolved root, everything else (prompt, dossier, chronicle, recap, roll) is regenerable from those records, and the app's real job is keeping continuity across scenes without becoming the authority over the data. A campaign is a copy-on-write overlay on its world, a scene transcript is the one artifact that cannot be regenerated (hence atomic writes and a single per-campaign lock domain), and everything the model sees is a template rendered from gathered data, so model behaviour is editable data rather than code. Its meta-theory is equally explicit and shared by every arm: any rule that must hold across files is declared once as data and held to the code by a test that reads the declaration, because 'a paragraph cannot fail a test run'.

Instead of: The other coherent reading is 'a SillyTavern-style chat client that happens to persist to files' — the chat loop at the centre, the store incidental. I rejected it on the shape of the code: the play routes are thin adapters over store calls (backend/src/grimoire/routes/scenes.py:31-46), while two thirds of the backend is continuity machinery (chronicle, dossiers, relationships, plot, commitments, facts, provenance, timeline) and the operation the architecture is actually built around is absorb — folding a played scene back into the world. A chat client would not need a campaign-over-world CoW overlay, a frozen old store as a fixture, or a sync engine that compares world/base/mine hashes.
