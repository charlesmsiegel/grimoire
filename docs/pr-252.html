Route every store record write through one crash-safe helper (closes #233)

base main @ a989ea88 → 6a49008c · 49 files · +1,346/−231 · generated 2026-07-28

What this change does to the system's behavior

A store record on disk is now always a complete record. Every Markdown and JSON write in the grimoire package publishes by writing a same-directory temp file and renaming it over the target, so a reader sees the whole previous version or the whole new one — never a truncated one. Previously ~100 write sites truncated the live file and then wrote into it, including scenes.append_message, which did that on every single chat message.

Two behaviors change beyond durability: a character image write can no longer destroy the existing image when it fails, and image lookup now returns the newest file rather than the alphabetically-first one.

The ordering bug atomicity could not have fixed

put_image deleted the old image before writing the new one. Making the write atomic does nothing for this: the destructive step came first, so any failure in between left the character with no image at all. This is a pre-existing data-loss path the retrofit happened to surface.

backend/src/grimoire/store/assets.py — put_image, lines 128–147
- for p in d.glob(f"{name}.*"): # drop any prior-ext file of this name - p.unlink() - (d / f"{name}.{ext}").write_bytes(data) + written = d / f"{name}.{ext}" + stale = [p for p in d.glob(f"{name}.*") if p != written] + atomic.write_bytes(written, data) + for p in stale: + try: + p.unlink() + except OSError: + pass

The snapshot-before-write is not cosmetic: globbing after the write let two concurrent put_image calls delete each other's brand-new file, leaving no image — strictly worse than the delete-first ordering being replaced. Found by the implementation-stage review.

What did NOT change

No locking was added

scenes.append_message still has no per-scene lock, so two concurrent appenders can still lose a message. Pre-existing and out of scope — but the os.replace retry was deliberately narrowed to winerror 32/33 so this change does not widen that window. backend/src/grimoire/store/atomic.py:68

No multi-file atomicity

characters.write_card still writes a card and a meta file separately; a crash between them still leaves the pair inconsistent. Each file is now individually valid, which is all this buys.

No power-loss durability

MoveFileExW runs without MOVEFILE_WRITE_THROUGH and the parent directory is never fsynced, so the rename itself may not survive a power cut. The first spec draft claimed otherwise; a review caught it.

No fix for promote_image

The avatar swap at backend/src/grimoire/store/assets.py:164 is a three-rename sequence that can strand a temp and leave the avatar missing. A recovery-protocol problem, explicitly scoped out — no issue filed yet

Absent where a reader would expect it

  • 16 changed source files have no test change — pcs.py, greetings.py, styles.py, tags.py and others. Defensible: they received only the mechanical substitution and their existing tests already exercise those writers. The guard test covers the property that actually changed.
  • No user-facing note about the new failure mode. os.replace can raise PermissionError where an in-place rewrite succeeded (a concurrent reader on Windows, a directory ACL permitting file-write but not child-create). That surfaces as a 500 with no tailored message.
  • No cleanup for orphaned temps. A hard power loss can leave a .tmp behind; the glob-based listers ignore it, but three bare iterdir()/rglob("*") call sites would see it. Documented in the spec, not swept.

One flow changed, and it changed everywhere

Every store write shares a single flow, so this is one before/after rather than several. The runtime delta is that the live pathname is never truncated: it flips from the old file to the new one in a single os.replace. Two secondary flows shift with it — the image write/lookup pair, and a new retry branch.

What moved

  • The truncation step is gone. No window exists in which the live path holds partial content — backend/src/grimoire/store/atomic.py:93.
  • A new fsync boundary. Every write now pays one flush, measured at ~1.0 ms median on local NVMe versus 0.11 ms for the old write_text. Human-paced writes absorb this; a 100-file bulk copy pays ~100 ms.
  • The mkstemp descriptor is closed before the caller runs (backend/src/grimoire/store/atomic.py:107), so thumbs can hand the path to PIL with no sharing-mode negotiation and nothing of ours blocking the rename on Windows. The fsync therefore needs its own reopen — O_RDWR, because Windows FlushFileBuffers requires write access.
  • A chmod appears before publication (backend/src/grimoire/store/atomic.py:74) so the file is never briefly visible under its real name carrying mkstemp's 0600.

Error paths — where the risk actually lives

flowchart TD
    A[mkstemp beside target] --> B[caller writes to temp]
    B -->|exception| X[best-effort unlink temp]
    X --> Y[re-raise; record untouched]
    B -->|clean| C[reopen O_RDWR + fsync]
    C --> D[chmod from target]
    D --> E{os.replace}
    E -->|"winerror 32/33"| F["sleep, retry, ~50ms total"]
    F --> E
    E -->|"other PermissionError"| Z[raise immediately]
    E -->|ok| G[published]

The retry is the one place this change can make concurrency worse. append_message is an unlocked read-modify-write, so every millisecond spent retrying is a millisecond in which another writer can complete — after which the retry would publish stale content over it. That is why it is restricted to transient sharing violations and capped at ~50 ms rather than retrying every PermissionError.

backend/src/grimoire/store/atomic.py — _replace, lines 62–71
for delay in _RETRY_DELAYS: try: os.replace(src, dst) return except PermissionError as e: + if getattr(e, "winerror", None) not in _TRANSIENT_WINERRORS: + raise time.sleep(delay)

Permanent causes — a read-only target, or a directory ACL that permits rewriting a file but denies creating and deleting children (rights temp+replace needs and an in-place rewrite does not) — now fail on the first attempt instead of after five.

What moved

  • The destructive step moved from first to last — backend/src/grimoire/store/assets.py:141.
  • The sibling list is captured before the write, so a concurrent writer's new file can never land in another call's delete set.
  • Lookup order changed from alphabetical to newest-mtime — backend/src/grimoire/store/assets.py:66 — which is what makes the transient two-file state resolve correctly.
  • Lookup no longer raises when a sibling disappears mid-scan (backend/src/grimoire/store/assets.py:40); the old sorted(...)[0] never called stat, so tolerating OSError restores prior robustness rather than adding a check.

Accepted residue: if two writers both snapshot before either publishes, neither delete set contains the other's file and both extensions survive until the next write cleans up. A stale duplicate beats a vanished image, and closing it properly needs the per-record lock this change lists as a non-goal.

Two things worth a second opinion

1. The image_path mtime tie-break is scope expansion. backend/src/grimoire/store/assets.py:66 changes what an existing read returns for every caller. It is necessary — reordering put_image without it introduces a stale-read window the old delete-first ordering did not have — but it is a semantic change to a function this issue never mentioned. The narrower alternative (reorder only, accept the window) was offered and deliberately declined. Reasonable people could prefer it.

2. sheets.seed now buffers whole files in memory. backend/src/grimoire/store/sheets.py:536 replaced shutil.copy2 with atomic.write_bytes(dst, p.read_bytes()). Correct, and sheet JSON is small — but it is a read-all-then-write where a streaming copy used to be, and it drops copy2's metadata preservation. Fine for these files; the wrong shape if this helper is ever reused for large binaries.

Invariant impact

  • Strengthened — "a store record on disk is always a complete record." Previously untrue at ~100 sites; now enforced package-wide and guarded against regression. The atlas ranked the violation of this invariant as its #1 risk; this PR closes it.
  • Unchanged — "concurrent writers to one record serialize." Still true only where a lock exists. rolls.py's docstring previously credited the temp-file pattern for this; corrected at backend/src/grimoire/store/rolls.py:11 to credit the lock, and to note that rolls is now the only module still keeping a private registry rather than joining #245's shared locks.campaign_lock domain.
  • New failure mode — os.replace can raise PermissionError where an in-place rewrite succeeded. A deliberate trade: a rare surfaced error instead of a silent truncation.
  • New litter — a hard power loss can orphan a .tmp. Invisible to the glob-based listers, but backend/src/grimoire/store/assets.py:76, backend/src/grimoire/store/overlay.py:332 and backend/src/grimoire/store/campaigns.py:222 use bare iterdir()/rglob("*") and would see one — overlay's emptiness check would read a stray temp as non-empty.
