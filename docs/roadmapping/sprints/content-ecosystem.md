# Content Import, Sharing and Module Packaging

**Priority:** staged after working source-aware reusable content; marketplace/distribution remains optional and later.

## Goal

Authors can reuse, import, maintain and share worlds, cards, rules, catalogs and supplements without duplicating all content or losing rights, source identity and their own edits.

## Work to plan

- **Content Import:** build on existing character-card and world imports. Distinguish setting facts, character portrayals, greetings, scenario instructions, internal lore, alternate versions, associated art and rule-specific stat sheets. Offer visible conflicts and reviewed adoption.
- **Content Composition:** publish and consume real shared bestiaries, item collections and world add-ons through [Content Composition](content-composition.md), preserving explicit qualified refs and relevance-limited retrieval.
- **Module Packaging:** when demonstrated necessary, add manifests, dependencies, versions, compatibility metadata, author/publisher information, file authority, safe upgrades and validation. Avoid a broad package manager before at least two independent real content sources can be consumed.
- **Content Sharing:** export/import consistent editable packages with character art/expression lineage, source attribution, license and optional private content boundaries. Local and unofficial modules are valid.
- **Creator add-ons and alternates:** imported third-party Faerûn cards can be optional world-compatible additions or alternate portrayals, not forced to create an entire duplicate world.
- **Community Marketplace (optional):** search/discovery, trust/security, licensing, dependency validation and user opt-in only after working offline/local module import and version management exist.
- **Export refinements:** polished campaign EPUB/HTML/Markdown/text is owned by [Campaign Management](campaign-management.md); the ecosystem layer deals with portable records, dependencies and attribution.
- **Procedural content:** reusable generated records can be proposed for human review but should use the same normal authoring format; see [Procedural Generation](procedural-generation.md).

## Proving scenario

Two settings install the same bestiary without copying it into their authored world trees. One adds a custom creature, the other excludes an entry. A third-party alternate NPC card remains a distinct, traceable portrayal. Removing the library produces explicit missing dependency resolution rather than quietly changing identity.

## Dependencies and boundaries

[World Resolution](world-resolution.md) and [Content Composition](content-composition.md) choose identity and dependency rules. [World Maintenance](world-maintenance.md) manages reviewable changes, with external file authors still fully supported. Publication repositories are not required to mirror runtime content types.

## Open questions

- What is the minimal first-class package format and version/dependency pin required by actual consumers?
- Which catalog/add-on content can be reused under what licenses and third-party attribution obligations?
- Should reusable add-ons be selected per campaign, by saved world preset, or both?
- Are sandboxing, malware/script policy and a trust/permissions model needed before any shared module catalog?
- When is a marketplace valuable enough to justify its review, hosting and compatibility costs?
