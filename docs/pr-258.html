Move the proposal heal-before-retire invariant from convention into the state machine

base main @ 46e6aae1 → fix-242-proposal-heal-invariant @ 64fb7863 · +379/−135 · generated 2026-07-29

A rule that five call sites had to remember is now a property of the state machine

A roll proposal that has resolved owes two writes to disk: an entry in rolls.json and a 🎲 line in the scene transcript. Before this change, the rule "finish those writes before you retire or replace the record" lived in a docstring, and five call sites each called _heal_current_proposal to honour it. A sixth path that forgot would leave a roll in rolls.json with no transcript line — permanently, with no error and no log.

The projection logic moves into backend/src/grimoire/store/proposals.py, the module that owns the record's state machine, and every exit from the projectable states now heals itself: supersede (retire), new (replace) and commit_narration (narrate). The generic CAS transition is closed as a back door. The five caller-side heals are deleted. Behaviour on the happy path is unchanged; what changes is that the guarantee no longer depends on the caller.

Two smaller things ride along, both in the same blast radius: a 500 in post_regenerate that the hardening exposed, and a shared roll_label so the roll log's label and the transcript line's head cannot drift.

Context for reviewers: this branch was rebased across the routes split. When the work started, all of this lived in a single routes.py. main has since split that file into a package, so the same edits now land in backend/src/grimoire/routes/streaming.py, backend/src/grimoire/routes/scenes.py and backend/src/grimoire/routes/mechanics.py. Worth knowing because the split spread the invariant across three modules — its docstring had grown a paragraph enumerating which call sites in which module to keep in step, which is the strongest possible argument for deleting the convention outright.

The heal moved one frame down the stack — and gained two more triggers

No new I/O, no new external calls, no changed lock domain. What moved is who performs the heal: the route handler used to do it and then call the primitive; now the primitive does it. The consequences that matter are the later diagrams: commit_narration was never a heal site and now is, and transition could silently perform an unhealed exit and now refuses.

  • The hole: transition(cid, sid, pid, ("resolved",), "narrated") moved a resolution carrying result past what project accepts, unhealed. Two existing store tests used exactly that shape.
  • Raises rather than returning False (backend/src/grimoire/store/proposals.py:110-113): False is reserved for a lost race, which callers are written to treat as "someone else won, stop". A bad target is a programming error and must not be swallowed as a race.
  • Healing inside transition was rejected, not overlooked. update_resolution performs a status-preserving resolved -> resolved CAS, so a heal there would recurse heal → project → update_resolution → transition → heal without bound. The reasoning is recorded at the constant (backend/src/grimoire/store/proposals.py:36-43) so the next reader does not retry it.

Reachability, stated honestly. Neither flow 3 nor flow 4 was reachable through production code: post_roll_proposal's resolved branch returns early when project yields None, so commit_narration cannot be reached without a successful projection, and no caller ever passed an exit status to transition. Both were worth closing anyway — "the only caller happens to order it correctly" is precisely the class of guarantee issue #242 exists to eliminate.

Should-consider (none blocking)

1. heal ignores project's return value (backend/src/grimoire/store/proposals.py:224-226). With commit_narration and transition both closed there is no longer a reachable state where it returns None for a record heal considered projectable — but nothing enforces that. Making heal raise on an unexpected None was considered and rejected: it would raise on every ordinary new following a narrated record, a legitimate already-projected state.

The docstrings say so and the module docstring frames projection as belonging here — but it is a genuine widening, and the issue's option 2 (retire_and_replace) would have kept the narrow primitive alongside a composite operation. Worth a maintainer's opinion, not a defect.
