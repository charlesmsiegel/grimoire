Overlay materialization records the sync base before it commits the copy (#247)

base origin/main @ 55b1022c → e6a2e36f · +191/−16 · generated 2026-07-28

Materializing a record now records its sync base first, and commits the copy last

Copying an inherited world record into a campaign writes two things — the record itself and its base hash in sync.md — and they cannot be made one write. This change reverses their order in all three materialization paths, so the state a crash can leave behind is the benign one (a base with no copy, which still reads through to the world live) rather than the harmful one (a copy with no base, which drops out of the sync engine permanently).

Two supporting changes make that ordering real. The base write is wrapped in a context manager that undoes it when the copy raises, restoring any value it displaced. And materialize_actor's copy loop is taught to skip the actor's meta file — its *.md glob was matching pc.md itself, so for PCs the commit point could land in the middle of the loop, ahead of later-sorting version files.

What did not change

The mirror-image window in sync.accept

That is the same two-write pair in the same order, and a crash there leaves the same base-without-copy residue this change now creates deliberately. It is the benign side, so leaving it is defensible — but it means the residue state is now reachable by two routes, not one.

Durability, still explicitly out of scope

Nothing here fsyncs the parent directory or orders the two renames on disk; backend/src/grimoire/store/atomic.py:12-19 already disclaims power-loss durability. This change buys crash-ordering within a running process, not survival of a power cut. No test or comment overclaims it.

No test covers the legacy-migration reading of the new residue state. campaigns._slim_full_copy treats a manifest ref whose file is missing as a record the user deleted, and tombstones it (backend/src/grimoire/store/campaigns.py:169-173). That is the one place in the codebase where base-without-copy means something other than "not materialized". See the Walkthrough for why it is reachable only through a narrow legacy path — but it is the one asymmetry this change introduces and it has no test.

What moved

  • The manifest write moved ahead of the copy in all three paths: backend/src/grimoire/store/overlay.py:129-130 (flat records), backend/src/grimoire/store/overlay.py:290-291 (plot map), backend/src/grimoire/store/overlay.py:343-349 (actors).
  • The source read moved ahead of both. src.read_text(...) now happens before the window opens (backend/src/grimoire/store/overlay.py:128), so a missing or unreadable world file raises without ever touching the manifest.
  • A rollback path is new. An exception inside the window restores the previous base value — or removes the ref if there was none — and re-raises (backend/src/grimoire/store/overlay.py:102-112). The restore's own failure is swallowed so it cannot mask the original error (backend/src/grimoire/store/overlay.py:110-111).
  • The actor commit point is now single. Version files are copied, then the meta file, and the meta file is excluded from the version loop (backend/src/grimoire/store/overlay.py:346-349). Before, sorted(src.glob("*.md")) wrote pc.md in alphabetical position — so a PC with a version sorting after "pc" could be committed with that version still missing.
  • No change to error propagation as seen by callers. The context manager re-raises unchanged; materialize_entity still raises EntityNotFound and materialize_actor still raises CharacterNotFound/PCNotFound on the not-in-world path, both decided before the window opens.

Why the two orderings are not symmetric

The asymmetry is what makes the fix work, and it rests on three existing guards, none of which this change touches:

  • backend/src/grimoire/store/sync.py:54-55 and backend/src/grimoire/store/sync.py:132-133 already skip a ref whose campaign copy is absent (mine_h is None).
  • backend/src/grimoire/store/characters.py:300 and backend/src/grimoire/store/pcs.py:199 return None from dir_hash when the meta file is missing — which is why a half-copied actor dir reads as "not materialized" rather than as a divergent one.
  • backend/src/grimoire/store/overlay.py:309-318 (actor_root) keys materialization on that same meta file, so the read path and the sync path agree on what "materialized" means.

Invariant impact

"A manifest ref implies a campaign copy" was never an invariant, but this change makes its absence load-bearing. Three readers already tolerate the base-without-copy state and treat it as "not materialized" (backend/src/grimoire/store/sync.py:54-55, backend/src/grimoire/store/sync.py:132-133, backend/src/grimoire/store/overlay.py:309-318). One reader does not:

backend/src/grimoire/store/campaigns.py — _slim_full_copy, lines 169–173
p = root / kind / f"{eid}.md" if not p.exists(): if (wroot / kind / f"{eid}.md").exists(): overlay.add_deleted(cid, ref) # keep the user's deletion deleted manifest.pop(ref)

The legacy full-copy migration reads that state as "the user deleted this record" and writes a permanent tombstone. Reaching it needs all three of: a campaign still stamped world_copy: full, a materialization on a world record created after the fork (otherwise the copy already exists and materialization is a no-op), and a hard crash inside the new window — after which the tombstone hides an inherited record the user never deleted. The same residue is already reachable through backend/src/grimoire/store/sync.py:203-204, so this change widens an existing hole rather than opening one; but nothing tests it and nothing documents the coupling.

Against the atlas's Invariants tab: this closes no listed invariant gap, but it is the same family as the resolved #233 entry — "each individual write is correct; sequences of writes are not protected". This is the first sequence in the store to get an explicit commit-point discipline. The atlas's framing of that gap should now note the exception.
