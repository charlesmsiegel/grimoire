Judge 1

Theory: This models the phone as one more machine that runs the *same* grimoire, not a second implementation of it: the unit's whole job is to supply the three things a desktop gets for free — a process that hosts the real FastAPI app (ServerRuntime + android_entry.start_server), a browser to render the real SPA from that server's origin (MainActivity), and a filesystem where store.paths' HOME/pointer/default resolution already works, including over a USB cable (android_entry's env contract and _open_store_to_usb). Every domain noun grimoire has — world, campaign, scene, character — is deliberately absent from this unit; what appears instead are port, assets, HOME, downloads, back, i.e. exactly the seams where Android differs from a PC. The 'no copies' rule is not a convention but a build fact: chaquopy srcDir points at the working tree's backend/src and a Gradle task builds frontend/dist into assets, so an APK is one git revision of the monorepo.

Instead of: The competing reading is 'a generic WebView wrapper around a localhost Python server' — a reusable shell that happens to be pointed at grimoire. I rejected it because roughly half the unit is grimoire-store-specific and would be wrong for any other app: setting HOME rather than GRIMOIRE_HOME specifically so the Storage-location settings page keeps winning (android/app/src/main/python/android_entry.py:92), extracting templates and dist because Jinja and StaticFiles need real paths (android/app/src/main/java/app/grimoire/ServerRuntime.kt:114), and the chmod walk that exists only because this app's product is a plain file tree someone syncs over a cable (android/app/src/main/python/android_entry.py:47). A second rejected reading — 'the start of an Android port' — is contradicted by the pip block being pinned to mirror backend/pyproject.toml rather than to an Android-flavoured subset (android/app/build.gradle.kts:76).

Judge 2

Theory: This models a phone as one more machine that runs the *same* grimoire, not as a second product: the unit is a browser window (WebView) plus a process host for the repo's own FastAPI app, so the only things it may contain are adaptations of the host environment - where the store lives, where static assets live, when the port becomes knowable, and which Android conventions (umask 0077, process death, system back, downloads, file chooser, cleartext policy) differ from a desktop browser. The rule that it holds no product logic is enforced structurally rather than by discipline: chaquopy's srcDir points at ../../backend/src and a Gradle task shells out to the real `npm run build`, so there is nowhere an Android-only feature could be written. Everything the shell does know is either an env-var translation (android_entry.start_server) or a WebView-to-OS bridge (MainActivity.configureWebView).

Instead of: The other coherent reading is 'an Android client for grimoire' - a shell that owns a mobile experience and will grow native screens, a settings surface, maybe a Kotlin-side API layer. I rejected it because nothing in the code is shaped that way: there is no model, no navigation, no Kotlin knowledge of any grimoire noun; MainActivity's 158 lines are entirely OS-to-WebView bridges, and the two places that could have accumulated product code (build.gradle.kts:96 srcDir, :110-127 buildFrontend/stageGrimoireAssets) instead make copying impossible. A second rejected reading is 'a process supervisor': ServerRuntime deliberately does not supervise - no health check, no restart, and a returned start_server is treated as terminal (ServerRuntime.kt:102).

Judge 3

Theory: The phone is not a new product but a new host: grimoire is already a complete HTTP application, so Android needs only a process to run the interpreter in, a browser to point at it, and a translation of the two things a phone's filesystem does differently from a desktop's — where HOME is, and that umask 0077 hides the store from the USB cable. Each of the four files owns exactly one of those, and the Gradle build packages backend/src and frontend/dist from the working tree so no fifth concern, and no domain knowledge, can accumulate here. The load-bearing claim is negative: platform divergence is made structurally impossible rather than merely discouraged.

Instead of: An Android app that happens to be powered by Python — the shell owning navigation, chrome, settings, and eventually a native model of what a campaign or a scene is. Rejected because the code refuses it at every seam: MainActivity's own docstring restricts the activity to hosting (MainActivity.kt:25), system back is handed to SPA history rather than an activity stack (MainActivity.kt:80), and the only value that ever crosses from Python into Kotlin is a port number (ServerRuntime.kt:13). The Kotlin comments that do mention lore, chub and character cards name *why* a generic browser capability is wired up, never what it operates on.
