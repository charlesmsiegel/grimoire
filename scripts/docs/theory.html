Judge 1

Theory: Everything that acts on a grimoire library from outside the running server: gating the repo's prompt and import invariants, starting and stopping the app on a desktop, carrying the store between a PC and a USB-attached phone, and mutating the store in bulk from a CLI or an agent. Its governing premise is that the store is a plain file tree with no transactions and holds scene transcripts nobody can regenerate, so every out-of-band writer must be resumable from its own journal, must checkpoint into git before it writes, and must prefer a visible duplicate or an outright refusal to a silent loss. The launchers and the two repo gates share the same stance one level up: never report a status the run did not actually earn.

Instead of: The other coherent reading is 'scripts/ is the junk drawer' -- a bag of one-off dev utilities whose only common property is being outside backend/src, with the three locations explained by where each was convenient to drop. I rejected it because the three largest members independently articulate the same specific stance and enforce it in code: grimoire_sync refuses to write when the phone has unreadable files (scripts/grimoire_sync.py:24), ingest_scene infers landedness from the artifact rather than a flag and files a duplicate rather than drop a scene (backend/scripts/ingest_scene.py:191), and populate_world_content refuses a commit it cannot explain (.claude/skills/populate-world-content/scripts/populate_world_content.py:701). A junk drawer does not converge on a loss-asymmetry doctrine. But the reading is not fully wrong either -- the launchers and a dead refactor tool sit in the same directory tree with nothing tying them in, and no README anywhere states the unit's boundary.

Judge 2

Theory: Everything that acts on a grimoire library, or on the repo that produces one, from outside the running server: cross-device file sync, bulk and one-shot store imports, the prompt-contract oracle, and the machine's install/run lifecycle. Each member is a CLI that first resolves the same store root the app resolves, then either drives grimoire.store as a library or moves files the app never parses. The commitment they actually share — and the one that shapes their internals — is that a tool must be interruptible and re-runnable without destroying content nobody can regenerate: grimoire_sync never deletes and never resolves a conflict, populate_world_content refuses to run against a dirty repo and commits by pathspec, ingest_scene's whole manifest exists so a crashed run resumes instead of double-appending, redownload_chub keeps failures per-version, verify_templates only reads and only into a throwaway store.

Instead of: The other coherent reading is the repo's own: README.md:256 says scripts/ is 'install / run / shutdown / android-bootstrap for unix and windows', which would make this unit the platform launchers and would file verify_templates.py, grimoire_sync.py and validate_partition.py as strays, with backend/scripts/ and the skill's scripts/ being separate things entirely. I rejected it because by weight the launchers are the minority (8 shell files, ~19 KB) against ~3,700 lines of Python that visibly share one model — resolve the store root the way store/paths.home() does, then never lose a scene — and because that reading cannot explain why grimoire_sync.py, which is pure store operation, sits next to run.sh. The launchers are the outlier inside the unit, not its definition. The cost of my reading is that README's map is then simply wrong, which I count against world_mapping rather than against the theory.

Judge 3

Theory: These are grimoire's out-of-band operators: programs a human or an agent runs by hand against the real store, the real repo, or the developer's machine at moments the running server cannot serve — proving the prompt builders still agree with templates/, carrying a library between PC and phone, bulk-importing a campaign log or bulk-populating a world, re-fetching chub cards, and starting/stopping the dev servers. Each file models one specific failure it exists to prevent (a silently drifted prompt, a lost unsynced edit, a twice-filed timeline batch, an unexplained write) and states that failure, with the alternative it rejected, in its own docstring.
